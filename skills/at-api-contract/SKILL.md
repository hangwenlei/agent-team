# 接口契约

**这个 skill 防的是这种失效**：后端写了一套接口、前端写了
另一套，两边**没有任何共同契约**，谁也不知道对不对得上。

## 规矩

**先定契约，再各写各的。** 契约写进架构产物（见 `${CLAUDE_PLUGIN_ROOT}/stages.json` 里 S3 的 produces），
不要散落在各自的实现文件里。

## 每个端点写清五项

| 项 | 说明 |
|---|---|
| 方法与路径 | `POST /api/auth/otp` |
| 请求体 | 字段名、类型、必填与否 |
| 成功响应 | 状态码 + 响应体结构 |
| **失败响应** | **每一种**失败的状态码与响应体。这是最常漏的一项 |
| 副作用 | 计数、锁定、发信之类。前端要据此决定 UI 状态 |

## 失败分支必须穷举

前端的状态机是按失败分支写的。后端漏写一种，前端就会把它归到「未知错误」——用户看到的是
一句没用的提示。

举例：验证码校验失败与「已被锁定」是**两种不同的失败**，前端要给不同的文案与不同的可操作性
（一个能重试、一个不能）。合并成一种，用户就会对着一个不能重试的表单反复重试。

## 端点之外的接头

两个 `S5` 产者之间不走 HTTP 的接头，同样先定再写：一方写、另一方用的组件，共享的类型定义，
事件（自定义事件、消息总线、跨端通知），本地存储的格式（`localStorage` 的键、数据库表、缓存文件）。
接头和端点一样写进架构产物。
每个接头写清六项：

| 项 | 说明 |
|---|---|
| 名字 | 组件名、类型名、事件名、存储的键或表名 |
| 所在文件 | 定义落在哪一份文件（落盘清单里归谁） |
| 签名或字段 | 组件的属性与回调、类型的字段与可选性、事件的载荷、存储的结构与版本 |
| 谁产出 | 哪个产者写它 |
| 谁使用 | 哪些产者读它、调它、订阅它 |
| 出错时怎样 | 缺字段、旧格式、加载失败、事件没人接时，双方各怎么处理 |

最常漏的是最后一项：存储格式改了，读旧数据的那一端崩掉；组件在加载失败时没有状态，用的那一端只好自己编。

## 谁定、谁改

- **定**：架构师在 S3 写进架构产物。
- **改**：实现过程中发现契约不对，**冒泡给架构师**，不要自己改了继续写——你改了，另一端
  不知道，就回到了这个 skill 要解决的那个问题。
