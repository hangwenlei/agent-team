# 接口契约

**这个 skill 是为一个真实发生过的问题建的**：一次完整 run 里，后端写了一套接口、前端写了
另一套，两边**没有任何共同契约**，谁也不知道对不对得上。

## 规矩

**先定契约，再各写各的。** 契约写进架构产物（见 `stages.json` 里 S3 的 produces），
不要散落在各自的实现文件里。

## 每个端点写清五项

| 项 | 说明 |
|---|---|
| 方法与路径 | `POST /api/auth/otp` |
| 请求体 | 字段名、类型、必填与否 |
| 成功响应 | 状态码 + 响应体结构 |
| **失败响应** | **每一种**失败的状态码与响应体。这是最常漏的一项 |
| 副作用 | 计数、锁定、发信之类。前端要据此决定 UI 状态 |

## 失败分支必须穷举

前端的状态机是按失败分支写的。后端漏写一种，前端就会把它归到「未知错误」——用户看到的是
一句没用的提示。

举例：验证码校验失败与「已被锁定」是**两种不同的失败**，前端要给不同的文案与不同的可操作性
（一个能重试、一个不能）。合并成一种，用户就会对着一个不能重试的表单反复重试。

## 谁定、谁改

- **定**：架构师在 S3 写进架构产物。
- **改**：实现过程中发现契约不对，**冒泡给架构师**，不要自己改了继续写——你改了，另一端
  不知道，就回到了这个 skill 要解决的那个问题。
