# 交接包

派发提示里的这份结构就是这个团队全部的类型系统——Claude Code 没有类型检查，**你写漏一项，
下游就真的少一项信息**（规格 §8）。

## 六项，一项都不能少

### 1. 目标
一句话说清这次要什么**结果**，不是要什么动作。

### 2. 约束
契约里与这件事相关的原文引用。**引用，不要转述**——转述会在第三次传递时失真，那正是十角色
链最隐蔽的失效。

### 3. 输入产物路径
它该读哪些文件，给**完整路径**。不要说「上一阶段的产物」——让它自己去猜是哪个文件，就是在
制造分歧。

### 4. 未决问题
你知道但没定的事。**明写出来**，否则下游会当作已定并自行填补。

### 5. 完成定义
什么算做完。**必须包含它该产出的文件**（见 `stages.json`），因为交付物校验就按这个判。

### 6. 验收回传通道
做完之后回报给谁、回报里要有什么。默认是回给派发它的那个角色。

## 三条别犯的错

- **不要把整份契约贴进去。** 只引用相关的条款。上下文是有成本的。
- **不要替下游做决定。** 属于它职责范围内的选择留给它；你替它定了，它的专业判断就没了
  用武之地。
- **不要省略「未决问题」这一项。** 空着就写「无」——写「无」和没写这一项，对读的人是两件
  完全不同的事。
