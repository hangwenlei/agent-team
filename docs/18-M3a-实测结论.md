# M3a · 真实环境验证 —— 产者交代判据的误报率，以及 `available_roles` 到底长什么样

## 0. 一句话结论

**那条判据在真实 run 里没有报过一次假的。** 本轮四趟 run（两趟自然、两趟构造），
报出来的 gap 逐条都是真的；两趟自然 run 里它**一次都没说话**，而那是对的——
一趟根本没有裁剪，另一趟 PM 在推进的**同一次写入**里就把裁剪记进了 `trimmed`。

**收窄的收益不是纸面上的。** `/agent-team:at-init` 三次实跑写出来的 `available_roles`
**都不是模板那份九人骨架**：两个 web 项目各自写出 `at-product`、`at-architect`、
`at-backend`、`at-frontend`、`at-ui`、`at-qa`、`at-acceptance`（**逐字节零 diff**，
两个独立会话），纯后端项目再减掉 `at-ui` 与 `at-frontend`。
**三份都不含 `at-pm`**，**两个 web 项目都去掉了 `at-ios` 与 `at-android`**
——而那两个角色正是 M2b 那一趟制造噪声的那两个。

**那条护栏第一次被真实检验，过了。** 把 `at-pm` 塞进 `available_roles`（`/at-init` 明令
不写、而今天没有任何运行时判据拦它），回传连着三轮点名 `at-pm`：PM **没有**把自己写进
`trimmed`，而是去 `project.json` 里把 `at-pm` 删掉了——正是那句护栏指的那条路。

**一条本轮新量到、与 M3a 无关但影响怎么读这份报告的**：在 CLI 2.1.278 的异步派发下，
**`PostToolUse:Agent` 在「派发启动」那一刻就触发**（记录级：`tool_use` 与 hook 相差
190 毫秒，而第一份产物在一分四十秒之后才落盘）。账本比对只挂在这个事件上，
**所以形状 B 那个窗口在两次采样点之间，本轮两趟自然 run 都没有采到它**。
这不是 `unrecorded` 新口径没用——**拿真实 run 的文件回放，新口径看得见 `at-ui` 的两份产物，
旧口径看不见**（§3.6）——而是「它在活会话里什么时候会说话」这件事，今天由接线决定。

## 3. 逐条

### 3.1 第 1 条：报没报——**两边都对，而「没报」那一边更难判**——记录级

**自然臂（`5bd2b210`，裁剪臂）整份转录里，hook 回传含「【产者交代】」的记录零条。**
它是对的，理由在磁盘上：PM 把 S2 推到 S3 的那**一次** `Edit`，
同时写了 `"roster": ["at-product"]` 与 `"trimmed": { "at-ui": "S2" }`
——`commands/at.md` 逐段推进第 4 步要求的「同一时刻写」，它照做了。
`PostToolUse` 触发的那一刻，`at-ui` 已经在 `trimmed` 里，判据没有可报的。

⚠️ **「没报」这件事本身不能只靠「转录里没有那段文字」来判。** 平台**不为零输出的 hook
留 attachment 记录**（`docs/17` §3.5 记过同一件事），所以「判据跑了但没话说」与
「那条分支根本没进」在转录里长得一模一样——这正是本仓库反复栽的那个形状。

**所以这一条配了离线正向对照**（`m3a-probe-replay`，把那一刻的真实 `state.json`
原样摆回去，直接喂 `gate.mjs ledger`）：

- **原样**（`trimmed` 含 `at-ui`）→ stdout **空**、stderr **空**，与真实 run 一致；
- **只把 `trimmed` 清空**（也就是 M2b 那一趟的真实形状）→ 立刻报：

      【产者交代】下面这些角色是**已经走过的阶段**的产者，而这一趟既没叫到它们、
      也没声明裁掉它们——它们的缺席今天不会被任何别的判据看见：
        - S2 的 at-ui

  举例形状逐字是 `{"at-ui": "S2"}`（收窄成功、且这一条不是驱动者，所以用的是真实那一条），
  **没有「口径比平时宽」那一段，也没有驱动者护栏**——两者都不该出现，它们没出现。

**构造臂（`ca3efd30`）在活会话里拿到了同一条。** 它的 state 是手工退回 M2b 形状的
（`stage: S2`、`roster: ["at-product"]`、`trimmed: {}`、`01-prd.md` 在盘上、
`02-*` 不在），用户消息只说「把 stage 推进到 S3，推进之后编排层给你什么回传，
按你自己的判断处理」。PM 一落盘就收到 `【产者交代】`，内容与上面那段**逐字相同**。
**它写完 `trimmed` 之后的下一次写入，回传里那一段消失了**，只剩 `history` 与 `stage`
分叉那条——一条提示的出现与消失，两头都在同一份转录里。

> **⚠️ 这一条要记准的是哪一半**：`docs/11` §5.22 第五节那个失效条件已经预先说过
> ——「下一趟裁剪都老实冒泡了，该记的是**正文那一句起了作用**，不是**判据够用**」。
> 本轮自然臂就是那种情形。**判据够不够用，本轮证不了；证到的是正文那句话在真实 PM 身上
> 生效了一次。**

### 3.2 第 2 条：PM 拿它怎么办——三种可能里只出现了一种——记录级 + 自述级

brief 要求三种（写 `trimmed` / 补派 / 忽略）都如实记。**实测只出现第一种，零次补派、零次忽略。**

**构造臂（`ca3efd30`）**：动作是记录级的——它先 `Read` 了 `00-contract.md`，
然后把 `trimmed` 从 `{}` 改成 `{ "at-ui": "S2" }`，没有派任何角色。
**理由是它自己说的（自述级）**：契约第 3 节「明确不做的事」第一条写着这一趟不出
`02-ui-spec.md` / `02-wireframe.html`，所以它判这是裁剪不是漏派；
它还明说了没有去补派，因为那才是「把洞填错方向」。

**护栏臂（`8762a6f6`）**：同样写了 `{ "at-ui": "S2" }`；
对回传里另外那条（`S1` 的 `at-pm`）**改的是 `project.json`**（§3.7）。

**自然臂（`5bd2b210`）**：根本没等到提示——它在推进那一刻就写了。

**三次都没有出现文案专门要防的那个错修法**（把名字写进 `roster` 让提示消失）。
`roster` 在构造臂与护栏臂里从头到尾是 `["at-product"]`，一个字没动。

### 3.3 第 3 条：误报率——**两趟自然 run 零条**，而零的原因值得单记——记录级

**对照臂（`8c478895`，不裁剪）同样零条。** 它最终的 `roster` 是

    ["at-product", "at-ui", "at-architect"]

**`at-ui` 不是 PM 派的**——`roster.json` 里 `at-pm` 根本派不动它，
它是 `at-product` 在 S2 里派的（`at-product.can_delegate_to = ["at-ui"]`）。
**而 PM 仍然把它累加进了 `roster`。** 这一条是零误报的直接原因：
如果 PM 只记自己直接派过的人，`at-ui` 就会既不在 `roster` 也不在 `trimmed`，
**一条真实的误报当场成立**。

> **所以这条判据的误报率，今天押在「PM 把孙代理也记进 `roster`」这个行为上。**
> `commands/at.md` 第 4 步的原话是「把这一段**真正叫到**的角色累加进 `roster`」
> ——它没有区分「你派的」和「你的人派的」，本轮实测 PM 读成了后者（更宽的那一种），
> **而更宽的那一种正是这条判据需要的**。**这是一次观测，不是一个不变量**：
> 没有任何判据钉着「孙代理也要进 `roster`」，正文里也没有一句话明写它。

**裁剪臂（`5bd2b210`）同样零条。**

**唯一量到的误报，出现在收窄失效那一支**（离线回放，`m3a-probe-replay`）：
把 `available_roles` 整个删掉 → 多出一条 `- S1 的 at-pm`。
它**是**误报（`at-pm` 是驱动者，不参与这个统计），但它**不是静默的**：

- stderr 留了一行痕迹：`agent-team 产者交代：读不到 .agent-team/project.json 的
  available_roles（可用班底），本次判据没能按它收窄，报出来的口径比平时宽。`
- 文案自己先说了「这一批**没能按「这个项目用得上哪些角色」收窄**……**先把
  available_roles 补上再判这批名字**」；
- 驱动者护栏点名了 `at-pm`，并指向真修法（去 `available_roles` 里删掉它）；
- **举例退回了占位形状 `{"<角色名>": "<阶段 id>"}`**，没有把任何一条真实 gap 递出去。

### 3.4 第 4 条：`/at-init` 实际写出来的 `available_roles`——**这一轮最要紧的一条**——记录级

`docs/11` §5.22 与 Task 2 的记录都指出：收窄的收益**完全押在这份名单贴不贴合这个项目**。
若它就是模板那份九人骨架，收窄后与收窄前**一模一样**。本轮三次实跑：

| 工程 | `/at-init` 写出来的 `available_roles` |
|---|---|
| `m3a-probe-trim`（web）| `at-product`、`at-architect`、`at-backend`、`at-frontend`、`at-ui`、`at-qa`、`at-acceptance` |
| `m3a-probe-plain`（同一份 web 骨架，**另一个会话**）| **与上面逐字节零 diff** |
| `m3a-probe-api`（纯后端）| `at-product`、`at-architect`、`at-backend`、`at-qa`、`at-acceptance` |

**三条成立的事实**：

1. **它不是模板那份骨架。** `templates/project.json` 里列的是九个
   （多 `at-ios` 与 `at-android`），**三份实测没有一份照抄**。
   **模板那份是骨架，不是默认值**——这件事此前只是设计意图，现在是实测的。
2. **两个 web 项目都去掉了 `at-ios` 与 `at-android`**，而那两个角色正是 M2b 那一趟
   在收窄之前制造噪声的那两个（`tests/coverage.test.mjs` 的「收窄前 / 收窄后」那一组
   把这个差钉着）。**收窄在真实配置下确实还在减东西。**
3. **三份都不含 `at-pm`。** `commands/at-init.md` 那句「不要写 `at-pm`」今天**没有任何
   运行时判据拦它**（Task 2 报过这条 concern），三次实跑三次照做了。
   **这是三次观测，不是一条不变量**——护栏臂就是把它故意破坏之后的样子（§3.7）。

⚠️ **纯后端那一份顺带把另一件事变成实物**：它的名单里**没有 `at-ui`**。
`agents/at-pm.md` 那句「裁掉的人要是不在那个名单里，它一个字都不会说」
在这样的项目上就是字面成立的——这不是推论，这份 `project.json` 在盘上。

### 3.5 第 5 条：`trimmed` 的格式——**两次都写对了**——记录级

两次真实写入逐字都是

    "trimmed": { "at-ui": "S2" }

`validateState` 的问题清单在两份转录里都出现过（`【state.json】` 那一段），
**但报的都是 `history` 的最后一条与 `stage` 对不上**，**没有一条是关于 `trimmed` 的**。

⚠️ **写错的那一侧本轮没量到**，记在 §5.1，**不记成「格式校验有效」**。
Task 1 给形状校验配的单测还在（`tests/state.test.mjs`），
但**真实 PM 写错时会发生什么，本轮没有观测**。

### 3.6 第 6 条：`unrecorded` 新口径——**两趟自然 run 里差额为零，而原因是接线**——记录级

**先摆事实。** 两趟自然 run 里 `【账本比对】` 各只出现一次，内容相同：

    【账本比对】以下产物对不上账：
      - 00-contract.md：磁盘上有这份文件，但 artifacts 里没记

**这一条与 M3a 无关。** 实测过：`expectedArtifacts(stages, [])` **本来就含
`00-contract.md`**（`S1` 是单角色段，`stageRolesInRun` 对这一类不按 `roster` 收窄），
所以旧口径同样会报它。**新口径在这两趟里带来的差额是零条。**

**为什么是零，是结构性的，不是「新口径没用」。** `compareArtifacts` 只在
`CHECK === 'deliverable'`（`PostToolUse:Agent`）上算——`hooks/gate.mjs` 自己的注释写着
H5b 走 `SubagentStop` 的 stderr 契约、没有 `additionalContext` 这条通道，所以不算。
而在 CLI 2.1.278 的异步派发下，**`PostToolUse:Agent` 在「派发启动」那一刻就触发**：

| 记录 | 时刻 |
|---|---|
| `tool_use` 发出 `Agent(agent-team:at-product)` | `04:19:16.233Z` |
| `PostToolUse:Agent` 的 attachment | `04:19:16.423Z` |
| `tool_result` 原文 `Async agent launched successfully.` | `04:19:16.424Z` |
| `01-prd.md` 第一次落盘（磁盘时间戳）| 约一分四十秒之后 |

**所以账本比对采样的是「刚派出去、对方还什么都没写」那一刻。**
H5a 那句「at-product 在 S2 应当产出 01-prd.md，但磁盘上还没有」因此**在每一段的第一次

## 4. 本轮新出的

### 4.1 ⭐ `PostToolUse:Agent` 在「派发启动」那一刻触发，不在子代理返回时

§3.6 那张时刻表是它的证据。**为什么值得单独记一条**：

- **H5a 的「磁盘上还没有」因此是结构性的，不是信号。** 本轮两个自然臂各两次顶层派发，
  两个臂逐字相同。读的人若把它当成「这个角色没干活」，会去核一个根本还没开始的东西。
  H5a 本来就是 fail-open 的记录性告警，**但「它每次都说」与「它这次说了」是两回事**。
- **所有挂在 `PostToolUse:Agent` 上的判据，采样点都在这里。** 今天挂着的是
  H5a 与账本比对。它们看到的永远是「刚派出去」那一帧。
- ⚠️ **这不是平台的毛病，也不是插件的毛病，是两者组合出来的一个采样口径。**
  `docs/11` 与 `docs/13` 早就记了异步派发本身（`requestShape: "background"`），
  **本轮新的是它对 `PostToolUse` 时机的后果**，此前没有记录。

**可照做的一条**：往 `PostToolUse:Agent` 上挂任何「去磁盘上看产物」的判据之前，
先问它**在派发启动那一帧**会说什么——那是它实际会被执行的那一帧。

  而且它长得跟真漏派**一模一样**。

**今天没有任何判据钉着这件事，正文里也没有一句话明写它。**
本轮实测的是**这一个 PM 读成了宽的那种**，不是「它必然如此」。
