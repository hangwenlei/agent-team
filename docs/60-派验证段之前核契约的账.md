# 派验证段之前核契约的账

> 2026-10-10，M4y，分支 `m4y-verify-dispatch-contract`。第十八轮（从开放边界索引挑）：`docs/37` §5、`docs/50` §5 与 §1 第 20 条里登着的
> 「`at-acceptance` 收不到契约漂移的告警」。

## 0. 一句话结论

- H2 派验证段的产者（`stages.json` 里 `"verifies": true` 的段、花名册里有人派得到的——`at-qa`、`at-acceptance`）之前，拿 `state.json` 的 `contract_sha` 对一遍磁盘上的契约：
  对不上（漂了、还是 PENDING、不是合法的 sha、记着值而契约不在）就拒，出路是【契约】那一句，再加「处理完再派」。契约这一次读不出（被占着）不拦、留痕。
- `at-acceptance` 的正文原来就对它承诺「PM 处理完才派你」，门禁不拦；现在这句话由门禁兑现。

## 1. 问题

- 【契约】（`contract_sha` 与磁盘上的契约对不上）只在派发返回与写 `state.json` 时回传给项目经理，派发本身不拦：项目经理收到之后不处理、照样派
  `at-qa`、`at-acceptance`，它们就对着一份没对上账的契约验。
- 结论出来之后再处理账，那份结论对着的可能正是一份要恢复原样的契约：契约被人改过、不是第 4 节的修订——【契约】给的出路是恢复原样；恢复之后没有修订块，
  契约基线（`docs/45`）不会叫验证段重出，对着改过的那一版写的结论留下来、照常推进与收口。
- `agents/at-acceptance.md` 写着「漂了会经账本回传报给 PM，PM 处理完才派你」，门禁不核——正文说拒，门禁得真拒。

## 2. 修法

- `hooks/lib/stages.mjs` 加 `verifyStageOf(stages, role)`：这个角色是阶段链上哪一个验证段（`verifies: true`）的产者（第一个），不是回 null。按 `stages.json`
  派生，不写死角色名——扩链时跟着 `verifies` 走。
- `hooks/gate.mjs` 的 H2（`readiness`）：排在最后——收口、别的一趟的人、前置、重做那几条都过了，目标是验证段的产者、花名册里有人派得到它（项目经理是
  最后一段的产者，没人派得到它）时，`contractCmp(ctx)`（与派发返回的【契约】共用的那一份比对，从 `contractNoticeFor` 里抽出来）不过、又不是
  「这一次读不出」，就拒：`agent-team H2 就绪门禁：<角色> 是 <段> 的产者，对着契约验——契约的账对上之前不派它。` + `contractCheckNotice` 那一句 +
  `处理完再派 <角色>。`调用者写不了 `state.json` 时（今天的花名册里没有这样的边，H1 会先拒），后半句换成转给 PM 的那一版（`contractNoticeFor` 的
  另一个分支），不许诺「再派」。
  - 出路照用【契约】那一句（写 `state.json`、派发返回时同一句）：漂了的列出几种可能、各给出路，不报磁盘上算出来的值；PENDING 的叫它记写契约那一次回传给的
    值；不合法的叫它写成 PENDING 再重写契约拿回传；契约不在的叫它告诉用户。
  - 契约在、这一次读不出：不拦，stderr 留一行「这一次读不出、派之前没核契约的账」——与派发返回的【契约】说「过一会儿再看」同一个口径。
  - PENDING 而契约不在：`compareContractSha` 一律当「还没写」，不拦（`docs/37` §5 登着那一条）；S6、S7 的前置里没有契约，这一路整段放行。
  - 角色名、段名都是插件自己的（目标已经对上了 `stages.json` 里的产者），原样写；记录的 sha 经 `shaOrNote`。
- 正文：`commands/at.md` 第 1 节说派验证段的产者之前门禁也对一遍、对不上不放行，第 4 节、`skills/at-contract-format/SKILL.md` 与 `templates/00-contract.md`
  的「`contract_sha` 没跟上的……」补上「派 `at-qa`、`at-acceptance` 也不放行」；`agents/at-acceptance.md` 那句改成「派你之前门禁再对一遍，对不上不让派」。
  `stages.README.md` 的消费方表与 `verifies` 一节补上 H2 这一处。
- 旧判据里三份测试的夹具（`gate-m4a`、`gate-m3z`、`gate-rework-freshness`）原来在契约已经在的 run 上把 `contract_sha` 写死成 PENDING，走到 S6、S7 派 `at-qa`、
  `at-acceptance` 时撞上这一条。真实的 run 走到验证段时这笔账早该记上了：改成契约在就记门禁按它算的 sha，不在才 PENDING。新判据没有为夹具放宽。

## 3. 判据与变异

- `tests/gate-readiness-contract.test.mjs`：
  - 账对得上——派 `at-qa`、`at-acceptance` 放行。
  - 漂了——两个都拒，理由带【契约】那一句、角色名与「处理完再派」，不带磁盘上算出来的值。
  - PENDING 而契约在、`contract_sha` 不合法、记着值而契约不在——都拒，各带那一支的出路。
  - 只管验证段的产者：账对不上时派 `at-architect`、`at-product` 不在这里拦。
  - PENDING 而契约还没写：不在这里拦。
  - 从 `verifies` 派生：插件副本里把 S6 的 `verifies` 拿掉，派 `at-qa` 不再核；没拿掉的 S7 照拒。
  - `verifyStageOf` 的单测；正文两句在、门禁真的拒。
  - 契约在却读不出（只在 POSIX 上用权限造）：不拦，stderr 说没核。
  - 顺序（复核）：已收口、前置缺、这一轮已经交过（重做）、派它的是别的一趟的人——账对不上时都说那几条、不说「处理完再派」。
  - 主线程（没有 `agent_type`）派、裸名 `at-qa`、S5 提前派——照样拒；调用者写不了 `state.json` 时给转给 PM 的那一版；派项目经理不在这里说契约的账。
- `tests/trusted-echo.test.mjs`：「`state.contract_sha`」与「契约不在」两格补上 H2 派 `at-qa` 这个入口。
- 变异（备份在仓库外，每一刀改完逐字节还原）：H2 不核这笔账、理由不带【契约】那一句、理由不说处理完再派、`verifyStageOf` 不看 `verifies`、取链上最后一个、
  不看阶段链形状；复核修订之后又加了这一段挪回就绪判据之前、挪到收口判据之前、挪到别的一趟之前、挪到重做判据之前（挪过去的那一段自己读花名册，
  免得它因为还没声明的变量直接崩掉）、不看派不派得到、不分收件人、只认带前缀的名字、主线程派发不核、只在它自己那一段核——每一刀都有判据红。「读不出也拒」那一刀只有 POSIX 那一格打得红，Windows 上那一格跳过、它存活；在本机用 PowerShell 以 `FileShare.None`
  独占打开契约、同时跑一次 H2 派 `at-qa`，手工核过：原代码不拦、stderr 留痕，变异体拒——POSIX 那一格认得出它。
- 没起真实会话：H2 的判定在子进程里全走到了。

## 4. 仍然开着的边界

- **派出去之后才漂的**：`at-acceptance` 正在验时契约被改，它照样收不到；派发返回时【契约】到项目经理。契约改了需求的，契约基线叫验证段重出；被人改过、
  又恢复原样的，那一轮的结论对着的是哪一版说不清。
- **执行角色（S5）照样派得出去**：只管验证段的产者——执行段对着契约做，账没对上时做出来的东西由之后的验证段对着对上账的契约验。
- **「契约在、却读不出」在 Windows 上没有自动判据**（与 `docs/37` §5 那一条同一族）：这一轮手工核过一次。
- **PENDING 而契约不在**：一律当「还没写」，不拦（`docs/37` §5 登着那一条）——过了第一段契约丢了、`contract_sha` 还是 PENDING 的，派验证段时也不说。

## 5. 没量到的

- 真实会话里项目经理被这一条拒了之后照不照【契约】那一句处理、再派。
  > **更新（2026-10-10，`docs/64`）**：正路在一趟真实会话里量过了——改需求之后项目经理记上了新的 `contract_sha`，派 `at-qa`、`at-acceptance` 时账对得上，没有误拦；拒绝那一路仍没量到。

## 6. 归属

- `hooks/lib/stages.mjs` 的 `verifyStageOf`；`hooks/gate.mjs` 的 `contractCmp` 与 H2 里那一段；判据在 `tests/gate-readiness-contract.test.mjs`。

## 8. 复核与修订

第一版（检查排在收口判据之后、就绪判据之前，`verifyStageOf` 认全部验证段的产者，理由一律许诺「处理完再派」）推上分支、CI 全绿之后，起了一个对抗复核的
子代理：把【契约】每一支的出路照做一遍（都放行）、在 Windows 上用独占锁复现「读不出」、对实现与判据做变异。结论是不会卡死正常流程；两个中等、几个小问题，
都在这一轮改了：

- **中 1：检查的位置没有判据钉着**——挪到收口判据之前，已收口又漂了的 run 上派 `at-qa`，理由变成一条走不通的「处理完再派」。挪到别的一趟之前、重做判据
  之后也都绿。→ 挪到 H2 最后（低 2 的修法之一），补「顺序」两格。
- **中 2：trusted-echo 的入口清单没补**——拒绝理由里原样拼 `contract_sha` 的变异，判据全绿。→ 两格补上 H2 派 `at-qa`。
- **低 1：`verifyStageOf` 也把项目经理算成验证段的产者**（S8），PM 派 `at-pm` 时 H2 许诺一条 H1 永远不放的出口。→ 只核花名册里有人派得到的角色。
- **低 2：「处理完再派」会落空、不分收件人**——重做的情形里处理完账照样被重做判据拒；调用者写不了 `state.json` 时收到的也是只有 PM 做得了的那一句。
  → 排在最后；写不了 `state.json` 的调用者给转给 PM 的那一版。
- **低 3：主线程派发、裸名、提前派三条路没有判据**。→ 补了。
- **低 4：§2 一句不准**（PENDING 而契约不在不是「由前置判」——前置里没有契约）。→ 改了。
- **低 5：三处正文没提派验证段会被拒**。→ 补了。
- 复核也确认了：PENDING、不合法、第 4 节修订之后没记、回传丢了、契约被人改过——每一支照做之后都放行，H6、H4 不拒项目经理单改 `contract_sha` 或在后段重写
  契约；H1 不会抢先拒掉合法的派发；别的插件前缀、大小写不同的名字 H1 直接拒；拒绝理由里的外部值都经 `shaOrNote`，五种载荷下没有漏。
