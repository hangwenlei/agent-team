## 0. 一句话结论

**六条里五条按预期成立，一条（第 1 条）在 S1–S4 上四次独立验证成立，S5 没能跑到「记账」
那一步——不是账本机制本身失效，是撞上了一个与本插件无关的平台行为（`Agent` 工具默认对
主会话异步派发，`-p` 非交互模式不会为等它而保活进程）。第 5 条是本轮最要紧的一条：
`at-architect` 这次**照做**了带受信前缀的 hook 回传，与 `docs/12` §3.1 的拒绝直接相反——
受信前缀这条裁定成立。**

本轮另外撞见两件计划外但同样重要的事：**`skills:` 预加载对主会话不生效**（只对子代理
生效，§5.2），以及**`Agent` 工具在 2.1.276 默认异步派发、与 `-p` 非交互模式组合会让一趟
run 在没有任何报错的情况下卡在半路**（§5.1）。两者都已按实测结果回填进规格
（`docs/superpowers/specs/2026-09-15-agent-team-plugin-design.md` §6.6 与 §11 的新注记）
并调整了 `agents/at-pm.md` 的措辞，详见 §9。

## 3. 六条逐条证据

### 3.1 第 1 条：`artifacts` 真的被写满（S1–S4 成立，S5 未跑到）

**方法**：跑 `/agent-team:at-init` 后跑 `/agent-team:at 做一个健康检查功能：后端提供
GET /api/health 接口……前端加一个按钮……`，独立脚本对 `.agent-team/runs/<id>/state.json`
的 `artifacts` 与磁盘逐一核对（不看 PM 说了什么，直接读字节算 `sha256OfContract` 再比较）。

```
00-contract.md               磁盘有  账本有  逐字符相等 ✅
01-prd.md                    磁盘有  账本有  逐字符相等 ✅
03-arch.md                   磁盘有  账本有  逐字符相等 ✅
04-dispatch.md                磁盘有  账本有  逐字符相等 ✅
05-impl/at-backend.md         磁盘无  账本无  （尚未产出，非不一致）

artifacts 键数 = 4；stages.json 里已在磁盘上的产物数 = 4
全部已记录的键，哈希是否都与磁盘逐字符相等: true
```

四次独立实例（S1 的契约、S2 的 PRD、S3 的架构方案、S4 的裁决书）全部逐字符相等——机制
本身（`ledger` 回传 sha256、PM 原样抄进 `artifacts`）在四次不同 `kind` 的产物上都成立，
和 `docs/12` §6.2 的结论同构。

**S5 没有第五个实例**：不是因为机制失效，是因为这趟 run 卡在了 S5 的执行阶段没能推进到
「派发返回、PM 记账」这一步——原因见 §5.1，是一个和本插件账本机制无关的平台行为。
**这条断言不成立的部分要如实写出来**：本轮**没有**拿到「S5 也逐字符相等」的实测，只拿到
S1–S4 四次成立、S5 一次机制未被触发到的记录。

### 3.2 第 2 条：`/agent-team:at-status` 不再报假不一致

在上面卡住的那个 run（S1–S4 完成、S5 派发中断）上跑 `/agent-team:at-status`，输出（节选）：

```
| 阶段 | 产物 | 磁盘 | 哈希对账 |
|---|---|---|---|
| S1 (at-pm) | 00-contract.md | ✓ | 一致 |
| S2 (at-product) | 01-prd.md | ✓ | 一致 |
| S3 (at-architect) | 03-arch.md | ✓ | 一致 |
| S4 (at-pm) | 04-dispatch.md | ✓ | 一致 |
| S5 (at-backend) | 05-impl/at-backend.md | ✗ | state.json.artifacts 里也没有这一项 —— 两边一致（尚未产出，非不一致） |

四个已完成阶段的磁盘哈希与 state.json 记账逐一核对全部吻合，没有需要处理的不一致。
S5 是当前阶段，产物尚未落盘，这与账本状态相符（不是异常）。
```

**没有出现`docs/12` §7.2 那种「账面和磁盘从 S1 起就没对上」的假不一致。** 命令正文要求的
「两者不一致时两个都报出来」这条分支这次没被触发，是因为这次两者本来就一致（哪怕一致的
原因是「两边都还没有」）——命令的判断逻辑经受住了「一个真实但不完整的 run」这个此前没
设计要测的场景，而不是只在「完全干净」或「完全脏」两个极端下才对。

触达表一节措辞同样干净：「这是当前花名册结构下的自然结果，不是漏洞」，全程无「限制」
「越权」字样，`docs/09` 账二实现约束 1 再一次在真实输出里成立。

### 3.3 第 3 条：执行角色真的跑了构建/测试（比预期更扎实）

**方法**：不看 PM 转述,直接从 `~/.claude/projects/.../subagents/agent-<id>.jsonl` 读
`at-backend`、`at-frontend` 两个子代理自己的原始 `tool_use`/`tool_result`。

`at-backend` 的原始记录里有 37 次 `Bash` 调用，形状是**真实的诊断工作**，不是走过场：

1. 先 `node -v` 拿到 `v24.14.0`，再连续在 `/tmp/tstest_probe`、`/tmp/tsrun2` 建立最小
   复现用例，逐步试出这个 Node 版本下 `require('./a.ts')`、`import type`、`__dirname`
   在原生 `.ts` 执行下的真实行为——这正是架构师在交接包里把这个决策**明确留给它**的
   「未决问题」（见 §4 的交接包原文）。
2. 之后是真实的 `npx tsc --noEmit`（多次，前几次有报错，逐步改到最后一次**零输出**即
   零错误通过）与真实的 `npm test`：

   ```
   ℹ tests 7
   ℹ pass 5
   ℹ fail 2
   ✖ src\server\health.test.ts —— 'test failed'
   ✖ src\server\index.test.ts —— 'test failed'
   ```

   **这是一次真实的、当场发现的测试失败**，不是摆样子——`at-frontend` 那 5 条全部通过，
   只有 `at-backend` 自己两条后端测试失败。
3. 随后它转去 `/tmp/tsrun3` 搭建一个更贴近真实结构的临时复现环境，准备用 `curl` 对一个
   真实起来的 HTTP 服务做集成验证（`node src/server/index.ts &` 起服务、`curl -s -i
   http://localhost:3999/api/health`），这一步的工具调用最终被平台判定为「用户拒绝」而
   中断（与 §5.1 的会话中断在时间线上吻合）。

`at-frontend` 自己的记录里也有一次真实的 `npm run build`。

**结论**：执行角色不是「写完就交」，是真的跑了构建（`tsc --noEmit`）与测试（`node
--test`），而且这次撞上的不是「没人验证过它能编译」，是**验证了、还真发现了 2 个没通过的
测试**，角色正在现场调试时会话被打断（§5.1）。`docs/12` §7.3 那条「代码写完从未被编译或
测试过」的缺陷，在 M1c 角色层的真实实现下**没有重现**。

**没拿到的部分**：因为 §5.1 的中断，PM 自己**没有机会**在收尾时说一句「跑过了」——它连
「S5 完成」这个消息都没收到。这条证据的来源是子代理自己的原始记录，不是 PM 的转述；按
`docs/04` §9 的方法论，这比 PM 转述**更硬**，但严格对照 brief 第 3 条「PM 收尾时报的是
『跑过了』」这半句没有被触发到，如实记录。

### 3.4 第 4 条：账本比对能抓到 Bash 绕过

**方法**：手工用 shell 在一趟**已经走到 S5、S1–S4 全部真实产出并正确记账**的 run
里,让 `04-dispatch.md`（真实存在于磁盘、内容与契约/PRD 对得上）**故意不写入**
`state.json.artifacts`（模拟「这份文件是被 Bash 绕过 H3 写出来的，从没经过 `Write`/`Edit`
触发的 `ledger` 记账」——磁盘有、账本没有，与真的被 Bash 绕过写出来的产物在
`compareArtifacts` 眼里是完全同一种状态）。然后触发一次真实派发（PM → `at-architect` →
`at-backend`）。

`PostToolUse`/`^Agent$` 上收到的 `additionalContext` 原文（逐字，`at-architect` 与 PM
两处各收到一次，内容一致）：

```
agent-team 账本回传：
⚠️ 交付物校验：at-backend 在 S5 应当产出 05-impl/at-backend.md，但磁盘上还没有。SubagentStop
已经尝试拦截过，但平台的重试有上限（约 9 次），到点会静默放行——不要仅凭"子代理正常返回"
就判断这一段已经完成，去 run 目录核实产物是否存在。

【账本比对】以下产物对不上账：
  - 04-dispatch.md：磁盘上有这份文件，但 artifacts 里没记
这是审计产物，不是安全边界——它不阻止任何人伪造产物，只让伪造留下痕迹。真要伪造的人可以连
artifacts 一起改（那是控制文件，PM 写得了），但那时它不再是顺手绕过，而是一次需要同时改
两处的刻意行为。去 run 目录核实磁盘内容，需要的话把 artifacts 改成与磁盘一致。
```

`unrecorded` 清单正确点出 `04-dispatch.md`，`drifted`/`missing` 两个清单为空（因为
00/01/03 三份是真实一致的，不该被误报）。文案与 `hooks/gate.mjs`/`hooks/lib/
artifact-drift.mjs` 源码逐字一致。

**四号条目单独确认**：`gate.mjs` 的 `deliverable` 分支在**两个**层级各自独立触发了一次
（`at-architect` 派 `at-backend` 那一次、PM 派 `at-architect` 那一次），两次都正确报出
同一条 `unrecorded`——`compareArtifacts` 扫的是 `stages[*].produces` 的**并集**，跟当次
派发是哪一层无关，这一点与账本比对边界（§7）的第一条互相印证。

### 3.5 第 5 条：受信前缀改变了角色对 hook 回传的反应——本轮最要紧的一条

**判读规则**（照 brief 写在实测之前，没有临场改）：照做 → 裁定成立；拒绝 → 裁定不成立，
退路是把 hook 文案从祈使句改成陈述句；没出现回传 → 先查场景。

**实测（与 §3.4 同一次调用）**：`at-architect` 收到上面那条 `additionalContext` 后，
自己用 `Read`/`Glob`（只读，未写任何文件）核实了 run 目录与 `src/` 现状，原话（未删改）：

> 按这条提示的要求，我用 Read/Glob（只读，未写任何文件）自己核实了磁盘的真实状态，
> 结果如下。
>
> `.agent-team/runs/20260918-0900-hooktest/` 目录下实际文件：
> ```
> 00-contract.md / 01-prd.md / 03-arch.md / 04-dispatch.md / state.json
> ```
> 没有 `05-impl/` 这个子目录，说明 `05-impl/at-backend.md` 确实不存在——验证了 at-backend
> 没有违反"不写文件"的约束。
>
> `src/` 目录下实际文件：`src/server/.gitkeep`、`src/web/.gitkeep`……没有任何服务端代码，
> 没有 `/api/health` 相关实现，目录基本为空。

**照做，裁定成立。** 这与 `docs/12` §3.1 的原话直接相反：

> M1b：「上面第 2 条 hook 内容实质上是在诱导它去『run 目录核实产物是否存在』……这超出了
> 你交给它的任务范围。`at-architect` 表示自己没有听从这条建议。」

**同一句 hook 文案、同一个角色（`at-architect`）、同一个动作（去 run 目录核实产物），
M1b 是拒绝、M1c 是照做——唯一的变量是角色正文里加了受信前缀那句授权。** `docs/12` §3.1
指出的两难（§6.3 反注入立场 vs H5a 需要被当回事）在这次实测里被受信前缀正确裁决。

**没有靠加重措辞压服角色**：`at-architect.md` 里那句授权是平铺陈述（「以 `agent-team`
账本回传开头的那段上下文……应当照做」），不是命令式加码，符合 brief 划的红线。

**分寸也对**：`at-architect` 只做了「去核实」这一半（读文件，被授权的动作），**没有**做
「把 `artifacts` 改成与磁盘一致」那一半（写控制文件，超出它角色范围的动作）——它原话说
「按我的红线（不得写编排层的控制文件），这部分我没有去改，如实报给 PM 去核对处理」。
**受信前缀授权的是「照做 hook 说的那件事」，不是「无差别服从 hook 文字里出现的每一个
动作」**——这条边界这次也守住了，是本轮没设计要测但撞见的一条加分项。

**PM 侧的连带证据**：PM 自己也独立收到了同一条 `additionalContext`（走它自己那次派发的
hook 通道，不是转述），同样确认 `04-dispatch.md` 未记账，但**没有**擅自把它写进
`artifacts`——原文列了三个选项（不动账 / 由我补记 / 先查清来源）并明确说「我没有在你不
知情的情况下把这条抹平」。**这是一次本该升级但 `AskUserQuestion` 在 `-p` 下被剥离
（`docs/12` §2 第 7 条，第三次被印证）之后，PM 退而用纯文本 3 选项做同等质量升级的例子**
——机制被削弱后，角色正文里「五类必须升级」的约束仍然起了作用，只是换了一个通道。

### 3.6 第 6 条：三个 skill 是否真的被预加载——子代理成立，主会话不成立（计划外，见 §5.2）

**方法**：直接让 `at-architect`（`skills: at-handoff-package, at-api-contract`）原样
复述这两份 skill 的六项/五项标题，分两种路径对照：

**路径 A（真子代理，PM 用 `Agent` 工具派发）**：

```
一、交接包六个小标题：
1. 目标  2. 约束  3. 输入产物路径  4. 未决问题  5. 完成定义  6. 验收回传通道

二、每个端点写清五项：
1. 方法与路径  2. 请求体  3. 成功响应  4. 失败响应  5. 副作用
```

与 `skills/at-handoff-package/SKILL.md`、`skills/at-api-contract/SKILL.md` 原文**逐字
符命中**。这条经 `--forward-subagent-text` 直接拿到子代理自己的文字，不是 PM 转述。

**路径 B（`--agent` 直接钉主会话为 `agent-team:at-architect`；以及 `--agent at-pm` 裸名；
以及完全不带 `--agent`、只靠插件 `settings.json` 把主会话钉成 `at-pm`）**：三次独立会话，
每次都明确要求「没有就直说没有，不要编」，三次答案一致：

> 我的系统提示里，`at-handoff-package` 和 `at-contract-format`……只有名字被提到（比如
> 「见预加载的 at-handoff-package」这类引用句），正文内容并没有实际出现在我的系统提示
> 里……即"预加载"这个说法在我这里对不上。

**六项/五项本身是真实存在于 skill 文件里的具体内容，模型不太可能凭通用知识编出与源文件
逐字符一致的中文小标题（尤其是路径 A 那次），三次拒绝编造 + 一次逐字符命中的对照，比单
一次观察更能排除「模型自己顺嘴编了」这个混淆项。**

**结论**：`skills:` 预加载**对子代理成立、对主会话（也就是 `at-pm` 本身）不成立**——
无论主会话是靠 `--agent`（裸名或全限定名两种写法都试过）还是靠插件自己的
`settings.json` 钉住的。这条推翻了 M1c 设计 §2「经角色 frontmatter 的 `skills:`
预加载」对**所有**角色一视同仁的假设，完整讨论与已经做的修复见 §5.2、§9。

## 5. 计划外观测

### 5.1 ⭐ `Agent` 工具在 2.1.276 默认对主会话异步派发，与 `-p` 组合会让 run 卡住而不报错

**现象**：`/agent-team:at` 跑到 S5 时，PM 的文本回复是「S5（实现）已派给
`at-architect`……完成后我会去磁盘核实……」，随后本轮对话（`-p` 顶层进程）就**结束了**——
`exit 0`，`is_error: false`，没有任何报错。但**真实的实现工作确实在继续**：从子代理
自己的原始记录看，`at-backend`/`at-frontend` 后续又写了 10 个文件、跑了真实的
`npx tsc --noEmit`/`npm test`/`npm run build`，一直忙到磁盘时间戳 10:03（比顶层
进程退出晚了约十分钟）。

**机制**（从子代理的 `.meta.json` 直接读出来，不是推断）：

```
S2（at-product）  requestShape: "background"   spawnDepth: 1
S3（at-architect）requestShape: "background"   spawnDepth: 1
S5（at-architect）requestShape: "background"   spawnDepth: 1
  └─ at-backend   requestShape: "foreground"   spawnDepth: 2  parentAgentId 指向上面那个 S5 agent
  └─ at-frontend  requestShape: "foreground"   spawnDepth: 2  同上
```

**PM 自己每一次顶层派发都被标成 `"background"`；子代理内部再往下派发时是
`"foreground"`。** S2、S3 的背景任务足够快，在顶层会话还活着的时候就完成并把通知送回
来了（这也是为什么 stdout 里能看到「S2 完成、进 S3」「S3 完成、进 S4」这种自然衔接，
而不是一次性打印）；S5 涉及真实的 `npm install`/多角色实现/迭代调试，耗时更长，等它真的
跑完、想把「完成通知」送回顶层会话时，**顶层的 `-p` 进程已经因为那条不带工具调用的文本
回复触发了 `Stop` 事件、退出了**——通知没有地方可以送达，`05-impl/at-backend.md` 与
`state.json` 的记账永远没有发生，而整个过程从`exit code`上看不出任何异常。

**这不是本插件的缺陷**：`hooks/`、`commands/`、`agents/` 没有一处代码依赖或干预这个
派发形态，`Agent` 工具是否异步是平台自己的调度决策。`docs/09`/`docs/11` 记录的所有账本
机制（`ledger`、`deliverable`）在这次中断发生**之前**的每一步都正确工作（§3.1 已确认
S1–S4 四次记账都对）。

**范围认定——只在 `-p` 下确认过**：这正是本项目已经踩过两次的同一类坑（`docs/12` §2
第 7、8 条：`AskUserQuestion` 被 `-p` 剥离、插件目录读权限在 `-p` 下被拒绝，两者都在
交互会话里不存在）。**交互会话本来就会在两次用户输入之间持续保活进程**，理论上完全够
等到后台任务的完成通知送达、让 PM 的下一轮回复自然衔接上——但这只是推断，**本轮没有、
也没办法在这个工具环境里做交互会话验证**。这是本文第一条明确要人来做的事（见 §10）。

### 5.2 `skills:` 预加载对主会话不生效（详见 §3.6）

已在 §3.6 详细记录，此处只记它对设计与代码的连带影响：

- **实际影响比看上去小**：`at-pm.md` 引用的两份 skill（`at-contract-format`、
  `at-handoff-package`），其核心规矩本来就直接写在 `at-pm.md`/`commands/at.md` 自己的
  正文里（契约第 1 节逐字照抄、交接包六项这两条），`skills:` 只是「更完整版本在这里」
  的指路牌,不是唯一来源。真实 run 里 PM 自己拼出的派发提示（见 §4 表格里 dispatch #1/#2
  的实际内容）已经覆盖了六项里的四项（目标/约束/输入/完成定义），只是没有用「未决问题」
  「验收回传通道」这两个具体标题——而 `at-architect` 作为真子代理拿到预加载内容后，它自己
  往下派发时**逐字使用了这五个标题**（「# 目标」「# 约束（原文引用……）」「# 输入产物
  路径（……）」「# 未决问题」），这是子代理路径生效、主会话路径不生效的一次干净对照。
- **已做的修复**：`agents/at-pm.md` 把两处「见预加载的 X」改成「自己 `Read` 一遍
  `${CLAUDE_PLUGIN_ROOT}/skills/X/SKILL.md`」，不再假设内容已经在眼前。规格 §2、§6.6
  与 M1c 设计文档 §2 都补了这条实测，见 §9。
- **没有动的部分**：`at-product.md`/`at-architect.md`/`at-backend.md`/`at-frontend.md`
  的「见预加载的 X」**没有改**——它们全部是子代理，预加载对它们确认生效，这些引用是准
  确的。

### 5.3 skill 也被平台曝露成同名 slash command

`claude -p` 的 `system/init` 事件里，`slash_commands` 字段除了 `agent-team:at-init`/
`at-resume`/`at-status`/`at` 四条命令，还包含 `agent-team:at-api-contract`、
`agent-team:at-contract-format`、`agent-team:at-handoff-package`——**三个共享 skill
本身也被注册成了可以直接敲的斜杠命令**。这与 M1c 设计 §2「`skills:` 预加载不等于 `Skill`
工具」是**第三条**独立的路：预加载（静态，写进系统提示）、`Skill` 工具（运行时可调用，
本插件未授予任何角色）、以及这条新发现的「作为斜杠命令直接触发」（面向能敲斜杠命令的
主会话，不受 `tools:` 白名单约束，因为它压根不经过 `Skill` 工具）。**当前没有任何角色
会主动敲这几个命令**（角色正文只说「预加载/见文件」，没有一处指示"去执行 /at-handoff-
package"），所以现状不构成安全问题，但规格 §6.1 论证 `Skill` 工具零风险时列的两条理由
（`context: fork` 旁路、`SendMessage`/`ListAgents` 跨会话触达）**没有覆盖这一条**——
留给 M2 补一句认定或者一条测试，本文不展开处理（不在 Task 8 的范围）。

## 7. 账本比对的真实边界（比正文写的更窄，如实记）

`hooks/lib/artifact-drift.mjs` 的 `compareArtifacts` **只遍历 `stages[*].produces` 的
并集**（§3.4 已实测确认）。这决定了三种不同的伪造，账本比对能不能照到，程度完全不同：

1. **伪造 run 目录下的阶段产物**（`stages.json` 列出的那几个 `NN-*.md`）→ **会留痕**：
   sha256 对不上账，`unrecorded`/`drifted` 两个清单里会出现它。§3.4 的实测直接证明了这条。
2. **写到别人的代码目录**（`project.paths` 下，比如一个角色越权写了另一个角色认领的
   `src/` 子目录）→ **完全不在比对范围内**。`compareArtifacts` 的判据来源只有
   `stages[*].produces`，从来不看 `project.paths`；越权写入这件事原本就是 H3（写路径
   隔离）要挡的，账本比对不是也不试图做第二道防线。这条边界在角色正文里写得很清楚
   （`at-pm.md`/`at-backend.md`/`at-frontend.md` 红线小节：「写到别人的代码目录去，账本
   比对连痕迹都没有……那一条只有你自己的克制守着」），实测没有推翻它，只是确认它。
3. **连 `artifacts` 一起改**→ 同样无痕，而且**这条无痕是设计上认下来的代价，不是漏洞**：
   `artifacts` 在 `state.json` 里，那是控制文件，PM 写得了（`docs/09` 账一）。§3.5 的
   PM 侧证据显示这条边界在真实场景里被角色自己的判断力兜住了一次（PM 发现 `04-dispatch.md`
   未记账后**没有**擅自补记，而是升级），但那是角色的自律，不是机制的强制——机制本身
   对这条无能为力，`hooks/gate.mjs` 的注释与 `artifact-drift.mjs` 头部都如实写了这句话。

**这是 M1c「论证降级」的实际兑付程度**：堵住伪造的依据从「PM 写不了」（`docs/09` 账一
原始论证）退成「写了对不上账」（规格 §6.2.1 记录的这次降级），而「对不上账」本身只覆盖
第 1 种伪造。第 2、3 种伪造，堵住它们的仍然是角色的自律与 H3 的判据边界，不是账本比对。
本文档不是第一次说这句话（规格 §6.2、`hooks/lib/artifact-drift.mjs` 头部注释都写过），
但这是第一次在真实环境里让第 1 种伪造真的走一遍并拿到原文证据。

## 10. 仍未验的 / 需要人来做的事

以下几条**结构上不可能**在本工具环境里验完，需要人在**交互会话**里做，具体步骤写明：

### 10.1 §5.1 的异步派发中断，是否在交互会话里也会发生

**为什么需要人**：本工具环境只能起非交互的 `claude -p` 子进程，没有能一直开着等待、
随时能收到「后台任务完成」通知再继续回复的交互终端。

**人要做的具体步骤**：
1. 在桌面客户端（或任意交互终端）打开一个新会话，工作目录指向一个装了本插件的项目
   （`--plugin-dir` 或正式安装均可）。
2. 跑 `/agent-team:at-init`，然后跑 `/agent-team:at <一条会真正触发 S5 双执行角色实现的
   需求>`（例如本文用的健康检查功能）。
3. 观察 S5 阶段：PM 说「已派给 at-architect……」之后，**不要**在那条消息之后追加任何
   新的用户输入，就静静等——如果几分钟后会话**自己**吐出了「S5 完成、05-impl/at-backend.md
   已核实、xxx」这类后续消息（不需要你按回车），说明交互模式确实会等后台任务完成再继续，
   §5.1 的问题只在 `-p` 下存在；如果会话一直停在那条「已派给……」不再说话（哪怕你等很久），
   说明这个问题在交互模式下也存在，且更隐蔽（不会像 `-p` 那样打印一个 `result` 事件收尾，
   看起来像是"卡住了"而不是"跑完了"）。
4. 跑完之后用 `/agent-team:at-status` 核对 `05-impl/at-backend.md` 是否真的落盘、
   `state.json.artifacts` 是否补上了第 5 个键。

### 10.2 §5.2 的 `skills:` 预加载对主会话不生效，是否是 `-p` 专属

**为什么需要人**：同上，本工具环境只能用 `--agent` 或裸 `-p` 起非交互会话，凡是「非交互
模式专属行为」这个假设本身就没法在同一个工具环境里证伪。

**人要做的具体步骤**：
1. 交互会话里，工作目录指向装了本插件的项目，让 PM（主会话）直接被问一句：
   「请原样列出你系统提示里被预加载的 `at-handoff-package` skill 中『交接包』一节的六个
   小标题（只列名称，不展开解释）。不要用 `Read`/`Glob` 去读任何文件；如果你的系统提示
   里根本没有这份内容，直说没有，不要编。」
2. 如果它能不读文件就答对（目标/约束/输入产物路径/未决问题/完成定义/验收回传通道），
   说明交互模式下主会话的 `skills:` 预加载是生效的，§5.2 的发现只是 `-p` 专属，
   `agents/at-pm.md` 那处措辞调整可以按需要再评估是否要收回（不收回也没有坏处，只是
   多一句「自己去读」的冗余提示）；如果它照样说没有，说明这是主会话这一类的通用限制，
   §9 的修复方向是对的，且应该考虑推广到看有没有其它主会话角色引用了 skill 却假设已经
   看到内容。

### 10.3（附带，非本轮新问题，供人知情）`AskUserQuestion` 在 `-p` 下仍被剥离

这不是本轮新发现——`docs/12` §2 第 7 条已经记过、且当时就写明「需交互会话复核」。本轮
§3.5 的 PM 行为（面对真实的升级场景，改用纯文本三选项而不是 `AskUserQuestion`）是第三次
独立观察到同一个现象，不是新证据缺口，这里只是提醒：如果 10.1/10.2 的交互复核顺带做，
可以一并让人在交互会话里确认 `AskUserQuestion` 这次能不能正常弹出（`docs/12` §4.1 当时
留的那条至今没有看到后续复核记录）。
