# 没叫过的产者被当前置时推进也要

> 2026-10-11，分支 `r47-uncalled-producer-prereq`。第四十七轮（从开放边界索引挑）：`docs/81` §4「推进那一侧对 `[]` 照旧放行」，也是 `docs/77` §4
> 「`stage_roles` 记成 `[]`」那一格的 S2 那一半。动门禁判据（推进与判齐）、推进的拒绝理由、`/agent-team:at`、at-status、`stages.produces.md` 的几句与判据。

## 0. 一句话结论

- 随参与者展开的段（S2、S5），离开时原来只要叫到的人那几份：S2 记成 `[]`、谁都没裁，`01-prd.md` 不在也放行推进，到 S3 派人时 H2 才按前置拒。现在这一段
  没叫过、也没在这一段裁掉的产者，它被后面某段当前置的产物（S2 的 `01-prd.md`）照样要——推进（`advance.mjs` 的 `departureNeeds`）与判齐（`state.mjs` 的
  `isStageDone`，【阶段】用它）同一个口径。不是前置的（`02-*`、`05-impl/*`）没叫就不要，照旧。
- 出路与下一道门禁接得上（复核之后，§8）：这一段一个产者都没叫的，派它、或者整段不做这一段（这一段的产者都写进 `trimmed`）；叫过别的产者的，只有派它——
  只把它写进 `trimmed`，下一段派人时 H2 照前置拒（这一段不算整段裁掉）。

## 1. 问题

- 「叫到」只看 `stage_roles` 与派发记录：S2 一个产者都没叫、也没裁，推进那一次核的是空集，放行；`01-prd.md` 是 S3、S4、S7 的前置，到 S3 派架构师时 H2 才拒，
  出路要回头补 S2——推进那一刻本可以说清。只叫了 `at-ui` 的 S2 同样：【阶段】说 S2 齐了（02-* 都在）、推进放行，`01-prd.md` 照样缺。

## 2. 修法

- `hooks/lib/advance.mjs` 的 `departureNeeds`：随参与者展开的段，叫到的人那几份之外，再要没叫过、也没在这一段裁掉（`trimmedAt`）的产者被后面某段当前置
  （`!mayWaive`）的那几份，带上 `prereq` 与 `othersCalled`。`departureLines` 按它给出路：一个产者都没叫的，「派它；这一趟整段不做 S2：同一次 Write 把
  `{"at-product": "S2", "at-ui": "S2"}` 写进 trimmed，整段裁掉」；叫过别的产者的，「派它（……只裁掉 at-product 走不下去）」。括号里只列要派人的段
  （产者全是项目经理的段不列）。
- `hooks/lib/rework-guard.mjs`：推进拒绝理由的抬头补「没叫过、也没裁掉的产者被后面某段当前置的那几份」。
- `hooks/lib/state.mjs` 的 `isStageDone`：同一条（传了 `state` 时，调用方都传）。
- 正文：`commands/at.md` 第 3 节「推进那一次，H6 核离开的这一段交齐了没有」补「再加上这一段没叫过、也没裁掉的产者被后面某段当前置的那几份（`S2` 的
  `01-prd.md`：派 `at-product`；这一趟整段不做 `S2` 的，把这一段的产者都写进 `trimmed`）」；`stages.produces.md` 对象写法那一行、at-status「产物随参与者展开的段」
  那一段各补一句。给维护者的 `stages.README.md` 消费方表跟着改。
- 判据：`tests/advance.test.mjs`（S2 记成 `[]`、只叫了 `at-ui`、裁掉了、记在别的段的 trimmed、旧 run、S5 记成 `[]`；H6 接线两种出路、括号、抬头）；
  `tests/stage-trim-done.test.mjs`（`isStageDone` 的同一组情形、旧 run、别的段的 trimmed、不传 state）；`tests/advance-completion-prose.test.mjs`、
  `tests/stages-produces.test.mjs`、`tests/stage-roles-empty-prose.test.mjs` 各补关键句；`tests/gate-rework.test.mjs`「正常推进」那一条的夹具补上 `01-prd.md`（它停在
  S2、一个产者都没叫，正是这一轮要拒的情形，夹具比真实会话少了这份产物）。

## 3. 判据与变异

- 变异（备份在仓库外，改完逐字节还原，每刀跑全量），每一刀都红：
  - 第一版：推进那一侧去掉新那一圈、不看是不是前置、不看 `trimmed`、一律说整段裁掉；判齐那一侧去掉新那一圈、不看 `trimmed`、不看是不是前置；`/agent-team:at` 删掉新加的那半句。
  - 复核之后：推进对旧 run 不生效；判齐只在有 `stage_roles` 时、「在任何段裁掉都算」、去掉「传了 state」的守卫；出路不看叫没叫过别的、一律只说派它、JSON 只写
    这一个产者、括号不去掉项目经理的段；抬头改回；at.md、at-status 删掉新那一句。

## 4. 仍然开着的边界

- **记成 `[]` 而前置产物都在时【阶段】照旧不说齐了**：`isStageDone` 对参与者展开出来是空集的段照旧算没齐（推进放行）——`docs/77` §4 那一格的另一半，没动。
- **S5 记成 `[]`、S6 整段裁掉**：照旧推进放行而【阶段】不发（`05-impl/*` 不是前置）。
- **项目经理自己把 `at-product` 写进 `trimmed`、只叫了 `at-ui` 的 S2**：推进放行（裁掉了就不要）；S3 派人时 H2 照前置拒（S2 不算整段裁掉）——门禁不再给这条路，
  自己走进去的照旧在 S3 被拒。
- **产物固定的段那一支的括号**：「（S7、S8 要它当前置：整段裁掉它……）」照旧列出产者全是项目经理的段、不提传递受影响的段（这一轮只改了随参与者展开的段那一支）。

## 5. 没量到的

- 真实会话里推进出 S2 被这一条拒之后，项目经理派 `at-product` 还是整段裁掉 S2。

## 6. 归属

  `commands/at.md` 第 3 节、`commands/at-status.md`、`stages.produces.md`；判据见 §2。

## 8. 复核与修订

第一版（879edd9）推上分支之后起了一个对抗复核的子代理。下面这些核过了：新规则只在 S2 的 `01-prd.md` 缺或空、`at-product` 没叫也没在 S2 裁掉时拒，S3 派人时
H2 本来就会拒，只是提前；返工轮里标了 `"accepted"` 的放行、还是上一轮的照旧由逐份比 `rework_base` 那一道拦；旧 run 同样生效；整段裁掉 S2 时不要；收口不用
`departureNeeds`；`isStageDone` 的各处调用只有「记了人但没有 `at-product`、`01-prd.md` 不在」那一格从齐变成不齐，交付物核验走 `decideDeliverable`、不拦错人。
一个中等、五个低：

- **中 1：门禁给的出路「把 at-product 写进 trimmed」下一道门禁不认**——照做之后推进放行，S3 派架构师时 H2 照前置拒（S2 不算整段裁掉），也不给「连 S3 一起整段
  裁掉」那条路；叫过却没交时门禁明说 trimmed 不是出路，没叫过时同一个理由照样成立。→ 一个产者都没叫的给「派它、或者整段不做这一段」（这一段的产者都写进
  trimmed，H2 的整段裁掉那段话接得上）；叫过别的产者的只给「派它」。at.md 那半句跟着改。
- **低 2：括号列了 S4**（项目经理自己的段，没有要派的人），「裁掉它（……：裁掉它……）」重复。→ 新那一支括号只列要派人的段；产物固定的段那一支登在 §4。
- **低 3：拒绝理由的抬头没跟上**。→ 补上。
- **低 4：`stages.produces.md` 对象写法那一行、at-status、`stages.README.md` 消费方表没跟上**（at-resume 指向 `isStageDone` 的那一句照旧成立）。→ 补上。
- **低 5：几刀打不红**——推进与判齐对旧 run 不生效、判齐「在任何段裁掉都算」、去掉「传了 state」的守卫、at.md 删掉那半句。→ 补判据，都红了。
- **低 6：CHANGELOG 漏了「产品定义不在或是空文件时」；`docs/81` 的收口说「【阶段】同一个口径」，对 `[]` 那一格是空话**（参与者为空时 `isStageDone` 早就答没齐）。→ 改准。
