# 门禁留痕 —— 静默放行的门禁怎么才看得见：先量通道，再裁定，再兑现

**日期** 2026-09-24（M3l） ｜ **CLI** `2.1.278 (Claude Code)` ｜ **node** `v24.14.0` ｜
Windows 11 Pro 10.0.26200，命令走 Git Bash

**口径** 全部会话都是 `claude --bg` 起的常驻后台会话（**不是 `-p`**），`--plugin-dir` 指向实现者
的隔离工作树；探针目录全在会话 scratchpad 里（**仓库外**）。

**证据分两级，分开标**：

- **记录级** —— CLI 自己写下的东西：会话转录（`~/.claude/projects/…/*.jsonl`）、`--debug-file`
  写出的调试日志、CLI 发到本机接收端的 OTel 事件，以及探针 hook 自己写的旁证文件（地面真值：
  「这个 hook 这一次真的跑了」）。**模型复述的那一句一概不取。**
- **源码级** —— 读的是本机那个 2.1.278 可执行文件里的源码串（只读，用来解释「为什么是这样」）。
  它比记录级低一档：它说明机制，不证明某一次真的发生了。

---

## 0. 一句话结论

1. **CLI 没有任何一条现成通道能把「某一道门禁这一次静默放行了」记成带身份的记录。**
   转录把它过滤掉；调试日志只留一行不带任何身份的 `Hook output does not start with {, treating
   as plain text`；OTel 只有「这一批几个 hook、成功几个」。**计数说得出有几个跑了，说不出是
   哪一道**——而这个插件要证明的恰恰是哪一道（§2）。
2. **只写 stderr、exit 0 会进转录，而且带身份**：一条 `hook_success`，它的 `command` 字段就是
   `hooks/hooks.json` 里那句 statusMessage，每道门禁一句、互不相同。**它不进模型上下文**（源码级，
   §2.3）。
3. **所以裁定：门禁自己留痕，默认关。** `AGENT_TEAM_GATE_TRACE=1` 时，每次门禁进程以 exit 0 结束，
   往 stderr 多写一行 `agent-team gate-trace check=<检查项> main=entered exit=0`。纯旁路、绝不抛异常、
   插件自己一个文件都不写（§3，实现在 `hooks/lib/trace.mjs`）。
4. **兑现了**：一个 `--bg` 会话加四个文件的夹具，五道静默门禁（H1 / H2 / H4 / H6 / H5b）各走一次
   放行路径，**转录里各有 CLI 写下的记录**（§5）。
5. **顺带量到一条会咬人的**：`claude --bg` 下，**在发起命令的那个 shell 里设环境变量，传不到
   hook 子进程**；`--settings '{"env":{…}}'` 传得到，含子代理里的 `SubagentStop`（§2.5）。

## 1. 问题

`docs/20` §7.3：整链那一趟的九份转录里，八道门禁**只有三道**留下过记录；H1 派发白名单、
H2 就绪门禁、H4 契约保护、H6 返工预算、H5b 交付物拦截**零足迹**。原因不是它们没跑，是
**一道静默 exit 0 的 hook 在转录里不留任何记录**——主线程 16 次 `Edit`/`Write` 对应 48 次
`PreToolUse` 调用，转录里只有 2 条；5 次 `Agent` 对应 10 次调用，记录 0 条。

后果：一趟干净的 run **既证明不了那五道跑过，也证明不了它们没跑**。`docs/19` §11「八道都真的被
平台调起来了」那个结论，靠的是**故意让每一道说话**（手工造违规状态）。「门禁强制」是这个插件的
卖点，而它**在真实使用的正常路径上不可验证**。

本轮的顺序是：**先量现成的通道，最理想的答案是「一行门禁都不改」**；量不出来再动门禁。

## 2. 第一阶段：现成的通道，逐个量

### 2.1 探针

探针 hook 是一个二十来行的 node 脚本，按参数以五种形状之一 **exit 0**：什么都不写 / 只写 stderr
一行 / stdout 写一行非 JSON 文本 / stdout 写 `{}` / stdout 只写空白与换行。**每次运行都往一个旁证
文件追加一行**（事件名、工具名、`agent_type`、以及几个环境变量的值）——那是「这一次真的跑了」的
地面真值，与 CLI 记不记无关。

探针 hook 是用 `--settings <文件>` 注册的（**只对那一个会话生效，不碰任何持久配置**）：
`PreToolUse`（matcher `^Write$`）五种形状各一条、`PostToolUse`（`^Write$`）五种各一条、
`SubagentStop` 静默与 stderr 各一条，每条的 statusMessage 形如 `probe-<形状>-pre`。

四个探针会话（逐字命令里的长路径缩写成 `$SP`，即会话 scratchpad 下的 `gate-obs/`）：

| 会话 | 命令要点 | 让模型做的事 | 量什么 |
|---|---|---|---|
| ch1 | `claude --bg --plugin-dir <工作树> --permission-mode bypassPermissions --debug-file $SP/out/ch1-debug.log "<提示词>"` | 在空目录里 `Write` 一次 | 调试日志里 agent-team 的门禁长什么样 |
| P1 | `GATE_OBS_PROBE_SHELL=1 CLAUDE_CODE_DEBUG_LOG_LEVEL=verbose claude --bg --permission-mode bypassPermissions --settings $SP/out/p1-settings.json --debug-file $SP/out/p1-debug.log "<提示词>"` | `Write` 一次，再派一个 `general-purpose` 子代理只回一个词 | 三个通道 + 环境变量 |
| P2 | 同 P1，加 `--verbose`，`--settings` 的 env 里加 `CLAUDE_CODE_DEBUG_LOG_LEVEL=verbose` | `Write` 一次 | `--verbose` / verbose 日志级别 |
| P3 | 同 P1，`--settings` 的 env 里打开 OTel、导出到本机 `127.0.0.1:43181` 上一个只落盘的接收端 | `Write` 一次 | OTel |

旁证文件逐行确认：**P1 的 12 个探针 hook（5 + 5 + 2）全部跑了**，P2、P3 各 10 个全部跑了。
下面每一格「记不记」都是对着这份地面真值说的。

### 2.2 通道一：CLI 自己的记录模式

| 模式 | 怎么开 | `--bg` 里生效吗 | 静默 exit 0 的 hook 记不记 | 记在哪、记了什么 | 等级 |
|---|---|---|---|---|---|
| `--debug-file <路径>` | 命令行参数 | **生效**（文件写出来了） | 记，但**不带身份** | 每个 hook 一行 `Hook output does not start with {, treating as plain text`——**不含事件名、不含命令**；有输出的 hook 另有一行 `Hook <事件:工具> (<事件>) success:` 加输出原文——有事件名，**仍然没有命令** | 记录级 |
| `--verbose` | 命令行参数 | 生效 | **不改变转录**：P2 的转录与 P1 逐格相同 | — | 记录级 |
| `CLAUDE_CODE_DEBUG_LOG_LEVEL=verbose` | 环境变量 | **两条路都没生效**：shell 里设（P1）与 `--settings` 的 env 里设（P2），调试日志里 verbose 级的行都是 0 | — | 源码级：它多出来的也只是「这次匹配到 N 个 hook」这类计数行 | 记录级（没生效）＋ 源码级 |
| OTel | `--settings` 的 env：`CLAUDE_CODE_ENABLE_TELEMETRY=1`、OTLP/HTTP-JSON 导出到本机 | **生效**（接收端收到了日志与指标） | 记，但**只有计数** | `hook_execution_start` / `hook_execution_complete` 每一批一条：`hook_name: PreToolUse:Write`、`num_hooks: 5`、`num_success: 5`——**没有命令、没有 statusMessage**；`hook_registered` 只在启动时按注册列一遍，也不带命令 | 记录级 |
| `--include-hook-events` | 命令行参数，**只在 `-p` + `--output-format stream-json` 下**有效（CLI 自己的帮助原文） | 结构上只在 `-p` 里 | **没量**（§7） | 源码级：每个 hook 发一对 `hook_started` / `hook_response`，带 `hook_name`（事件:工具）、退出码与输出原文，**不带命令**——静默的那一次，输出是空的 | 源码级 |
| 转录本身 | — | — | **不记** | 源码级：落盘前有一道过滤，`content`、`stdout`、`stderr` 三样 trim 之后都为空的 `hook_success` 直接丢掉；CLI 内嵌的一段诊断提示原话是「successful runs with empty output are never persisted to transcripts」 | 记录级＋源码级 |
| `Stop` 的 `stop_hook_summary` | — | — | 记（按命令列出每个 `Stop` hook，**静默的也列**） | **只对主线程的 `Stop` 事件**；`SubagentStop` 在 P1 里一条 summary 都没有（主转录与子代理转录都查过）；本插件**没有** `Stop` hook | 记录级 |

**调试日志那一格的原文**（P1，同一次 `Write`，五个 `PreToolUse` 探针 hook，旁证文件确认五个都跑了）：

11:36:35.614Z [DEBUG] Hook output does not start with {, treating as plain text
11:36:35.614Z [DEBUG] "Hook PreToolUse:Write (PreToolUse) success:\ngate-obs probe stderr PreToolUse:Write"
11:36:35.620Z [DEBUG] Hook output does not start with {, treating as plain text

静默那一个**只剩头一行**，而那一行与别的 hook 的同一行一字不差。ch1 里 agent-team 自己的门禁
长得一模一样：一次 `Write` 之后 `PreToolUse` 有三行 `does not start with {`（H3 那一行后面跟着它的
stderr，H4 与 H6 两行光秃秃），`PostToolUse` 有两行（ledger 那一行后面跟着它的 stderr，另一行

**「H4 跑了、H6 没跑」与「H6 跑了、H4 没跑」在任何一种计数上都长得一样。**

### 2.3 通道二：只写 stderr、exit 0

| 事件 | 转录里有没有 | 记录的形状（逐字段） | 落在哪一份转录 |
|---|---|---|---|
| `PreToolUse:Write` | **有** | `type: hook_success`、`hookName: PreToolUse:Write`、`command: probe-stderr-pre`（**就是 statusMessage**）、`exitCode: 0`、`stdout: ""`、`stderr:` 原文、`content: ""` | 主转录 |
| `PostToolUse:Write` | **有** | 同上，`command: probe-stderr-post` | 主转录 |
| `SubagentStop` | **有** | 同上，`command: probe-stderr-sstop`，`hookName: SubagentStop` | **子代理自己那份** `subagents/agent-*.jsonl` |

`command` 字段是这条通道的全部价值：**身份是 CLI 自己写下的，不靠 hook 自报**。

**它进不进模型上下文——不进，源码级**：把附件转成发给模型的消息那一段里，`hook_success`
只在 `SessionStart` / `UserPromptSubmit` / `UserPromptExpansion` 三个事件上转，别的事件一律转成空；
界面渲染那一段对 `hook_success` 也是什么都不画。**所以这条通道的收件人是转录，不是模型，也不是
用户。** 真实会话里的旁证见 §5.4。

⚠️ **与交待下来的框架不一致的一处**：题目写「上一轮挖到的 `hook_success` 附件来自往 stdout 写 JSON
的那几道；纯 stderr + exit 0 是另一种形状，没量过」。**核下来这个形状上一轮的原料里就有**：
`docs/20` §7.2 数的那六条「fail open 留痕」全是它（例：`9a45d294-….jsonl` 里 H3 那一条，
`stdout` 长度 0、`stderr` 长度 268、`exitCode: 0`、`command: 校验写路径归属…`）。
**它被数过，只是没被当成一条通道来问**——本轮是第一次在一个受控探针上把它和另外四种形状并排量。

### 2.4 通道三：stdout 写非 JSON / `{}` / 只有空白，exit 0

| 形状 | 转录里有没有 | 调试日志 | 备注 |
|---|---|---|---|
| 一行非 JSON 文本 | **有**：`hook_success`，`content` 就是那行文本 | `success:\n<文本>` | 源码级：`PreToolUse` / `PostToolUse` 上同样不进模型上下文 |
| `{}` | **有**：`hook_success`，`stdout: "{}"`、`content: ""` | `success:\n{}` | 走 JSON 那条路，解析成功、没有任何决定 |
| 只有空白与换行 | **没有** | 一行 `success:` 加空白 | trim 之后为空，与静默同一个下场 |

**这条通道对门禁不能用，理由是具体的**：stdout 是 `PreToolUse` 表达拒绝的唯一通道（stdout 上的
`permissionDecision` JSON）。往 stdout 多写一行文本，**整段输出就不再以 `{` 开头**，CLI 会把它当成
纯文本——**那条拒绝 JSON 就被当成一句话吞掉了，一次拒绝变成一次放行**。stderr 是唯一一条与判定
正交的通道。

### 2.5 顺带：环境变量到不到得了 hook 子进程（实测，记录级）

题目要求「环境变量能不能传到 hook 子进程，要实测，别假设」。旁证文件里每一行都带着 hook 子进程
自己读到的环境变量：

| 怎么设 | P1 的 12 次 hook 运行里读到的值 |
|---|---|
| 在发起 `claude --bg` 的 shell 里设 `GATE_OBS_PROBE_SHELL=1` | **12 次全是 null** |
| 写进 `--settings` 文件的 `env` 键：`GATE_OBS_PROBE_SETTINGS=1` | **12 次全是 `"1"`**——含子代理里的两次 `SubagentStop` |
| shell 里设 `CLAUDE_CODE_DEBUG_LOG_LEVEL=verbose` | 12 次全是 null（CLI 自己也没切到 verbose 日志） |
| P2：`--settings` 的 `env` 里设 `CLAUDE_CODE_DEBUG_LOG_LEVEL=verbose` | hook 读到了 `"verbose"`，**CLI 自己的调试日志照样没切**（推的：源码里日志级别在日志器构造时从进程环境读一次，settings 的 `env` 在那之后才生效） |

**机制（推的，没量）**：`claude --bg` 第一次用时打印 `Starting background service…`，会话由那个后台
服务起，继承的是**服务的**环境，不是发起命令那个 shell 的。⚠️ P1 起的时候服务已经在跑（ch1 起的），
**「一个刚被这条命令拉起来的服务会不会继承这个 shell 的环境」本轮没量**（§7）。
**给用的人的结论不依赖这一格**：`--settings` 那条路在两种情形下都通。

### 2.6 汇总：三个通道各一行

- **通道一（CLI 自己的记录模式）**：调试日志记每一次 hook，但静默的那一次**只剩一行不带身份的
  文字**；OTel 只有**按批的计数**；`--verbose` 不改变转录；verbose 日志级别在 `--bg` 下送不进去；
  `--include-hook-events` 只在 `-p` 下有、源码里它也只带「事件:工具」。**都说不出是哪一道。**
- **通道二（stderr + exit 0）**：**进转录，带 CLI 自己写下的身份**（`command` = statusMessage），
  **不进模型上下文**，子代理事件落在子代理自己那份转录里。
- **通道三（stdout 非 JSON / `{}` / 空白）**：前两种进转录、空白不进；**但 stdout 是拒绝的通道，
  往里写东西会把拒绝变成放行**，门禁不能用。

## 3. 第二阶段：裁定 —— 门禁自己留痕，默认关

### 3.1 为什么没有「零改动」的答案

零改动要的是：**不动门禁，就能从 CLI 已经写下的东西里认出「H4 这一次跑过」**。§2 量下来，
CLI 写下的关于静默 hook 的一切都**不带那一道的身份**——要么是一行对谁都一样的字，要么是一个
随机器上装了哪些插件而变的数。**不是量得不够细，是那个字段不在记录里。** 所以最好的那个结果
（「写清楚怎么用现成的通道」）本轮拿不到，理由写在这里，不硬造。

### 3.2 机制

`hooks/lib/trace.mjs`，加 `hooks/gate.mjs` 里四行代码（一行 import、一个标记对象、一次注册、
`main()` 第一行置标记）：

- 模块顶层、`main()` 调用之前，`installTrace` 注册一个 `process.on('exit')` 监听——**只在
  `AGENT_TEAM_GATE_TRACE` 恰好是 `'1'` 时注册**；
- `main()` 第一行把一个标记置真（`main=entered`）；
- 监听在进程退出那一刻：**退出码是 0 才写**，只写 stderr，写一行：

```
agent-team gate-trace check=<检查项> main=entered exit=0
```

`check` 就是 `hooks.json` 传给 `gate.mjs` 的那个参数（`delegation` / `readiness` / `writepath` /
`contract` / `rework` / `deliverable` / `stop-gate` / `ledger`）。**全 ASCII 是有意的**：转录是 JSONL，
这一行在里面是一段被 JSON 转义过的字符串，ASCII 前缀在转义前后逐字相同，`grep` 一把就中。

⚠️ **为什么是退出监听、不是在每个出口手写一句**：`gate.mjs` 有十几处 `process.exit(0)`，逐个加是
十几处与判定逻辑交织的改动。监听一处注册，**判定逻辑一个字没动**。
⚠️ **为什么注册在 `main()` 之外**：M0 那次 junction 守卫误判的形状，是进程正常 exit 0、`main()` 一行
都没跑（`gate.mjs` 末尾那段历史教训）。监听在外面，那种退出也会留一行——写的是
`main=not-entered`，**不会被读成一次判过的放行**。

### 3.3 四条硬约束各自怎么落地

| 约束 | 落地 | 判据（`tests/gate-trace.test.mjs`） |
|---|---|---|
| **默认关**，正常会话零噪声、零额外磁盘写入 | 只认 `'1'`；关着时**什么都不注册** | 纯函数层：`'0'`/`''`/`'true'`/`'yes'`/带空白的 `'1'` 都算关、一个监听都不注册；子进程层：这几种写法与不设，stdout/stderr/退出码逐字节相同 |
| **纯旁路**，不改变任何一道门禁的判定 | 只在 exit 0 写、只写 stderr；exit 2（`SubagentStop` 的拒绝）一个字都不加——那段 stderr 就是平台原样发回给子代理的 Stop hook feedback | 十八格矩阵（覆盖八个检查项、静默 / stderr 留痕 / stdout 拒绝 JSON / stdout additionalContext / exit 2 五种形状），**开/关各跑一次**：stdout 逐字节相同、退出码相同、stderr 只在 exit 0 时多出恰好那一行 |
| **绝不抛异常**，绝不把一次放行变成失败 | 注册、写入各包一层 try/catch，写不出去就吞掉。`exit` 监听里漏出去的异常会把 exit 0 变成非零退出——那就是把放行改判成失败 | 纯函数层：注册抛、写入抛、`env` 取值抛、`proc` 残缺，一样都不漏 |
| **写到哪里要想清楚** | **插件自己一个文件都不写**，落盘的是 CLI 本来就在写的那份转录 | 开着把整张矩阵跑一遍，每一格项目目录的文件清单前后相同 |

另有两条配套判据：测试帮手（`tests/helpers/gate-runner.mjs`）缺省把这个开关从子进程环境里剥掉
——否则谁在自己 shell 里开着它跑 `node --test`，九条逐字比 stderr 的既有用例会一起红（§8 的 M1 量出来
的数），而红的原因不在它们测的东西里；以及本文件里写的开关名、前缀与 §4 那张判读表，必须就是源码里
与 `hooks/hooks.json` 里的那几样（照着文档 grep 却零命中，在这里恰好长得跟「门禁没跑」一模一样）。

### 3.4 写到哪里：为什么没选「写进 `runs/<id>/`」

题目点名要核两件事，核了：

- **账本比对会不会把它当成来路不明的产物**：不会。`compareArtifacts` 的 `unrecorded` 只遍历
  `producedNames(stages)`（`stages.json` 里各段 `produces` 展开出来的那些名字），一个不在任何
  `produces` 里的留痕文件**根本不在它的宇宙里**。
- **会不会撞上 H3 / H4 的路径判定**：不会。H3 / H4 挂在 `PreToolUse:Edit|Write|NotebookEdit` 上，
  管的是**工具调用**；hook 进程自己用 `fs` 写文件不经过任何 hook。

**核下来两样都「不撞」，但仍然不选它**：那是一次额外的磁盘写入（违反「零额外磁盘写入」的精神——
开着时才写也是插件自己在写）、八道门禁并发往同一个文件追加要处理交错、而且它会**留在用户的项目里**。
stderr 那条路这三样都不需要：CLI 本来就在写转录。

### 3.5 它能证明什么、不能证明什么

- **能**：平台为这一次事件调起了这道门禁（记录的 `command` 字段，CLI 写的）；进程进入了 `main()`；
  以 exit 0 结束。配合记录的 `toolUseID`，还能对上是哪一次工具调用。
- **不能**：**走的是哪一支**。「判定之后放行」「与本检查项无关、提前退出」（比如 H4 对 PM 的短路、
  H6 对非 `state.json` 的跳过）「输入读不出来、fail open 静默退出」三者在这一行上长得一样。
  §5 里「走的是判定那一支」是**从夹具状态推的**，预检（§5.2）把每一格的推断摆在明处。
- **不能**：**`PreToolUse` 的拒绝那一次**。拒绝是 stdout 上的 JSON、退出码 0，留痕那一行照样写了，
  但 CLI 只把那次拒绝记成一条 `is_error` 的工具结果，**不带 stderr、也没有 hook 附件**——那一次的证据
  是拒绝本身（§5.3 有实物）。
- **不能**：留痕关着的 run。**默认就是关着的**，所以 `docs/20` §7.3 那句「一趟正常的 run 证明不了
  那五道跑过」对**默认配置**仍然成立；变的是：**现在有一个开关能让它不成立。**

## 4. 怎么用它验证一趟 run 里每道门禁都跑过

**第一步：起会话时把开关打开。**

```sh
# 后台会话：只能走 --settings（在 shell 里 export 传不到 hook，§2.5）
claude --bg --plugin-dir /path/to/agent-team \
  --settings '{"env":{"AGENT_TEAM_GATE_TRACE":"1"}}' "<提示词>"
```

交互终端里同一个 `--settings` 参数照样适用（**没量，需要人来操作**，§7）。
⚠️ **不要把它写进项目的 `.claude/settings.local.json`**：那是持久配置，那个项目此后每一个会话都
开着——这个开关存在的前提就是「默认关」。

**第二步：找到这一趟的全部转录。** 主转录是 `~/.claude/projects/<cwd 编码>/<session-id>.jsonl`；
子代理的在 `~/.claude/projects/<cwd 编码>/<session-id>/subagents/agent-*.jsonl`。
**两处都要扫**：`SubagentStop`（H5b）的记录**只在**子代理那份里，子代理发起的 `Write` / `Agent`
（H3 / H4 / H6 / ledger / 下一层的 H1 / H2 / H5a）也在子代理那份里。上一轮就在这里栽过一次
（`docs/20` §7.1：二十六条门禁记录里有九条只在子代理转录里）。

**第三步：数。**

```sh
D=~/.claude/projects/<cwd 编码>; S=<session-id>
grep -rhoE 'agent-team gate-trace check=[a-z-]+ main=[a-z-]+' "$D/$S.jsonl" "$D/$S/" | sort | uniq -c
```

**第四步：判读。** 每道门禁对应一个 `check` 值、一句 statusMessage（记录里的 `command` 字段）：

| 门禁 | `check=` | 记录的 `command` | 挂在 | 每发生一次这个事件，应当有 |
|---|---|---|---|---|
| H1 派发白名单 | `delegation` | `校验派发白名单…` | `PreToolUse:Agent` | 一行（被拒的那次除外，见下） |
| H2 就绪门禁 | `readiness` | `校验前置产物…` | `PreToolUse:Agent` | 一行 |
| H3 写路径 | `writepath` | `校验写路径归属…` | `PreToolUse:Edit/Write/NotebookEdit` | 一行 |
| H4 契约保护 | `contract` | `校验契约保护…` | 同上 | 一行 |
| H6 返工预算 | `rework` | `校验返工预算…` | 同上 | 一行 |
| H5a 交付物记录 | `deliverable` | `记录交付物校验…` | `PostToolUse:Agent` | 一行 |
| H5b 交付物拦截 | `stop-gate` | `校验交付物…` | `SubagentStop`（**子代理那份转录**） | 放行时一行；拦截（exit 2）时没有这一行，有平台写的 `Stop hook feedback` |
| 账本回传 | `ledger` | `回传契约哈希与触达表…` | `PostToolUse:Edit/Write/NotebookEdit` | 一行 |

- **某个 `check` 一行都没有**：先看这一趟有没有发生过它挂的那个事件（没有 `Agent` 调用，H1/H2/H5a
  就该是零）。事件发生过而这一行没有——**那才是「没跑」**，而这件事**在打开开关之前根本分辨不出来**。
- **`main=not-entered`**：进程起来了、`main()` 没进去——入口坏了（M0 那个形状），不是一次放行。
- **`PreToolUse` 被拒的那一次没有这一行**：拒绝本身就是记录——那次工具结果 `is_error: true`，
  正文就是那道门禁的拒绝理由原文（§5.3 有实物）。那一次在转录里**没有** hook 附件记录。
  > ⚠️ **补一层（2026-09-24，控制方合入前复核）：没有这一行的是转录，不是门禁。**
  > 门禁这一侧，`PreToolUse` 的拒绝本来就是 `exit 0` + stdout 上的拒绝 JSON，所以留痕开着时
  > **门禁确实往 stderr 写了那一行**。控制方子进程级实测（执行角色写 `state.json`）：
  > 开着留痕，stdout 与 BASE **逐字相同**、仍是 `deny`；stderr 多出
  > `agent-team gate-trace check=writepath main=entered exit=0`。
  > **是平台在拒绝那一次把 hook 的输出记成了 `is_error` 的工具结果，没有记成 hook 附件**
  > —— 调试日志那一侧也只打 stdout（拒绝那一次 stdout 非空），所以那一行在任何一个通道里都看不见。
  > **失效条件**：哪天 CLI 开始在拒绝那一次也把 hook 的 stderr 记进转录，读的人会在一次拒绝上
  > 看到留痕行，而这张判读表说那不可能 —— 那时不是门禁变了，是平台变了，这一条要跟着改。
  > ⚠️ 顺带：留痕行上的 `exit=0` 在门禁层**分不出**「放行」与「`PreToolUse` 拒绝」，两者都是退出码 0；
  > 在转录层分得出来，只是因为平台替它丢掉了拒绝那一次。**别拿门禁的 stderr 直接当放行的证据。**
- **转录数出来的是下限，不是全数**：CLI 自己起的内部分叉代理（`agent_summary`、`prompt_suggestion`）
  停下时也会触发 `SubagentStop`，H5b 照样跑、照样留痕，**但那几次的记录不进任何一份转录**（§5.5）。
  要全数，起会话时再加一个 `--debug-file <路径>`：留痕开着时，调试日志里 stdout 为空的那几次会有
  `Hook <事件> (<事件>) success:` 后面跟着这一行（stdout 非空的那几次，调试日志只打 stdout）。
- 要对到具体哪一次工具调用：用记录的 `toolUseID` 去对 `tool_use` 块的 `id`。

## 6. 本轮顺带看见的两件

**一、第一道防线挡住了探针的措辞，第二道逼它把活干了。** `at-product` 收到「门禁探针：……写完立即结束」

`docs/11` §5.30）在这一趟又出现了一次，而这一次**两道都在做自己该做的事**：第一道拒了一句
不该照做的话，第二道没让它空手离开。

**二、`PreToolUse` 的拒绝在转录里没有 hook 附件。** 第 0 步 H3 拒了，转录里那次调用只有 H4、H6
两条 `hook_success`，H3 那一次**只**以工具结果（`is_error: true`）的形式存在——整份主转录里

各 **0 次**。
**这碰到了上一轮的一句话**：`docs/20` §7.2「真拒绝零条」的依据是「`permissionDecision`、`hook_error` /
`hook_blocked`、`Stop hook feedback` 各零次」——**而 `PreToolUse` 的拒绝本来就不会以那几种形状出现**，
那几个词扫到零，证明不了没有 `PreToolUse` 拒绝。
**本轮把缺的那一半补扫了**（同一个目录、九份转录、只读）：`is_error` 的工具结果**一共五条**——
三条 Bash 退出码（`Exit code 1` / `2` / `26`，业务测试脚本）、一条主线程 Bash `Exit code 2`、
一条 `File does not exist`——**没有一条是门禁的拒绝原文**。**结论不变，依据补齐**；补在 `docs/20` §7.2
原话的标题底下。

## 7. 没能验证的项 —— 逐条标明是哪一种

分四类：**环境不允许** / **需要人来操作** / **结构上不可能** / **我没做**。每一条「我没做」都附了归属，
**挂在那句会变假的话上**（`docs/16` §3.9 第 9 条的教训）。

1. **「交互终端里，shell 里 `export` 的开关传不传得到 hook」——需要人来操作。**
   全部实测都在 `--bg` 下；`--bg` 下传不到（§2.5），交互终端**大概率**传得到（那时 CLI 就是那个 shell 的
   子进程），**但没量**。§4 的操作步骤因此只写了 `--settings` 那条路——它在 `--bg` 下量过、不依赖这一格。
2. **「`--include-hook-events` 记不记静默 hook」——我没做。**
   它只在 `-p` + `--output-format stream-json` 下有效，而本轮的量法约束是只用 `--bg`。源码级的判断是
   「记，但只带事件名、不带命令」——**这一句是读源码推的，不是量的**。
   **归属**：下一个在 `-p` / SDK 的 stream-json 输出上量 hook 事件的人，把这一格改成量出来的。
3. **「一个刚被这条命令拉起来的后台服务，会不会继承发起命令那个 shell 的环境」——我没做。**
   P1 起的时候后台服务已经在跑。要量就得先停掉它，而它是这台机器上所有 `--bg` 会话共用的。
   **归属**：下一个在一台后台服务**没在跑**的机器上起 `--bg` 的人。
4. **「OTel 事件里的 `hook_definitions`」——我没做。** 源码级：只有 beta 的详细追踪打开时才附带
   hook 定义，而那一格的开关有一半是内部特性标志。**什么会让答案改变**：Claude Code 把这一格写进
   公开的监控文档——那时它可能就是「零改动」的那个答案，本文件 §3.1 要回来重判。
   **归属**：下一个读到那份文档变化的人。
5. **「分叉代理进来的 `agent_type` 是什么」——我没做**（§5.5）。hook 输入没落进任何日志。
   它**今天不承重**：五次都放行了；**会让它承重的是**哪天某个分叉代理带着一个执行角色的名字进来
   ——那时 H5b 会去拦一个替界面写摘要的分叉。**归属**：下一个给 `stop-gate` 的输入加日志、
   或者看见 H5b 在没有子代理的时刻出了一条 `Stop hook feedback` 的人。
6. **「走的是哪一支」——我没做，而且是裁定不做。** 要分支级证据，得在 `gate.mjs` 十几个出口前各标一个
   分支名，那是十几处与判定逻辑交织的改动，与「纯旁路、判定逻辑一个字不动」直接冲突。
   **什么会让答案改变**：哪天真的需要从一趟真实 run 里区分「判定放行」与「提前退出」——
   那时要付的代价写在这里。
7. **「POSIX（macOS / Linux）上 `exit` 监听里写 stderr 会不会丢」——我没做。** 本机是 Windows，
   `spawnSync` 与 CLI 都走管道，量下来一个字节没丢；**既有的 fail open 留痕（写完立刻 `process.exit`）
   也从没在 POSIX 上量过，与这一条同一个风险**。**归属**：下一个在 macOS / Linux 上跑本仓库测试的人
   ——`tests/gate-trace.test.mjs` 的矩阵就是那个判据，它在那里红就是答案。
8. **「一整趟 S1–S8 开着留痕会写多少行」——我没做。** 按事件估：每次 `Edit`/`Write` 四行、每次 `Agent`
   三行、每次子代理停下一行、外加分叉代理的那几次。**没有真的跑一整趟。**
   **归属**：下一个开着留痕跑整链的人——那一趟的转录本身就是答案。

## 8. 变异红清单

做法：`cp` 备份 → 变异（替换前断言 `find` 在文件里**恰好命中一次**，并打印命中的那一整行，**确认命中的
是要的那一处**——「命中了一次」防的是没命中，防不了命中错的那一个）→ 裸 `node --test` → `cp` 还原 →
`diff` 零差异。基线 `885 / 0`。位置按 Ruling 11 写符号名，不写行号。

| # | 命中的那一处（文件 + 符号） | 变异 | 结果 |
|---|---|---|---|
| M1 | `trace.mjs` 的 `traceEnabled` 里 `return env?.[TRACE_ENV] === '1'` | 改成 `return true`（默认开） | **红 45**：新用例 36 条（纯函数三条、测试帮手一条、矩阵里夹具自检十五格与「stderr 只多一行」十七格），**外加九条既有用例**（逐字断言 stderr 为空的那些，例如 `stop-gate：产物已经写到磁盘时放行，不拦截、不留任何告警`） |
| M2 | 同一句 | 改成 `Boolean(env?.[TRACE_ENV])`（真值判断） | **红 5**：纯函数两条、「默认关」`'0'` / `'true'` / `'yes'` 三条 |
| M3 | `installTrace` 的退出监听里 `if (code !== 0) return` | 删掉（退出码守卫） | **红 2**：纯函数「exit 2 与 exit 1 一个字不写」、矩阵「H5b 产物缺失，exit 2」那一格 |
| M4 | 同一个监听里 `proc.stderr.write(traceLine(` | 改成写 stdout | **红 36**：矩阵里 exit 0 的十七格各两条（「stdout 逐字节相同」「stderr 只多一行」）、纯函数两条 |

| M11 | `gate.mjs` 的 `main()` 第一行 `TRACE_STATE.entered = true` | 改成 `void 0` | **红 17**：同上（每一行都成了 `main=not-entered`） |
| M12 | `tests/helpers/gate-runner.mjs` 的 `envWithoutTrace` 里 `delete env[TRACE_ENV]` | 改成 `void 0` | **红 1**：「跑测试的进程自己开着留痕，`run()` 缺省仍然按关跑」 |

**十三刀，刀刀见红，每一刀还原后 `diff` 零差异。** M5 / M6 / M7 三刀的 `find` 都以 `try {` 起头，
**这正是「命中数对、命中的那一处错」最容易发生的地方**——三刀的 `find` 各带了足以区分的上下文
（监听体、注册体、`traceEnabled` 的函数体），打印出来的命中行各不相同、各在各自的函数里。

纯 LF；十份都无 lone-CR、无 BOM、无其它控制字节，**没有一份行尾混用**。
（仓库 `core.autocrlf=true`，索引里一律 LF。）
**变异全表在定稿之后又整张重跑了一遍**（注释改动挪了行号），十三刀的红数逐刀相同。

两条值得单记：

- **M1 的四十五条里有九条是既有用例**：「开关默认开」这件事，**旧套件本来就会拦**——那些逐字断言

  新用例红）、「exit 2 一个字不加」（M3）、「不写 stdout」（M4 里旧用例一条没红——旧用例全在「关」下跑）。

  都是「stderr 没多出**那**一行」——前者是一行都没多，后者多的是 `main=not-entered`。
  **断言比的是整行，所以两者都红**；只比「有没有 `gate-trace`」的话，M11 会全绿。
