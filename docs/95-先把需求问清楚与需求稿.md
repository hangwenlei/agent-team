# 先把需求问清楚与需求稿

> 2026-10-14，分支 `r52-brief-in-at`。用户想先用 superpowers 的头脑风暴把需求想清楚、再交给项目经理，问能不能加一条命令、问完顺手进入
> `/agent-team:at`，又问两条命令能不能合并。本轮把「先把需求问清楚」并进 `/agent-team:at`，门禁在用户批准需求稿的那一刻把它记成这一趟的原话。

## 0. 一句话结论

- **合并成一条命令**：`/agent-team:at` 第 1 节在建 run 之前多一步「先把需求问清楚」——命令没带参数、话里说了要先想清楚、或者话里有几处怎么猜都可能白做
  （这一种先问用户要不要）时，项目经理一次问一件事，问清之后整理成一份纯文本的需求稿，单独用一道 `AskUserQuestion` 单选题问「照这份需求开始」还是「再改改」。
  话已经说清楚的照旧直接开始。
- **需求稿由门禁记**：用户选了「照这份需求开始」，批准记录器（`approval-ask`）把那道题的题面原样记进项目一级的 `user-words.json`（`source: "ask"`），整份换掉命令
  那一次记下的；之后建 run 那一次绑进 run 目录、推进出第一段时第 1 节对着它核，与命令带参数时同一条路。对不上的说法按来源说（「对不上用户批准的需求稿」）。
- **命令没带参数的那一趟也核了**：原来不带参数的不记、不核（`docs/50` §5 第一条），现在问清需求、批准过需求稿的照样核。

## 1. 起因与比较过的做法

用户的原意是在别处跑 superpowers 的头脑风暴，再把结果交给项目经理。上一轮的分析（本会话里）指出三件事：装了 agent-team 的项目里主会话一律是 `at-pm`，
它的工具面没有 `Skill`，superpowers 的技能在那里调不起来；头脑风暴的设计文档整份贴进 `/agent-team:at` 会让「怎么做」与模型自己拍板的小决定都成了用户原话，
验收逐条判、架构师偏一句都要问用户；只贴一个文件路径，文件里的话不受契约基线保护，「不要测试」这类只认契约里用户那一句的话写在文件里不算数。

比较过三种接法：

| 做法 | 问题 |
|---|---|
| 另起一条 `/agent-team:at-brief`，问完再提示用户发 `/agent-team:at` | 多一条命令；问完之后要用户再发一次，或者由项目经理照 `at.md` 接着做（`$ARGUMENTS` 是空的，原话记录器在那一刻没有东西可记，第 1 节不核） |
| 项目经理问完之后自己把需求稿写进第 1 节 | 第 1 节的保证是「门禁记下的是用户的话，不是项目经理转写的」；项目经理自己写进去的，门禁拿不到对照 |
| **问完用 `AskUserQuestion` 让用户批准，题面就是需求稿，门禁记题面** | 用户点的那张卡片上的字就是记下的字，之后整条原话核对的路不用改 |

取第三种，并进 `/agent-team:at`：一条命令，话说清楚的照旧直接开始，没说清的先问——用户只记一条命令。

## 2. 裁定

- **入口合并（裁定：并进 `/agent-team:at` 第 1 节，不另加命令）**：问清需求要发生在建 run 之前（原话记录只在这个会话建出新 run 的 `state.json` 那一次绑，
  `docs/50`、`docs/58`），而 `/agent-team:at` 第 1 节本来就在建 run 之前先处理上一趟。放在「上一趟那一问」之后、「run id」之前：用户选了续跑上一趟的，不问。
  若错：想单独做需求澄清、不打算马上开工的用户没有入口——他们可以选「再改改」一直改，或者不批准就停下，项目里不留任何东西。
- **什么时候问（裁定：三种情形，项目经理判第三种）**：命令没带参数；话里说了要先想清楚；有几处怎么猜都可能白做——第三种先单选问一次「先把需求问清楚」还是
  「照原话直接开始」，用户可以不问。复核之后收窄：第一版还算上「写不出能逐条核对的做完的样子」，那样大多数一句话的需求都会多问一次（§8 设计层面）。
  收口之后照第 6 节自己另起的一趟，「话」是用户提出改动的那几条消息。若错：判断只靠正文，判宽了多问一次，判窄了照旧走第 4 节的 `contract-hole`。
- **不主动问测试（裁定：要不要自动化测试、项目里本来就没过的测试算不算，不列进要问的事，用户自己提了才写）**：这两句一旦进了需求稿就是用户原话，验收与 `at-qa`
  照它豁免；项目经理主动拿单选题去问，等于在建 run 之前把豁免招出来，而「挂着的用例」本来要在测试报告写成之后逐份经「照现状交付」批（复核中 1，§8）。
- **题面就是需求稿（裁定：门禁记 `tool_response` 里那道题的 `question` 原样）**：不记项目经理在消息里另贴的那一份——用户点的是题目卡片。题面逐字、不夹别的话，
  开头不加说明、末尾不加问句（第 1 节要逐字照抄题面，多一句就多抄一句）。SDK 宿主上量过往返：多行、空行、带变体选择符的表情、反引号，`tool_input`、
  `tool_response.questions` 与 `answers` 的键逐字相同（§5）。若错：界面把长题面截断显示时，用户批准的是自己没看全的东西（§5）。
- **回答要对得上一道显示过的题（裁定：门禁核）**：门禁记的是 `answers` 的键，它要与 `tool_response.questions` 里某一道的题面逐字相同（`unmatched`）——对不上的，
  记下的就不是用户看到的那张卡片，多选与备注也核不了（第二条后台安全复核，§8）。
- **单独问（裁定：门禁核）**：这一次问里还有别的题的不记（`not-alone`）——别的题的答案进不了第 1 节。第一版只靠正文、还放行同一次里的别的题（复核，§8）。
- **题面里不许有界面上可能看不见的内容（裁定：门禁核，`hiddenIn`）**：信任锚是「用户点的那张卡片上的字就是记下的字」；控制字符、零宽与双向控制这类不可见的字
  （表情用的零宽连接符与 U+FE0E、U+FE0F 除外）、行分隔符与段分隔符、私用区的字、HTML 注释、声明、处理指令或标签、Markdown 的链接定义与行内链接、图片会让两者不一样，夹进去的话就成了用户原话。这一条来自推上分支之后
  的后台安全复核（§8）。正文要求需求稿写纯文本。
- **认「像批准」只认以标签开头的答案**：只是在话里提到这几个字的（「要，照这份需求开始做就行」）多半是别的题的回答，不出声；以标签开头、后面夹了别的话的
  不记、说原因。第一版答案里含这几个字就算，进行中的 run 里会误报（复核低 7）。
- **只认问答（裁定：用户在对话里单独发「照这份需求开始」不算）**：门禁在 `UserPromptSubmit` 上看不到批的是哪一份。返工与照现状交付的批准认这一路，是因为它们批的
  对象（段、那一刻的结论）门禁自己知道。问不了用户（`-p`、`--bg`）时不做这一步。
- **不记的形状与别的批准同一套**：离开键盘自动提交、要追问、另写了话、带备注、多选、数组、标签夹了别的话——模型收到的不是一句干净的批准，门禁不能比模型看到的更宽
  （`docs/34` 的 P6、platform-7）。再加两种：题面空、不止一道题选了它。回传说原因、叫项目经理改好再问，不要建 run。
- **门禁这一侧记不下的出路（裁定：请用户把需求稿贴在 `/agent-team:at` 后面重发）**：写不进、读不到会话 id。照现在这样往下建，命令那一次记下的旧原话会被
  绑上、第 1 节对不上；重发一次命令，展开那一刻的记录器记下它，路是通的。项目里没有 `.agent-team` 的，命令展开时同样不记，出路是先跑 `/agent-team:at-init`
  再重发（复核低 5）。回传按三组给出路：用户这一侧（照用户的话改、再问）、这一问不合要求（照要求重问）、门禁这一侧（请用户重发）。
- **批准之前就建好的 run 不认需求稿（有意）**：批准那一刻的 `runs_before` 里有它，项目经理再写它的 `state.json` 时这份记录作废（`bindDecision` 的既有规则）。
  正文要求先问后建。`current-run` 正指着这样一趟、它还没收口时，【需求稿】点明这份需求稿不会绑给它、照需求稿走就换一个新的 run id 另建（复核低 6）；回传不引
  磁盘上的 run id。
- **第 1 节的名字不改**：还叫「用户原话」——用户批准过的需求稿就是这一趟的原话。各角色正文里「第 1 节用户原话」的规矩（验收逐条对它、不要测试与挂着的用例只认
  用户的话）照旧适用于它。代价写在 §4 第一条。
- **需求稿的样子**：纯文本，每行顶格，几行固定的开头（要做什么、为什么；给谁用；做完的样子；不做；约束），不用 `##` 标题——契约按编号节标题认自己的节（`docs/90`）。
  第一版把样子放在一个缩进两格的代码块里，模型照抄会把缩进带进题面、第 1 节对不上（复核低 8），改成一句话说清。只写用户说过或认可过的；只问会改变做出来什么、
  怎么算做完的事，架构与技术选型用户没要求的不问——那是后面各段的事。正文不写「挂着」二字：`commands/at.md` 里提挂着的用例只许在两处，`tests/gate-test-verdict.test.mjs`
  钉着（第一版写了「已经挂着的用例算不算」被它挡下，改成「项目里本来就没过的测试算不算」，复核之后整句挪出了要问的事）。
- **批准记录器不另起一个检查项**：并在 `approval-ask` 里（同一个 `PostToolUse:AskUserQuestion` 事件，它本来就记返工与照现状交付两种批准）。状态文案从「记录返工批准…」
  改成「记录批准…」，`docs/00-现行参考.md` 的判读表跟着改。同一次问里既有像批准需求稿的、又有返工或照现状交付的回答时，两段都回给项目经理，给用户那一行
  两句并成一行。

## 4. 仍然开着的边界

- **需求稿是项目经理写的、经用户批准才成了原话**：门禁只核「第 1 节是不是用户点过的那份」「那份里有没有看不见的内容」，不核每一句是不是用户说过——用户没细看就点，
  项目经理的推断就有了用户原话的分量。测试豁免不主动问（§2），别的只靠正文那一句与用户自己看。
- **看不见的内容只认列着的几种**：Markdown 的别的写法（强调、标题、引用块）照常显示，不算；界面怎么渲染题面门禁不知道，列举之外还有渲染时被吞掉的写法，照样记。
- **「话够不够清楚」由项目经理判**：判宽了多问一次，判窄了照旧在 S1 之后走 `contract-hole`；门禁不核。
- **用户在对话里打字批准不认**（有意，§2）。
- **批准之前就建好的 run 不认需求稿**（有意，§2）：项目经理先建了 run 再问，那一趟照命令带的原话核，回传点明换一个 run id 另建。
- **命令在 at-init 之前、别的会话建的、不经门禁建的**：与命令带参数时同一组（`docs/50` §5），需求稿不改变它们。

## 5. 没量到的

- 真实会话里整条走一遍：不带参数或话没说清、问清、批准、建 run、第 1 节照抄需求稿、推进出 S1。本轮有子进程判据与一次 SDK 宿主上的问答往返（§3），没有整条链。
- 交互终端与桌面端显示长题面会不会截断或折叠（SDK 宿主没有界面）。
- 项目经理在真实会话里照不照「一次问一件事」「架构不问」「需求稿只写用户说过的」「题面不加问句」。

## 8. 复核与修订

第一版（b7f42e5）推上分支之后，CI 三个系统与最低版本全绿；起了一个对抗复核的子代理，另有一条后台安全复核的提示。复核者核过没问题的：答案形状的认法与
`approvals.mjs`、平台事实同口径；各种先后组合（命令记下再批准、不带参数清掉再批准、批准之后又发命令、续跑上一趟、别的会话、建 run 那一次被拒、S1 里重新批准）
都绑对、不卡死；`source` 的升级兼容；几条硬规矩；它另砍的八刀都红。没有高，两个中、九个低，加上安全复核那一条：

- **安全复核：题面里藏看不见的内容**（只给了标题：解析差异 / 信任锚）。→ 门禁不记带控制字符、不可见的字、HTML 注释或标签、Markdown 链接定义的题面（`hiddenIn`），
  正文要求纯文本（§2）。
- **中 1：主动问「要不要自动化测试」「本来就没过的测试算不算」等于在建 run 之前把豁免招出来**，措辞还绕开了「挂着」那条反向判据。→ 两项挪出要问的事，改成不主动问、
  用户自己提了才写；判据核要问的那一串里没有「测试」。
