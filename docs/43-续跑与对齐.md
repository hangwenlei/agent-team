## 0. 一句话结论

- **续跑先读规矩**：`/agent-team:at-resume` 第 2 节最前面一条——动手之前先读 `/agent-team:at` 第 3–6 节，不凭记忆。
- **`03-alignment.md` 有了定义**：架构师正文写它装什么（各端对齐的结论、依赖与先后、未决问题；只有一端也要写）；`/agent-team:at` 的 S3 完成定义
  列上它；派发裁决模板不再说「拉通」，改指它。
- **整段裁掉之后的前置**：缺的前置是整段裁掉的那一段的产物时，H2 的拒绝理由说清是整段裁掉、给两条路（补回来，或者把要它当前置的段一起裁掉）；
  派发者改不了 `state.json` 的冒泡。「整段裁掉」与推进、收口同一份判定（`wholeStageTrimmed`，「叫过」并上门禁的派发记录）。
- **切走 `current-run`**：`/agent-team:at` 第 1 节「放弃」那一支先确认那一趟没有还在跑的派发；PM 写 `current-run` 时，门禁列出别的、没收口的 run 里
  「派出去了、门禁还没见它停下」的派发（【派发】）。
- **S2 的协调者进度**：`at-product` 返回时自己那份交了、S2 却没齐（它派的 `at-ui` 还在跑），照样报 `at-ui` 的现状。
- **进程红线**：红线与 `sensitive` 加一项「结束不是自己起的进程」；每个持 Bash 的角色（连同项目经理）有同一句停服务的做法——按自己起的
  PID 停，Windows 的 Git Bash 里按进程树停（`kill` 只停掉 `npm`、`npx` 外面那一层）；停不掉的照实报，不按名字或端口一把杀。

## 1. 修法

### 1.1 第 40 条：续跑先读规矩

- `/agent-team:at-resume` 第 2 节最前面加一条「先读规矩」：上下文可能已经压缩掉了 `/agent-team:at` 的正文，动手之前先 `Read` 它的第 3–6 节（逐段推进、
  回退、问用户、收尾），下面说「照 /agent-team:at 第几节」的地方照它办，不凭记忆。原来只有「产物齐了」那一条叫它读第 3 节的几条，回退、问用户、
  收口那几支都指过去却没叫它先读。

### 1.2 第 38 条：`03-alignment.md`、整段裁掉之后的前置

- `agents/at-architect.md`：`03-alignment.md` 是 S3 的第二份产物——各端对齐的结论（接口契约在各端怎么落：谁调谁、字段与错误码、鉴权）、几端之间的
  依赖与先后、未决问题（要 PM 定或要问用户的，逐条列；没有就写「无」）；只有一端的项目也要写，一两行就够。M4d 起它是推进出 S3 的硬条件（H6 核它
  在不在、空不空），可它在任何正文里都没有定义（`docs/11` §5.18 C1 当时记着它零出现）。
- `/agent-team:at` 的 S3 那一条：完成定义里写上 `03-alignment.md`（两份的写法都见架构师正文）。
- `templates/04-dispatch.md`：标题与第 3 节不再说「S3 拉通」——门禁下没有并行拉通这一步（S3 只派架构师，H2 按前置拦），改指 `03-alignment.md` 与它的
  未决问题。
- `hooks/lib/readiness.mjs` 的 `decideReadiness` 多收一个 `trimmedAway(sid)`：缺的前置是整段裁掉的那一段的产物（例：S2 整段裁掉之后在 S3 派架构师，
  缺 `01-prd.md`）——原来说「先把产出这些产物的阶段跑完再回来」，那一段是 PM 自己裁掉的，跑不完。现在说清是整段裁掉，给两条路：把那一段补回来
  （产者从 `trimmed` 里拿掉、派它补交，叫到的人补记进 `stage_roles`），或者把要它当前置的段也整段裁掉、交付文档里写明少了哪几段；派发者改不了
  `state.json` 的冒泡。缺的里面还有别的段的，照旧那一句也说。`hooks/gate.mjs` 用 `hooks/lib/advance.mjs` 的 `wholeStageTrimmed` 判——与推进、收口同一份，
  「叫过」并上门禁的派发记录：派发记录里有人在那一段被派过的，不算整段裁掉。

### 1.3 第 24-1 条：切走 `current-run`

- `/agent-team:at` 第 1 节「放弃」那一支：改 `current-run` 之前先确认那一趟没有还在跑的派发（它派出去的人的完成通知都到了）——还在跑的，它们停下时
  门禁按新的这一趟判、那一趟的产物没人核；写 `current-run` 那一次的回传里有【派发】一段的，照它办。
- `hooks/gate.mjs`：PM 写 `current-run` 时，列出别的、没收口的 run 里「派出去了、门禁还没见它停下」的派发（`inflightElsewhere`）。最后一回停下是「拦」的
  也算没停（拦了它会接着跑）；这一趟自己的派发不列；角色与段只在花名册、阶段链认得它们时说出来（派发记录 `Bash` 写得进），run 目录名加引号
  （`docs/27` §2.1）。不按时间猜还在不在跑：门禁没见它停下的，可能还在跑，也可能早就中断了、平台没报——【派发】两种都照实说。

### 1.4 第 14 条的 S2 进度

- M4d 的协调者进度只认「这一段没有它自己的产物」的协调者（返回的角色不在这一段的产者里，交付物核验跳过它）——S2 的 `at-product` 既是协调者又是
  产者，那一支走不进去：它返回时自己那份交了、`at-ui` 还在后台跑，PM 收不到 `at-ui` 的现状。现在 H5a 与完成核验两处都认「自己也是这一段产者、
  能派到这一段别的产者」的协调者（`hooks/gate.mjs` 的 `dispatchesOtherProducers`；`isCoordinatorFor` 认的是「能派到这一段的 role」，`at-product` 本身就是
  S2 的 role，那一条认不出它，它的口径不改），它自己那几份交了、这一段没齐时照样报进度。`hooks/lib/completion.mjs` 的 `coordinatorProgress` 头一句按它
  自己交没交说（「它自己的那几份交了」），不是执行段的不提实现记录、不说「执行角色」。

### 1.5 实测里冒出来的：进程红线

- M9 续跑那一段（§3），项目经理在 S7 自己冒烟：`npm start` 放到后台、`curl` 几下，收尾用 `taskkill //F //IM node.exe` 停服务——这台机器上所有
  node 进程都被杀了，驱动连同别的跑在 node 上的工具一起没了，会话断在 S7。六个持 Bash 的执行角色的红线、`/agent-team:at` 第 4 节 `sensitive`
  那一行都没有这一项，项目经理自己的红线也只管 git 命令。
- 起因之一在本机核过：Windows 的 Git Bash 里 `npm start &` 之后 `kill $!` 只停掉 `npm` 那一层，服务照样在跑；`taskkill //PID "$(cat /proc/$!/winpid)" //T //F`
  按进程树停得掉；直接 `node server.js &` 的，`kill $!` 停得掉。停不掉自己起的那个，角色就去按名字杀。
- 红线与 `sensitive` 加一项：结束不是自己起的进程（按名字或端口一把杀——`taskkill /IM`、`killall`、`pkill` 这类——会把这台机器上同名的进程
  全杀掉，连带用户别的程序，还可能有 Claude Code 自己与它的工具）。执行角色碰到就冒泡，项目经理照 `sensitive` 问用户；README 两半「什么时候
  会问你」那一行跟上。
- 每个持 Bash 的角色（六个执行角色与项目经理）加同一句停服务的做法：起的时候记下 PID、按它停；Windows 的 Git Bash 里 `npm`、`npx` 拉起来的
  服务按进程树停；停不掉的照实报出端口与 PID。执行角色的放在「`Bash` 只用来……起停……服务」那一句后面，项目经理的放在它红线新加的那一条
  （「不是你自己起的进程你也不结束」）里。
- 不选：门禁加 Bash 的 matcher（`docs/40` §1.1 不选的理由照旧）；叫角色别起服务（S5 的执行角色要起停验证用的服务，红线的例外里写着）。

## 4. 仍然开着的边界

- **按 `agent_id` 认 run（M，照 `docs/39` 往后放）**：切走指针之后，旧 run 上的人停下时门禁仍按新的这一趟判——停下行记进新 run 的派发记录、交付物核验按
  新 run 的段判，那一趟的产物没人核。这一轮只在写指针那一刻把它们报出来，让 PM 先等。
- **【派发】只在写 `current-run` 的那一刻报**：之后旧 run 的派发停下了，门禁不再提；报的时候分不出「还在跑」与「早已中断、平台没报」，照实说两种。
- **「整段裁掉」只在 H2 的拒绝理由里说**：PM 往 `trimmed` 里写下整段裁掉的那一刻，门禁不提醒后面哪几段要它当前置。审查第 38 条给的另两条修法
  （状态校验禁止裁掉 `at-product`、`requires` 按 `trimmed` 动态剔除）不选：前者把「这一趟确实不要产品设计」这条合法的路堵死，后者让 H2 放过一份
  后面真要读的前置。
- **`03-alignment.md` 的内容门禁不读**：只核在不在、空不空；写得敷衍（一行「已对齐」）照样算交了。
- **规格原话不改**：设计文档（`docs/superpowers/specs/2026-09-15-agent-team-plugin-design.md`）阶段表里 S3 那一行的「at-architect + 并行拉通」是带日期的设计，
  照「原话不改」留着；门禁下没有并行拉通这一步（H2 按前置拦）。
- **S2 的进度只在 `at-product` 自己那份交了、S2 没齐时报**：它自己那份没交的走原来的交付物核验，不报 `at-ui`。
- **进程红线只在正文里**：门禁不看 Bash（`docs/40` §1.1）；按名字一把杀的命令，外层只有平台的权限模式。实测驱动里拒掉这类命令的那一道
  是实测用的，不是插件的一部分。
- **停服务的做法只在这台 Windows 上核过**：macOS、Linux 上 `kill` 停 `npm` 拉起来的服务停不停得掉没量（§5）；判据只核每个角色都有同一句。

## 5. 没量到的

- S2 的协调者进度：`at-product` 的正文要它前台派 `at-ui`，SDK 宿主里它等 `at-ui` 返回再返回，那时 S2 已经齐了；交互模式下 `at-ui` 的完成
  通知回到停车的 `at-product`，同样多半齐了才返回。这一支只有子进程判据量过。
- 写 `current-run` 时的【派发】：真实会话里没有切走指针。
- 整段裁掉之后 H2 的拒绝理由：真实会话里没有整段裁掉 S2。
- macOS、Linux 上 `npm start &` 之后 `kill $!` 停不停得掉服务。
- 新红线拦不拦得住按名字杀：M9c 里项目经理没再冒烟，执行角色也没碰到要停的服务，没有样本。
