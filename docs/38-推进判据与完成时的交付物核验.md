# 推进判据与完成时的交付物核验

> 2026-10-05，M4d，分支 `m4d-advance-and-completion`，v2.2.0。全量审查第 17 条（阶段推进没有判据）、第 19 条（异步派发下 H5a 只在启动
> 那一刻跑，完成时没人核产物）。

## 0. 一句话结论

- **推进有了判据**：H6 在推进那一次写入里核两件事——一次只推进一段；离开的那一段交齐了（这一段叫到的产者各自那几份、这一段固定的
  产物都在、不是空文件，裁掉的不算，标了 `"accepted"` 的算交了）。「叫到」并上门禁自己的派发记录。冒泡之后不补齐、也没照出路裁掉，
  就推不过去。
- **交付物核验挪到了子代理真正完成的那一刻**：后台派发启动那一刻 H5a 不再判产物；子代理完成、主会话收到完成通知时，新检查项
  `completion`（UserPromptSubmit）按门禁自己记的派发记录对回角色与段，核它的产物，没交齐的说清成因——按它最后一回停下的结果判
  （冒泡了、门禁最后一回拦了它而它却结束了、门禁放它停下时它不在那一段的名单上、没正常结束、门禁没见它停下）。前台派发跑完时 H5a
  同样按成因说。协调者返回时报它派出去的人各自的进度，不报缺，也不许诺之后的通知会到 PM。

## 1. 问题

### 1.1 第 17 条：推进没有判据

H6 推进那一次只核「还是上一轮的」（`rework_base`），不核「缺」；收口那一次核最后一段（M4a）；H2 只在派发时核 `requires`，PM 自己的段
（S1、S4、S8）没人派它。于是在原代码上（调研复现，门禁子进程实跑）：

- `S2` 一次写到 `S8`，H6 放行；ledger 照收口的口径回传「S8 的产物已经写了……还收不了口」，叫 PM 去补 06、07——等于替跳段背书；
- `S3`→`S4` 时 `03-alignment.md` 不在，放行；
- `S5`→`S6` 时某个参与者的实现记录不在、或者是 0 字节、只有空白，放行；
- `S2` 里叫到的 `at-ui` 一份 `02-*` 都没交，`S2`→`S3` 放行。

不在任何前置里的产物（`02-*`、`03-alignment.md`、`05-impl/*`）离开那一段之后就再没有门禁查它。上一轮（`docs/37` §5）登记过：冒泡之后它们
照样能被推进过去。

### 1.2 第 19 条：后台派发下，交付物核验的时机全错

H5a 挂在 `PostToolUse:Agent` 上，从不读 `tool_response`。后台派发（默认）时这个事件在子代理刚启动那一刻就跑完了：H5a 对每一次首次派发
都报一条「产物还没有」（M4c 的四场真实会话里每一次后台派生产角色都有这一条，PM 没被它带偏，但要靠「看工具结果第一句是不是 Async agent
launched successfully.」自己分辨）；子代理真正完成时，没有任何门禁再核产物。H5b 顶到平台上限静默放行、子代理冒泡停下，父级那一侧都只剩
子代理自己的回复。`S5` 里 PM 派的协调者（`at-architect`）返回、这一段还没齐时，H5a 整段静默。

### 1.3 平台事实（CLI 2.1.286，探针与源码）

调研起了一个最小探针插件（每一回 hook 的输入原样落日志、SubagentStop 按角色决定拦不拦；十来个 `-p` 会话、几个 `--bg` 会话，haiku，
合计约 0.75 美元，收尾核过 `~/.claude.json`、`~/.claude/jobs` 与残留进程），又读了 `claude.exe` 里的源码。要点：

- **交互模式（终端、`--bg`）没有前台派发**：Agent 工具的输入 schema 里没有 `run_in_background`，`PostToolUse:Agent` 一律是 `async_launched`。
  只有非交互会话（`-p`、SDK 宿主；桌面端按推断属于这一类）能前台派发。
- **后台派发**：`tool_response` 是 `{ isAsync, status: "async_launched", agentId, description, … }`，`agentId` 等于 SubagentStop 的 `agent_id`、
  等于完成通知的 `<task-id>`；`PostToolUse` 的 `tool_use_id` 等于第一条通知的 `<tool-use-id>`（之后同一个 task-id 的通知里会换掉或没有）。
- **前台派发**：`PostToolUse:Agent` 在子代理跑完之后才到，`status` 是 `completed`，`content` 是最终文本；冒泡、被续跑上限覆盖，在
  `tool_response` 上都和正常完成长得一样。API 失败、轮数上限、被停下都不触发 SubagentStop。
- **完成通知**：每一条在主会话触发一次 UserPromptSubmit（两条几乎同时到也是两次），`prompt` 就是那段 `<task-notification>` XML，输入里没有
  任何字段标明「这是通知」；UserPromptSubmit 从不在子代理上下文里触发。`additionalContext` 与纯文本 stdout 都进得了主会话的上下文。
  `<status>` 只有 `completed`、`failed`、`killed`，后两种没有 `<result>`；`<result>` 只转义 `&`、`<`、`>`。同一个 task-id 会通知不止一次
  （续跑、交互模式下带着后台 shell 停下）。
- **CLI 的注记**：子代理回报里出现指令形状的字样、或者撞了轮数上限时，`content` 与 `<result>` 最前面会插一段 `[harness: …]`——冒泡标记就不在
  第一行了。
- **嵌套派发的通知路由按模式分**：`-p` 下协调者还在跑，孙代理的通知送给协调者、不触发任何 hook，主会话看不到；协调者结束了才送主会话。
  交互模式下协调者停下时先「停车」，孙代理的通知回到它那里、把它唤醒，主会话最后只收到协调者的一条。
- **`background_tasks`** 只在 Stop、SubagentStop 的输入里有，是整个会话的快照、没有 owner；PreToolUse、PostToolUse、UserPromptSubmit 都没有
  类似字段——门禁在别的事件上看不出「还有后台任务没完成」。

## 2. 修法

### 2.1 推进判据（H6）

`hooks/lib/advance.mjs`，接线在 `hooks/lib/rework-guard.mjs` 的 `decideReworkBase`（`decideCarry` → `decideSingleStep` → `decideAdvance`）。
跳过条件与 `rework_base` 那几条相同：写入前读不出来（首写或修复路）、阶段链读不出来，就不核。

- **一次只推进一段**：不是回退的写入里，写入后的 `stage` 在链上必须恰好是写入前的下一段。回退、原地重来、写入前后有一边不在链上的不管；
  补记（回退那一条之后同一次写入又往前记了几段）走回退那一路，离开的各段逐段核。回退（或原地重来）那一条**之前**同一次写入先往前记了几段的，
  往前那一截照推进核（复核补的，§3）。
- **离开的那一段要交齐**：
  - 参与者 = 写入后与写入前两份 `participantsOf` 的并集，再并上门禁派发记录里在这一段派出去过的角色（§2.3；读不出来就当没有），与这一段的
    产者求交——同一次写入从 `stage_roles` 删名字、PM 少记一个人，都翻不成「没叫过」。收口与 ledger 的收口阻碍用同一份（`calledIn`、
    `wholeStageTrimmed`）。
  - 产物固定的段（S1、S3、S4、S6、S7）：不论叫没叫谁都要；整段裁掉的不要求（这一段的产者都在 `trimmed`、值是这一段、一个都没叫过（含派发
    记录），而且不是 PM 自己的段）。
  - 产物随参与者展开的段（S2、S5）：叫到的产者各自那几份；`stage_roles` 是对象而没有这一段的键、或者它的值不是数组时拒（这一段还没记账，
    核不了）。叫到之后又不要了的，只有不在任何前置里、不是验证段的那几份（`02-ui-spec.md`、`02-wireframe.html`、`05-impl/<角色>.md`）能靠
    `trimmed`（值写这一段）免掉——`01-prd.md` 是 S3 的前置，裁了推进放行、到 S3 被 H2 拒，所以不给这条路。
  - 每份产物：不在算缺；统一行尾之后只剩空白算空文件；在、但读不出来的不拦、往 stderr 留痕；标了 `"accepted"` 的只要在、不是空的就算交了。
    还是上一轮的照原来那条判据，已经因为缺、空被点名的不重复列。
- **最后一段没有「离开」**：照旧由收口核。
- **拒绝理由**：头一句说从哪段推进到哪段、离开的那一段没交齐（括号里说清口径）；逐个（段、角色）一行，按参与者从哪来分开说（`stage_roles`
  记着的、旧 run 按整趟 `roster` 算的、只在派发记录里有的）；出路——还在跑的等它返回、去磁盘核过再推进；返回了的读它的回复，冒泡的照
  `/agent-team:at` 第 3 节「核实」定，没冒泡就是漏了，同一段里重派（PM 派不到的经这一段的协调者去派）；能免的给出 `trimmed` 的写法（理由记进
  `04-dispatch.md`，S4 之前的段等 S4 写它时补上）；不能免的明说「叫过却没交，`trimmed` 不是出路」并说原因；没叫过的产者派它或整段裁掉，后面要
  它当前置的段跟着派不出人、只能一起整段裁掉。只有还旧时文案与原来逐字相同。跳段：「一次只推进一段……先只推进到下一段，之后每一段推进各一次
  Write」。回显的只有写入前后的 `stage`（过 `quote`；走到这两条判据时它们必然是链上的段）。

不选的做法：只在 ledger 写完 `state.json` 后回传告警、不拦（告警到时已经推进了，PM 可能已经派出下一段；这个仓库里提示被忽略过不止一次，
`docs/33` §2.1 就因此把推进核查挪进了 H6；也拦不住跳段）；拦和告警都做（ledger 那一半只补得上 H6 跳过的几种少见情形，同一件事说两遍）；
只用写入后的参与者（同一次写入删名字就能逃过）；只用写入前的（首轮离开时这一段还没记 `stage_roles`）；旧 run 的随参与者展开的产物一律不核
（洞留着）；叫到之后又裁掉一律免或一律不免；跨段写入逐段核过就放行（正文本来就要求每一段推进各一次 Write）；让 H2 也豁免「整段裁掉的段」
产出的前置（整段裁掉 S6 之后照样能派验收——验收拿不到测试结论；这一轮选了在拒绝理由与正文里说清「后面的段跟着裁」）。审查修法 2（PM 写
自己那几段的产物时核 `requires`）与修法 3（S6 的 `requires` 加 `05-impl` 的展开）不做：一次只推进一段之后，S4、S6 的前置在离开更早那几段时
已经核过。

### 2.2 后台启动那一刻不判产物（H5a）

`hooks/gate.mjs` 的 deliverable 分支按 `tool_response.status` 分三刻（`completion.mjs` 的 `dispatchPhase`）：

- `async_launched`：不出交付物校验；账本比对、【契约】、「停在旧阶段」「不是当前段执行者」那几格照发（它们审的是整趟 run 或这次派发本身，
  说的是「刚派出去的」）。不说「已启动」：工具结果第一句已经说了，PM 这时没有可做的事。
- `completed`（前台派发跑完）：没交齐时按成因说（§2.4），知道它已经跑完的几格不再说「等它写完（异步派发时）」；账本比对不报当前段的产物
  「没记」——它自己与同一段的兄弟刚交、PM 还没记的那几份（PM 读过回报、核过磁盘才记，那一条每次都会出现、还要协调者原样冒泡上去；前台并发
  派发时，后返回的那个会带上先返回的兄弟刚交的那一份，§4 的 M5）。
- 没有 `status`（旧版 CLI 或别的形状）：照改之前的口径，`SUBAGENT_STOP_RETRY_NOTE` 只留给这一格。

### 2.3 派发记录（`runs/<id>/dispatches.jsonl`）

门禁专属文件（`control-files.mjs` 的 `GATE_FILES`）：H3 对任何人的 Edit/Write 都拒，排在主线程豁免之前；Bash 写得进，与 `approvals.jsonl`、
`delivered.json` 同档。每行一个 JSON 对象，两种：

- `{ kind: "dispatch", at, agent_id, tool_use_id, role, stage, caller, caller_id, mode }`：H5a 在团队角色的每一次派发返回时记（`mode` 是后台启动
  或前台跑完；`stage` 是那一刻的 `state.stage`——完成时按派它时的那一段核；`caller_id` 是协调者这一次运行的 `agent_id`，主线程没有）。
- `{ kind: "stop", at, agent_id, role, stage, outcome }`：H5b 每一回停下记一行，`outcome` 是放行（`pass`）、认冒泡放行（`bubble`）、拦（`block`）；
  产物在、最后一条回复第一行却是冒泡标记的，放行也记 `bubble`（§4 的 M5：执行角色把卡在哪写进实现记录再冒泡）。
  原型只记拦截，复核指出「拦过一回」被当成了「平台静默放行」——冒泡之前必然先被拦一回（§3）；进度也分不出「还在跑」与「已经停了」。

只追加、一行一次写入，不读后判、不加锁（复核在 Windows 上实测 16–24 个进程并发追加、单行 70KB、文件长到 336MB，没有一行撕开或交错）；
末字节不是换行时先补一个（只读最后一个字节）；读的一方跳过解析不出的行，角色名与段名在原样拼进文字之前再拿花名册与阶段链核。写不进只往
stderr 留痕：完成核验这一次少核，拦不拦与记不记无关。只记团队角色、阶段链上的段、没收口的 run。不进 `artifacts`、不进交付快照。推进与收口判
「叫过」时并上派发行（§2.1）。

### 2.4 完成核验（`completion`，UserPromptSubmit）

新检查项，不是门禁：不拦任何东西（这个事件上 exit 2 或 `decision` 会把这条消息吞掉，出口契约钉着），只发受信回传。`checks.mjs` 里标
`speaks: true`——`hookOutput` 在 UserPromptSubmit 上只放标了它的检查项发 `additionalContext`，`approval-prompt` 照旧一个字都不写；
`tests/helpers/gate-runner.mjs` 的出口契约同一个口径。

1. `prompt` 里没有行首的 `<task-notification>`：不出声，不读运行状态。头几行逐行认，认得的（task-id、tool-use-id、status）取值、不认得的跳过，
   认到 `<result>` 或者第一行不是头字段就停；`<result>` 取第一对、反转义；一个 prompt 里几段、一段里几个 task-id 都认，按 task-id 去重；没有
   task-id 的跳过。
2. 运行状态读不出来只留痕；没有 run 不出声。
3. 在派发记录里按 `agent_id` 找这一次派发（同一个 `agent_id` 记过几次，挑 `tool_use_id` 与通知相同的那一条，挑不出取最后一条——被续上之后再
   通知，tool-use-id 换了照认）；找不到（别的 agent、后台 Bash、别的 run、没记下）不出声；记录里的角色不在花名册、段不在链上的不认。
4. 已收口：PM 收件时只说一句「它在这一趟收口之后才完成……不计入这一趟」。
5. 按记录里的段跑 `decideDeliverable`（经 freshness）：交齐了不出声；没交齐的出「⚠️ 交付物校验」，成因依次是：`status` 不是 `completed`（派发失败了、
   被停下了，认不出的值过 `quote`）；它最后一回停下是冒泡、或者 `<result>`（剥掉开头的 CLI 注记之后）第一行是冒泡标记（引出理由）；它最后一回
   停下门禁拦了它、它却结束了（多半是平台的续跑上限到了，引 `CAP_FACT`——推断语气）；它最后一回停下门禁放行了（那一刻它不在那一段的名单上，
   或者那时交了、之后又没了）；门禁没见它停下（停下那一刻没核，或者记录没写成）。出路：PM 派得到它就说「同一段里再派一次」，派不到就说「经
   <记录里的派发者> 再派」（派发者不在花名册或是 PM 时退回「经派得到它的那一层」）；没交的那几份能靠 `trimmed` 免掉时给出写法。
6. 不带账本比对与【契约】：回放 M4c 的四场会话，完成那一刻带上它们，每一次都多一段「artifacts 里没记」——PM 总是读完通知才记账。

### 2.5 前台跑完的成因、协调者的进度

- **前台跑完**：H5a 逐个文字块看（每一块先剥掉开头的 CLI 注记），认冒泡与 H5b 的 `isBubbleStop` 共用一个正则（`bubbleReason`）；理由过
  `quote`、上限 160 码点，只剥标记后面紧跟的 `*`、`_`（M4 那句理由以行内代码开头，剥反引号会把它拆坏）。成因同 §2.4。
- **协调者进度**（审查修法 3）：协调者返回（前台跑完那一刻，或完成核验）、它协调的那一段还是当前段、而且没齐时，列出派发记录里它这一次运行
  （`caller_id` 等于它的 `agent_id`；认不出就不报）在这一段派出去的执行角色、各自产物现在的样子（在磁盘上、还没有、是空文件、还是上一轮的）
  与门禁见没见它停下：没见它停下的后台派发说「可能还在跑」，停下了没交的说它停下时怎样（冒泡了、门禁最后一回拦了它、门禁放行了），交了却
  冒泡的说「那一份可能只写了它卡在哪，读它再定」（§4 的 M5、M5b：两个方向都见过，门禁不下结论）。不许诺
  「它完成时完成通知会到 PM」——交互模式下、`-p` 下协调者还在跑时，那条通知都不到 PM（§1.3）。收尾按各行的状态说：都交了、也没有一个冒泡，
  才说「名单上的都交了……再推进」；还在跑的说「等它停下再核」；停下了却没交齐、或者交了却冒泡的给出路。不带 ⚠️，一个都没记着时不出声；
  后台启动那一刻不报。

### 2.6 正文

- `/agent-team:at` 第 3 节：核实那一条补「后台派发启动那一刻门禁不判产物、完成时有交付物核验、成因有哪几种、协调者派的人完成通知不一定到你
  这里、进度不是报缺」与「这一趟确实不要它这几份的，推进那一次写进 `trimmed`」（只限 S2、S5 这类段里不在任何前置里的）；记账那一条补「只推
  一段」与「推进那一次 H6 核什么」一段；`S2`、`S5` 一个都没叫也写 `[]`；「叫到之后又不要了」一段（能免的清单与 `mayWaive` 照阶段链派生的逐份

- **旧 run 的多段角色**：at-ui 在 S2 叫过，离开 S5 时会被要求交 S5 那一份，出路是 `trimmed`——会盖掉它在 S2 的那一条。没有真实样本。
- **`trimmed` 每个角色一个值、不分轮次**：返工轮里重新叫回首轮裁掉的 at-ui，旧的那条还在，它这一轮没交也会被免掉；at-ui 在 S2、S5 都叫到之后又裁掉，两段记不下。
- **补记可以在 history 里跳段**（`[S3, S6]`）：产物逐段核，但被跳过的段返工计数不涨——预算那一边（第 16 条）的洞。
- **提前派下一段**（S5 里就派 at-qa）：H2 不看 `stage`，推进判据帮不上，靠 at-qa 正文自查。
- **整段裁掉一段之后，后面要它当前置的段派不出人**：只说清后果，不让 H2 豁免（§2.1）。
- **roster 坏了、又没有 `stage_roles`**：推进按「谁都没叫」算，只核固定产物，与 `stageRolesInRun`「宁可多算」的方向相反；`validateState` 会报 roster 的形状。
- **门禁本来就不管的路**：读不出来的产物不拦；H6 的跳过路径（写入前读不出来、阶段链坏）；Bash 直接改 `state.json`。
- **阶段链改了产物**：像 `03-alignment.md` 那样后加的产物，更早落盘的 run 推进时要补交。
- **免除里「不是验证段」那一条、拒绝理由里「验证段的产物」那一句**：今天的链上走不到，前提判据钉着「验证段都是产物固定的段」。

完成核验：

- **派发记录 Bash 写得进**：删了它，完成核验静默、推进判据退回只看 `stage_roles`；改了它，核错人、说错成因——只是说错，不放行任何东西。记录写失败只留痕，
  而 UserPromptSubmit 上的 stderr 在转录里看不见。
- **协调者派出去的人的完成通知不一定到 PM**（交互模式下送回协调者；`-p` 下协调者还在跑时也一样）：PM 收不到单个执行角色的核验，只能靠协调者返回时的进度与
  推进那一次的 H6。
- **完成核验不带账本比对**：后台派发下，最后一段新写的产物的账本比对没人报。
- **重复通知会重复回传**；读不出运行状态时完成核验不出声。
- **H5b 仍按停下那一刻的 `state.stage` 判**（§2.7）。
- **「门禁最后一回拦了它、它却结束了」的别的成因**：被中断时补发的 SubagentStop 记成拦截之类，所以那一句是推断语气。
- **CLI 注记按 2.1.286 的样子剥**（以「[harness:」开头、到「]」结尾的行）：格式变了，注记后面的冒泡就认不出（按「门禁最后一回停下的结果」判的那一支不受影响）。
- **冒泡标记的真假门禁核不了**（`docs/37` 继承）。
- **进度只在那一段还是当前段时报**；收口时还在跑的派发，只在通知到了时说一句。
- **前台派发的协调者返回时，原有的「停在旧阶段」那一格照旧**：M1 那种时序（`stage_roles.S5` 是上一轮留下的）会误报。
- **echo 自检提醒在每一条完成通知上都触发**（既有）。

## 6. 没量到的

- 终端 TUI 里 UserPromptSubmit 对完成通知的触发、`prompt` 的形状、回传进不进上下文（量过 `-p`、SDK 宿主与 `--bg`）；桌面端是非交互模式只是推断。
- 交互模式下孙代理的通知回到协调者时，协调者那一侧有没有 hook（探针看到 SubagentStart、SubagentStop 再触发，UserPromptSubmit 不在子代理上下文里触发）。
- hand-back 模式（auto 权限加内部开关）下 `content` 与 `<result>` 的形状——冒泡标记检测的一个风险点。
- 最低支持版本 2.1.139 上 `tool_response` 有没有 `status`（没有的走旧口径）。
- 架构师改成前台派之后，桌面端 Background tasks 面板里执行角色是不是还各占一条（README 那句「每个角色一条（包括架构师再派出去的下级）」是在后台派发下量的）。
