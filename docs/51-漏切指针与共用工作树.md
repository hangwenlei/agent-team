# 漏切指针与共用工作树

> 2026-10-07，M4p，分支 `m4p-pointer-and-worktree`。第九轮，从 `docs/00-开放边界.md` 挑的两条：`docs/30` §4 第一条「第二趟起漏切指针、契约写在
> 当前 run 之外时账本一句不说」（门禁侧有原型，没做），与全量审查第 39 条剩下的那一半「并行的执行角色共用一棵工作树」（`docs/39` 重核时没再列，
> 之后没人处置）。正文是复核修订之后的样子，复核与改了什么在 §8。

## 0. 一句话结论

- **漏切指针**：项目经理把契约或阶段产物写进 `runs/` 下一趟不是 `current-run` 的 run 目录时，账本原来一句不说——这次写入不在当前 run 里，按设计
  提前退出：没有 sha 回传、不进账本比对，门禁照旧按指针指着的那一趟判。现在回传一段【指针】，说清写在哪一趟、门禁按哪一趟判，按情形给出路。
  指针指着的那一趟 `state.json` 读不出来时同样说，并叫项目经理别去修那一趟。
- **共用工作树**：裁定门禁不强制串行（§1.2）。承重的是架构师正文那一句串行规矩（`/agent-team:at` 里给项目经理看的那一份也是），原来没有判据钉它，
  现在配上。

## 1. 修法与裁定

### 1.1 漏切指针：【指针】

- 账本（`hooks/gate.mjs` 的 ledger）在「不在当前 run 里」那一处提前退出之前，先问 `otherRunWrite`：写者是项目经理（含主线程），写的是 `runs/<另一趟>/`
  下的契约，或者某一段的产物（产物名照阶段链认，与写路径隔离同一个 `stageOwnerOfRunPath`），就回传【指针】（`pointerNotice`）：写在哪一趟、
  `current-run` 指着哪一趟、门禁按哪一趟判；这次写入没有 sha 回传、不进账本比对。出路按情形各一条：
  - **新建的就是那一趟、忘了改指针**：照 `/agent-team:at` 第 1 节把 `current-run` 指到它。契约与项目经理自己的产物（派发裁决、交付文档）再原样重写一次
    拿回传；别的角色的产物（例如 `01-prd.md`）再派它的产者重交——指过去之后那一趟成了当前 run，写路径隔离拒项目经理写别的角色的产物，原样重写走
    不通；这一份是项目经理写的，不算产者交的，产者重交之前别拿它当这一段交齐了。
  - **写错了目录、要写的是指针指着的那一趟**：照原样写进那一趟；被写的那一趟里这一份已经被这次写入改了，告诉用户。
  - **要接着做的是那一趟**：用户定过放弃的、或者拿不准，先问用户（`/agent-team:at` 第 1 节那一问）；用户要接着做，再把 `current-run` 指到它、跑
    `/agent-team:at-resume`。那一趟已经收口的不给这一条：说它已经收口，交付之后的新改动另起一趟。
- **目录名当不了 run id 的**（例如资源管理器复制出来的「r1 - Copy」）：不给「指过去」「接着做」——它当不了 `current-run`，指过去门禁判丢指针。说它
  不是一趟 run 的目录，出路是用合法的 run id 另建一趟写进去，并告诉用户那一份。与 `runLogs` 跳过这类目录同一个理由（`docs/49` §8）。
- **指针指着的那一趟 `state.json` 读不出来时**：门禁读不出运行上下文，原来走的是【门禁】那一支，修法叫项目经理照 `current-run` 写回一份合法的
  `state.json`——可 `/agent-team:at` 第 1 节说原来那一趟坏了就另起一趟、不写它的任何文件，项目经理正是照这一条另起了一趟才漏切指针的。现在这一支里，
  项目经理写的是另一趟（`current-run` 的原文是合法的 run id、写的不是它）的契约或产物时，先说【指针】：那一趟读不出来，门禁这一次什么都没核，
  别去修那一趟；不给「写错了目录」那一条。阶段链从插件自己那份读。
- 收窄到契约与产物，原型那一条「免得 PM 有意改上一趟文件时误报」这样落地：
  - 写另一趟的 `state.json` 不说——建新 run 时它本来就先于指针（`/agent-team:at` 第 1 节：先写 `state.json`，再写 `current-run`，再写契约）；
  - 写别的文件（不是契约、也不是哪一段的产物，包括另一趟里深一层的同名文件）不说；
  - 执行角色的写入不说——它们写别的 run 的目录，H3 本来就拒。
- 两个 run id 都是磁盘上的值，过 `quote`；显示的目录名照这次给的路径原样取（规范化之后的路径在 Windows、macOS 上折成了小写）。文件名、角色名是插件
  自己的名字，原样。
- 回传在写完之后：账本不是门禁，写进去了就写进去了，不拦。

### 1.2 裁定：并行的执行角色共用一棵工作树——门禁不强制串行

两个执行角色并发改同一份文件（共列的根级清单、共列目录里的同一份），后写的覆盖先写的；各自跑 `npm install`、测试、构建，互相踩 lockfile、`node_modules`、
构建产物与端口。审查原文的修法只给了红线（执行角色不跑整棵树的 git 命令，第一轮做了），没给并发的出路。

- **拒绝的做法**：H2 在派发一个执行角色时，同一段里另一个执行角色已经派出去、门禁还没见它放行地停下，而两者在 `paths` 里共列了同一份文件或同一条前缀，
  就拒，理由叫派发者等它停下再派。
- **它打不红的那一刀**：共用工作树的冲突大半不在 `paths` 里——lockfile、`node_modules`、构建产物、端口、git 的 `index.lock`，都经 `Bash`；两个执行角色
  经 `Bash` 改同一份共列文件，同样不经门禁。
- **它的代价**：「还在跑」只能按派发记录与停下行认。会话中断、后台被停掉的子代理没有停下行；被平台续跑上限放过的，最后一行是「拦」，没有放行的
  停下行——H2 会一直拒，这一段卡死；派发记录是门禁专属文件，项目经理清不掉，没有出口。
- **提醒也不做**：PreToolUse 上不发受信块（`docs/30`），能说话的是 PostToolUse——那时第二个已经派出去了，两个人已经在一棵树上跑。架构师正文那一句管在
  派发之前。
- **什么会让答案改变**：真实会话里观测到并发的执行角色互相覆盖了共列的文件；或者平台给出可靠的子代理存活状态（例如 hook 输入里带着正在跑的子代理），
  「还在跑」不再靠停下行认。
- **现状**：
  - 架构师正文那一句——只改各自地盘的几个执行角色可以并发派；要改同一份文件的，派一个、等它返回、读过它的实现记录再派下一个，不放到后台——
    与 `/agent-team:at` 里给项目经理看的那一份（几个都要改同一份文件的除外：派一个、等它返回再派下一个），现在由 `tests/shared-worktree-prose.test.mjs`
    钉着。
  - 平台给并行派发的 worktree 隔离（Agent 的 `isolation`），H1 拒：隔离出去的子代理找不到这一趟 run，写回来的路径无人认领（`docs/24` §2.1）。

## 3. 实测

- 没起真实会话：漏切指针要项目经理真漏了那一步才走得到，判据的输入形状与账本别的几支相同。
- 分支第一次推（`19f8d47`）ci 三个系统与 min-node 全绿；复核修订推上去之后的结果写在合并之后的收口里。

## 4. 仍然开着的边界

- **只说契约与产物**：项目经理把别的文件写进另一趟（手抄的笔记、实现记录以外的东西）不说；用 `Bash` 写的照旧不说。
- **写完之后才说**：账本不拦，写进去的就在那一趟里；项目经理照出路做之前，那一趟的目录里多了一份不归它的文件——别的角色的产物那一份，派产者重交
  之前门禁的前置与【阶段】会把它当成产者交的。
- **指针指着的那一趟读不出来时**：只在 `current-run` 的原文是合法 run id、那一趟的 `state.json` 读不出来这一格说；指针丢了、指着不存在的目录走的是原来
  那一支（它的修法指向最后建的那一趟，方向是对的）。
- **共用工作树门禁不管**（§1.2，有意）：靠架构师正文的串行规矩；经 `Bash` 的共享状态冲突门禁看不见。

## 5. 没量到的

- 真实会话里项目经理漏切指针、收到【指针】之后照哪一条出路做。
- 真实会话里并发的执行角色互相覆盖共列的文件。

## 8. 复核与修订

收口之后另起）都不误报；出路一对契约走得通。

- **中 1　指针指着的那一趟 `state.json` 读不出来时，【指针】出不来，【门禁】的修法反而叫项目经理去重建那一趟**：`/agent-team:at` 第 1 节说原来那一趟坏了
