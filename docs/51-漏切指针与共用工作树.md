# 漏切指针与共用工作树

> 2026-10-07，M4p，分支 `m4p-pointer-and-worktree`。第九轮，从 `docs/00-开放边界.md` 挑的两条：`docs/30` §4 第一条「第二趟起漏切指针、契约写在
> 当前 run 之外时账本一句不说」（门禁侧有原型，没做），与全量审查第 39 条剩下的那一半「并行的执行角色共用一棵工作树」（`docs/39` 重核时没再列，
> 之后没人处置）。

## 0. 一句话结论

- **漏切指针**：项目经理把契约或阶段产物写进 `runs/` 下一趟不是 `current-run` 的 run 目录时，账本原来一句不说——这次写入不在当前 run 里，按设计
  提前退出：没有 sha 回传、不进账本比对，门禁照旧按指针指着的那一趟判。现在回传一段【指针】，说清写在哪一趟、门禁按哪一趟判，给两条出路。
- **共用工作树**：裁定门禁不强制串行（§1.2）。承重的是架构师正文那一句串行规矩，原来没有判据钉它，现在配上。

## 1. 修法与裁定

### 1.1 漏切指针：【指针】

- 账本（`hooks/gate.mjs` 的 ledger）在「不在当前 run 里」那一处提前退出之前，先问 `otherRunWrite`：写者是项目经理，写的是 `runs/<另一趟>/` 下的契约
  或某一段的产物（产物名照阶段链认，与写路径隔离同一个 `stageOwnerOfRunPath`），就回传【指针】（`pointerNotice`）：
  - 这次写的是哪一趟 run 目录里的哪一份，`current-run` 指着哪一趟，门禁按哪一趟判；这次写入没有 sha 回传、不进账本比对；
  - 新建的那一趟：照 `/agent-team:at` 第 1 节先把 `current-run` 指过去，再原样重写一次这份文件拿回传；
  - 要接着做的确是那一趟：先把 `current-run` 改回它，再跑 `/agent-team:at-resume`。
- 收窄到契约与产物，原型那一条「免得项目经理有意改上一趟的文件时误报」这样落地：
  - 写另一趟的 `state.json` 不说——建新 run 时它本来就先于指针（`/agent-team:at` 第 1 节：先写 `state.json`，再写 `current-run`，再写契约），替旧的一趟
    收口写的也是它；
  - 写别的文件（不是契约、也不是哪一段的产物）不说；
  - 执行角色的写入不说——它们写别的 run 的目录，H3 本来就拒。
- 两个 run id 都是磁盘上的值（目录名、`current-run` 的内容），过 `quote`；文件名是插件自己的名字，原样。`current-run` 的内容不是合法的 run id 时门禁读不出
  运行上下文，走的是原来那一支（【门禁】），走不到这一段。
- 回传在写完之后：账本不是门禁，写进去了就写进去了，不拦。

### 1.2 裁定：并行的执行角色共用一棵工作树——门禁不强制串行

两个执行角色并发改同一份文件（共列的根级清单、共列目录里的同一份），后写的覆盖先写的；各自跑 `npm install`、测试、构建，互相踩 lockfile、`node_modules`、
构建产物与端口。审查原文的修法只给了红线（执行角色不跑整棵树的 git 命令，第一轮做了），没给并发的出路。

- **拒绝的做法**：H2 在派发一个执行角色时，同一段里另一个执行角色已经派出去、门禁还没见它停下，而两者在 `paths` 里共列了同一份文件或同一条前缀，就拒，
  理由叫派发者等它停下再派。
- **它打不红的那一刀**：
  - 「还在跑」只能按派发记录与停下行认。会话中断、被平台续跑上限放过、后台被停掉的子代理，永远没有停下行——H2 会一直拒，这一段卡死；派发记录是门禁
    专属文件，项目经理清不掉，没有出口。
  - 共用工作树的冲突大半不在 `paths` 里：lockfile、`node_modules`、构建产物、端口、git 的 `index.lock`，都经 `Bash`，门禁看不见。
- **什么会让答案改变**：真实会话里观测到并发的执行角色互相覆盖了共列的文件；或者平台给出可靠的子代理存活状态（例如 hook 输入里带着正在跑的子代理），
  「还在跑」不再靠停下行认。
- **现状**：
  - 架构师正文那一句——只改各自地盘的几个执行角色可以并发派；要改同一份文件的，派一个、等它返回、读过它的实现记录再派下一个，不放到后台——
    现在由 `tests/shared-worktree-prose.test.mjs` 钉着。
  - 平台给并行派发的 worktree 隔离（Agent 的 `isolation`），H1 拒：`.agent-team` 不进版本库，隔离出来的 worktree 里门禁看不到这一趟 run
    （`docs/24` §4）。

## 2. 判据与变异

- `tests/gate-pointer-notice.test.mjs`（子进程）：项目经理把契约写进另一趟，【指针】说清写在哪一趟、门禁按哪一趟判、两条出路；写产物同样说，产物名照阶段链认；
  收窄——写另一趟的 `state.json`、别的文件、执行角色的写入、当前这一趟的契约、项目代码里同名的文件都不说；带空格的目录名在一对引号里。
- `tests/trusted-echo.test.mjs`：另一趟的 run 目录名带行分隔符（Windows 上合法的那三种），【指针】不回显。
- `tests/shared-worktree-prose.test.mjs`：架构师正文的串行规矩。

变异（备份在仓库外，改完逐字节还原），各红：`otherRunWrite` 恒回 null；不判是不是当前这一趟；只认契约、不认产物；不收窄到契约与产物；不看写者；
`state.json` 也算；目录名不过 `quote`；架构师那一句改坏。

## 3. 实测

- 没起真实会话：漏切指针要项目经理真漏了那一步才走得到，判据的输入形状与账本别的几支相同。
- 分支 CI 的结果写在合并之后的收口里。

## 4. 仍然开着的边界

- **只说契约与产物**：项目经理把别的文件写进另一趟（手抄的笔记、实现记录以外的东西）不说；用 `Bash` 写的照旧不说。
- **写完之后才说**：账本不拦，写进去的就在那一趟里；项目经理照出路做之前，那一趟的目录里多了一份不归它的文件。
- **共用工作树门禁不管**（§1.2，有意）：靠架构师正文的串行规矩；经 `Bash` 的共享状态冲突门禁看不见。

## 5. 没量到的

- 真实会话里项目经理漏切指针、收到【指针】之后照哪一条出路做。
- 真实会话里并发的执行角色互相覆盖共列的文件。
