# 返工到上限之后与不记回退的重做

**日期** 2026-10-01 ｜ **口径** 分支 `m3z-rework-protocol`（`e6283df` 与其后的复核修订），版本 `1.8.0`；修的是全量审查（`docs/24-附录-全量审查报告.md`）
第 16 条。真实会话在本机 CLI 2.1.286 上

## 0. 一句话结论

规格 §4.2 ③ 写「第 3 轮终局，不过则升级」，可升级之后没有一条诚实的写法：`rework` 不许低于 `history` 的派生值（H6 判据③），又不许超过 3
（判据④），第 4 轮两条互斥。PM 只剩「不记账就派人」，而那条路同时绕过了返工预算与第 15 条的回退快照——不记回退的重派，每一帧都放行。
现在：用户在 `AskUserQuestion` 里选了规范标签「再返工一轮：回到 <段>」（问不了用户的会话里，用户单独发一条整条只写这一句的消息也算），
而这一轮确实会越限时，门禁自己把批准记进 `runs/<当前 run>/approvals.jsonl`，越限的那几段各多一轮上限；H6 在回退那一次写入就按「这一轮走完」
预判，越限就拒、理由里给标签。另一半：不记回退就派人重做，门禁在派发（H2，派的是叶子角色）与写入（H3，执行角色改它早段交过的产物）两帧拦下；
只改 `stage`、往 `stage` 或 `history` 里写链外的段、改写 `history` 里已有条目的段名，H6 拒。

## 1. 问题（审查原文与复现）

- 审查原文三条修法：①`/agent-team:at` 加「返工」一节（第 15 条已经补了「回退」一节）；②`state.json` 加 `rework_override`，引用用户确认过的那条
  升级，H6 见到它就放过超过上限的计数；③H2 在 `history` 显示已回退、`rework` 没涨时拒派。
- 调研（四路：复现、合法模式普查、预算与升级语义、历史裁定）推翻了后两条的写法：
  - ②让 PM 自己写一个字段去放宽自己的预算。`escalations` 是 PM 转写的自由文本，没有任何字段分得出「批准继续」与「停」；门禁要的是一个
    PM 伪造不了的来源。平台实测（CLI 2.1.286，SDK 宿主）：`PostToolUse:AskUserQuestion` 拿到的是宿主的真实答案，模型在 `tool_input` 里预填的
    `answers` 被覆盖；用户拒答时 `PostToolUse` 不触发。所以批准由门禁在用户作答那一刻自己记。
  - ③描述的状态（`history` 显示回退、`rework` 没涨）H6 本来就不让写进去；真正漏掉的是连 `history` 都不记的那一种——派发那一刻分不出
    咨询、补派与重做（合法模式普查 L1–L11：S5 派架构师、架构师在 S5 改 `03-arch.md`、PM 改契约与 `04-dispatch.md`、产者交代②与【返工】出口的
    补派……）。所以只在分得出的地方拦。
- 放大：只放开回退那一次写入不够——同一轮里重进 S6 也是第 4 次；需求回 S2 时墙推迟到三段之后的推进上，【阶段】还指着那条会被拒的写法。
- 一条 H6 放行、事后只报一次的绕路：只改 `stage`、不追加 `history`（零代价地撤回推进，或者不记账就回到早段）；往 `stage`/`history` 里写
  链外的段（`S5b`、「需求驳回」、`DONE`），回退预判、回退快照与这一条的重做判据都只认链上的段，一写全部失效。

## 2. 修法

### 2.1 批准：谁记、记什么、算多少（`hooks/lib/budget.mjs`、`hooks/lib/approvals.mjs`）

- **规范标签** `再返工一轮：回到 <段>`（全角冒号，段是阶段链上的 id）。认法：先 NFKC、删掉全部空白，再剥一次末尾的「(Recommended)」或「(推荐)」——
  平台的 `AskUserQuestion` 说明叫模型往推荐项标签上加「(Recommended)」，转录里 PM 写进标签的推荐后缀很常见，模型也会把全角冒号写成半角。
  闭集：「（不推荐）」「（最快，推荐）」不剥。段 id 只认字母、数字、下划线与连字符。
- **两个记录器**（各占一个事件，`checks.mjs` 一个检查项一个事件）：
  - `approval-ask`（`PostToolUse` / `^AskUserQuestion$`）：只读 `tool_response`。只认单选题（`multiSelect` 不是 `true`）上的字符串答案；
    `tool_response` 带 `afkTimeoutMs`（离开键盘、对话框自动提交）、`followUp === true`（要追问）、`response` 非空（另写了一段话）、批准那道题
    带非空备注（`annotations[题].notes`）时整次不记——那几种情况下模型收到的分别是「用户离开了，自行判断」「先别动手」「用户回复了……」「用户的
    备注」，门禁不能比模型看到的更宽。记下了、或者像批准却没记下，都回一段【门禁】说结果与原因，给用户一行固定文字。
  - `approval-prompt`（`UserPromptSubmit`）：整条 prompt 规范化之后等于标签才算。`UserPromptSubmit` 也对 task-notification（子代理回报、后台
    Bash 的说明）触发，那里的文字是模型写的；用户贴回 PM 的问题原文也会带上标签——都不算。这个事件上 stdout 会进模型上下文、exit 2 会拦掉
    用户的话，它两样都不做，只往 stderr 留痕。
- **只在需要时记**（`needOf`）：假设现在回退到 T（T 晚于 `history` 里最近一条在链上的条目就不是回退；同一段是原地重来，算回退），按 H6 的预判口径算这一轮会越限的段；
  一个都没有就不记（上限内顺手说的、同一次两题都选的、对话里再发一遍的，都不多给额度），有就追加一行 `{"at","source","rework_to","covers"}`，
  `covers` 是越限的段。同一次回答里的几条逐条判，判下一条时把前面判成要记的算进已有批准（先在内存里判完，再逐条追加；前一条写不进时，
  后一条也不会补记）。
- **上限** `limitOf(S) = 3 + 覆盖 S 的批准条数`。`readGrants` 只认 `covers` 是「链上段 id 组成的非空数组」的行；`rework_to` 只留给人读。
  一条批准只盖记下那一刻会越限的段——批准回到 S2 不会让还没走到的 S5、S6 多一轮。
- **并发与坏行**：读批准、判需不需要、追加，三步在一把锁里（run 目录里的 `approvals.jsonl.lock`，最多等约 5 秒，旧于 5 秒的锁当崩掉的
  进程留下的；到头拿不到就不加锁照做）。末行没有换行（手改过）时先补一个。

### 2.2 H6：回退预判、判据④、stage 不变量（`hooks/lib/rework-guard.mjs` 的 `decideRework`）

顺序：新内容是对象 → `history` 只许追加（条数不减、**写入前已有的条目段名不许改**、各段出现次数不减）→ 回退预判 → ③ 不低于派生值 →
④ 类型与上限 → stage 不变量。

- **回退预判**：这次写入记了一次回退（新追加的条目在链上不晚于它之前最近一条在链上的条目；链外条目跳过），就按「这一轮走完」算各段的
  返工轮数——写入后 `history` 里、最后那条回退条目之前 S 的出现次数（不早于回到的那一段）。有一段超过上限就拒，理由给规范标签、怎么问、
  用户叫停怎么办、问不了怎么办、门禁这一趟记下了几条批准。排在③④之前：第 4 轮不管把 `rework` 写成多少，拿到的都是这一条。
  计数口径在设计评审里被逐条推翻过两种读法：按写入后整份计数会拒掉预算内的补记，按写入前计数会放过一次写入记两轮。
  回退条目之前、同一次写入里还追加了别的条目（先推进再回退，或者一次记了两轮）时，记录器只能从磁盘模拟「回到那一段」，批准盖不全——
  这种写法越限时理由叫它拆开写，不给记不下的标签。
- **判据④只罚改大**：类型照旧先验（非负整数）；超过 `limitOf` 而且比写入前大才拒，理由给标签（取 `history` 里最后一次回退回到的那一段；它晚于
  越限的段、或者没有回退时，取越限的段本身）。
  原样带着的旧值不重复拒——批准记录丢了也不把整趟锁死。
- **stage 不变量**（阶段链读得出时）：`stage` 在链上；这次新追加的 `history` 条目都在链上；`stage` 等于 `history` 末条。写入前读不出来
  （第一次写、修坏文件）只核 `stage` 在链上。
- **已有条目的段名不许改**：此前「只许追加」只核条数与各段出现次数，把一条更早的 S5 改成还有额度的段、同时照常追加一条 S5，次数都不降、
  S5 的派生值却不涨（复核找到的，审查第 5、6 条的同族）。
- 拒绝理由在返工预算那几种（预判、④的上限）末尾补一句诊断：门禁读不到运行状态、或者这份 `state.json` 不在 `current-run` 指向的那一趟里时，
  照理由问了也记不下或记到别处。

### 2.3 【返工预算】与【阶段】（`hooks/lib/state.mjs`、`hooks/lib/ledger.mjs`）

- `validateState` 的上限一条改成比 `history` 的派生值（不比写着的值），越限单列成 `budget`，ledger 出【返工预算】——不进【state.json】
  「改完再继续」那一块：越限的唯一出路是问用户，把计数改小会被 H6 拒。写着的值与派生值对不上照旧在【state.json】里报。
- 【阶段】：推进进下一段会越限（批准记录丢了、`history` 在别处被改过才走得到）时，写 `state.json` 那一次给全问用户的做法；写产物触发的
  【阶段】会发给执行角色，只说「PM 推进之前要先问用户」。
- `history` 里链外的旧条目（v1.7.0 及更早写进去的 `DONE`）现在改不了也删不掉，单列成 `legacy`，ledger 不再每次叫「改完再继续」。

### 2.4 不记回退的重做：交付快照、H2、H3（`hooks/lib/redo.mjs`）

- **交付快照** `runs/<id>/delivered.json`：PM 写 `state.json`、而 `stage` 变了（推进、回退）或者还没有快照时，ledger 照磁盘拍下早于当前段的
  各段产物（按全部产者展开）的 sha，记着拍它时的 `stage`。「交过」= 快照里有、磁盘与快照相同、不是上一轮的（第 15 条的 freshness）。
  快照之后才落盘的、快照之后改过的、还是上一轮的，都不算交过——补派与【返工】的出口写几次都放行，直到下一次推进或回退；只记账、不动
  `stage` 的写入不关这个窗口。不依赖 PM 把 sha 记进 `artifacts`（那条回传只发给写者，第 28 条）。
- **H2**，只管叶子角色（花名册里派不出任何人）：按派发者选出的候选段（与 H2 选段同一个 `candidateStages`）全都早于 `state.stage`、它在这些段
  自己的产物全都交过 → 拒。PM 收件：先记一次回退再派；只是要问它点什么，读它的产物或问用户。别人收件：自己读产物与代码，真要重做就冒泡。
  协调者（`at-architect`、`at-product`）派发时不判——分不出咨询、补派与重做；它真动手，落到 H3 与它往下派的那一跳。不加「目标在当前段有活」
  这个豁免：`at-product` 在 S5 派 `at-ui` 重做 S2 照拒。
- **H3**：非 PM 写 run 目录里自己名下、早于 `state.stage` 那一段的产物，它在当前段没有活（不是当前段的 `role` 或产者、也派不到当前段的
  `role`），这一份交过，又没有一份兄弟产物是这一窗口刚补上的（在磁盘上、却不算交过）→ 拒。这和 H2 的「整段」口径不同：兄弟产物从没写过时
  照拒；交了一半的补派，等缺的那份落盘之后，改已交的那份才放行。架构师在 S5 改 `03-arch.md`、`at-ui` 在 S5 改 `02-*`：在 S5 有活，放行。
  PM 自己的产物不判。
- 「是不是重做」看 `state.stage`。H2 只拿选出的段与 `stage` 比先后：落后（齐了没推进）只会少拦，超前（第 17 条的提前推进）会多拦，出口是
  记回退。H3 还按 `stage` 判写者在当前段有没有活：落后也会多拦（S4 齐了没推进、架构师已在做 S5 时改 `03-*`），那时的出口是推进 `stage`，
  H3 的拒绝理由说了。`docs/31` §2.2「H2 选段不看 `state.stage`」不变——选段仍按派发者。

### 2.5 门禁专属文件（`hooks/lib/control-files.mjs` 的 `GATE_FILES`）

`runs/*/approvals.jsonl` 与 `runs/*/delivered.json`：任何人的 Edit/Write/NotebookEdit 都拒，PM 与主线程也拒，排在主线程豁免与读运行上下文之前
（与门禁自检同一个位置）。按路径形状认任何项目的 `.agent-team/runs/<id>/` 下的这两个名字，每一次写入都经 `norm()`（解析 `.`、`..`、链接、8.3 短名）
认一遍；末段先规范化（剥流后缀、结尾的点与空格，与 H6 认 `state.json` 共用 `leafName`），`.agent-team` 在的项目里认不出的写法一律拒。
`Bash` 照样写得进——与 `state.json` 同一档：那是一次要刻意去做的伪造。

### 2.6 失败策略与平台契约

两个记录器 `failClosed: false`、`recorder: true`。它们不放行任何东西，失败的后果是「这次的回答没有记下」：`boot.mjs` 加载失败与 Node 太旧、
`crashNotice`、读不出输入、最外层 catch 的说法都照 `recorder` 改成「记不下」。给用户的那一行只在 `PreToolUse`、`PostToolUse` 上发
（`UserPromptSubmit` 上 stdout 进模型上下文，`hookOutput` 对它有东西要发就报 BUG）。`boot.mjs` 的失败策略表读不到、输入里又没有
`hook_event_name` 时，没有 `tool_name` 的输入不按 `PreToolUse` 拒（`PreToolUse` 的输入总带 `tool_name`）。出口契约
（`tests/helpers/gate-runner.mjs`）补一条：非 `PreToolUse`、`PostToolUse` 事件上 stdout 必须为空。

> **订正（M4d，2026-10-05，`docs/38` §2.4）**：「非 PreToolUse、PostToolUse 事件上 stdout 必须为空、有东西要发就报 BUG」不再无条件成立——
> UserPromptSubmit 上标了 `speaks` 的检查项（完成核验 `completion`）可以发受信回传（`additionalContext`；不带 systemMessage、永不 exit 2）；
> `approval-prompt` 照旧一个字都不写。

## 3. 设计评审与复核

**设计评审**（三路：语义、平台、正文与判据，各条再由一个驳论者在原型上复跑；27 条意见）推翻或改写了初稿的这些地方：

- 初稿把 `approvals.jsonl` 里每一条规范标签答复都算进上限、永久有效（O1）：上限内顺手说的、同一次两题都选的、对话里再发一遍的、
  换目标再批的，每一条都多给一轮。改成只在那一刻会越限时记、记 `covers`。初稿的「一条批准覆盖回到的那一段及之后各段」（O2）会把额度给到
  批准时还没走到的段，同一个改法收掉。
- 回退预判「其余是现在的出现次数」有写入后、写入前两种读法（O5），两份独立原型都用了写入后那种；驳论者实测两种都错（前者拒掉预算内的补记，
  后者放过一次写入记两轮），改成显式公式，判据每一格打红一种读法。
- 链外的 `stage` 或 `history` 条目一写，预判、不变量与重做判据全部失效（O3），加 stage 不变量。

## 5. 仍然开着的边界

- **拦不到的重做**：协调者自己动手改 `src/`（不经它的执行角色）、PM 自己改 `src/`、`at-qa`/`at-acceptance` 改别人认领的实现代码（第 34 条：没有
  `paths` 键的角色在 run 目录外全放行；`at-qa` 还有 Bash）。只改代码、不碰阶段产物的重做，门禁看不见。
- **绕开 S3/S4**：设计错了却按「回到 S5」记、让架构师在 S5 改 `03-*`（它在 S5 有活，放行）——S3、S4 的预算与批准都没经过（O9）。
- **提前推进**（第 17 条）：PM 推进之后执行角色才交的那一份，第一次写是补派、放行；PM 再推进或回退一次之后再写就被拦，出口是记回退。
- **快照的窗口**：只在推进或回退之后重拍。两次之间才落盘、或者被改过的产物，写几次都放行；快照拍下之前就交了、又在同一段里被它的产者重写，不算重做。
- **Bash**：写门禁专属文件（伪造批准、清空快照）、写产物，都不经门禁——与 `state.json` 同一档，需要刻意去做。
- **问法**：PM 用误导的问题配上规范标签，用户点的就是标签上写的那一句（「再返工一轮：回到 S5」），门禁只认这一句。
- **问不了用户的宿主**（`-p` 不带权限工具、`--bg`）：只剩用户在对话里单独发标签；那一路没有回传，PM 只能从 H6 不再拒推断批准记下了。
- **补批准**：【阶段】、【返工预算】、判据④给的标签按「现在回到那一段」算 `covers`，可能多给已经在上限上的段一轮（批准记录丢了、`history` 被别处改过才走得到）。
- **提前批准**只盖当时越限的段，真回退时可能还要再问一次。
- **门禁不强制「停」**：用户选「停在这里」之后，PM 照样能做别的事；`escalations` 是人读的记录，不承重。`rejectTo` 仍没有消费方。
- **放大效应**（`docs/11` §5.10(c)）：上游驳回照旧吃下游的额度；另起一个 run 清零预算（第 24 条）。
  > **订正（2026-10-02，M4a，`docs/35`）**：有了收口标记之后，交付之后的新改动另起一趟是正路，预算从零开始；没收口的 run PM 自己不能丢下它
  > 另起（正文；`current-run` 的切换门禁仍不拦），用户跑 `/agent-team:at` 时第 1 节先看旧的那一趟收不收得了口。
- **S6 之后执行角色不能被叫来做只读诊断**：门禁分不出咨询与重做，按重做拦；正文叫 PM 与架构师自己读产物与代码。
- **每条用户消息多起一个 node 进程**（`approval-prompt`）；Node 太旧或插件装坏时每条用户消息多一行 hook error（首行说「记不下」）。
- **插件被加载两份**：所有门禁都会双跑；记录器有锁，不会重复记。
- **`boot.mjs` 的双故障**：失败策略表读不到、hook 输入也读不出时，照旧按 `PreToolUse` 拒（读得出却既没有 `hook_event_name` 也没有 `tool_name` 时不再）。
- **链外的旧 `history` 条目**永远在（不许改、不许删），单列成 `legacy`、不再报；插件升级改了阶段 id 的迁移仍然没有。

> **收口（M4d，2026-10-05，`docs/38` §2.1）**：「提前推进」——PM 推进时离开那一段叫到的人没交齐，H6 拒；推进之后执行角色才交的那一种，在推进判据
> 之下只剩「派了却没记、也没进派发记录」那一格。

## 6. 没量到的
