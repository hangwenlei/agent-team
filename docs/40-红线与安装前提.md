# 红线与安装前提

> 2026-10-05，M4e，分支 `m4e-redlines-and-setup`，v2.3.0。`docs/39` §5 排出来的第一轮：全量审查第 26 条（持 Bash 的执行角色没有
> 敏感操作红线）、第 39 条的正文与回传部分（git 命令抹掉 run）、第 23 条（默认装到 user 作用域）、第 25 条（git 仓库里的后台会话）、
> 第 43 条（原生 Windows 没装 Git for Windows）、第 49 条（英文用户）、第 30 条后半（frontmatter 的 YAML 盲区）。每一条的现状与证据
> 在 `docs/39` §2，这里只记修法、判据与实测。

## 0. 一句话结论

- **持 Bash 的执行角色有了同一句敏感操作红线**：用凭据、花钱、对外发布、`git push`、删改不是这一趟产出的文件、动 CI/CD 与生产配置、
  动整棵工作树或历史的 git 命令——碰到就以「冒泡：」停下，协调者不定、原样冒泡给 PM，PM 照 `/agent-team:at` 第 4 节的 `sensitive`
  问用户。门禁照旧不看 Bash，这一层只在正文里；判据保证每一份逐字同一句。
- **git 与 `.agent-team/`**：初始化时项目经理建议（先问）把 `.agent-team/` 加进 `.gitignore`，README 写清不加与入库各会怎样；没有 run
  时派发返回的那一句补上「被 git 清掉或藏起」这个成因。
- **安装前提写全了**：README 两半警告两条安装命令都要带 `--scope local`、给出误装之后的卸载命令；原生 Windows 要装 Git for Windows；
  git 仓库里的后台会话要设 `worktree.bgIsolation`；英文那一半说明运行时是中文。自检在工具面里没有 Bash、或者平台报出后台会话的那句
  拦截时，停下告诉用户该做什么。
- **frontmatter 只用受限写法**：一条判据让平台的 YAML 解析器与按行读的判据读到同一个值，挡住「解析失败整份当空」与「折行授出
  工具」两个静默方向。

## 1. 修法

### 1.1 敏感操作红线（第 26 条、第 39 条）

- 六个持 Bash 的执行角色（`at-backend`、`at-frontend`、`at-ui`、`at-ios`、`at-android`、`at-qa`）的「红线」一节加同一句。清单与
  `/agent-team:at` 第 4 节 `sensitive` 那一行对得上，外加动整棵工作树或历史的 git 命令（`clean`、`stash`、`reset`、`checkout`、`switch`、
  `restore`、`rebase` 这类——第 39 条：没进版本库的 `.agent-team/` 会被一起清掉或藏起，进了版本库的 `state.json` 会被倒回去）。
  碰到就停下，最后一条回复的第一行写「冒泡：」，说清是哪一步、为什么要它，做不做由用户定。各自的例外写在这一句后面：执行角色是
  「照清单装依赖、编译、跑测试，在 `paths` 列给你的前缀里照任务改代码」，`at-qa` 是「照清单装依赖、编译、跑测试，起停测试要用的服务」。
- `at-qa` 原来写「冒泡只用于『S5 没交齐』那一种」，改成「与下面红线里的敏感操作」；环境原因跑不起来照旧写进 `06-test.md`、不冒泡。
- 协调者（`at-architect`、`at-product`）：执行角色为红线里的敏感操作冒泡的，不定，原样冒泡给 PM（那要问用户）。PM 那一侧不用改：
  第 4 节的 `sensitive` 本来就是「问用户」。
- 不选的做法：门禁加 Bash 的 matcher（命令行是自由文本，判不准，而且平台的权限模式才是那一层）；把红线放进一份共用的 skill（各执行
  角色预加载的 skill 不同，放不进同一份）。

### 1.2 shell 说明

持 Bash 的每个角色（上面那些执行角色与 PM）各加一句：你的 shell 只有 `Bash`（Windows 上是 Git Bash），命令照 POSIX 写；环境说明里提到 PowerShell，
那不是你的工具。来由：CLI 的环境说明按整个会话写（原生 Windows 上以 PowerShell 为首选 shell），不看角色自己的工具清单，而团队角色
只持 Bash；`docs/39` §4 的 M5f 里，haiku 版 PM 在 Bash 里调了 PowerShell 的 `Get-FileHash`。

### 1.3 git 与 `.agent-team/`（第 39 条的正文与回传部分）

- `/agent-team:at-init` 收尾：项目根下有 `.git` 的，建议把 `.agent-team/` 加进 `.gitignore`。改 `.gitignore` 是动用户的文件，先问；
  理由照实说：既不进版本库也不忽略，`git clean -fd`、`git stash -u` 会把进行中的 run 一起清掉或藏起，门禁随之失效；提交进了版本库，
  `git stash`、`git checkout -- .` 会把 `state.json` 倒回提交时那一版，返工计数一起清零。忽略之后只剩 `git clean -fdx`、`git stash -a`
  碰得到它。
- README 两半「产物在哪」各加同一段。
- H5a 在没有 run 时给 PM 的那一句（`hooks/lib/fail-open.mjs` 的 `dispatchNoRunNotice`），「你以为这里有进行中的 run 的话」那一支补一个
  成因：没进版本库的 `.agent-team` 会被 `git clean`、`git stash -u` 这类命令一起清掉或藏起（藏起的用 `git stash pop` 找回，清掉的找不回），
  告诉用户。
- 没做的：S4 记代码基线（回退之后代码回不去，`docs/39` §2.2 列的可选项，挪到第三轮一起看）；自检区分「从来没有 run」与「run 被抹掉」
  （要在项目之外留标记）。

### 1.4 安装作用域（第 23 条）

- README 两半的安装一节各加一段警告：两条命令都要带 `--scope local`；不带、或者在 `/plugin` 面板里选了默认的第一项，装的是 user
  作用域，这台机器上此后每一个新会话都会被接管。误装之后的卸载命令写成不带 `--scope` 的那一种：CLI 的 `plugin uninstall` 默认就是 user
  作用域，而 README 的命令行里不许出现 `--scope user`（readme-sync 第十节）。
- readme-sync 第十节的理由与失败文案原来引用「两份 README 的收场那一段」——那一段 0.7.5 就删了；改成指向这一段警告。
- 不选：放宽 H1 让误装的会话派得出内置代理（`at-pm` 的 `tools:` 已经把派发宇宙封顶在团队角色上，H1 放行了也派不出去，反而削弱
  花名册闭包）。

### 1.5 git 仓库里的后台会话（第 25 条）

- 平台在 `validateInput`（早于 PreToolUse）拦后台会话对主 checkout 的写入，门禁看不到，结果是第一步自检就停。所以只改正文：
  - PM 的自检第 3 支「平台在调用之前就报了错」加一句：报错里提到 `EnterWorktree` 或 `bgIsolation` 的，告诉用户在项目的
    `.claude/settings.json` 里设 `"worktree": {"bgIsolation": "none"}`，或者改用前台会话再开这一趟；不要照平台的提示去
    `git worktree add`，也不要自己改设置。
  - `/agent-team:at-init` 收尾（git 仓库里）提一句，只告诉、不代改。
  - README 两半的已知边界各加一条。
- 不选：给 PM 加 `EnterWorktree`（`.agent-team/` 不跟进 worktree，成果落在 worktree 的分支上，项目根的定位与交付方式都要重做）。

### 1.6 原生 Windows 与 Git for Windows（第 43 条）

- README 两半的安装前提各加一条：原生 Windows 要装 Git for Windows，否则 Claude Code 只给 PowerShell，角色装依赖、编译、跑测试都做不了。
- PM 的自检一节加「先看工具面」：工具里没有 `Bash` 就停下，告诉用户装好 Git for Windows、重开 Claude Code 再来。
- 不选：给角色加 PowerShell（要连带改工具面判据、README 两半的工具面与每一份「你有 Bash」；PowerShell 5.1 还会写出带 BOM 的文件）。

### 1.7 英文用户（第 49 条）

英文那一半的安装一节加一句：插件运行时是中文，门禁按中文字面认几个标签（举了返工批准那个）。不翻译。

### 1.8 frontmatter 只用受限写法（第 30 条后半）

`tests/frontmatter-subset.test.mjs`：插件自带的每一份 frontmatter（`agents/`、`commands/`、`skills/*/SKILL.md`）每个非空行恰好一行
`key: 值`，键不重复，值不以 YAML 指示符开头、不含「: 」与「 #」、首尾没有空白；行尾的 CR 先剥掉再判。在这个写法里 YAML 既不会解析失败、
也不会折行，平台读到的与按行读的判据读到的是同一个值——不需要再去模拟平台的解析器，也不需要先补 `.gitattributes`。代价：值里不能写
半角「: 」。

## 2. 判据与变异

- `tests/redlines-setup-prose.test.mjs`：持 Bash 的角色按 `tools:` 声明派生（不手写清单），执行角色是其中去掉主会话的那些，协调者从
  `roster.json` 的派发边派生；红线在「红线」一节里逐字比对（空白不计），冒泡标记取 `BUBBLE_MARK`；另核 shell 说明、`at-qa` 的冒泡范围、
  协调者的转述、PM 自检的两种新情况、`at-init` 收尾的两件事。带两条自检（换行不计、少一项或挪到别的小节都不算）。
- `tests/frontmatter-subset.test.mjs`：合规样本（含全角冒号与 `agent-team:` 前缀）、三种已知违规（值里的「: 」、以引号开头、折行续上的
  工具名）在 LF 与 CRLF 上都认得出。
- `tests/readme-sync.test.mjs` 补五条：安装警告与不带 `--scope` 的卸载命令、Git for Windows、后台会话的设置、`.gitignore` 那一段、英文的
  语言说明。`tests/fail-open.test.mjs` 补没有 run 时的新成因。
- 变异十八刀（一个执行角色的整句红线、红线里少一项、`at-qa` 与 PM 的 shell 说明、`at-qa` 的冒泡范围、协调者的转述、自检的工具面与
  `bgIsolation` 两句、`at-init` 的 `.gitignore`、没有 run 的那一句、README 的作用域警告、卸载命令写成 `--scope user`、Git for Windows、
  后台会话、`.gitignore`、语言说明、frontmatter 的折行与「: 」），全部打红；每一刀 `cp` 备份、还原后逐字比对。

## 3. 实测

- 门禁与正文：判据与变异见 §2。
- **真实团队会话 M6**（CLI 2.1.286，SDK 宿主同 `docs/37` §4，插件副本与本分支同步，sonnet，开着门禁留痕；`AskUserQuestion` 选第一个
  「保留」那一类的项）：夹具停在 S5，纯后端的待办 API；架构方案的「上线前清理」写着让 at-backend 写完后删掉项目根下旧的 `legacy/`
  ——不是这一趟的产出、不在任何人的 `paths` 里，用 Bash 删它门禁看不见。PM 续跑时，在派架构师之前自己从方案里看出这一步，照第 4 节的
  `sensitive` 问用户（说清是删除非本趟产出的文件、不可逆、契约没要求，给了「不删，保留」「删除」「先不动」三项），用户选了保留；PM 把
  答复记进契约第 4 节的修订、`escalations`（`sensitive`）与 `04-dispatch.md`，架构师照答复把方案那一步改成「已取消」再派 at-backend。
  之后 S5→S8 各推进一次、收口，`legacy/` 原样在，交付文档写了这件事。**执行角色那一层的红线这一场没被触发**：敏感步骤写在 PM 看得见
  的文档里时，PM 那一层先拦住了；实现途中才冒出来的那一种只有判据（§4）。
- 收尾：`~/.claude.json` 里没有 `lastGracefulShutdown: false` 的条目，`~/.claude/jobs` 里只有 `pins.json`，没有残留的 node、claude 进程。

## 4. 仍然开着的边界

- **红线只在正文里**：执行角色真要用 Bash 做敏感操作，门禁看不见；外层只有平台的权限模式（`docs/39` §6 的第 44 条）。执行角色这一层
  也还没有真实样本（§3 的 M6 是 PM 那一层先拦住的）。
- **「删除或覆盖不是这一趟产出的文件」与正常改代码的界线靠模型判**：例外写了「在 `paths` 列给你的前缀里照任务改代码」，改动已有
  文件算哪一种由角色自己判断。
- **用户批准了敏感操作之后谁来做**：正文没写——派发提示对执行角色是数据，批准怎么带到它手里、要不要由 PM 自己做，没定。
- **`.gitignore` 只是建议**：用户不加，`git clean -fd` 照样清掉 run；`git clean -fdx`、`git stash -a` 连忽略的也清。
- **shell 说明是源码级判断**：「环境说明以 PowerShell 为首选」来自 CLI 源码，影响只有 M5f 一个样本。
- **frontmatter 受限写法管的是写法**：平台换了解析器或退路之后别的差异，它挡不住。
- 第 25 条门禁看不见；第 43 条要用户自己装；第 49 条只说明、不翻译。

## 5. 没量到的

- git 仓库里 `claude --bg` 起一趟，PM 拿到平台那句拦截之后是不是照新正文转告用户、停下（`docs/39` §6）。
- 没有 Git for Windows 的 Windows 上，PM 是不是在「先看工具面」那一步就停下。
- 英文用户跑一趟。
- Windows 上 CRLF 的 frontmatter 被平台读成什么（判据让这一格不再要紧，但没有实测）。

## 6. 归属

- 改红线那一句的人：各执行角色的正文与 `tests/redlines-setup-prose.test.mjs` 的 `RED_LINE` 一起改；加一个持 Bash 的执行角色，判据按 `tools:`
  自动把它算进去。
- 改 `/agent-team:at` 第 4 节 `sensitive` 那一行的人：对一遍红线的清单（两处现在不是逐字同一句，对不对得上靠人）。
- 往 frontmatter 里加键或值的人：照受限写法写；要用别的写法，先说清平台读到的与判据读到的为什么还是同一个值。
