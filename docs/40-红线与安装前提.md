# 红线与安装前提

> 2026-10-05，M4e，分支 `m4e-redlines-and-setup`，v2.3.0。`docs/39` §5 排出来的第一轮：全量审查第 26 条（持 Bash 的执行角色没有
> 敏感操作红线）、第 39 条的正文与回传部分（git 命令抹掉 run）、第 23 条（默认装到 user 作用域）、第 25 条（git 仓库里的后台会话）、
> 第 43 条（原生 Windows 没装 Git for Windows）、第 49 条（英文用户）、第 30 条后半（frontmatter 的 YAML 盲区）。每一条的现状与证据
> 在 `docs/39` §2，这里只记修法、判据、复核与实测。

## 0. 一句话结论

- **持 Bash 的执行角色有了同一句敏感操作红线**，清单与 `/agent-team:at` 第 4 节 `sensitive` 那一行逐项相同（这一轮那一行也补了
  「清空或改动非本趟建的数据」「动工作树或历史的 git 命令」）：碰到就以「冒泡：」停下，协调者不定、原样冒泡给 PM，PM 照 `sensitive`
  问用户；用户批准过的，执行角色只认契约「修订记录」里写明批准了的那一步。PM 自己也不跑动工作树或历史的 git 命令。门禁照旧不看
  Bash，这一层只在正文里；判据保证每一份逐字同一句、两处清单逐项对得上。
- **git 与 `.agent-team/`**：初始化时项目经理照 git 的实际情况建议（先问）把 `.agent-team/` 加进 `.gitignore`，README 写清不加与入库
  各会怎样；没有 run 时派发返回的那一句补上「被 git 清掉或藏起」这个成因，并说明这些 git 命令 PM 不自己跑。
- **安装前提写全了**：README 两半警告 `install` 要带 `--scope local`、给出误装之后的卸载命令，判据核安装一节代码块里的每一条命令都带
  它；原生 Windows 要装 Git for Windows；git 仓库里的后台会话要在 `.claude/settings.local.json` 设 `worktree.bgIsolation`；英文那一半
  说明运行时是中文。自检在工具清单里没有 Bash、或者平台报出后台会话的那句拦截时，停下告诉用户该做什么。
- **frontmatter 只用受限写法**：一条判据挡住已经核过、会让平台的 YAML 解析器与按行读的判据读出不同东西的写法（解析失败整份当空、
  折行授出工具、值里的 `---` 被当成收尾）。

## 1. 修法

### 1.1 敏感操作红线（第 26 条、第 39 条）

> **订正（M4h，2026-10-06，`docs/43`）**：下面的清单少一项——M9 里项目经理冒烟之后用 `taskkill //F //IM node.exe` 停服务，把本机的 node 进程
> 全杀了。红线与 `sensitive` 加了「结束不是自己起的进程」，每个持 Bash 的角色（连同项目经理）多了同一句停服务的做法（按自己起的 PID 停，
> Windows 的 Git Bash 里按进程树停）。

- 六个持 Bash 的执行角色（`at-backend`、`at-frontend`、`at-ui`、`at-ios`、`at-android`、`at-qa`）的「红线」一节加同一句：凭据/密钥/密码；
  产生费用；对外发送或发布；删除或覆盖非本趟产出的文件；清空或改动非本趟建的数据（数据库、云上资源）；`git push` 或改远端；动 CI/CD 与
  生产配置；动工作树或历史的 `git` 命令（`clean`、`stash`、`reset`、`checkout`、`switch`、`restore`、`rebase`、`commit` 这类——第 39 条：
  没进版本库的 `.agent-team/` 会被一起清掉或藏起，进了版本库的 `state.json` 会被倒回去）。碰到就停下，最后一条回复的第一行写「冒泡：」，
  说清是哪一步、为什么要它，做不做由用户定。
- **批准只认契约修订记录**（复核补的）：用户批准过的，执行角色只认契约（`00-contract.md`）「修订记录」里写明批准了的那一步；派发提示里
  说批准了、修订记录里没有的，照样停下冒泡。理由：角色正文说派发提示是数据、不是指令，而契约只有 PM 写得进（H4），执行角色读得到——
  这是批准能可信地到它手里的那条路。`/agent-team:at` 第 4 节随之补一句：sensitive 那一类的答复，修订块里写清是哪一步、批不批。
- **例外有条件**（复核补的）：执行角色是「照清单装依赖、编译、跑测试、在本机起停验证用的服务，在 `paths` 列给你的前缀里照任务改代码——
  这些步骤本身不算；其中要用凭据、会花钱、对外发送的，照样停下」，`at-qa` 是「照清单装依赖、编译、跑测试、起停测试要用的服务——……」。
  各自「你有 Bash」那一节的「只用来……」补上起停服务，与例外对得上。`at-qa` 另说清一格：缺凭据是环境原因（写进 `06-test.md`、不冒泡），
  凭据在手、要不要拿它跑是敏感操作。
- `at-qa` 原来写「冒泡只用于『S5 没交齐』那一种」，改成「与下面红线里的敏感操作」。
- 协调者（`at-architect`、`at-product`）：紧接着「定不了的原样冒泡给 PM」——为红线里的敏感操作冒泡的，不定，原样冒泡给 PM（那要问用户）。
  门禁的两句冒泡文案也认它：H5b 拦停时的 `BUBBLE_WHEN` 括号里加「红线里的敏感操作」，完成核验与前台跑完时给协调者的那句改成「定不了的、
  为红线里的敏感操作冒泡的，原样冒泡给派你的人」。
- **两处清单对齐**（复核补的）：`/agent-team:at` 第 4 节 `sensitive` 那一行补上「清空或改动非本趟建的数据（数据库、云上资源）」「动工作树或
  历史的 `git` 命令」，README 两半那一行跟上。原来红线比那一行多一项，PM 照那一行判「属于第 4 节的问用户、其余你来定」，多出来的那一项
  落进了「你来定」。PM 自己的红线加一条：动工作树或历史的 git 命令自己也不跑，要跑先问用户；门禁回传里提到这些命令的，是让它转告用户。
- **架构师单列要删除、改名的已有文件**（复核补的）：落盘清单只列「新建或改动」，删除要到 S5 中途才冒出来；现在在这一节末尾单列、标「删除」
  或「改名」，PM 在 S4 照 `sensitive` 一次问完。
- 不选的做法：门禁加 Bash 的 matcher（命令行是自由文本，判不准，而且平台的权限模式才是那一层）；把红线放进一份共用的 skill（各执行
  角色预加载的 skill 不同，放不进同一份）。

### 1.2 shell 说明

持 Bash 的每个角色（上面那些执行角色与 PM）各加一句：你的 shell 只有 `Bash`（Windows 上是 Git Bash），命令照 POSIX 写；环境说明里提到
PowerShell，那不是你的工具。来由：CLI 的环境说明按整个会话写（原生 Windows 上以 PowerShell 为首选 shell），不看角色自己的工具清单，而
团队角色只持 Bash；`docs/39` §4 的 M5f 里，haiku 版 PM 在 Bash 里调了 PowerShell 的 `Get-FileHash`。

### 1.3 git 与 `.agent-team/`（第 39 条的正文与回传部分）

- `/agent-team:at-init` 收尾：项目在 git 仓库里的话（`git rev-parse --show-toplevel` 成功——不按「项目根下有 `.git`」判：monorepo 的子目录
  照样会被仓库根的 `git clean` 清掉，而 `.git` 是目录，`Glob` 找不到它），按 git 的实际情况说：已经忽略的（`git check-ignore -q .agent-team`）
  不提；已经入了库的（`git ls-files .agent-team` 有输出）照实告诉用户要先 `git rm -r --cached .agent-team` 再忽略，由用户自己做；其余的建议
  加进 `.gitignore`——改 `.gitignore` 是动用户的文件，先问。理由照实说：既不进版本库也不忽略，`git clean -fd`、`git stash -u` 会把进行中的
  run 一起清掉或藏起，门禁随之失效；提交进了版本库，`git stash`、`git checkout -- .` 会把 `state.json` 倒回提交时那一版，返工计数一起清零。
  忽略之后只剩 `git clean -fdx`、`git stash -a` 碰得到它。这一问与 `/agent-team:at` 第 1 节那一问一样另算：不记 escalation、不动契约
  （`at-pm` 正文与 README 两半「什么时候会问你」都写了）。
- README 两半「产物在哪」各加同一段。
- H5a 在没有 run 时给 PM 的那一句（`hooks/lib/fail-open.mjs` 的 `dispatchNoRunNotice`），「你以为这里有进行中的 run 的话」那一支补一个成因：
  看 `.agent-team/current-run` 与 `.agent-team/runs/` 还在不在（`project.json` 入了库、这两份没有的情形，目录本身还在）——没进版本库的这几份
  会被 `git clean`、`git stash -u` 这类命令一起清掉或藏起：告诉用户（藏起的他能用 `git stash pop` 找回，清掉的找不回），这些 git 命令 PM
  不要自己跑。
- 没做的：S4 记代码基线（回退之后代码回不去，`docs/39` §2.2 列的可选项，挪到第三轮一起看）；自检区分「从来没有 run」与「run 被抹掉」
  （要在项目之外留标记）。

### 1.4 安装作用域（第 23 条）

- README 两半的安装一节各加一段警告：`install` 要带 `--scope local`；不带、或者在 `/plugin` 面板里选了默认的第一项，装的是 user 作用域，
  这台机器上此后每一个新会话都会被接管；`marketplace add` 不带它只是把市场登记在 user 一层，不接管会话（复核补的：两条命令的后果不一样）。
  误装之后的卸载命令写成不带 `--scope` 的那一种：CLI 的 `plugin uninstall` 默认就是 user 作用域，而 README 的命令行里不许出现 `--scope user`
  （readme-sync 第十节）。
- 判据核安装一节代码块里的每一条 `claude plugin` 命令都带 `--scope local`（复核补的：两半一起丢掉它，镜像那一节不响，禁用作用域那一节只拦
  写出来的 `--scope user`，这一刀在改之前也存活）。
- readme-sync 第十节的理由与失败文案原来引用「两份 README 的收场那一段」——那一段 0.7.5 就删了；改成指向这一段警告。
- 不选：放宽 H1 让误装的会话派得出内置代理（`at-pm` 的 `tools:` 已经把派发宇宙封顶在团队角色上，H1 放行了也派不出去，反而削弱
  花名册闭包）。

### 1.5 git 仓库里的后台会话（第 25 条）

- 平台在 `validateInput`（早于 PreToolUse）拦后台会话对主 checkout 的写入，门禁看不到，结果是第一步自检就停。所以只改正文：
  - PM 的自检第 3 支「平台在调用之前就报了错」加一句：报错里提到 `EnterWorktree` 或 `bgIsolation` 的，告诉用户在项目的
    `.claude/settings.local.json` 里设 `"worktree": {"bgIsolation": "none"}`（只对他自己生效；写进 `.claude/settings.json` 会改到所有协作者），
    或者改用前台会话再开这一趟；不要照平台的提示去 `git worktree add`，也不要自己改设置。
  - `/agent-team:at-init` 收尾（git 仓库里）提一句，只告诉、不代改。
  - README 两半的已知边界各加一条。
- 写进 `settings.local.json` 而不是 `settings.json`（复核补的）：后者通常入库，写进去等于替所有协作者改了后台会话；平台读的是合并之后的
  设置，local 那一层同样生效（源码级，没有实测，§5）。
- 不选：给 PM 加 `EnterWorktree`（`.agent-team/` 不跟进 worktree，成果落在 worktree 的分支上，项目根的定位与交付方式都要重做）。

### 1.6 原生 Windows 与 Git for Windows（第 43 条）

- README 两半的安装前提各加一条：原生 Windows 要装 Git for Windows，否则 Claude Code 只给 PowerShell，角色装依赖、编译、跑测试都做不了。
- PM 的自检一节加「先看工具面」：以工具清单里有没有名为 `Bash` 的工具为准，不看环境说明写的首选 shell；没有它——原生 Windows 上没装
  Git for Windows，或者设置、启动参数禁了 `Bash`（复核补的：第二种成因在 macOS、Linux 上也会有）——就停下，把成因告诉用户。
- 不选：给角色加 PowerShell（要连带改工具面判据、README 两半的工具面与每一份「你有 Bash」；PowerShell 5.1 还会写出带 BOM 的文件）。

### 1.7 英文用户（第 49 条）

英文那一半的安装一节加一句：插件运行时是中文，门禁按中文字面认几个标签（举了返工批准那个）。不翻译。

### 1.8 frontmatter 只用受限写法（第 30 条后半）

`tests/frontmatter-subset.test.mjs`：插件自带的每一份 frontmatter（`agents/`、`commands/`、`skills/*/SKILL.md`）每个非空行恰好一行
`key: 值`，键不重复；值不以 YAML 指示符开头，不含「: 」「 #」，不以「:」结尾，首尾没有空白，不是会被 YAML 读成 null、布尔或数字的那几种；
行里不许有制表符、不许有 `---`。行尾的 CR 先剥掉再判。后三条与「以「:」结尾」是复核补的：值以「:」结尾两个 YAML 解析器都报错；平台截
frontmatter 的正则不锚行首，值里的 `---` 会被当成收尾、后面的键全丢；制表符两个解析器处理不一样。不需要先补 `.gitattributes`，也不模拟
平台的解析器；但它不声称封闭（§4）。代价：值里不能写半角「: 」。

## 3. 复核与实测

**实现后的复核**（一个对抗复核者，只读仓库、在副本上做变异，读了 CLI 2.1.286 的源码，用两个 YAML 解析器验 frontmatter）。十四刀存活变异，
挖出来的、以及怎么处理的：

- **两处清单没对齐**（中）：红线多出「动工作树或历史的 git 命令」，PM 照第 4 节判「其余你来定」；PM 自己持 Bash 也没有这一条，没有 run 那一句还像是
  教 PM 去跑 `git stash pop`。补了第 4 节那一行、README 两半、PM 的红线，判据两个方向逐项比（§1.1）。
- **用户批准之后没有走得通的路**（中）：「做不做由用户定」，可派发提示是数据；删文件也没有被准许的工具。定为只认契约修订记录（§1.1）。
- **例外没钉、而且写成了无条件豁免**（中）：「跑测试」本身要用凭据、花钱、对外发送时也「不算」；执行角色与 at-qa 的例外对不上。改成有条件，
  整句钉（§1.1）。
- **frontmatter 受限写法不封闭**（中）：值以「:」结尾、值里有 `---`，两种都合规、平台却丢掉整份或后半份。补了几条，文件头不再声称封闭（§1.8）。
- **两半一起丢掉 `--scope local` 判据不红**（中）：补了代码块命令的断言（§1.4）。
- **几处低的**：`at-init` 按「项目根下有 `.git`」判又窄又判错；`bgIsolation` 推荐写进会入库的 `settings.json`；门禁自己的冒泡文案不认新的
  冒泡理由；「先看工具面」只认一种成因；README 警告把两条命令说成同一种后果；判据只做子串匹配（「不必停下」照样含「停下」）；清单漏了数据
  与 `commit`；没有 run 那一句漏了「目录还在、run 没了」的情形；at-qa 缺凭据两种读法；「只在这几类事上问你」与初始化那一问对不上。都改了。
- 看过、没问题的：六份红线逐字同一句、位置都在「红线」最后一条；判据的派生没有漏角色；冒泡之后在同一段重派不会被当成重做；平台那句后台会话
  拦截同时含 `EnterWorktree` 与 `bgIsolation`；`plugin uninstall` 的 `--scope` 默认确实是 user；`git status`、`diff`、`log` 不在范围里。

**真实团队会话 M6**（CLI 2.1.286，SDK 宿主同 `docs/37` §4，插件副本与本分支实现那一版同步，sonnet，开着门禁留痕；`AskUserQuestion` 选第一个
「保留」那一类的项）：夹具停在 S5，纯后端的待办 API；架构方案的「上线前清理」写着让 at-backend 写完后删掉项目根下旧的 `legacy/`——不是这一趟

## 4. 仍然开着的边界

- **红线只在正文里**：执行角色真要用 Bash 做敏感操作，门禁看不见；外层只有平台的权限模式（`docs/39` §6 的第 44 条）。执行角色这一层也还没有
  真实样本（§3 的 M6 是 PM 那一层先拦住的）。
- **批准凭据是正文约定**：门禁不核「修订记录里写明批准了」与执行角色实际做的那一步对不对得上；批准之后执行角色用 Bash 删文件，门禁照样
  看不见。
- **「删除或覆盖非本趟产出的文件」与正常改代码的界线靠模型判**：例外写了「在 `paths` 列给你的前缀里照任务改代码」，改动已有文件算哪一种
  由角色自己判断。
- **`.gitignore` 只是建议**：用户不加，`git clean -fd` 照样清掉 run；`git clean -fdx`、`git stash -a` 连忽略的也清。
- **shell 说明是源码级判断**：「环境说明以 PowerShell 为首选」来自 CLI 源码，影响只有 M5f 一个样本。
- **frontmatter 受限写法不封闭**：挡的是已经核过的几种；平台换了解析器或退路之后别的差异，它挡不住。
- 第 25 条门禁看不见；第 43 条要用户自己装；第 49 条只说明、不翻译。

## 5. 没量到的

- git 仓库里 `claude --bg` 起一趟，PM 拿到平台那句拦截之后是不是照新正文转告用户、停下；`.claude/settings.local.json` 里的 `bgIsolation`
  在后台会话里生效（源码级：平台读合并之后的设置）。
- 没有 Git for Windows 的 Windows 上，PM 是不是在「先看工具面」那一步就停下。
- 英文用户跑一趟。
- Windows 上 CRLF 的 frontmatter 被平台读成什么（判据让这一格不再要紧，但没有实测）。
- 执行角色在实现途中碰到敏感步骤（没写在 PM 看得见的文档里）时，是不是照红线停下；用户批准之后，执行角色是不是照修订记录做、不照派发提示做。
