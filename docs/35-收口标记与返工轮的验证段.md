# 收口标记与返工轮的验证段

**日期** 2026-10-02 ｜ **口径** 分支 `m4a-closed-run-and-accepted`（`1882c8c` 与其后的复核修订），版本 `1.9.0`；修的是 2026-10-01 那次「还开着的条目」核验
新发现的两处（都在常用路径上，都是 1.7.0、1.8.0 带出来的副作用），外加全量审查（`docs/24-附录-全量审查报告.md`）第 24 条的修法 2（收口标记）与
24-1 的正文一半。真实会话在本机 CLI 2.1.286 上。

## 0. 一句话结论

一趟走完之后用户在同一会话里要改一处，门禁原来把它当成旧 run 的重做、只给「记回退」，最省事的路成了 PM 自己写代码；返工轮里门禁自己把
「把上一轮的 `06-test.md` 标 accepted」列成出路，标了之后没测过的改动进了验收。现在：`state.json` 有了收口标记 `closed_at`，收口那一次由 H6 核
最后一段的前置与产物，收口之后这一趟冻结、不再派人，交付之后的新改动另起一趟；`stages.json` 的 S6、S7、S8 是验证段（`"verifies": true`），
它们的产物在返工轮里一律重新出，H6 不许标 accepted，每一处回传都不再给这条路。

## 1. 问题（核验原文的复现）

**问题 A：交付之后，同一会话里接着要求改一处。** 一趟走完（`stage` 是 S8，交付快照已拍）之后：PM 派 `at-architect` 放行，H5a 回「刚返回的
at-architect 不是当前阶段的执行者……或者这次派发本身不该发生……若是返工记回退」；架构师派 `at-backend`，H2 拒「不记回退重做 S5……冒泡」；
PM 派 `at-qa`，H2 拒「先记一次回退（回到 S6），再派它」；PM 自己写 `src/`，三道都放行。每一条理由都不提「这一趟已经走完，新改动另起一趟」。
照理由做，新需求塞进旧契约、吃旧 run 的返工额度；不照做，最省事的路是 PM 自己写代码，绕过测试与验收。另外，没有收口标记，【阶段】对走完的
run 反复说「该收口了」（审查第 24 条-2）；收口本身不经任何门禁（`docs/33` §4「收口不经 H6」；审查第 17 条-5：交付文档缺了没人发现）。

**问题 B：返工轮里门禁自己给出「把上一轮的 `06-test.md` 标 accepted」。** S6 测试不过回到 S5，后端改代码并重写实现记录，推进到 S6。异步派
`at-qa` 那一刻，H5a 给 PM 的第一条出路是「这一轮接受上一轮那份原样，就……改成 accepted」。PM 标了：H6 放行，【阶段】说 S6 齐了，`at-qa` 不重测
原样停下（H5b 放行），S6→S7 放行，派 `at-acceptance` 放行。同一次写入里标 accepted，S5→S7 直接跳过 S6 也放行。H6 的推进拒绝理由、H2 的前置
拒绝理由、ledger 的【返工】都把「标 accepted」列成出路。

## 2. 修法

### 2.1 验证段（`stages.json` 的 `verifies`，`hooks/lib/stages.mjs` 的 `isVerifyStage`、`mayAcceptProduct`）

S6、S7、S8 写着 `"verifies": true`：这一段的产物是对上游当时那一版的结论（测试报告、验收报告、交付报告），返工轮里上游可能已经变了，上一轮
那份不再对应现在的东西，所以一律重新出。

- H6：所在段（链上最早产出它的段）是验证段的产物，`rework_base` 里不许从 sha 改成 `"accepted"`——回退那一次写入（`decideAtRestart`）与之后的
  写入（`decideCarry`）同一条。别的产物照旧（不晚于写入后 `stage`）。已经落盘的、验证段产物标过 accepted 的旧 run 原样带着，只判这一次的改动。
- 每一处给出「标 accepted」出路的回传（H5a、H5b、H2 的前置、推进拒绝理由、【返工】、补记提示）都经 `splitByAccept` 把还旧的分成两组：能标的
  照旧给两条出路，验证段的只给「产者这一轮重跑之后重写」（`hooks/lib/freshness.mjs` 的 `VERIFY_REDO`；H5b 对产者本人说，用 `VERIFY_REDO_SELF`，
  并说明重跑结果与上一轮相同时也要写明这一轮在哪一版上跑的、跑了哪些）。
- 补记（回退之后同一次写入又往前记）照推进核离开的段；补记跨过验证段的直接拒、叫它拆开写（先只记回退）；一次写入只许记一次回退。

### 2.2 收口标记（`state.json` 的 `closed_at`，`hooks/lib/closing.mjs`）

- 模板初值 null（没收口）；收口时写收口那一刻的 ISO 时间。「收没收口」只问 `closedAt`：只认 ISO 形状的时间（`"null"`、`"false"` 之类按形状拒，
  理由引出原值）。缺这个键的旧 run 当作没收口。
- H6（排在返工预算与回退快照之前，`decideClosing`）：形状；**冻结**——写入前已收口，`closed_at`、`stage`、`history` 的条数都不许再改（不依赖阶段链，
  别的记账字段照常能补）；**关上**——写入后收口、写入前没收口（读不出来也算）：阶段链读得出（读不出来就拒，单向门）、`stage` 是最后一段、写入前读得出
  时这次不往 `history` 追加、最后一段的 `requires` 与 `produces` 都在、不是空文件、读得出、不是上一轮的。`requires` 由整段裁掉、而且这一趟在那一段
  一个都没叫过的段产出的不要求。拒绝理由逐份按情形给出路：缺的派产者补交（不用记回退）、从没叫过的可以补记进 `trimmed`、叫过没交的点明
  `trimmed` 不是出路。
- H2（排在就绪与重派判据之前，`decideClosedDispatch`）：收口之后派花名册里的任何角色都拒——PM 收到另起一趟的两条路（请用户用
  `/agent-team:at <改动>`，或者照 at.md 第 0–2 节自己建，契约第 1 节逐字照抄用户提出这次改动的那几条消息）；最后一段、没收口时派协调者拒。
  叶子角色交给重派判据，在最后一段的拒绝理由先给「收口、另起一趟」。
- ledger：已收口的 run 不发【阶段】【返工】【返工预算】；最后一段齐了、没收口时，收得了口说「该收口了」，收不了口列阻碍（与 H6 同一份
  `closeBlockers`）。【产者交代】在已收口的 run 上不叫 PM 派人，在最后一段对只能经协调者派的角色给出记回退那条路。返工批准的记录器在已收口的
  run 上不记。H5a「不是当前段执行者」那一格在已收口的 run 上不发；H3 的重做拒绝理由改说已经收口。
- `validateState` 核 `closed_at` 的形状与「只在最后一段」；修坏 `state.json` 的修法保留 `closed_at`；链不变量的理由指向 `closed_at`。

### 2.3 正文

`/agent-team:at` 第 1 节建 run 之前先看 `current-run` 指着的那一趟：`closed_at` 是一个时间的直接建；停在最后一段、没收口的先看验收过没过、
交付文档写了没有，收得了口就替它收口再建，收不了口就和停在更早段的一样问用户续跑还是放弃（审查 24-1 的正文一半；这一问不在五类里，
不记 escalation）。第 3 节「回退」：验证段的产物不能标 accepted；补记跨过验证段要拆开写；一次 Write 只记一次回退。第 6 节收尾整节重写：
验收没过不收口 → 先算 `never_invoked` → 写交付文档 → 同一次 Write 记 `never_invoked` 与 `closed_at` → 没被 H6 拒就是收好了（收口成功不另发回传）；
收口之后冻结，新改动另起一趟；用户明说直接改的照办并告诉他不经测试与验收。`at-resume`、`at-status`、`at-pm`、`at-qa`、`at-acceptance`、
`stages.README.md`、规格、README 两半同步。

## 3. 设计评审与复核

**设计评审**（五个视角：收口把关、accepted 规则、PM 逐帧走流程、更简单的设计、失败策略与判据计划，各配一名复核者）推翻了草案的两处：

- 草案的规则 R1（「上游这一轮改过的，不许标 accepted」）站不住：标了 accepted 就覆盖掉快照里的 sha，R1 再也看不出它改过（一次写入、两步走、
  回退那一次标都能绕过）；每次回退「这一轮」从头算（原地回退、回 S6 补跑测试）；回到的那一段之前各段的改动看不见（S6 直接依赖 `03-arch.md`、
  `04-dispatch.md`）；中间各段又过严（这一轮裁掉的产者的旧记录只能把它再派出来）。改成按段的属性判（`verifies`）：不看基线、不看「这一轮」从哪
  算起，这几条一起关掉；中间各段由 PM 判断，兜底是验证段必须重出。
- 草案的收口后拒派只认 `closed_at`：没写标记的 run（升级前交付的、忘了收口的）问题原样还在。改成最后一段没收口时拒派协调者。
- 另外：冻结挪到 H6 最前面（否则已收口的 run 上记回退，PM 先被引去「问用户批准再返工一轮」，记录器还真把批准记下了）；「收没收口」定成单一
  谓词；被认可的裁剪（裁掉 `at-qa`、`at-acceptance`）不能让收口永远过不去；`/at` 第 1 节先分流已经走完的 run。

**实现后的对抗复核**（第一轮五个视角：收口门禁、验证段规则、逐帧走流程、变异验证、契约与正文；每个视角的发现再由一名独立复核者复现或驳倒）。
没有 high；成立、修了的：

- 正文用「有 `closed_at`」判收口，可模板让每一趟新 run 一开始就带着 `"closed_at": null`；第 1 节把「停在最后一段、没收口」一律当已交付、不问
  就另起，与 at-pm 的红线、第 6 节第一步、H2 的拒绝理由口径相反（验收没过的那一趟会被悄悄丢下）。
- 收口那一次才补写 `trimmed`，就能豁免一个在那一段被叫到过、却没交的产者（等于用 `trimmed` 绕过一份没交的测试报告）。改成只豁免这一趟在那一段
  一个都没叫过的；从没叫过的，拒绝理由给补记 `trimmed` 这条路（项目本来就不用 `at-qa` 时原来只给「派它补交」）。
- `closed_at` 写成 `"null"`（`at.md` 专门提醒不带引号的那个笔误）被当成一次收口，理由叫 S1 上的 PM「先推进进 S8」。改成只认 ISO 形状的时间。
- 已在 S8 时收口那一次多追加了一条 `history`，理由叫它「先单独一次 Write 推进进 S8」——照做就是原地回退、吃一轮不可逆的返工。
- 补记跨过验证段（回到 S5 又记到 S7）：快照照写入那一刻的磁盘拍，区间里的产物按定义都是上一轮的，验证段的又不能标——理由却叫产者「重跑之后
  再推进」，照做是死循环。一次写入追加了不止一条回退（`[S5, S7, S7]`）：快照只拍最后那条，前面那截不经推进核查。
- 已收口的 run 照样发【返工预算】叫 PM 问用户（记录器不记、H6 拒）；最后一段的【产者交代】叫 PM 派只能经协调者派的 `at-ui`（H2 在最后一段
  拒派协调者）；收口成功那一次没有回传，正文却三处写「收到回传之后再汇报」；`at-acceptance` 说「只追加一句会被拦」，门禁其实放行（按 sha 判，
  内容一变就算这一轮的）。
- 判据：H6、H2 里「收口判据排在前面」这两处顺序把前后对调全量照样绿；一批文案分支改了也全绿。补了判据。
- 变异：对 `1882c8c` 的判定逻辑做了 101 个变异，68 个打红、33 个存活。存活的 12 个是等价变异（在插件自带的阶段链下：没有产物由两段产出、S8 的
  前置来自单产者段、验证段的产物里没有 `.html` 等），1 个只在纯函数层面没钉住、门禁级等价（冻结判据只拦变长，`decideRework` 也拒截短；补了纯函数格），
  20 个不等价——19 个补了判据（`tests/*` 里「复核」开头的那几条），剩下 G07（ledger 的收口阻碍把「在、却读不出来」算成齐了）在子进程里造不出
  「在、却读不出来」的产物，登记在 §5。

第二轮复核（修订之后）：见 §3.1。

### 3.1 第二轮复核

对第一轮修订（`c11ef3f`）再做一轮（三个视角：修订改到的门禁代码路径、正文与逐帧流程、修订代码的变异验证，各配复核者）。没有 high；成立、修了的：

- **空文件的口径只在收口那一处**（三个视角都找到）：收口拒绝理由叫 PM「派它补交、不用记回退」，可交付快照把空文件当成交过，H2 拒重派、
  H3 拒重写——出路自相矛盾。改成一个谓词（`hooks/lib/text-norm.mjs` 的 `isBlankText`：归一化之后去掉空白什么都不剩）：收口、交付快照、
  「交过」都经它；只有换行、空白的也算空。
- **「叫没叫过」只看写入后的 state**：收口那一次把 `at-qa` 从 `stage_roles` 的 S6 挪走、或者旧 run 新加一个 `stage_roles`，就把叫过的翻成没叫过；
  旧 run 照拒绝理由「并进 stage_roles」去做，同样会翻过去。改取写入前后的并集；旧 run 的补交只叫它并进 `roster`。
- **最后一段的【产者交代】没修干净**：只给「PM 派不到的」补了一句，架构师、产品这两个协调者 PM 派得到，② 仍说「派出去」，H2 在最后一段照拒。
  改成问 `decideClosedDispatch` 同一个判定，驱动者本人不算，花名册读不出来不说。
- **补交之后直接收口**：正文、H6 与 H5a 都领 PM 补交完就收口，跳过「读验收结论」与「重写交付文档」，验收不通过照样收得了。改成从第 6 节第一步重走。
- 补记跨验证段的拒绝只算快照里真有产物的验证段（整段裁掉了 `at-qa`、`at-acceptance` 的项目原来被错拦）；`08-delivery.md` 还旧时说「你自己这一轮重写」；
  已收口的 run 上改坏 `closed_at` 说「原样带着」（原来叫它写 null，照做又被冻结拒）；第 1 节替旧 run 收口要连同算 `never_invoked`、回复里告诉用户。
- 变异：对 `c11ef3f` 改到的判定做了 67 个变异，43 个打红、24 个存活：2 个完全等价，4 个在插件自带的阶段链下等价（最后一段的前置都来自单产者段——
  补了一条前提判据，链一变就红），18 个不等价，补了 17 个的判据（其中两条守的正是这一轮修掉的洞：一次写入里追加两条回退时链外条目要跳过、
  补记跨验证段的区间包含回到的那一段）。剩下一个是这次之前就有的括注条件，变异后的写法同样无害。

## 5. 仍然开着的边界

- **PM 自己写项目代码**：主线程的写豁免是整套设计的前提，收口之后照样写得进；正文写明交付之后的改动另起一趟，用户明说直接改的照办并告诉他不经测试与验收。
- **Bash**：用 Bash 改 `state.json`（去掉 `closed_at`、改 `stage`）、往验证段的产物里追加一句，都不经门禁。门禁按内容判新旧，看不出测试跑没跑——
  「只追加一句「核过」不算」是给角色的规矩，不是门禁的判据。
- **运行上下文读不出来时的派发**（`project.json` 写坏、`stages.json` 读不出来）：H2 对已收口 run 的拒派与别的就绪判据一样 fail open；被派出去的角色
  在这期间的写入一律被 H3 拒，ledger 与 H5a 会说运行上下文读不出来。
- **`current-run` 的切换不拦**（审查第 24 条-1 的门禁一半）：`/agent-team:at` 第 1 节先问只在正文里。
- **收口不读验收结论**：正文写明验收没过不收口；门禁只核文件在不在、空不空、是不是这一轮的。
- **空文件只在收口与「交过」两处认**：H5b 与【阶段】的「齐了」照旧「写下任何东西都算交」（审查第 18 条-3），不在最后一段的空产物照样算齐。
- **在、却读不出来的产物**：收口拒；ledger 的收口阻碍那一支（读不出来）在子进程里造不出这种文件，没有判据。
- **中间各段的 accepted 仍由 PM 判断**：PRD 改了，`03-arch.md` 照样能标；只改代码、不重写实现记录的返工，实现记录也能标。兜底是验证段必须重出。
- **`trimmed` 的豁免按那一段的全部产者判**，不按缺的那一份是谁的：插件自带的阶段链里最后一段的前置都来自单产者段，判据钉着这个前提。
- **升级前交付的 run 没有 `closed_at`**：停在最后一段的，H2 拒派协调者、`/agent-team:at` 第 1 节先看收不收得了口；停在 `DONE` 的旧 run（stage 在链外）
  收不了口，照自检「另外，」那一支另起。已落盘的、验证段产物标过 accepted 的 run 原样带着，不追溯。
- **收口时还在跑的后台派发**：正文写明收口之前确认没有；门禁不拦它们的返回（H5a 那一格在已收口的 run 上不发）。
- **H5b 不认冒泡**（审查第 18 条）：真实会话里 `at-qa` 因自查误判冒泡，被一路顶回到平台的重试上限（`066acaaa`）。自查那句正文已改，H5b 本身没动。

## 6. 没量到的

- 交互终端（TUI）与 default、auto 权限模式（审查第 44 条）：都只在 SDK 宿主上量过。
- 收口被拒、补交、从第一步重走再收口的整条真实链；裁掉验收的收口；收口之后用户明说「直接改」：只有子进程逐帧。
- 项目经理跑在 haiku、opus 上：这一轮只跑了 sonnet。

## 7. 归属

- 改 `stages.json` 的段或产物的人：`verifies` 只认布尔 `true`；加一段验证段、或者让最后一段的前置改由多产者段产出时，重核 `closeBlockers` 的
  `trimmedAway` 与 `calledIn`（按整段的产者判，`tests/closing.test.mjs` 的前提判据会红）。最后一段换了，`lastStageId` 跟着书写顺序走。
- 动 `hooks/lib/closing.mjs` 的人：`closedAt` 是「收没收口」的唯一谓词；冻结不依赖阶段链、关上判不了就拒，这两条方向不能反过来。
- 动交付快照或「交过」的人：空文件的口径在 `isBlankText`，收口、快照与「交过」三处共用，只改一处会重演第二轮的那条矛盾。
- 修审查第 17 条（推进判据）的人：推进时核「在不在」可以复用 `closeBlockers` 的形状；验证段必须重出这一条在返工轮里已经成立。
