# U7 实测结论

> 环境：Windows 11 · Claude 桌面客户端 Code tab · 2026-09-16
> 依据：规格 `docs/superpowers/specs/2026-09-15-agent-team-plugin-design.md` §10 U7；
> 体例照 `docs/04-本机实测结论.md` §7/§8——怎么测的 / 原文观测 / 结论 / 对设计的影响。
> 本文只记录**在本机实际跑出来的观测**，推论与结论单独成段，不与观测原文混排。
> U7 不属于 M0 范围（M0 只答 U1–U4，见 `docs/05-M0-结论.md`），是 M1 第一步的独立记录。
> 与 04/05 冲突时，以本文为准。

## 0. 问题

M0 判定「§6 的 H1 派发门禁不是补充手段，而是层级的唯一强制手段」（规格 §3.3 结论 3，
M0 时的表述）。U7 要验的是这句话本身站不站得住：H1 只注册在 `PreToolUse` / `Agent`
上——**除 `Agent` 工具外，是否还有别的路径能起一个 subagent？** 若有，那条路上没有门禁。

候选四条：`Task`（传闻中的别名）、`Workflow`、`Skill` 的 `context: fork`、`SendMessage`。

## 1. 怎么测的

环境：插件经 junction 挂载并启用；主会话被 `settings.json` 的 `agent` 键钉成 `at-pm`；
`at-pm` 的白名单（宇宙）是
`Agent(agent-team:at-product, agent-team:at-architect, agent-team:at-worker-a, agent-team:at-worker-b)`；
花名册里 `at-pm` 的 `can_delegate_to` 只有 `["at-product","at-architect"]`。两个临时探针
skill 用 `context: fork` + `agent:` 指定目标，测完已删除。

四个候选里，只有 `Skill` 的 `context: fork` 走了完整的探针会话——下面 §2.1/§2.4 引号
内的内容是那次会话的逐字观测。`Task` 与 `Workflow` 是排除项：`Workflow` 的排除依据是
规格 §3.2.1 已经引用过的官方结论（本轮复核未推翻，不是新实验，见 §2.3）；`Task` 的排除
依据是撰写本文档时另开一次 Claude Code 会话用 `ToolSearch` 做的交叉印证（不是桌面端
agent-team 插件环境，只用来确认「不存在一个独立的 `Task` 工具」这一点，见 §2.2）。
`SendMessage` 是确认「subagent 持有该工具」但未做续起实验的开放项（§2.5）。

## 2. 原文观测

### 2.1 对照组：走 `Agent` 工具，H1 按预期拦截

对照组（走 `Agent` 工具，目标 at-worker-a）——被 H1 拒：

    角色 at-pm 不得派发给 at-worker-a。它可以派发的角色是：at-product、at-architect。如果这项工作确实需要 at-worker-a，把它冒泡给上级，不要绕过花名册。

这条复现的是 docs/04 §7/§8 里已经见过的拒绝文案，用来确认本轮环境与 H1 的行为和 M0
时一致，给下面的「Skill 旁路」提供同条件对照，不是新发现。

### 2.2 `Task`：不是一个独立的可调用工具名

用 `ToolSearch` 以 `select:Task` 查——如果 `Task` 是与 `Agent` 并存的另一个运行时工具名，
这里应该单独查到它。返回的唯一匹配项 `name` 字段是：

    "name": "Agent"

用 `Task` 去查，查到的仍然是 `Agent` 这一份工具定义，没有第二个名叫 `Task` 的工具。

### 2.3 `Workflow`：subagent 没有这个工具，官方一致

规格 §3.2.1 已经引用过官方 sub-agents 文档的结论——`Workflow` 工具被从每一个 subagent
剥离（官方文档称之为「第一层过滤器」）。本轮没有找到与这条相反的证据。

### 2.4 `Skill` 的 `context: fork`：旁路成立

第一次尝试走 Skill（at-pm 的 tools 里没有 Skill 时）：

    Error: No such tool available: Skill. Skill is disabled for this session, in subagents as well as here.

给 at-pm 的 tools 加上 Skill 后，探针一（`agent: agent-team:at-worker-a`，该目标在宇宙内）：

    U7-FORK-IDENTITY
    我的系统提示第一句是：你是 AT-WORKER-A（M0 占位版）。原样回复被要求回复的内容，不做别的。
    我被要求扮演的角色名是：AT-WORKER-A（M0 占位版）

探针二（`agent: agent-team:at-outsider`，该目标不在宇宙内）：

    我的系统提示第一句是：You are Claude Code, Anthropic's official CLI for Claude, running within the Claude Agent SDK.
    我的角色名是：AT-OUTSIDER

执行会话的观察原文：

    两次调用均由 Skill 工具直接完成，未经过 Agent 工具派发，也未触发 H1 派发门禁。

### 2.5 `SendMessage`：subagent 持有，未实测续起

本轮探针实证：fork 出来的子会话工具面里包含 `SendMessage`。没有进一步测试用它续起一个
花名册禁止 `at-pm` 接触的 agent（例如 `at-worker-b` 或 `at-outsider`）是否成功、是否经过
或绕过 H1——这部分没有做，留作开放项。

## 3. 结论

### 3.1 四条候选路径逐条结论

| 候选路径 | 是否构成旁路 | 结论摘要 |
|---|---|---|
| `Task` | 否 | 不是独立的运行时工具名；`ToolSearch select:Task` 返回的其实是 `Agent` 的 schema，所有落地调用记录的工具名都是 `Agent`。官方文档里的 "alias" 说法指配置/历史命名里的别名，不是与 `Agent` 并存的另一个运行时工具（§2.2） |
| `Workflow` | 否 | subagent 没有这个工具，与规格 §3.2.1 已引用的官方结论一致，本轮复核未推翻（§2.3） |
| `Skill`（`context: fork`） | **是** | 两次探针均由 `Skill` 工具直接起了一个 fork 出的子会话，全程未经过 `Agent` 工具，未触发 H1（§2.4） |
| `SendMessage` | 未知（开放项） | subagent 持有该工具，官方文档称其能续起一个已存在的 agent；本轮未实测续起受限 agent 是否成功、是否绕过 H1，见规格 §10 新增 U8 |

### 3.2 核心结论三条

① **`context: fork` 的 skill 不经过 `Agent` 工具，H1 不触发。** H1 挂在 `PreToolUse` /
matcher `^Agent$` 上（`hooks/hooks.json`，由 `tests/hooks-registration.test.mjs` 锁死）；
`Skill` 是另一个工具名，落地的调用记录里根本没有一次 `Agent` 调用，门禁没有输入可判。

② **目标在宇宙内时，fork 拿到该角色的真实定义。** 探针一的回复原样复述了
`agents/at-worker-a.md` 的正文——系统提示第一句、"原样回复被要求回复的内容，不做别的"
这条行为约束，都与该文件 frontmatter 之下的正文逐字对应。fork 不是"假装"了一个身份，
是真的加载了那份角色定义并据此运作。

③ **目标在宇宙外时，fork 仍然成功，但角色定义没加载。** 探针二的目标
`agent-team:at-outsider` 不在 `at-pm` 的白名单（宇宙）里，但调用没有像 `Agent` 工具那样
被拒——它成功起了一个子会话，只是这个子会话拿到的是默认 Claude Code 系统提示，而不是
`agents/at-outsider.md` 里"你是 AT-OUTSIDER……"那段正文。换句话说：**宇宙过滤管得住
「加载谁的定义」，管不住「能不能起一个 agent」。** 这与 M0 · U4 的发现（白名单是宇宙、
不是边）是同一枚硬币的另一面——那次证明白名单挡不住"越权派发"这条边，这次证明白名单
甚至挡不住"绕过 `Agent` 工具本身去起一个进程"，它只在"这个进程能不能加载到一份角色
定义"这一层起作用。

### 3.3 连带事实一：主线程 `tools:` 限定的是整棵子树的工具面

`Skill is disabled for this session, **in subagents as well as here**` 这句错误文案本身
就是证据：`at-pm`（M0 占位版）的 frontmatter 里 `tools:` 行原本没有 `Skill`，而这条报错是
在确认"没有 Skill 就调不了 fork"时撞到的——它不只是说"这里（主线程）没有"，而是明确说
"在 subagent 里同样没有"。

这与 M0 · U4 发现的机制是同一件事的两个观测面：U4 证明主线程 `tools: Agent(A, B)` 圈定
的是**整个会话可解析到的 agent 集合**，被所有子孙代理继承；U7 这条证明主线程 `tools:`
圈定的其实是**整个会话的工具面**本身——`Agent` 只是其中一项。**主线程 agent 定义的是
整个会话的能力上界，不是它自己的权限。** 少写一个工具，不是"我不能用"，是"这棵子树里
没有人能用"。

### 3.4 连带事实二：skill 正文在会话启动时加载

跟 agent 定义一样，skill 正文也是会话启动时加载的常量：改了 `SKILL.md` 不重开会话不
生效。原文观测：同一个会话里改完再调，返回的仍是旧正文的常量，逐字相同。M1 开发阶段会
反复踩这一条——迭代探针 skill 或将来任何 skill 正文时，编辑后必须开新会话才能看到效果，
同会话内重试只会验证"没生效"这件事本身，不代表改动有误。

## 4. 对设计的影响

- 规格 §3.3 结论 3 原文「H1 派发门禁不是补充手段，而是层级的唯一强制手段」改写为
  「H1 是**派发路径**的唯一强制手段，而**派发不是获得 agent 的唯一路径**」，并在 §3.3
  末尾补一小节（§3.3.1）把 §3.3 这条连带事实写成更一般的表述。
- 规格 §6 新增 §6.1「角色工具面禁止包含 `Skill`」（原 §6.1/§6.2 顺延为 §6.2/§6.3）：
  主防线是不给角色 `Skill` 这个工具，不是加 hook。
- 规格 §10 回填 U7：状态由「未测」改为「是（存在旁路）」；新增 U8（`SendMessage` 续起
  受限 agent，未测，M1 中段验证）。
- `tests/tool-surface.test.mjs` 把「角色 `tools:` 不含 `Skill`」与「仓库内所有
  `skills/**/SKILL.md` 不声明 `context: fork`」钉成回归测试，防止将来某次角色正文改动
  或新增 skill 时悄悄打开这条旁路。
