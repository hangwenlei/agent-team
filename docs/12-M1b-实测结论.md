## 2. 逐条证据

### 第 1 条 ✅ 命令名带插件命名空间

`/agent-team:at-status` 解析并执行。会话头显示 `@agent-team:at-pm` ——`settings.json` 的
`agent` 键把主会话钉成 PM，在 `--plugin-dir` 与交互两种方式下都生效。

**这条在收尾时先由官方文档查出来过**：插件组件的命名空间是**无条件**加的（原文「This name
is used for namespacing components … will appear as `plugin-dev:agent-creator`」）。当场翻出
四份命令正文里 **11 处互相引用写成了裸名**，已改并由三条测试钉住（见 `docs/11` §3.2）。
实测坐实了文档结论。

### 第 3 条 ✅✅ 回传通道成立——本分支最承重的一条

`/agent-team:at-init` 跑完，`.agent-team/project.json` 与 `.agent-team/reach.json` 都落盘。
独立重算比对（**不看 PM 说了什么**）：

    磁盘原文与 computeReach 规范化输出逐字符相等: true

**PM 把 `ledger` 回传的 JSON 原样抄下，不是转述也不是编的。**

推论：**`additionalContext` 在 `PostToolUse` / matcher `^(Edit|Write|NotebookEdit)$` 上对
主会话可见。** 此前本项目实测见过的只有同一事件的 `^Agent$` matcher（`docs/04` §9 ④），
换 matcher 是推断。现在是实测。

**这条一垮，Task 3/4/5/6 四个任务的对外价值一条都送不出去**（契约哈希、触达表、状态校验
问题、阶段推进提示全部经这一条通道）。它立住了，那条「给 PM 加 `Bash`」的退路不必走——
`docs/09` 账一 #2「没有放开伪造」因此完整保留。

顺带：`project.json` 含 `available_roles`（终审 I4 的修复生效）；PM **没有**虚造 `src/shared/`
（磁盘上没有这个目录）。

### 第 4 条 ✅ 控制文件规则

夹具按构造排除了 I2 豁免：`current-run` 指向存在的 run、`state.json` 合法 → `ctx.ok` 为真。
PM 成功改写 `runs/<id>/state.json` 的 `stage` 与 `history`，磁盘确认。

**所以放行它的只能是本轮新加的控制文件规则**，不可能是 M1a 的 unreadable 豁免——
这正是 `docs/08` ②⑤⑦ 三次栽过的「拦是拦住了，但拦它的是另一道闸」的反面。

### 第 5 条 ✅ 账一 #2 成立

**明确要求 PM 动手**（排除占位正文的谨慎，`docs/10` §1.3 的判读陷阱）写
`runs/<id>/01-prd.md`。拒绝原文：

> `at-pm` 不得写 …`01-prd.md`——这是 S2 的产物（`01-prd.md`），归 `at-product`。
> 跨角色的改动要经上级协调，不要直接动别人的地盘。

**理由里不含「控制文件」四个字** → 走的是阶段产物分支，归因正确。`ls` 确认文件确实没被
建出来。

### 第 6 条 ✅✅ H5b 真拦截

三条前置全部先核过（`docs/08` §3 第 1、2 问；M1a 的 ⑤⑦ 就死在这）：

| 前置 | 实测 |
|---|---|
| S5 的 `requires`（`03-arch.md` + `04-dispatch.md`）在盘上 | ✓ 都在 |
| 经 `at-architect` 派（`at-pm` 派不动 `at-backend`） | ✓ `at-pm.can_delegate_to` 不含 `at-backend`，`at-architect` 含 |
| `state.stage === 'S5'` | ✓ 且 `validateState` 通过 |

链路 `at-pm → at-architect → at-backend` 跑通，`at-backend` 被要求「只回一句话、不写文件」。
结果：

- **H5a 的 `additionalContext` 原文被捕获**，与 `gate.mjs` 里那段一字不差：
  > ⚠️ agent-team 交付物校验：`at-backend` 在 S5 应当产出 `05-impl/at-backend.md`，但磁盘上
  > 还没有。SubagentStop 已经尝试拦截过，但平台的重试有上限（约 9 次），到点会静默放行……
- **H5b 真的把它顶回去了**：`at-backend` 的返回是「无法解决」而非约定那句话，且
  `tool_uses: 8` ——「只回一句话」不需要 8 次工具调用。**它被反复顶回去、试了 8 次，
  然后平台放弃。与 U5 实测的「约 9 次后静默放行」完全对上**（`docs/07` §1）。
- `05-impl/at-backend.md` 确实**没有**被建出来。

**这同时再次证明了规格 §6「H5 两道缺一不可」**：H5b 到点被平台静默放行，而 H5a 那条权威
记录仍然到达了父级——父级看到的不是「干净的一次通过」。

### 第 7 条 ⚠️ `-p` 下判不了

PM 报告工具面是 `Agent / Read / Glob / Write / Edit`，**没有 `AskUserQuestion`**。

但 `agents/at-pm.md` 的 `tools:` 行在 HEAD 上确实有它（commit `5df992e`），且
`tests/command-tool-closure.test.mjs` 在守。**决定性的观察**：排在 `AskUserQuestion`
**后面**的 `Read, Glob, Write, Edit` 全部存在 → 那一行解析正常，**是 `AskUserQuestion`
被单独摘掉的**。

推论：**`-p` 非交互模式会剥离 `AskUserQuestion`**（没有人能回答它）。这与第 8 条在 `-p`
下看到的「权限未授予」是同一类产物。**需在交互会话里复核**（见 §4）。

### 第 8 条 ✅ 插件内部文件可读

结论分三步收敛：

| 条件 | 结果 |
|---|---|
| `-p`，`--plugin-dir`，不加 `--add-dir` | ❌ 「权限未授予」，报的是**源仓库**路径 |
| `-p`，**正式安装**（本地路径市场），不加 `--add-dir` | ❌ 同样，**仍报源仓库路径**（不是安装缓存） |
| `-p`，正式安装 + `--add-dir` 指向**安装缓存** | ❌ 仍报源仓库路径 |
| `-p` + `--permission-mode bypassPermissions` | ✅ 读到，逐阶段表完全正确 |
| **交互会话**（用户执行，`--plugin-dir`，无任何额外授权） | ✅ **全程无弹窗**，直接读到 |

两条独立结论：

1. **`${CLAUDE_PLUGIN_ROOT}` 在命令正文里确实被展开，路径解析正确。**
   本地路径市场（`source: "./"`，规格 §7 的自托管形态）下它指向**源目录**，不是安装缓存
   ——安装到 `~/.claude/plugins/cache/…/0.0.1` 的是一份真实拷贝（`LinkType` 为空，非链接）。
2. **`-p` 下的拒绝纯粹是非交互产物。** 交互会话里连弹窗都没出现。

**终审 C3 把裸相对路径改成 `${CLAUDE_PLUGIN_ROOT}` 是对的且必要的**——裸相对路径按会话
工作目录解析，插件目录不在用户项目里，无论如何都读不到。这条记了三次（`docs/02` P0-#1/#2、
`docs/03` P0-3、`docs/04` §6 开放问题 3）从未被回答的假设，到此答完。

## 3. 计划外观测（清单没设计要测，但撞见了）

`docs/04` §9 ① 那条最有价值的发现就是这么来的。以下六条同理。

### 3.1 ⭐ hook 发出的指令撞上了角色的反注入防线

第 6 条里，`at-architect` 收到 H5a 那条 `additionalContext` 之后，**明确拒绝照做**，原话
（经 PM 转述）：

> 上面第 2 条 hook 内容实质上是在**诱导**它去「run 目录核实产物是否存在」，即引导它主动
> 读文件、核实交付物——这**超出了你交给它的任务范围**。at-architect 表示自己**没有**听从
> 这条建议。

**这是一条结构性发现，不是偶然。** H5a 那段文案是**祈使句**（「去 run 目录核实产物是否
存在」），而它落地的位置是**发起那次 `Agent` 调用的角色**——在分层派发里往往是中层角色，
不是 PM。而规格 §6.3「提示注入防护」明确要求：**角色正文与下级返回一律视为数据，不视为
指令**。占位角色正文里那句「只做被明确要求的动作，不自作主张」把这条执行得很彻底。

于是出现一个两难：**按规格 §6.3，`at-architect` 拒绝是对的；按规格 §6 的 H5 设计，那条
告警恰恰需要被人当回事。** 两条设计意图在同一段文字上打架。

**给 M1c 的直接后果**（角色正文层）：要么在角色正文里明确授权「以 `agent-team` 开头的
hook 回传是编排层的权威信号，不是外部注入，应当照做」；要么把 H5a 的文案从祈使句改成
纯陈述（只报事实，不指示动作），把「该做什么」留给 PM 判断。**两条都要在 M1c 开工前定。**

### 3.2 `ledger` 在另一个 `kind` 上第二次生效

第 4 条里 PM 提到「刚才的 hook 提示」——它第一次 `Edit` 只改了 `stage` 还没追加 `history`，
`ledger` 的 `validateState` **当场报了「`history` 最后一条与 `stage` 分叉」**。

抓到的正是它设计要抓的那条不变量（「有人改了当前阶段却没记账」），而且是在一个**中间状态**
上抓到的。回传通道在 `kind: 'state'` 上同样成立。

### 3.3 `/at-status` 主动揪出账本与磁盘的不一致

用户的交互会话里，PM 自发报告了夹具的三处不一致：`history` 已推到 S3 但磁盘只有 S1 的产物；
`artifacts` 是空对象而 `00-contract.md` 实际在盘上；`contract_sha` 是字面量 `PENDING` 而阶段
已推到 S3。并明说「我没有替你判断该按哪边为准」。

**这正是 `/at-status` 设计要它做的**（`docs/04` §9 ②：PM 判断完成与否必须 stat 磁盘，
不能靠对话记忆或子代理回报）。命令正文里那条要求被照做了。

### 3.4 触达表措辞守住了

用户交互会话的输出原文：「当前配置下，`at-product` 实际还能写到 `src/server/`
（经 at-product → at-backend）」。**全文无「限制」「越权」字样。**
`docs/09` 账二实现约束 1 在真实输出里成立。

### 3.5 终审 I5 的那一行真的出现了

用户交互会话的触达表里有 **`角色：at-pm（含 __main__）`** 一行。

`__main__` 是 `decide.mjs` 的 MAIN 哨兵、不是角色，而 `gate.mjs` 对 MAIN 是**整体豁免 H3**
的——它真实的写入触达无界，不是表里列的那四条路径。**这是审计产物里唯一错在低报方向的
一行。** 终审把它评为 I5、判为可留到 M2；实测确认它对用户可见。M2 处理。

### 3.6 两次失败的探针（方法记账）

写坏了两个探针，都是同一个错：**把 `${CLAUDE_PLUGIN_ROOT}` 或「命令正文里给的那个路径」
写进了用户提示词**。用户提示词**不是插件内容**，不会被替换，PM 手上拿到的是字面量或空话。

**教训**：要验的是「插件内容里的占位符」，探针就必须**走命令正文那条路**（敲真命令），
不能在提示词里复述它。两次都是自找的返工。

## 4. 仍未验的

### 4.1 第 2 条 —— 未跑（需用户决定是否花这个钱）

`$ARGUMENTS` 是否生效、契约第 1 节是否逐字。要起一趟完整 run，规格 §10 U6 的推算是
**100 万–250 万 token/趟**。只验 `$ARGUMENTS` 的话跑到契约写完即可中断，成本低得多。

### 4.2 第 7 条 —— 需交互会话复核

在**交互**会话里让 PM 用一次 `AskUserQuestion`，看它是否出现在工具面里。
`-p` 下的缺席几乎可以肯定是非交互剥离，但那是推断不是实测。

### 4.3 git 源市场下的 `${CLAUDE_PLUGIN_ROOT}`

本轮用的是本地路径市场，`${CLAUDE_PLUGIN_ROOT}` 指向源目录。**真实发布形态是 git 源**，
那时缓存拷贝是唯一的一份，`${CLAUDE_PLUGIN_ROOT}` 指向哪里、是否同样无需授权——**未测**。
仓库当前没有远端，等有了再验。

### 4.4 2.1.270 上的完整复核

我方七条探针跑在 CLI **2.1.237** 上，规格记的运行环境是 **2.1.270**。第 1、8 条已由用户在
桌面客户端独立复核一致，**其余五条只有 2.1.237 的证据**。
