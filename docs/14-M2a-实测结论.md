## 0. 一句话结论

**六条验证项全部拿到真实环境证据，五条完整（记录级），第 6 条的 `available_roles`
半完整记录级、`never_invoked` 半是独立复算（真实数据、真实算法，但没等到 PM 自己产出

1. **全程未使用 `claude plugin enable`**——两个探针项目、全部会话都用 `--plugin-dir`。
2. **`--bg` 起常驻后台会话**，`claude logs <id>` 读输出；本轮再次确认异步派发在常驻会话里
   正常完成（§3.1）。

   边界，见 §9.2（`--resume` 不继承调用者的 cwd，不是 `--plugin-dir` 本身的问题，但同一类
   "续会话时哪些东西不会自动带上"）。
4. **`--bg` + `bypassPermissions`**：全部会话直接可用，未撞到免责声明拦截，与派发指令给的
   信息一致。

## 3. 六条逐条证据

### 3.1 第 1 条：S5 多产者槽位——**记录级证据**

**方法**：探针工程 `m2a-task9-probe`（`package.json`/`tsconfig.json`/`src/server/`/
`src/web/`/`docs/` 齐全），`claude --bg --plugin-dir` 常驻会话，先 `/agent-team:at-init`，
再 `/agent-team:at 做一个健康检查功能：后端提供 GET /api/health 接口，返回 { status: "ok",
time: 当前ISO时间 }；前端加一个按钮，点击后调用这个接口并把返回的状态和时间显示在页面上。`
——与 `docs/13` §10.1 用过的原文逐字相同（同一个场景，只换了 M2a 的代码），便于跟那次的
M1c 结果直接对照。

**`at-frontend` 独立写出了自己的 `05-impl/at-frontend.md`**（磁盘路径
`.agent-team/runs/20260919-2203-health-check/05-impl/at-frontend.md`），内容摘录：

> 认领范围：`src/web/`（未改动 `src/server/` 下任何文件，未新增任何 npm 依赖）
>
> 在我验证过程中，`src/server/health.ts` 与 `src/server/index.ts` 陆续出现（**不是我
> 写的，是 at-backend 并行交付的**）……

这份文件本身的内容质量也值得记一笔（不是本条判据要求的，但能看出真实性）：它记录了
"backend 尚未就绪时先做了两轮不依赖真实后端的自测（mock fetch + 临时桩 HTTP 服务器）"、
"backend 就绪后补做了真实联调（真实 fetch 打真实运行中的服务）"，并且明确说明"没有用图形
界面浏览器真正点击，我的工具集里没有浏览器/GUI 自动化能力"——不把 Node 级别的验证包装成
"已经在浏览器里点过了"。

**关键判据——没有 PM 代笔**：这份文件的落盘时间点在 PM 仍处于派发等待状态时（`state.json`
在这次落盘前后 `roster` 仍是 `["at-product","at-architect"]`，不含 `at-frontend`/
`at-backend`——见 §4 的 roster 时间线），是 `at-frontend` 自己（被 `at-architect` 直接
派发）用 `Write` 工具写出来的，不是 PM 转写。这与 §9.4 独立核实的机制结论吻合：H3 现在
只放行 `at-frontend` 自己写这条路径，PM/`at-backend` 写同一路径都会被拒——`docs/13` §6.1
那次"PM 代笔"在这里没有重演。

**与 §5.1 那条文档漂移担忧的对照**：`agents/at-frontend.md` 的系统提示仍然停留在 M1c
"你没有阶段、不需要写 `05-impl/*`"的说法，但**实测中它照样写了**。合理的解释是：`at-architect`
按`交接包六项`格式给它的派发提示里直接指明了要产出的东西（`04-dispatch.md`/交接包通常会
写"完成定义"），这条具体指令盖过了角色系统提示里那句已经过期的话。**这条文档漂移目前
没有造成实际后果**，但"没造成后果"是这一次派发提示恰好给对了，不是机制本身保证的——
下一次如果派发提示写得更简略，是否还会一样，本轮没有把这个变量单独隔离验证，如实记这一句，
不夸大也不轻描淡写。

（`at-backend` 一侧的 `05-impl/at-backend.md` 与两个角色都完成后的账本、`roster`、
`isStageDone` 情况见下文与 §4。）

**计划外但价值很高的观察：真实 run 里自发触发了一次驳回（`rejectTo`/H6 rework 的真实
使用，不是本文 §3.4 那个刻意构造的夹具）**。`at-backend` 在 `05-impl/at-backend.md`
里如实报告了两个环境阻塞（`package.json` 不在任何角色的 `project.json` 路径认领范围内、
沙箱里没有装 `typescript` 包），PM 读完两份 `05-impl` 之后，**没有**把这两条当成需要
升级给用户的问题，而是判定为"技术选型层面可以自行决定"的范畴（规格 §5.2 自决范围），
决定把后端改成纯 JS（与前端的选型对齐），从而整个绕开"缺 `typescript` 包"与
"`package.json` 无人认领"这两个问题——**PM 把 `state.json` 的 `stage` 从 `S5` 写回
`S3`，`history` 追加一条新的 `{"stage":"S3", ...}`（不是覆盖旧的），`rework` 相应写成
`{"S3":1}`**：

```json
"stage": "S3",
"roster": ["at-product", "at-architect", "at-backend", "at-frontend"],
"rework": { "S3": 1 },
"history": [..., {"stage":"S5",...}, {"stage":"S3","at":"2026-09-19T22:32:24Z"}]
```

这与规格 §4.3 的驳回路由、`hooks/lib/state.mjs` 的 `rejectTo()`/`reworkFromHistory()`
设计的形状完全一致（"回退 = `history` 追加，不是修改或删除已有条目"；"`rework[S]` 等于
该阶段在 `history` 里出现次数减一"），但这一次不是我用夹具逼出来的，是 PM 在真实
运行中自己判断后做出的决定——**这是 M2a 扩链之后返工/驳回机制在真实环境里第一次被
自然触发的实例**，不在 brief 要求的六条之内，但值得记一笔，也顺带给 §4 的 roster
观察项提供了一个"返工期间 roster 会不会继续增长"的额外数据点（见下文：会，`roster`
在这次回退后仍然是只增不减，新增了 `at-backend`/`at-frontend`，不因为它们的产物被
驳回而从 `roster` 里移除）。

### 3.3 第 3 条：阶段推进判据——**记录级证据**

**方法**：用仓库真实的 `hooks/lib/state.mjs` 的 `isStageDone`，对同一趟真实 run 当前磁盘
状态（`05-impl/at-backend.md`、`05-impl/at-frontend.md` 都已存在）直接函数调用（不经
hook 子进程，纯函数级记录级证据），逐个 roster 假设对比：

```
真实 state.roster: ["at-product","at-architect","at-backend","at-frontend"]

isStageDone(S5, 真实 roster)：                          true
isStageDone(S5, roster=[仅 at-backend])：                true
isStageDone(S5, roster=[仅 at-frontend])：                true
isStageDone(S5, roster=[at-backend, at-ios]（一个真交了一个没交））：false
```

最后一行是关键判据：假设这一趟"声称"派了 `at-ios`（但磁盘上没有
`05-impl/at-ios.md`，因为真实 run 里从未真正派过它），`isStageDone` 正确判定**未完成**
——证明"两个角色都交了才为真"不是巧合，是真的在按 `roster ∩ producers` 逐个检查磁盘。

**补充**：同一次检查也顺带核实了 `validateState`（真实 `state.json`，包含上面那次
驳回之后的 `rework: {"S3":1}`）：`{"ok":true,"problems":[]}`——真实的返工状态本身也是
一份自洽、能通过完整 schema 校验的记录，不只是"看起来正确"。

### 3.4 第 4 条：H6 真的拦得住——**记录级证据**

**方法**：按 brief Step 2 明令，不等真实 run 自然触发。手工构造一个已经合法的夹具 run
（`m2a-task9-fixture` 项目，`.agent-team/runs/20260919-2200-h6h5a-fixture/`）：`stage=S5`，
`roster=[at-backend]`，`history` 六条（`S1→S2→S3→S4→S5→S5`，S5 出现两次），`rework={"S5":1}`
——这份状态本身先用仓库真实的 `validateState`/`isStageDone` 核过（§9.3），`ok:true`，
`isStageDone(S5)` 为真。构造过程本身**不经过任何 hook**（等同于 `tests/fixtures/make-run.mjs`
的角色：只是把"已经合法存在的历史"摆到磁盘上），真正要观察的动作留给一个真实的
`claude --bg --plugin-dir` 会话去做。

指令：让该会话（PM）用 **Edit** 工具把 `state.json` 里 `"S5": 1` 改成 `"S5": 0`，明确要求
"如果被拒绝，不要重试、不要换方式（Write/Bash）达成同样效果"。

**实际 Edit 调用**（原始会话 transcript，`tool_use`）：
```json
{"file_path":"...\\runs\\20260919-2200-h6h5a-fixture\\state.json",
 "old_string":"  \"rework\": {\n    \"S5\": 1\n  },",
 "new_string":"  \"rework\": {\n    \"S5\": 0\n  },"}
```

**实际 hook 返回**（`tool_result`，`is_error: true`，平台原文逐字）：
```
PreToolUse:Edit hook error: rework["S5"] 写成 0，但 history 里 S5 出现 2 次、
派生值是 1——返工计数不可重置（规格 §4.2 ③）。
```

**独立复核**：Edit 之后重新读盘，`state.json` 的 `rework` 字段**仍是 `{"S5":1}`**，
`stage` 仍是 `S5`——不只是"收到了一条报错文案"，磁盘上的写入确实被真实拦下，没有半写入
或先写后报的情况。

**结论**：H6 在真实环境（真实 `hooks.json` matcher → 真实 `gate.mjs` 子进程 → 真实
`decideRework`）里对"把 `rework` 改小"的写入确实 deny，理由文案与
`hooks/lib/rework-guard.mjs` 的判据③逐字对应。这是本条目前**唯一**的真实环境实例
（另有单测 `tests/gate-rework.test.mjs` 覆盖同一夹具形状，但 brief 明确要求不能只有
单测证据）。

### 3.5 第 5 条：H5a 新判据——**记录级证据**

**方法**：同一个夹具 run（`stage=S5`、`roster=[at-backend]`、磁盘上已有
`05-impl/at-backend.md` 且哈希与账本一致，`isStageDone(S5)` 为真），指令同一个会话用
**Agent** 工具派发 `at-architect`，任务内容明确写"不需要做任何实际工作，不要读写任何
文件、不要用 Bash，只需要回复一句收到即可返回"（让协调者尽快返回，不引入无关噪音）。

**实际派发**（`tool_use`）：
```json
{"subagent_type":"agent-team:at-architect",
 "prompt":"这是一次机制自检，不需要做任何实际工作，不要读写任何文件、不要用 Bash，
只需要回复一句收到，无需操作即可返回。"}
```

**实际 hook 返回**（PostToolUse，平台原文逐字）：
```
PostToolUse:Agent hook additional context: agent-team 账本回传：
⚠️ 交付物校验：刚返回的 at-architect 不是当前阶段（state.stage = "S5"）的执行者，
但它能（传递地）派到当前阶段的执行角色——这原本是合法的层级协调。只是当前阶段的产物
已经全部齐备，state.stage 大概率没有随之推进到下一阶段：这正是**停在旧阶段**，H5 会对
新阶段全程哑火。去 run 目录核实产物是否真的都已完成，确认后把 state.stage 推进到正确
的阶段。
```

文案与 `tests/gate-deliverable.test.mjs`「H5a：协调者返回但当前阶段已经 done——报」那条
的断言（`assert.match(stdout, /停在旧阶段/)`）完全对应，且是**同一份夹具形状在真实
Claude Code 会话里走了一遍**，不是子进程直接喂 JSON 给 `gate.mjs`。

**一个连带的模型行为观察（自述层面，未作为机制验证的依据）**：这条回传的建议是"核实产物
并推进 `state.stage`"，但该会话（当时的身份是 `at-pm`）**没有**照做，理由是我在派发指令
里明确划了"严格按步骤做，不要自由发挥"的边界，它判断"推进 state.stage"不在我给的步骤
清单内。这不是机制失效——H5a 本来就是 fail-open 的记录性告警，不是闸，"要不要听劝"从来
是角色自己的判断，这里只是如实记录一次真实交互里这个判断具体是怎么做的。

**独立复核**：Agent 调用之后重新读盘，`state.json` 的 `stage` 仍是 `S5`（与上面模型的自述
一致，双重确认它确实没有借这次派发顺手改状态）。

### 5.1 ⭐ `agents/at-frontend.md` 没有跟着 M2a 更新——可能让 M1c 那个"PM 代笔"的症状复发

**事实**：`hooks/lib/stages.mjs`、`state.mjs`、`writepath.mjs`、`readiness.mjs`、
`deliverable.mjs` 五个文件的注释里都能搜到"M2a 补"这类字样，记录了 S5 从单产者改多产者
之后各自要跟着改的地方；但 `agents/at-frontend.md`（这个角色自己的系统提示）**没有任何
一处提到 M2a、`producers`、或 `05-impl/at-frontend.md`**。它现在的原文是：

> 这份文件里没有任何一段的 `role` 是 `at-frontend`——M1 的阶段链止于 S5，前端阶段是 M2
> 才补的事（`docs/11` §1.1）。不要去里面找你自己那一段，找不到；这不是漏配，是这个角色
> 在 M1 的实际形状。因此你**不走** `stages[*].produces` 那条路——没有一份 `NN-*.md` 记在
> 你名下，也不需要有。

这句话是 M1c 写的，在 M2a 落地之前是对的（`stages.json` 的 S5 那时确实只有 `at-backend`
一个产者）。**M2a 把这件事改掉了**：`stages.json` 现在的 `S5.producers` 含
`at-frontend`，`produces` 是 `["05-impl/<role>.md"]`，`hooks/lib/writepath.mjs` 的
`stageOwnerOfRunPath` 也确实会把 `05-impl/at-frontend.md` 判给 `at-frontend`
（本文 §9.4 独立核实过）——**代码层已经支持 at-frontend 写自己的实现记录，但 at-frontend
自己的系统提示还在说"不需要有"**。

**为什么这不是无害的过期注释**：这份文件是 at-frontend **自己的系统提示**，不是给别人看的
参考文档。如果它当真读了这句话、按它做，就不会去尝试写 `05-impl/at-frontend.md`——不是
因为写不了（H3 现在允许），是因为它自己的角色说明书告诉它"不需要"。这与 `docs/13` §6.1
记的那次"M1 阶段链对前端角色结构性不完整，逼 PM 代笔"是**同一个外部症状**，但如果这次
复现，根源会是**文档没跟上代码**，不是代码本身的缺口——两种根因对应的修法完全不同（改
`agents/at-frontend.md` 一句话 vs 改 `stages.json`/`hooks/`）。

**本轮实测结果（见 §3.1）：没有复现——`at-frontend` 照样自己写出了
`05-impl/at-frontend.md`**，机制没有被这处过期文档实际卡住。推断的原因：`at-architect`
按交接包格式给它的派发提示里直接写明了要交付什么，这条具体指令的权重盖过了角色系统提示里
那句过期的话。**这不代表这条文档漂移不值得修**——它是真实存在的、与代码不一致的文字，
这次没造成后果是"这次派发提示恰好给得够具体"，不是机制本身保证"派发提示不够具体时也不会
出事"。如实记录：过期文档 + 实测未复现症状，两者都是事实，不互相抵消。

**证据等级**：文档内容比对（记录级）+ 本轮唯一一次真实 run 的观察（记录级，但只有一次
样本，不能当作"这条漂移无害"的证明）。

**不在本任务修**：Task 9 是验证任务，"本任务不碰代码"——这条也不碰文档。留给 M2b（它本来
就要重写五个角色的真正文）或者专门一轮小修。

### 5.2 ⭐ H5a 的"非协调者"告警对 S5 的非 `role` 产者（`at-frontend`/`at-ui`/`at-ios`/`at-android`）存在结构性误报——记录级证据

**背景**：M2a 设计文档 §1.1 的四消费方表（H3 写路径 / `isStageDone` / 账本比对 /
`ledger` 的 `produce` 回传）与 §1.3 的 H5a 静默判据重算，都只讨论了"协调者能不能传递派到
`stage.role`"与"当前阶段是否已 done"这两个轴，**没有讨论第三种情形**：S5 的产者里除了
`stage.role`（`at-backend`）本人，还有四个"合法产者但既不是 `role` 也不是协调者"的角色
（`at-frontend`/`at-ui`/`at-ios`/`at-android`，花名册里 `can_delegate_to` 全是空数组）。

**独立核实**（不依赖真实 run，用仓库真实的 `hooks/lib/reach.mjs` + `roster.json` 直接算）：

```
at-frontend.reachableRoles: []
at-frontend 能传递派到 at-backend 吗: false
```

`hooks/gate.mjs` 的 H5a 判据是：

```js
if (CHECK === 'deliverable' && r.skipped === 'role-not-in-stage' && (!coordinator || stageDone)) { … }
```

当 `at-architect` 派发 `at-frontend`、`at-frontend` 自己完整交付（写完
`05-impl/at-frontend.md`）后返回，`decideDeliverable({role:'at-frontend', stageId:'S5', …})`
因为 `stage.role`（`at-backend`）≠ `role`（`at-frontend`）而返回
`{ok:true, skipped:'role-not-in-stage'}`（这一段是设计**有意**的范围限制，
`stages.README.md` 明确写着"其它 producers 返回时仍然落进 `role-not-in-stage`"）。
但接下来 `coordinator = isCoordinatorFor(ctx, 'at-frontend')` 恒为 `false`（上面独立算过），
`!coordinator` 恒真，**告警会无条件触发，不看 `stageDone`**——即便 `at-frontend` 这次
交付完全合法、当前阶段也确实还没做完。

**实际效果**：`at-architect` 每次派发 `at-frontend`（M2a 唯一新增的、被设计着重要支持的
并发派发形态）之后，都会收到一条写着"而且它也派不到那个执行者……两种可能：state.stage
停在旧阶段没推进；或者这次派发本身不该发生"的告警——而这两种可能**都不是真的**，
`at-frontend` 的这次派发恰恰是 `commands/at.md` 明文指示的正路（"架构师可以在一条消息里
并发派多个执行角色"）。

**本轮实测结果：这一条我没做，如实说明是哪一种做不到**——不是"结构上不可能"（分析与
§9.4 的独立函数级验证已经证明机制上一定会触发），是"我没做"：`at-architect` 收到的
hook 回传记在**它自己的子代理 transcript**里，不在 PM 的顶层会话记录里（M1c
`docs/13` §3.4 用过 `--forward-subagent-text` 或直接读子代理的 `.jsonl` 才拿到过这类
证据）；派发 `at-architect` 时平台明确提示"子代理的完整 JSONL transcript 不要用 shell
工具直接读,会撑爆上下文"，本轮为了控制篇幅与时间没有去取这份子代理原始记录，转而依赖
§3.5 那个专门构造的夹具（同样的判据、同样的真实 hook 链路，只是角色换成了 `at-architect`
本身而不是 `at-frontend`）作为"机制在真实会话里成立"的证据。**这条记录级证据的缺口是
真实存在的**：本文能确定"这条误报在机制上必然发生"（§9.4 独立验证），但不能确定"这次
主线 run 里 `at-architect` 具体看没看到这句话、看到之后有没有做出什么反应"——如实标注,
不假装已经拿到。

**严重性判断**：这是 H5a 的**误报**，不是安全洞——H5a 全程 fail-open、只记录不拦截
（"这是审计产物,不是安全边界"同族），告警内容也没有教唆任何危险动作。代价是**噪音**：
每次合法的多产者并发派发，协调者都会收到一条方向错误的告警，长期可能让"停在旧阶段"这个
真正有意义的信号被噪音淹没（`docs/09` 账二一直强调的"每次都刷一段会把真正要看的东西淹掉"，
这里是同一类代价，只是换了个触发条件）。

**不在本任务修**：同上，记录并留给 M2b/后续任务判断怎么补——可能的方向是把"协调者"判据
换成"是不是 `stage` 的合法产者之一"（`stageRoles(stage).includes(role)`），但这需要
重新过一遍 §1.3 那张真值表，不是本任务的范围。

## 8. 未能验证的项

按 brief 要求，逐条说清楚"是哪一种做不到"：环境不允许 / 需要人来操作 / 结构上不可能 /
我没做。

**1. 验证项 3 字面意义上的"`state.json` 的 `stage` 字段真的被写成 `S6`"——我没做，说明
为什么**。

机制本身（H3 写路径隔离与 H6 返工预算写时强制都只管"改小"、不管 `stage` 这个字段的取值,
两者都不阻止把 `stage` 从 `S5` 改成 `S6`）已经用**直接函数调用独立验证过**（§9.4 的
`decideWritePath`、§3.4 的 `decideRework` 检查逻辑本身），不是没查过就下结论。

没做的是"让真实 run 里那个 `state.json` 真的走到 `stage: "S6"` 这一步"：这趟主线 run 在
到达"S5 两个角色都交付"之后,PM 判断需要驳回重做（见 §3.1 附记),转向了 S3 → S4 → S5
的第二轮，把原本"下一步该推进到 S6"的窗口岔开了。有两条路可以把"stage 写成 S6"这件事
坐实，我都没有选：

- **等真实 run 走完第二轮、PM 自己再走一次"S5 完成、该不该推进"的判断**——这是最干净的
  路径，但会让本已经很长的验证过程再拖一个完整的 S3–S5 周期（前一轮从 S1 到两份
  `05-impl` 都交齐，实测耗时约 22 分钟），而 §3.3 已经用真实磁盘数据把"两个角色都交了
  `isStageDone` 才为真"这条核心判据坐实，S6 是不是字面出现在 `stage` 字段里不影响这条
  判据成不成立。
- **我自己直接把 `state.json` 的 `stage` 改成 `S6`（用 Edit，走真实 hook）**——这条本来
  可以做,且能顺带把"H3/H6 都不拦推进"这件事也用一次真实工具调用坐实,而不只是直接函数
  调用。**没做的原因是权衡取舍，不是做不到**：这么做会把"这是真实 run 自己走出来的结果"
  和"我从外部插了一手"混在同一个 `state.json` 里，后续任何人再读这趟 run 的记录都无法
  区分——本文其余各条证据都刻意保持"真实 run 的产物"与"我构造的夹具"两条线分开
  （§3.1–§3.3 是前者，§3.4/§3.5 是后者），临时在主线 run 上插一次改动会污染这条界线。

**结论**：机制成立（有独立证据），但这一条"真实 run 里 `stage` 字面推进到 S6"最终没有
拿到——如实计入未完成，不算进"六条全部完整验证"。

**2. 验证项 6 的 `never_invoked`——PM 自己产出的那份原文——我没做，理由同上**（见 §3.6
的证据等级说明，此处不重复）。

**3. 主线 run 的第二轮 S3–S5 周期是否会顺利完成（比如纯 JS 改造之后 curl 验证是否通过、
是否还会再撞上需要冒泡的问题）——我没做，没有等到结果**。这不在 brief 六条验证项的范围

### 9.1 CLI 版本与派发指令不一致

patch 版本号上的断言，`docs/13` §10.1 自己也写过"版本不够就说明这条没法在那个版本上
复核，不是结论错了"这条方法论，这里对称地适用：版本更新（而不是更旧）通常不会让已经
成立的行为模式失效，但如实记录版本差异，不假装两次实测在同一个版本上做的。

### 9.2 一次操作失误：`--resume` 不继承调用者的 cwd

派发主线第二步时，第一次 `claude --bg --resume 06cc9794 --plugin-dir "<repo>" ...` 命令
忘了先 `cd` 进探针目录（沿用了当时 shell 的 cwd，即本仓库根）。`claude agents --json`
显示新会话的 `cwd` 确实是 `C:\Users\82370\Desktop\Agent-Team`（本仓库），不是探针目录——
**`--resume`（含 `--bg --resume`）用的是发起调用那一刻的进程 cwd，不会沿用被续的那个
会话原来的 cwd**。当场用 `git status`/`ls .agent-team` 确认本仓库没有被污染（会话当时还在
"busy/thinking"阶段，没来得及写任何文件），立即 `claude stop` 掉这个跑错目录的会话，
换一条带正确 `cd` 的命令重新 `--resume`。

**记录级证据**：`claude agents --json` 里该会话（`98dcaa75`）的 `cwd` 字段原文就是仓库根路径；
`git status` 在停掉它之后确认 working tree 仍然 `clean`。

**不算一条新的"操作纪律"**，是同一类"续会话时哪些东西不会自动带上"的教训在 cwd 这个
维度上的实例（`--plugin-dir` 不继承是 docs/11 §5.5 记的那一半，这次撞见的是 cwd 这一半）
——如果续会话的项目目录会挪动，`--resume`/`--bg --resume` 每次都要显式 `cd` 到目标目录，
不能假设它会记住原会话的工作目录。

### 9.3 H6/H5a 夹具的独立自检（不经真实会话，纯函数级记录级证据）

### 9.4 `at-frontend` 写路径独立核实（不经真实会话，纯函数级记录级证据）

用仓库真实的 `hooks/lib/writepath.mjs` 的 `stageOwnerOfRunPath`/`decideWritePath` 与真实
`stages.json` 直接核对（服务于 §5.1 的分析）：
