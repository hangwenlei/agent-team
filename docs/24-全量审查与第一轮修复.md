# 全量审查与第一轮修复

**日期** 2026-09-28 ｜ **口径** 审查基于 main `e0dc7ba`（v0.7.7）；修复在分支 `m3p-audit-hardening`
（`8b7ef59`…`51c9644`），版本 `0.8.0`

## 0. 一句话结论

在它依赖的环境前提都成立时，门禁判得对。审查查出的大问题几乎都落在这些前提不成立的时候：
hook 的 cwd 不在项目根、判定代码没加载起来、没人在别的系统上跑过判据、接线改坏了没有判据会红。
这一轮修的就是这四处。修完做的独立复核又抓到一处回归：只认 `CLAUDE_PROJECT_DIR` 时，用户
`/cd` 到别的项目后，那边的 run 被整个看丢。已改成现行口径（§2.1）。CI 第一次在 macOS 上跑，
打出了一族路径别名的问题，它在产品侧也有同族形状，登记为下一轮优先（§3）。

## 1. 做法与它的边界

**审查**：十路并行审查，按子系统分：写路径、派发、状态与账本、收尾门禁、配置健壮性、平台假设、
提示层、变异验证、安全、工程化。每条发现交给两位独立核验者：一位复现，一位查先例与设计意图，
看它是不是已登记的边界或有意的取舍。之后一路补漏，最后终审汇总。123 条原始发现合并成 49 条，
原文存档在 `docs/24-附录-全量审查报告.md`。

**修复**：挑四条先修，就是报告的第 1、2、3、11 条。挑它们的理由是：修掉以后，门禁在环境异常时
要么拒绝，要么留下看得见的痕，而不是静默放行。每一条都是先写判据、看着它红，再改代码。

**复核**：修完之后另起一轮独立复核，分四路：
- 在隔离 worktree 里做变异扫描，覆盖这一轮新写与改动的代码；
- 对抗评审，并用实验验证怀疑；
- 平台事实核对：读本机 CLI 2.1.283 与 2.1.284 的内嵌源码，加官方文档；
- 查被本分支变成假话的陈述。

每条发现再交一位核验者去反驳。一共 34 条，1 条被驳回，其余确认，多数降为低。改动见 §2 各节。

**证据等级**：门禁的行为是在仓库外的夹具上跑子进程实测的，**记录级**。平台的行为，比如 hook
进程的 cwd、`CLAUDE_PROJECT_DIR` 的取值、`isolation` 的两个入口、后台会话的写入拦截，来自
内嵌源码与官方文档，**源码级**，没有起会话实测。

## 2. 这一轮改了什么

### 2.1 项目根（报告第 1 条）

> **补充（2026-09-30，M3v）**：往上找时跳过位于某个 `.agent-team` 目录里的候选——PM 用 Bash `cd` 进 run 目录之后，相对路径的
> Write 会在那里造出嵌套的 `.agent-team`，「离最近的那个赢」就把 run 目录认成了项目根（`docs/30` §3 第三轮的真实会话）。

**问题**：`hooks/gate.mjs` 用 `process.cwd()` 当项目根。平台按会话**当前**的 cwd 起 hook 进程，
而主线程的 Bash 做过 `cd` 之后，这个 cwd 会一直停在子目录里；子代理的 Bash 不跨调用保留 `cd`。
at-pm 就是主线程，持有 Bash，正文还要它跑构建与测试。它只要跑一次 `cd web && npm test`，本会话
余下的时间里 `<子目录>/.agent-team` 就找不到 run，H2 到 H6 全部 fail open，只往 stderr 写一句
「当前没有进行中的 run」。夹具实测：同一组输入，cwd 在项目根时 H3、H4 都拒，换到 `src/server`
就全部放行。

**第一版修法**（`8b7ef59`）：项目根改取平台注入的 `CLAUDE_PROJECT_DIR`。

**复核抓到的回归**：`CLAUDE_PROJECT_DIR` 是**会话启动时**的项目根。平台文档的原话是，move
之后的 hook「still receive `${CLAUDE_PROJECT_DIR}` set to the project root where the session
started」。所以用户 `/cd` 到另一个有 run 的项目 B 以后，第一版的门禁在启动项目里找不到 run，
B 里的一切都 fail open，而修复前它反倒是对的。核验者把两份代码导出来，用同一组输入对照实测过。

**现行口径**（`62a0512`，`hooks/lib/runctx.mjs` 的 `projectRootFrom`）：

- 从 cwd 往上找，离得最近的那个带 `.agent-team` 的目录就是项目根。
- cwd 还在启动项目里时，找到启动项目为止，不越过它。祖先目录（home、外层仓库）里要是躺着一个
  不相干的 `.agent-team`，读错别人的 run 比读不到更糟。
- cwd 已经离开启动项目时，不设上界。
- 哪里都没有 `.agent-team`，就退回 `CLAUDE_PROJECT_DIR`；再没有，就用 cwd。

**同一条的另一半：`isolation`**。平台给子代理的隔离检出有两个入口：Agent 调用参数里的
`isolation`，以及 agent 定义 frontmatter 里的 `isolation: worktree`。插件 agent 的这一项平台
照样生效。隔离出去的子代理要么找不到 run、整体 fail open，要么写回的路径被判成无人认领，它交的
产物也落不回 run 目录。所以两个入口都管上：
- H1 拒绝受管辖调用者带 `isolation` 的派发（`hooks/lib/decide.mjs`）。
- `tests/agents.test.mjs` 给角色 frontmatter 的顶层键加白名单，只许 name、description、tools、
  model、skills 五个键。

**判据**：`tests/project-root.test.mjs` 把 cwd 钉在别处，要么是项目的子目录，要么是 `/cd` 之后的
另一个项目。`gate.mjs` 里项目根的每一处消费点各配一条，改回 `process.cwd()` 就全红。纯函数部分用
注入的探测函数，覆盖「不越界」「离开之后不设上界」「最近的赢」「探测出错不抛」。

### 2.2 判定代码加载失败（报告第 2 条）

**问题**：`gate.mjs` 的静态 import 在 ESM 链接期解析。任何一个 lib 缺失、有语法错误，或在模块
顶层抛错，都发生在它那层 try/catch 建立之前：进程 exit 1、stdout 为空，平台当作 non-blocking
error、工具照常执行。声明 fail closed 的四道门禁就这样整体消失，而推 main 就是发布。

**修法**（`dd3298c`）：加一层进程入口 `hooks/boot.mjs`，`hooks.json` 改为注册它。
- 它只静态 import node 内建模块，再动态 import `gate.mjs`。
- 加载失败时读 `checks.mjs` 的 `failClosed`：fail closed 的输出 deny；fail open 的放行并以
  exit 1 退出，让平台记一条 hook error。
- `checks.mjs` 本身读不到时，按 hook 输入自报的事件取安全方向，PreToolUse 一律拒。
- `deny.mjs` 读不到时，用内置的 PreToolUse 形状。

**复核补的**（`62a0512`）：
- 原来那条「boot.mjs 只静态 import 内建模块」的判据靠正则抠 import，漏了 `export … from` 与
  `import{…}from'…'` 两种写法。改成行为判据：把整个 `hooks/lib/` 删掉，boot 仍须照失败策略收尾。
- `gate.mjs` 外层 catch 与 `crashNotice` 对非 Error 的 throw 不再自己抛。否则一次运行期崩溃会
  掉进 boot 的退路，被报成「代码加载失败，重装插件」。

**裁定：加载失败时的波及面，接受。** 插件装坏以后，这个会话里每一次 Edit、Write、NotebookEdit
都会被拒，主线程也不例外，没有 run 的项目也不例外。这比 `gate.mjs` 里任何一条路径都宽：
那里 H3 对主线程直接放行，H4 对 PM 短路，没有 run 时 fail open。接受的理由：
- Agent 这一侧早有同形的先例：`roster.json` 读坏时，H1 对所有调用者一律拒。
- 修一个坏掉的插件不需要 Edit/Write，要的是重装或更新，拒绝理由里就写着这一步。
- 另一个方向是门禁整体静默消失。

**什么会让答案改变**：要是出现「插件装坏而用户一时修不好、又必须继续用这个会话写文件」的真实
场景，最小的收窄是对输入里没有 `agent_type` 的调用放行并留痕。那样会复制 `callerOf` 的一小段
知识，要配一条对账判据。

### 2.3 CI 与发布纪律（报告第 3 条；改判 `docs/19` §9.2）

**问题**：没有 CI，推 main 就是发布，测试只在一台 Windows 机器上跑过。

**修法**（`f1a6627`、`51c9644`）：
- `.github/workflows/ci.yml` 在 ubuntu、macOS、Windows 三个系统上，各用 Node 22 与 24 裸跑
  `node --test`。
- 推 main、或向 main 提 PR 时，跑 `scripts/check-version-bump.mjs`，核版本号有没有按纪律挪。

**改判**：`docs/19` §9.2 当年裁定发布纪律「只立纪律、不配判据」，理由是「发布」在这个仓库里
没有机械表征。它同时写明，出现 `.github/workflows/` 时要重裁。现在推 main 这个事件有东西在跑
了，所以这条改成有判据。判据只在这两个事件上比事件前后两个提交，开发中的提交不受影响，当年
拒绝它的那条理由（「开发全程都红着」）因此不再成立。

**判定细节**：
- 插件会加载的清单在 `scripts/lib/version-bump.mjs` 的 `PLUGIN_LOADED`，是单一真源。它按
  `docs/19` §9.3 的纪律正文列，再补上 §9.3 漏掉的 `stages.README.md`：at-resume 与 at-status
  在运行时读它的一节。
- `plugin.json` 只改了 version 的那一次，不算改了插件会加载的东西。
- 往回挪一律判红。事件之前的提交拿不到（force push 之后）时，先补拉一次，还拿不到也判红。
- 改名当删除算；路径按原样读，不被 git 加引号转义。

拿 main 的 first-parent 历史回放了 39 对提交：纪律立起来（0.1.1）之后只红了两对，都是只改
文档却没挪版本号的真实违规。

**边界**：main 没开分支保护。CI 对「推 main」只是**事后**告警，用户那时已经能 update 了。
要在发布前拦住，有两条路：
- 开分支保护，把这些检查设为必需，改走 PR 合并；
- 维持现在的做法，约定「先推功能分支、等 CI 全绿，再合进 main 推送」（README「开发」一节）。

改工作流是用户的决定。**用户 2026-09-29 定：维持现状**，走第二条路。

### 2.4 `hooks.json` 接线判据（报告第 11 条）

**问题**：原有判据只核「注册项指向的文件与检查名对不对」，不核挂在哪个事件上、matcher 放进
哪些工具。审查时做了三刀变异：把 H3/H4/H6 的 matcher 改成 `^(Edit|Write)$`、把 stop-gate 挪到
`Stop`、把一条注册复制成两条。三刀都改坏了门禁，套件仍然 910/910 全绿。

**修法**（`1b1dba2`）：以 `checks.mjs` 里各检查项自己声明的 `event` 与 `toolNames` 为真源，逐条
对账 `hooks.json`：
- 每项挂的事件对得上；
- 工具事件的 matcher 放进来的恰好是 `toolNames`，工具宇宙里放了几个「差一点就对」的名字，专抓
  不锚定的写法；
- 生命周期事件不带 matcher；
- 每项恰好注册一次；
- 每条都经 `boot.mjs` 进门。

变异七刀全红。

> **收口（2026-09-29，M3q）**：下面 ⚠️ 那一段说的产品侧路径别名问题（报告第 8、9 条）修了，连同第 31 条
> 的 run id 部分，见 `docs/25`。

判据第一次在别的机器上跑，两处此前只在这台 Windows 机器上成立的假设露了出来（`827d22c`）：

- **macOS 挂 65 条**。`tmpdir()` 是 `/var/folders/...`，而 `/var` 是 `/private/var` 的软链接。
  子进程的 `process.cwd()` 给的是解析后的路径，夹具交给测试的是没解析的。门禁按字面比较路径，
  于是「这是不是契约、这是不是 run 目录」全判成「不是」。修法是 `makeRun` 改发 realpath。
- **Windows 挂 2 条**。盘符大小写的用例写死了 `c:`，而 GitHub 的 runner 把仓库签出在 D 盘，测成了
  跨盘。修法是改取当前盘。

⚠️ **前一处在产品侧有同族问题，没有在这一轮改**：门禁按字面比较路径，项目经由软链接访问、而
模型给的路径与门禁拿到的项目根不是同一种写法时，H3 与 H4 会认错，**而且错在放行的方向**：
「这是契约」判成「不是」。这就是报告第 8、9 条（路径别名）那一族，这一次在 macOS 上实际打了出来。
它要改的是核心比较器 `hooks/lib/path-norm.mjs` 的 `norm`，按目录做 realpath，要单独设计、配
判据。**下一轮优先。**

## 4. 本轮新登记的已知边界

### 4.1 会话中途进了启动项目之下的 worktree

**形状**：cwd 落在 `<项目>/.claude/worktrees/<名>/…`，而那个 worktree 里没有 `.agent-team`。
这时往上找会找回启动项目的 run，拿它去判 worktree 里的写入，执行角色写 worktree 里自己的地盘，
会被 H3 判成无人认领。这与第一版修法的行为相同；修复之前是 fail open。

**为什么先不动**：团队自己进不了 worktree。没有角色持有 EnterWorktree，H1 又拒绝带 `isolation`
的派发，frontmatter 里也不许 `isolation`。能走到这里的只有用户手动让会话进 worktree。

**什么会让答案改变**：有角色需要在 worktree 里干活，或者用户在真实使用中撞上它。

### 4.2 后台会话在 git 仓库里跑不起来

**形状**：这是平台行为，源码级核实。`claude --bg`、agent view 新开的会话、fleet 派发，只要是在
git 仓库里、而 `worktree.bgIsolation` 不是 `"none"`，写共享检出的 Edit/Write 都会被平台拦下，
主线程和子代理都拦，直到会话调了 EnterWorktree 为止。团队里没有角色持有 EnterWorktree，所以
at-pm 连 `.agent-team/` 都写不进去。平台给子代理指的出路是带 `isolation` 重派，而那正是 H1
要拒的。

不受影响的：从交互会话转到后台的 `/bg`（平台为它注入 `bgIsolation=none`），以及桌面端会话。
既往的探针都跑在非 git 目录里，所以落在平台的非 git 豁免分支里，那些实测结论不因此失效。

**这一轮做的**：H1 的拒绝文案补了一句，说清这种情形要停下来交给用户，出路是用户把项目设置里
的 `worktree.bgIsolation` 设为 `"none"`，或者换成前台会话，不要自己去改设置。

**开放**：`at-init` 是否要在 git 仓库里提示用户这项设置，以及 README 要不要写，没定。

### 4.3 其它

- **嵌套的 `.agent-team`**：「离得最近的赢」按目录判，不看里面有没有 run。monorepo 里某个子包单独跑过
  `at-init`、只留下 `project.json`，而真正的 run 在根目录时，cwd 进了那个子包，门禁会在子包里判 no-run、
  fail open。改成「最近的**有 run** 的那个」会让 ledger 认不出子包里新写的 `project.json`（触达表不发），
  同样是边角；两害相权取了简单的那个。**什么会让答案改变**：真实用户撞上它。
- `CLAUDE_PROJECT_DIR` 会注入给 exec 形式的 hook，这一点只在 2.1.283 与 2.1.284 上核过，没有逐版核。
  hooks.json 用的 args 写法要 2.1.139 以上，中间那些版本是推断。
- 平台在并行派发时会建议带 `isolation: "worktree"`。这段提示由服务端特性开关控制，本账号上没开，
  只在 2.1.283 里有；开了的话会与 H1 撞上。代价上限大约是同一上下文里多一次被拒的派发。
- `boot.mjs` 收尾的那一次不留门禁留痕行：`installTrace` 就在没加载起来的 `gate.mjs` 里，
  `hooks/lib/trace.mjs` 头部已写明。

## 6. 没量到的

- **没有起真实会话**。「主线程 cd 之后 hook 在子目录里起进程」「`/cd` 之后 `CLAUDE_PROJECT_DIR`
  不变」都是源码级；门禁在这两种情形下的判定是夹具实测。要记录级，得在一个真实的会话里让 at-pm
  `cd` 进子目录，再看门禁留痕。
