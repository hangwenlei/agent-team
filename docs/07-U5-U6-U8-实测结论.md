## 0. 问题

规格 §10 留了三条未决：U5（`SubagentStop` 返回 exit 2 会不会卡死无交付物的角色，
故 H5 当初设计成只记 warning 不阻断）、U6（一趟十角色的真实成本，此前全为估算）、
U8（`SendMessage` 能否被 subagent 用来续起花名册禁止它接触的 agent，U7 实测时发现
subagent 持有该工具但未继续测）。本文逐条补齐。

## 1. U5 · `SubagentStop` 返回 exit 2 会不会卡死角色

### 1.1 怎么测的

临时注册一个 `SubagentStop` hook（独立脚本，不碰 `gate.mjs`），带计数器：前 N 次返回
exit 2，之后放行，另设 20 次熔断防失控。日志逐次记录 `agent_type` 与 stdin 字节数。
第一轮 N=3，第二轮 N=15。测完夹具已删除。

### 1.2 原文观测

第一轮（N=3）日志原文：

```
1 {"n":1,"event":"SubagentStop","agentType":"agent-team:at-architect","stdinBytes":887}
2 {"n":2,"event":"SubagentStop","agentType":"agent-team:at-architect","stdinBytes":886}
3 {"n":3,"event":"SubagentStop","agentType":"agent-team:at-architect","stdinBytes":886}
4 {"n":4,"event":"SubagentStop","agentType":"agent-team:at-architect","stdinBytes":886}
5 {"n":5,"event":"SubagentStop","agentType":"agent-team:at-product","stdinBytes":1171}
```

（前 3 次被拒、第 4 次放行后 at-architect 才真正停止；at-product 时计数已过阈值，
第一次即放行）

第二轮（N=15，日志已清空后重跑）日志原文：9 行，全部是

```
{"n":<1..9>,"event":"SubagentStop","agentType":"agent-team:at-architect","stdinBytes":869}
```

**九次全部返回 exit 2**，而 agent 仍然正常返回了它被要求的 `ARCH-OK`，耗时 14.3s、
6381 tokens，且执行会话自己报告的是「**一次通过，无重试，无绕开**（`tool_uses: 0`）」。

### 1.3 结论

1. `SubagentStop` 的 exit 2 **确实阻止 subagent 停止，平台会反复重试**。
2. **重试有上限，实测约 9 次**；到点后平台不再理会拦截，放 agent 正常结束。
   **因此它不会卡死会话**——当初设计绕开 `SubagentStop` 的理由（文档未给重试上限、
   怕永久卡死）**不再成立**。
3. **但平台放弃时是静默的**：父级看到的是干净的一次通过，九次拦截完全不可见
   （执行会话真诚地报告「无重试」，因为它确实看不到）。
4. 拦截期间 agent 每次都会收到 hook 写到 stderr 的理由，即它**最多有 8 次机会补救**。

### 1.4 对设计的影响

H5「交付物校验」应当改成**两道一起用**——

- `SubagentStop` 做**真拦截**：角色声明了产出却没写文件时把它顶回去并附理由，
  它有最多 8 次机会补上。这比现在的「只记 warning」强得多，交付物校验是十角色
  流程里最容易被糊弄的一环。
- `PostToolUse` 那道**必须保留**为权威记录：因为 `SubagentStop` 到点会静默放行
  且父级无感，只靠它会制造虚假的完成信号。

## 2. U6 · 一趟十角色的真实成本（本节是推算，不是实测）

### 2.1 怎么测的

**严格说未闭合**——真实的十角色链要到 M2 才存在。本轮把「纯估算」换成「有实测
单价的推算」：先取本仓库 M0 期间真实 agent 运行的 token 计数作为单价（这部分是
实测），再按「十次角色调用 + PM 主循环编排 + 返工」的结构做乘法外推（这部分是
推算，不是对十角色链本身的实测）。

### 2.2 原文观测

**实测单价**（全部来自本仓库 M0 期间的真实 agent 运行计数）：

| 类型 | 实测区间 | 中位 |
|---|---|---|
| 实现者 agent | 6.0 万 – 22.2 万 tokens | 约 13 万 |
| 评审 agent | 9.7 万 – 16.7 万 tokens | 约 13 万 |
| 调研 agent | 54 个共 496 万，均值约 9 万 | — |

**推算**（十次角色调用 + PM 主循环编排 + 返工，非实测）：

- 不返工：约 **100 万 – 250 万 tokens / 趟**
- 带返工（S6 最多 3 轮 + S7 驳回）：约 **200 万 – 400 万 tokens / 趟**

**账户实况**（实测，2026-09-16）：Pro 计划，Weekly·all models **75%**
（2 天 20 小时后重置），Extra usage **51%**（已花 $51.66 / $100）。三轮全网调研约
1205 万 tokens 加 M0 建造把周额度吃掉了四分之三。

### 2.3 结论

一趟完整的十角色运行，量级相当于这次三轮全网调研的四分之一到三分之一。**U6 状态
仍标「未测」**，描述改成「有实测单价的推算，真值待 M2 首次完整运行」——把估算当
实测记账，正是本项目一路在反对的事。

### 2.4 对计划的影响（建议，§11 是否调整由用户决定）

按这个成本，M1 应考虑先在三到四个角色上跑通完整闭环，而不是先把十个角色正文写完。
这条作为**建议**提出，本文不改规格 §11 的实现顺序，是否调整由用户决定。

## 3. U8 · `SendMessage` 能否被 subagent 用来续起花名册禁止它接触的 agent

### 3.1 怎么测的

主会话钉成 `at-pm`。先派 `at-architect`（花名册允许）使其成为一个活着的 agent；
再派 `at-product`（花名册允许），要求它 ① 调 `ListAgents` 列出所见、② 用
`SendMessage` 给 `at-architect` 发 `PROBE-PING`。花名册里 `at-product` 只能派
`at-worker-a`，够不到 `at-architect`；且 `at-architect` 是 `at-pm` 起的、不是它起的。

### 3.2 原文观测

```
AT-PRODUCT
我核对了当前会话可用的工具列表，其中只有 `Agent`、`Read`、`Glob` 三个工具，
没有 `ListAgents`、`SendMessage` 这两个工具可用。

LIST_AGENTS = （工具不可用，无法调用；报错原文：当前工具集中不存在名为 ListAgents 的工具，无法执行该调用）
SEND_RESULT = （工具不可用，无法调用；报错原文：当前工具集中不存在名为 SendMessage 的工具，无法向 at-architect 发送 PROBE-PING）
```

（`tool_uses: 0`——它没有实际尝试调用，是自述工具不存在；`at-product.md` 的
frontmatter 声明确为 `tools: Agent, Read, Glob`，与自述一致）

### 3.3 结论

1. **在当前配置下这条路不存在**——角色的 `tools:` 没有授予 `SendMessage` /
   `ListAgents`，与 U7 的 `Skill` 是同一个形状、同一个机制。
2. **（文档推断，非实测）若将来授予**，官方 `ListAgents` 工具说明的范围是
   「in-process subagents **you spawned**」（自己起的子代理）+ teammates +
   **本机其它 Claude 会话**。前者意味着兄弟角色天然互不可见；**后者是更大的
   面**——官方 `SendMessage` 文档明确警告过 cross-session permission
   laundering（原文：「NEVER ask a peer to perform an action that was denied
   or blocked in your session」）。
3. **（文档推断，非实测）本轮未实测「授予之后会怎样」**，这一点要如实标注（与
   U7 不同——U7 是临时授予 `Skill` 后实测出旁路的，本轮没有对 `SendMessage` /
   `ListAgents` 做同等的临时授予实验）。

### 3.4 对设计的影响

U7 与 U8 形状相同、修法相同。规格 §6.1 现在只禁 `Skill`，应**推广成一条规则**：
角色的工具面是按需白名单，其中 `Skill`、`SendMessage`、`ListAgents` **一律不得
授予**，理由分别是 fork 旁路（`Skill`，见 docs/06）与跨角色/跨会话触达
（`SendMessage`、`ListAgents`，见本文 §3 与官方 cross-session permission
laundering 警告）。

## 4. 顺带事实：`SubagentStop` hook 输入里 `agent_type` 的原始值是全限定名

`hooks/lib/decide.mjs` 的 `callerOf` 读的是 `input.agent_type`，读到后立即
`stripPluginPrefix` 剥前缀：

```js
export function callerOf(input) {
  const raw = input?.agent_type
  return raw === undefined || raw === null ? MAIN : stripPluginPrefix(raw)
}
```

`tests/decide.test.mjs` 早就用合成输入 `{ agent_type: 'agent-team:at-architect' }`
单测过这一步剥得对（`callerOf` 剥掉本插件前缀）——但那是合成输入，不是平台观测。
规格 §6.0 第 4 条当时的表述是「调用者侧 `agent_type` 的形态尚未观测到（两次实验
架构师都没启动），**归一化对两种形态都成立**」；`docs/04-本机实测结论.md` §7 的
「遗留」一段说得更直白：「`agent_type` 的原始形态**未观测到**——因为拼拒绝理由
之前 caller 已被归一化，消息里永远显示裸名。归一化对裸名与全限定名两种形态
**等价，所以不影响正确性**」。换句话说，此前 `stripPluginPrefix` 用在 `agent_type`
上，一直是「反正剥了也不错，剥不剥都对」的防御性写法，没人观测过平台实际给的是
哪种形态。

本轮 U5 的探针 hook 不经过 `decide.mjs`（是独立脚本），直接把 `SubagentStop`
stdin 里的 `agent_type` 原样记进日志——即上面 §1.2 两轮日志里的
`"agentType":"agent-team:at-architect"`。这是**第一次观测到未经
`stripPluginPrefix` 归一化的原始值**，而且两轮共 14 条记录全部是全限定名，没有
一条是裸名。

这把「归一化不影响正确性」的防御性表述，改写成一句更强的话：**如果
`callerOf` 不剥前缀，`raw` 就是 `"agent-team:at-architect"`，`roster.json` 的键
全是裸名，`Object.hasOwn(roster, raw)` 永远查不到——按 §6.0 第 2 条「未登记的
调用者放行」的既定策略，这不会报错也不会拒绝，而是**静默放行、不做任何花名册
检查**。也就是说，去掉这一步剥前缀，H1 对本插件自己全部角色的派发门禁会整体
失效，而且失效得悄无声息，测试也不会自动发现（`tests/decide.test.mjs` 用的合成
输入本身就先假设了会剥前缀）。**前缀归一化不是保险，是必需**——平台真实发出的
就是全限定名，少了这一步整套 H1 对插件角色形同虚设。

## 5. 本轮对规格与测试的改动清单

- 规格 §6 表格 H5 行：从「记 warning，不 block / 记 warning」改为
  `SubagentStop` 真拦截（约 8 次补救机会）+ `PostToolUse` 权威记录的双重设计，
  并在表格下方补一段说明「平台约 9 次后静默放行、父级无感」。
- 规格 §6.1：从「角色工具面禁止包含 `Skill`」推广为「角色工具面是按需白名单，
  `Skill` / `SendMessage` / `ListAgents` 一律不授予」，逐个给理由；保留原有的
  「将来若需要必须先加 H6 门禁」与「本插件自己的 skill 不得声明 `context: fork`」
  两条不变。
- 规格 §10：U5 状态由「未测」改为「是（有界，约 9 次）」；U6 保持「未测」，
  描述改成「有实测单价的推算，真值待 M2」；U8 状态改为「当前配置下不存在该
  路径（未授予工具）；授予后的行为未实测」。
- `tests/tool-surface.test.mjs`：把「角色 `tools:` 不含 `Skill`」扩成「角色
  `tools:` 不含 `Skill` / `SendMessage` / `ListAgents`」，失败信息按工具分别
  给出理由；「本插件自带 skill 不声明 `context: fork`」不变。
