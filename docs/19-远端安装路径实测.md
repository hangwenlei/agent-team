# M3b · 远端安装路径实测 —— 仓库公开那天，两份 README 的安装那一节当场变假

## 0. 一句话结论

**从 GitHub 公开仓库装（`marketplace add hangwenlei/agent-team` + `install ... --scope local`）
装得上，而且在本轮量到的每一条上都与 `docs/17` 那条本地目录源的路径同形**：
主会话同样被钉成 `at-pm`、四条 `/agent-team:*` 命令同样展开得到、
九个可派发角色的 `tools:` 与 `agents/*.md` 逐字一致、H1 派发白名单同样 fail-closed
且拒绝原文逐字相同、`uninstall` 之后新会话同样干净。

**唯一实质不同的那一条，正是 `docs/17` §5.4 记成「我没做」的那一条**：
`CLAUDE_PLUGIN_ROOT` 解析到**哪里**。
本地目录源解析到**源目录**（活连），**GitHub 源解析到 `~/.claude/plugins/cache/` 下那份
脱离 git 的副本**——既不是市场留下的那个 clone，也不是任何工作树。
`docs/17` §3.4.1 把这条记成「很可能」，本轮把它量成了「是」。

⚠️ **而本轮最该被记住的不是这条结论，是它照出来的一件事**：
两份 README 里那句「尚未发布到任何市场」在仓库公开的那一刻变假，
「GitHub 源的插件根解析到哪里没看过」在 §3.2 做完的那一刻变假，
**而把后一句原样塞回 README 再跑整套，772 / 0，一条没红**（§4.1 有实测记录）。
处置见 §7。

### 3.2 ⭐ 第 7 条：`CLAUDE_PLUGIN_ROOT` 指的是 cache 副本——**记录级，本轮的主结论**

`docs/17` §3.4.1 写着：

> **什么时候这条区别会变成真问题**：`source: "directory"` 的市场之外——
> GitHub 源会先 clone 进 `~/.claude/plugins/marketplaces/`，那时加载的**很可能**就是副本
> 而不是源。

**「很可能」量出来了，而且它猜中了一半、猜错了一半。**
猜中的是「加载的是副本不是源」；**猜错的是副本在哪**——不在
`~/.claude/plugins/marketplaces/`（那个 clone 一次都没被引用过），
在 `~/.claude/plugins/cache/`。

**三份独立证据：**

**一、命令正文里的展开。** `d1b1f3fd` 的转录里，`commands/at-status.md` 正文中的
`${CLAUDE_PLUGIN_ROOT}` 被展开成：

    插件的 `C:/Users/82370/.claude/plugins/cache/agent-team-marketplace/agent-team/0.1.0/stages.json`（阶段链）

**二、六份转录里搜遍三个候选路径**：

| 候选 | 命中 |
|---|---|
| `~/.claude/plugins/cache/agent-team-marketplace/…` | **有** |
| `~/.claude/plugins/marketplaces/…`（那个 clone） | **0** |
| 本仓库工作树 `C:\Users\82370\Desktop\Agent-Team` | **0** |

⚠️ **第三行差点被我判错，方法上的坑写在这里。** 第一次用
`grep -c "Desktop.Agent-Team"` 去扫，每份转录都报二十多条命中，看起来像是
「会话在读本仓库」。**那二十多条全部是假的**——探针工程自己的路径里就含着
`C--Users-82370-Desktop-Agent-Team`（scratchpad 按本仓库名压平出来的目录名）。
换成只认真实分隔符的 `Desktop\Agent-Team` / `Desktop/Agent-Team` 之后，**命中 0**。
**这是 `docs/16` §3.11 那个形状（「我查过的地方没有」≠「没有」）的镜像**：
这一次是**「我查到的命中」≠「真的命中」**，成因同样是判据比它要答的问题宽。

**三、逐字节比对。** 把 cache 副本与本仓库工作树（此刻 = BASE）整目录 diff：

    $ diff -rq --strip-trailing-cr ~/.claude/plugins/cache/agent-team-marketplace/agent-team/0.1.0/ \
                                   /c/Users/82370/Desktop/Agent-Team/
    Only in ~/.claude/plugins/cache/agent-team-marketplace/agent-team/0.1.0/: .in_use

（`.git` 与 `.superpowers` 两项已排除——前者副本没有，后者不在版本库里。）
**除了 CLI 自己加的一个 `.in_use` 标记目录，零差异。**
副本里**没有 `.git`**：`git -C <副本> rev-parse HEAD` 报
`fatal: not a git repository`。

#### 3.2.1 这三条证据支持什么、**不支持**什么——别把它读宽了

**支持的**：本轮这个会话加载的是那份 cache 副本；那份副本的内容等于 BASE；
安装记录里钉着 BASE 的哈希。

**不支持的，逐条**：

- **「往仓库推新 commit 不会改变已装的那一份」**——这是**推论**，不是实测。
  本轮**没有推过任何 commit**，也**没有跑过 `claude plugin update`**。
  副本没有 git 远端、安装记录钉着哈希，这两条让这个推论很自然，
  但**「很自然」正是 `docs/17` §3.4.1 上一轮用过的那个词，而本轮把它证伪了一半**。
  按 §5.3 记成「我没做」。
- **「`docs/17` 那条本地目录源是活连」**——那条在 `docs/17` §3.3.1 里就明写着是**推论**
  （「本轮没有去改源目录验证这一点」）。本轮同样没有去验它。
  **两条路径各有一半是推论，而两份 README 里一句都不许这么写**——措辞按此改（§7）。

### 3.3 第 4 条：主会话被钉成 `at-pm`——**记录级**

六个会话的转录里**每一个**都有 `type: "agent-setting"`、值为
`"agentSetting":"agent-team:at-pm"` 的记录（装着的五个各 3 条上下）。

`e1b7c1e4` 里 `at-pm` 自述的系统提示原文：

> 你是 **AT-PM**，项目经理，也是这个团队里**唯一能问用户的角色**。

它报的工具面是

    Agent / AskUserQuestion / Bash / Read / Glob / Write / Edit

与 `agents/at-pm.md` 的 `tools:` 声明相同（`Agent(...)` 的参数表收敛成 `Agent`）。

⚠️ **`docs/17` §4.2 那条更正在本轮仍然适用，而本轮没有机会用上它**：
`agent-setting` 记录**不是**「此刻还被钉着」的充分条件，判它要**同时**看有没有那条
`type: "system"` / `level: "warning"` 的降级告警。**本轮六个会话一条降级告警都没有**
（也没有任何 `--resume`，见 §5.2），所以两条口径给出同一个答案；
**这不等于那条判据在本轮被复核过**。

#### 3.4.1 `at-init` 不只展开了，它**真的跑完并落了盘**——这条是收尾时捡到的

**但 `at-init` 那一个在被停掉之前已经把活干完了**：收尾删探针工程时，
`app/.agent-team/` 下有 `project.json` 与 `reach.json` 两份文件

## 4. 本轮新出的两条

### 4.1 ⭐ 一句「我们没做过 X」的话，在 X 被做掉的那一刻自动变假，而**没有任何机械形状会因此改变**

`docs/11` §5.20 四记的那条是：**判据把真源选在冻结文档上，它就不是判据，是一句注释。**
本轮照出来的是它的**下一级**：**有些话根本没有真源可选。**

两份 README 的「有意不写，因为没有实测过」那一段里，M2d 留下了这一句（英文那份）：

    Neither has any marketplace that is not a local directory: a GitHub-sourced install may
    resolve the plugin root somewhere else entirely, and this project has not looked.

**它在 §3.2 做完的那一刻变假。** 而本轮的实测是：

- 把它（连同中文那半句）改对之后，整套 **772 / 0 全绿**；
- **把英文那一句原样塞回去再跑，仍然 772 / 0，一条没红。**

**成因不是哪条判据写窄了，是这一族话的形状**：「我们没做过 X」的真值取决于
**仓库之外发生了什么**（有没有人去做 X），而仓库里没有任何东西随之改变。
**它与 §5.20 四那条的区别值得写清楚**：那一条的真源存在、只是选错了（选了冻结文档）；
**这一条是没有真源**。

**拿得到的那一点，和它不假装的那些：**

处置是把这两句加进 `tests/readme-sync.test.mjs` 的 `RETIRED_CLAIMS`
（连同「尚未发布到任何市场」那一句的中英两半，共四条）。
**这条判据钉的是一张退役原话清单，不是「任何把某件事说成没做过的写法」**
——换一种措辞把同一件事说回去，它仍然不会红。
**这不是这次加进去的四条写窄了，是这一族没有更强的那条可拿**：
穷举「把某件事说成没做过」的写法是开放集合，`docs/16` §3.4 判过它的结构性上限。

⚠️ **所以这一节真正的产出不是那四条判据，是一条可照做的话**：
**每次做掉一件 README 里写着「没做过」的事，回去删那句话是收口的一部分，
而不会有任何测试提醒你。** 这与 `docs/11` §5.19 的第三问（「同一刀砍下去，
还有谁本该说话？」）是同一句，只是这一次答案是「**没有谁**」——
而「没有谁」本身必须被写下来，否则下一个人会以为有。

### 4.2 `docs/17` §5.4 那条「我没做」被做掉了，而它的**上一版猜测对了一半**

`docs/17` §3.4.1 的原话是「GitHub 源会先 clone 进 `~/.claude/plugins/marketplaces/`，
那时加载的**很可能**就是副本而不是源」。

**对的那一半**：加载的确实是副本，不是源。
**错的那一半**：副本不在 `marketplaces/`，在 `cache/`；而 `marketplaces/` 下那个 clone
**一次都没有被引用过**（§3.2 证据二）。

**这条值得单独记，理由在方法上**：那句猜测**读起来像是在说位置**
（它点名了一个具体目录），实际承重的只有「是副本不是源」那半句。
**一句推论里哪一半承重、哪一半是顺手写的，写的时候分不开，被引用的时候更分不开。**
`docs/17` 当时把整句都标成了「推论」——**那个标注是对的，也正是它救了这一次**：
如果当时把那句写成结论，本轮就是在推翻一条已经写进记录的「事实」。

**可照做的**：推论要标，而且**标的是整句**，不是句子里你自己觉得弱的那一半。

**「装上之后就冻住了」如果为真，它对一个刚公开的仓库是一条很重的用户可见行为**

## 8. 续测 · 装上之后那份副本会不会随上游更新

⚠️ **这一节是 §5.3 那条「我没做」被做掉之后追加的，同一天（2026-09-21）。**
**§0–§7 一个字没改**，只在 §5.3 末尾加了一条指向这里的注记。
上面每一句仍然说的是那一轮：那一轮确实没有推过 commit、没有跑过 `claude plugin update`。

### 8.0 一句话结论

**「装上之后就冻住」是真的，而且它冻得比 §5.3 那条推论猜的还要硬一格。**

| 你做了什么 | `marketplaces/` 那个 clone | `cache/` 那份副本（真正被加载的） |
|---|---|---|
| 什么都不做 | 不动 | **不动** |
| `claude plugin marketplace update <市场>` | **拉到上游最新 commit** | **不动** |
| `claude plugin update <插件>@<市场> --scope local`，上游动了但 `version` 没变 | 拉到最新 | **不动**，回执是「已经是最新版本」 |
| 同上，但 `version` 变了 | 拉到最新 | **新开一个版本目录**，旧的原样留着 |

**承重的是中间那一行**：`claude plugin update` 比的是 `.claude-plugin/plugin.json` 里的
**`version` 字符串**，不是 commit。上游真的往前走了一个 commit、
市场 clone 也已经站在那个新 commit 上，**只要 `version` 没变，它回
`✔ ... is already at the latest version (0.1.0).` 然后什么都不做**（§8.4.3 有原文）。

⚠️ **对这个仓库当下的直接后果，写在最前面**：
`.claude-plugin/plugin.json` 的 `version` 从 `0.1.0` 起**一次都没动过**，
而今天已经往 `main` 推了两次。**所以「别人昨天装的，拿不拿得到今天推的修复」的答案是：
拿不到，`claude plugin update` 也拿不到。**

**那怎么才拿得到**：`claude plugin uninstall` 再 `claude plugin install` 一遍。
这条路单独量过（§8.4.6，**而且是在真的 `hangwenlei/agent-team` 上量的**）：
`install` 撞上一个已经存在、内容是旧的同版本目录时，**把它整个重写**，
不是「目录在就跳过」。两份 README 按此改（§8.6）。

**第五条**：一个**已经在跑的会话**，在一次真的生效了的 `plugin update` 之后，
下一轮仍然展开**旧版本**的命令正文——与 CLI 自己打的 `Restart to apply changes.` 一致（§8.4.5）。

⚠️ **追记（同一天，M3d「发布纪律」）：上面那句「`version` 从 `0.1.0` 起一次都没动过」
今天不再成立——它被做掉了。** 本节正文一个字没改，它记的仍然是写下它那一刻的事实；
**这一轮做了什么、没做什么、以及这个数以后按什么规矩挪，全在 §9。**
⚠️ **而这条注记本身正是 §8 那条 concern 的收口**：concern 原话是
「这个仓库今天没有任何发布纪律，改了插件却不动版本号对已装的人完全无声，
而仓库里没有任何测试会因此变红」——**前两句已处理，第三句仍然成立**（§9.2 是裁定，不是遗漏）。

### 8.2 为什么是两条路，而不是一条

#### 8.2.1 B 路那个远端是怎么起来的——以及 CLI 只认哪几种源

`claude plugin marketplace add` 的 help 写着 `Add a marketplace from a URL, path, or GitHub repo`。
实测**它认哪几种**：

    fatal: unable to access 'http://127.0.0.1:9/at-probe.git/': The requested URL returned error: 502

**`file://` 与 `git://` 在格式检查那一关就被顶回，`http://` 过得去**

所以 B 路的远端必须是 **HTTP smart 协议**：

- 裸仓库 `scratchpad/.../upstream/at-probe.git`（`git init --bare --initial-branch=main`）；

自检：`git ls-remote http://127.0.0.1:8899/at-probe.git` 回
`b8328fc...	HEAD` / `b8328fc...	refs/heads/main`。

⚠️ **B 路那个插件不是 agent-team，是一个叫 `at-probe` 的一次性插件**
（市场名 `at-probe-marketplace`，内容只有 `.claude-plugin/` 两份清单、一个
`MARKER.txt`、一条 `commands/probe-cmd.md`）。**这是有意的**：本节要量的是
**CLI 的更新机制**，那是 CLI 这一层的事、与插件内容无关；
而换个名字同时躲开了与 `agent-team@skills-dir`、以及与 A 路那个安装的命名撞车。

**这条界限要说清楚**：B 路量到的是**机制**（`update` 拿什么当判据、副本往哪写、
运行中的会话跟不跟）。它**没有**量 `hangwenlei/agent-team` 在 GitHub 上被更新时的
那一趟具体 I/O。两边的共同点是 A 路量到的那几条（浅克隆、`install` 先刷新、
`update` 的回执形状）在两条路上**逐字同形**；不同点是 HTTPS 与本机 HTTP 的传输层。
**「传输层不影响版本比较逻辑」是推论，不是实测**，按 §8.5 记成「我没做」。

#### 8.2.2 一条走不通的路，留痕——而它作废的原因本身就是一条结论

**上游真的往前走了一个 commit，那个 commit 改的正是这个插件自己的命令文件，
市场 clone 已经站在它上面——而 `plugin update` 说「已经是最新版本」，然后什么都不做。**

⚠️ **这一条是本节唯一一条「结论与直觉相反」的**，所以把它是怎么被隔离出来的写清楚：
`docs/19` §3.1.1 量到安装记录里钉着 `gitCommitSha`，于是很容易顺着读成
「它按 commit 决定要不要更新」。**那个字段是一条记录，不是一个判据**——
它被写下来，但更新时没有被拿去比。**「字段存在」不等于「字段承重」**，
与 `docs/19` §4.2 那条「一句推论里哪一半承重」是同一个形状，只是这次的载体是一个 JSON 键。

#### 8.4.4 第 4 问之三：`version` 变了它才动，而且是**新开一个目录**——**记录级**

push 掉 V3（`a98e506..7253c7f`，`version` `0.1.0` → `0.2.0`）之后
（**注意这一步之前没有单独跑 `marketplace update`**，`plugin update` 自己去刷新的）：

    $ claude plugin update at-probe@at-probe-marketplace --scope local
    Checking for updates for plugin "at-probe@at-probe-marketplace" at local scope…
    ✔ Plugin "at-probe" updated from 0.1.0 to 0.2.0 for scope local (C:\...\m3c\probe2\app). Restart to apply changes.

    $ ls ~/.claude/plugins/cache/at-probe-marketplace/at-probe/
    0.1.0
    0.2.0
    $ cat .../at-probe/0.2.0/MARKER.txt
    UPSTREAM-STATE=V3
    $ cat .../at-probe/0.1.0/MARKER.txt
    UPSTREAM-STATE=V1

安装记录整条被改写，指向新目录：

    "installPath": "C:\\...\\cache\\at-probe-marketplace\\at-probe\\0.2.0",
    "version": "0.2.0",
    "installedAt": "2026-09-21T13:02:17.545Z",
    "lastUpdated": "2026-09-21T13:05:21.071Z",
    "gitCommitSha": "7253c7f405f6074e0b6e7b1440a04ae2b591e082",

**旧版本目录一个字节都没动，也没被删。** 再更新一次（V4，`0.2.0` → `0.3.0`）之后，
`cache/at-probe-marketplace/at-probe/` 下是 `0.1.0`、`0.2.0`、`0.3.0` 三个目录。

⚠️ **这条与 `docs/19` §3.1.1 那句「`uninstall` 不清 cache」合起来才是完整的那句话**：
cache 下的东西**只增不减**——更新一次多一个版本目录，卸载一次一个都不少。
两份 README 的卸载那一段按此扩（§8.6）。

#### 8.4.5 第 5 问：一个**已经在跑的**会话，更新之后仍然是旧的——**记录级**

`claude --bg` 起的后台会话只能收第一条消息，CLI 也没有命令能往一个活着的会话里发第二条
（`attach` 要交互终端）。所以这一条用 **`claude -p --input-format stream-json`** 量：
一个进程、一个会话、两轮用户消息，中间隔着一次真的更新。

- **第 1 轮**（此刻装着 `0.2.0` = V3）：`/at-probe:probe-cmd` → `PROBE-COMMAND-BODY-V3`；
- 第 1 轮结束、**这个会话仍然活着**时，外面 push V4 并跑
  `claude plugin update ... --scope local` → `updated from 0.2.0 to 0.3.0 ... Restart to apply changes.`；
- **第 2 轮**（**同一个进程、同一个会话**）：`/at-probe:probe-cmd` → **仍然是 `PROBE-COMMAND-BODY-V3`**。

四个会话的转录一起看（`grep -o PROBE-COMMAND-BODY-V[0-9]`）：

| 会话 | 起的时机 | 展开到 |
|---|---|---|
| `86bf522b` | 装完 V1 之后 | **V1** |
| `c7d5faea` | 上游已到 V2、什么都没跑 | **V1** |
| `42bd3cb1` | 活会话，两轮跨一次成功的更新 | **两轮都是 V3** |
| `b12d012c` | 更新到 `0.3.0` 之后新起 | **V4** |

⚠️ **这一条的证据只到「运行中的会话拿到的是旧正文」为止，别读宽。**
本节**没有**把「为什么」隔离出来：更新是**新开目录**的，
所以那个会话的 `CLAUDE_PLUGIN_ROOT` 指着的旧目录**至今仍然存在、内容仍然是旧的**
——「会话把注册表缓存在内存里」与「会话每次都去读盘，只是那个盘上的路径没变」
**两种机制会给出同一个观测**。要分开它们得去改那个旧目录再问同一个会话一次，
**我没做**（§8.5）。**用户可见的结论在两种机制下相同，机制不同**。

#### 8.4.6 ⭐ 那条真的拿得到更新的路：**卸了重装**——**记录级，这一条跑在真 GitHub 上**

§8.4.3 只回答了「`plugin update` 拿不到」，**没有回答「那怎么才拿得到」**。
而两份 README 要给用户一条能照做的路，所以这一条单独量，**而且是在真的
`hangwenlei/agent-team` 上量的**（第三个探针工程 `m3c/probe3/app`）。

`cache/<市场>/<插件>/<版本>/` 这个路径**按版本号编址**，所以「重装」撞上的正是
一个**已经存在、而且内容是旧的**同名目录——它会不会被重写，是这条路成不成立的全部。

    $ claude plugin marketplace add hangwenlei/agent-team --scope local
    ✔ Successfully added marketplace: agent-team-marketplace (declared in local settings)
    $ claude plugin install agent-team@agent-team-marketplace --scope local
    ✔ Successfully installed plugin: agent-team@agent-team-marketplace (scope: local)
    （副本 133 个文件，取一份 md5 清单 R1）
    $ claude plugin uninstall agent-team@agent-team-marketplace --scope local
    ✔ Successfully uninstalled plugin: agent-team (scope: local)
    （副本仍在——与 docs/19 §3.1.1 那条一致）

**把留下的那份副本弄成「旧的」**，两处，一处加一处减：

    $ echo STALE-EDIT-MARKER >> <副本>/roster.json
    $ mv <副本>/docs/19-远端安装路径实测.md <scratchpad>/moved-away-docs19.md

然后原地重装：

    $ claude plugin install agent-team@agent-team-marketplace --scope local
    ✔ Successfully installed plugin: agent-team@agent-team-marketplace (scope: local)
    $ grep -c STALE-EDIT-MARKER <副本>/roster.json
    0
    $ ls <副本>/docs/ | grep -c 19-
    1
    $ diff R1 R2
    （无输出）

**加进去的那行没了，搬走的那份文件回来了，整份清单与一次全新安装逐行相同。**
所以 **`uninstall` + `install` 会把那份副本整个重写，而不是「目录已存在就跳过」**
——这就是今天唯一一条真的拿得到新代码的路，两份 README 按此写（§8.6）。

⚠️ **这一条里有一处是合成的，写清楚**：让副本变「旧」用的是手工改两个文件，
**不是**让上游真的往前走。两者对这条判据来说是同一件事——
`install` 面对的都是「一个同版本、但内容与上游不一致的目录」——
**但它们不是同一个因**。**「上游真的动了之后重装能拿到新代码」是推论**，
按 §8.5 记成「我没做」。

⚠️ **M3b/M3c 那几轮门禁修复不在这个差额里**：它们是在 `0.1.0` 这棵树里**一起公开的**
（`fb0c9ba` 已经含着它们）。**这一条是本判断成立的前提**——如果它们落在差额里，
下面那句「没有行为改动」当场为假。

**所以：公开以来没有任何行为改动，挪最后一位 → `0.1.1`。**

**两条各自被单独核过、而不是一起想当然的事**：

1. **README 的修改不算行为改动。** 安装时整棵树（含 `README.md` 与 `docs/`）
   都会被复制进 `cache/`，所以它们**确实是发出去的内容**；但插件加载时不读它们，
   而绝大多数人读的是 GitHub 上那一份，**那一份与版本号无关、始终是最新的**。
2. **`tests/` 的修改同样不算。** 插件不加载 `tests/`，`node --test` 也只在本仓库里跑。

**顺带一条约束，它对本轮不生效、对下一轮起就生效**：
`0.1.0` → `0.1.1` 在**两种可能的比较语义**下都是往前走
（文本比较 `"0.1.1" > "0.1.0"`，semver 同向）。
⚠️ **而 §8 从来没有把 CLI 用的是哪一种隔离出来**——§8.4.4 量的是
`0.1.0 → 0.2.0 → 0.3.0`，**三步都是两种读法一致的那种**，所以那三步分不开它们。
**两种读法第一个会分道扬镳的实物是 `0.9.0` → `0.10.0`**：按 semver 是往前，
按文本是**往后退**（逐字符比到第三位，`1` 小于 `9`）。
§8.5.5 把「`version` 是非 semver 的串」记成了「我没做」，**但没有记这一条**
——它不是非 semver，它是**合法 semver 而文本序相反**。补记在 §9.5，
两份 README 的纪律里也写了一句「不要让任何一位数长到 `10`」。

### 9.2 判据 vs 纪律：判的是**纪律**——三样逐样付

**先把两难摆出来，不绕开它。**

真判据的形状大概是：**`HEAD` 的 `version` ≠ 上一次改
`agents/`/`commands/`/`hooks/`/`skills/`/`stages.json` 那几个目录时的 `version`**。
**它能红，是真的。** 但它会在**每一个碰这几个目录的开发中 commit 上红**
——而这个仓库的做法就是一轮几十个 commit，版本号合理地只在最后动（或者压根不动，
因为那一轮只改了文档）。**一条在每个正常工作日全程都红着的判据等于没有判据，
而且比没有更坏**：人会学会忽略它，于是它在真正该红的那一次也不会被看见。

**更底下那一层**：**「发布」这个事件在这个仓库里今天没有任何机械表征。**
本轮现场核过三样——`git tag -l` **空**；**没有 `.github/`**，更没有
`.github/workflows/`；`scripts/` 下只有一个 `dev-link.mjs`。
**推 `main` 就是发布，而 `git push` 不在工作树里留下任何产物。**
**没有事件，就钉不住「发布时必须怎样」**——`node --test` 分不出一个轮中 commit 与一次发布。

⚠️ **裁定：这一条不配机械判据。** 按 `docs/16` §3 开头那条规矩，三样逐样写在下面。

**① 我拒绝写的那条判据（X）长什么样**：
从 git 历史里取出「最近一次改 `agents/` / `commands/` / `hooks/` / `skills/` /
`settings.json` / `stages.json` / `roster.json` / `templates/` 的那个 commit」，
读它那一刻 `.claude-plugin/plugin.json` 的 `version`，与 `HEAD` 的 `version` 比；
**相等就红**，红的含义是「你改了插件会加载的东西而没有挪版本号」。

**② X 打不红的那一刀**：**三刀，一刀比一刀便宜。**

- **最便宜的那刀：X 根本没有机会红。** 它在开发全程都红着，所以它的红**没有信息**。
  真正该红的那一次（发布前最后一个 commit）与前面几十次长得一模一样。
  **要让它只在发布时红，就得知道哪一次是发布——而那正是仓库里不存在的那个事件。**
- **第二刀：把版本号改成一个别的字符串就够了。** X 比的是「变没变」，
  不是「发布了没有」。把 `0.1.1` 改成 `0.1.1-wip` 也让它转绿，
  **而那个串在 CLI 那头是什么行为，§8.5.5 明写没量过。**
- **第三刀，也是最狠的：`git push` 不在树里留产物。** 一个人可以在本地
  挪了版本号、commit 了、X 全绿，**然后不推**；也可以从一条分支上直接推一次热修。
  **X 能核的只是树里的字，而这件事的失败发生在树之外**——
  与 `docs/16` §3.9 ① 那条「最狠的一刀是出错的那一步根本不在仓库里留下产物」同形。

**③ 什么会让答案改变**：**只要「发布」长出一个机械表征，X 就有东西可比，这条豁免就该重新考虑。**
具体地说，下面任何一样出现，都够：

- 每次发布打一个 **annotated tag**（于是 X 变成「`version` 必须大于最近一个 tag 上的 `version`」）；
- 出现 **`.github/workflows/`**，也就是有东西在 push 到 `main` 这个时刻真的跑一次；
- 出现一份 **`CHANGELOG`**，且它最新一条必须与 `plugin.json` 的 `version` 一致
  ——这一条不需要 git 历史，**纯粹是树内两处的一致性**，是三样里最便宜的。

**在那之前它是豁免，不是永久。**

⚠️ **第三条路（先给「发布」造一个机械表征，再钉它）——本轮判成不值得，理由两条**：

1. **tag 是 ref，不是树内容。** 一次 `git clone` 不带 `--tags` 拿不到它，
   而**装好的那份 `cache/` 副本连 `.git` 都没有**（§3.2 逐字量过）。
   **一条基于 tag 的判据，从用户真正加载的那个产物上根本无法复核。**
2. **造发布流程是动机制**，本轮 brief 明令不碰机制；
   **而为了让一条判据有东西可钉去造一个流程，是本末倒置**——
   `docs/16` §3.9 逐字写着「硬造一条会更糟，这个仓库为它栽过两次」。

**归属规则**（照 `docs/16` §3.11 末尾，不写成「再犯 N 次」）：
**下一个给这个仓库加 CI、加 tag、加 `CHANGELOG`，或者第二次去改 `version` 的人，
负责连这一条一起裁。** 在那之前这一格的状态是**已知、可观测、没钉**——不是「不需要钉」。

⚠️ **本轮确实新加了判据，但它钉的不是发布纪律，别读混了**：
新加的那一条（`tests/twin-list-sync.test.mjs`）钉的是 §9.4 那两张同族清单的条目数必须相等。
**发布纪律这一侧，本轮一条判据都没加。**

### 9.3 纪律正文落在哪、说了什么

**落在两份 README 的「开发 / Development」那一节**，中英两份逐段镜像
（它们被 `tests/readme-sync.test.mjs` 的标题配对表钉着）。
**为什么是那一节而不是新开一份 `docs/`**：这是一条给**改这个仓库的人**看的规矩，
而 `Development` 正是这个仓库放这类规矩的地方（那一节原本只有一条：裸 `node --test`）；
`docs/` 是给下一个实现者看的记录，**一条要被天天照做的规矩放进去等于埋掉**。

**口径本身**（这是这个仓库第一次写下它）：

- **推 `main` 是本项目唯一的发布事件，所以每一次推 `main` 都挪 `version`。**
- **只碰了散文 / `docs/` / `tests/` → 挪最后一位**（patch）；
- **碰了插件真正会加载的任何东西 → 挪中间那一位**（minor）：
  `agents/` · `commands/` · `hooks/` · `skills/` · `settings.json` · `stages.json` ·
  `roster.json` · `templates/` · `.claude-plugin/` 下两份清单。
- **任何一位数都不要长到 `10`**，直到有人把 §9.1 末尾那个比较语义量出来。

**两份 README 的安装那一节同时改了两处**，因为本轮把它们说的话变成了假话：

1. 「`claude plugin update` **多半也搬不动它**」——**版本号会动之后这句不再成立**，
   改成「搬不搬得动它，取决于一个字符串」，后面那一整段的机制描述**一个字没改**
   （它量的是 CLI 行为，仍然为真）。
2. 「**本仓库的清单至今写着 `0.1.0`，从第一个 commit 起就没动过**」——**本轮落盘即为假**，
   改成写清楚「公开后头三次推送那个串一次都没动，所以谁也没收到；现在有规矩了」。

⚠️ **改法上守了两条**：

- **新正文里不写当前版本号。** 写了就是把同一个数在仓库里存第二份
  （`docs/16` §3.4 / `docs/11` §5.15 那个形状），而它没有判据钉着。
  §8 引的那句 `is already at the latest version (0.1.0)` **原样留着**——
  它是一次实测的**引文**，是过去时，永远为真。
- **重装那条路一个字没删。** 它是**不依赖任何人记性**的那一条；
  纪律是规矩不是机制，而 README 里必须留着一条在规矩被忘掉时仍然有效的路。
  **README 里也明写了「没有任何测试会因为有人忘了它而变红」**
  ——`docs/16` §3.7：把有风险的说成没风险，是这一族里最贵的那种。

### 9.4 第五次：「本轮没有做 X，而下一轮紧接着就做了 X」

**这一轮正是那张清单的第五个实物**，而且形状与前四次完全一样：
§8（`e5006d6`/`243a7e2`）当轮写下「这个仓库今天没有任何发布纪律」并把
「本仓库的清单至今写着 `0.1.0`」写进两份 README，**下一轮（本轮，同一天）就把它做掉了**，
那句 README **落盘即为假**。

**两张同族清单都加了第五条**：`docs/16` §3.9 的 M3b 追记、`docs/11` §5.23 修复轮 2 的收口块。

⚠️ **那条归属规则（「下一个往这张清单加条目的人，负责把两份合成一份、或者写下为什么不合」）
本轮走的是第三条路：不合并，改成给它写判据。** 理由：

- **合并要从一个带日期的收口块里删掉正文**，而这个仓库的规矩是带日期的记录**原话不改**
  （`docs/16` §3.6）。为了造一个单一真源去改写一份记录，**换来的毛病比治掉的大**。
- **更要紧的是，合并根本不治那个defect。** 那条归属规则说的毛病是
  「**改一边另一边不会红**」——那是**没有判据**，不是**有两份拷贝**。
  合成一份之后，同一份知识仍然会被第二处引用，引用一样会过期，**同一族**。
- **而那条判据是写得出来的**：两张清单的**条目数必须相等**。
  `tests/twin-list-sync.test.mjs`——往一边加一条而忘了另一边，**当场红**。
  ⚠️ **它钉不住的那一半写清楚**：它只钉**条目数**，
  **不钉条目内容**——把一边某一条改写成另一件事，它全绿。
  两张清单今天本来就不是逐字相同（第 3 条两边写的是不同的实物），
  **所以「逐条相等」这个更强的口径今天就红，不能用**。

⚠️ **这条判据的自检锚当场被一次存活变异逼着改窄了一次，记在这里**：
初稿用来钉「起始锚必须唯一」的那个合成样本，**同时犯了两种毛病**——两个 `START`
**和**两个 `END`。于是把起始锚那一格从「恰好一次」放宽成「至少一次」，
**这条自检照样绿**（变异 M8 第一轮存活）：报错是从**结束锚**那一格出来的，
起始锚那一格根本没被走到。**两个样本各自只犯一种毛病**之后，M8 与新加的 M8b 各自红。
**这是 §3.12「洞不长在判据的缝里，长在两条判据之间」的又一个实物，
而且它长在本轮新写的十几行代码上**——成因也是那一节点名的那个：
一个样本同时触发两条检查，于是它们互相兜底，谁也没被单独钉住。

### 10.3 本节新出的三条

#### 10.3.1 ⭐ `cache/<市场>/<插件>/<版本>/` 下有一对生命周期标记，而它们解释了「旧目录为什么删不掉」

**`.in_use/` 是一个目录，里面每个活着的使用者一个文件，文件名就是进程号**：

    $ cat …/agent-team/0.1.0/.in_use/37408
    {"pid":37408,"procStartFt":"134344729003805158"}

`procStartFt` 是进程启动时刻的 Windows FILETIME——**带着它，一个被回收复用的 pid
不会被误认成还活着**。这个文件在那个活会话起来的那一刻（`07:01`）出现，
在它退出之后消失（收尾时两个版本目录的 `.in_use/` 都是空的）。

**`.orphaned_at` 是一个文件，内容是一个毫秒时间戳**：

    $ cat …/agent-team/0.1.0/.orphaned_at
    1789999418264

它在 `plugin update` 成功、`0.1.1/` 被建起来的那一刻出现在**旧目录**上。
**而 `uninstall` 也会写一个**：卸载之后 `0.1.1/` 上也出现了 `.orphaned_at`（`1789999603297`）。

⚠️ **这一对合起来是一个「标记 + 引用计数」式的回收机制**，
它让 §8.4.4 那条「新开目录、旧的原样留着」从一个观测变成一个**有机制的**观测：
旧目录不是被忘了，是**被标成了孤儿等着回收，而回收要等没人占着它**。
**但「标了之后到底什么时候、由谁来删」本节没有量到**（§10.5.2）——
本轮观测到的是：卸载完两个目录都带着 `.orphaned_at`、都还在，
**最后是我手工 `rm -rf` 删的**。所以 §8.6 写进两份 README 的那句
「`cache/` 下只会长不会消」在**用户可见**这一层仍然成立。

#### 10.3.2 `raw.githubusercontent.com` 会在 `git` 协议已经看得见新 commit 的同一时刻回旧内容

控制方推完之后，同一分钟里：

    $ git ls-remote …/agent-team.git refs/heads/main
    ce1cb314147404ea06b281414c9abcf717495df9          # 已经是新的

    $ curl …/hangwenlei/agent-team/main/.claude-plugin/plugin.json | grep version
      "version": "0.1.0",                             # 还是旧的

    $ curl -D - …/main/.claude-plugin/plugin.json
    Cache-Control: max-age=300
    Source-Age: 252

    $ curl …/hangwenlei/agent-team/ce1cb314…/.claude-plugin/plugin.json | grep version
      "version": "0.1.1",                             # 按 commit 取就是新的

**按分支名取的那条路有一个 5 分钟的 CDN 缓存**，`Cache-Control: no-cache` 请求头与
查询串 cache-buster **都没有把它绕开**；按 commit sha 取立刻就是新的。

⚠️ **这一条不影响本节任何一条结论**——`claude plugin` 这一侧走的是 `git clone`/`fetch`，
不是 `raw`，而 §10.2.2 那次 `marketplace update` 当场就拉到了 `ce1cb31`。
**记它是因为它差一点把本节的第一步判错**：
如果只用 `raw` 去确认「上游动了没有」，会得到「控制方还没推」这个错误结论，
而真相是推完了、只是那条 URL 还在回旧的。**核远端状态要用 `git ls-remote`，
或者按 commit sha 取 `raw`，不要按分支名。**

#### 10.3.3 装上之后，`agent-team@skills-dir` 在 `plugin list` 里换了一行字——**这是遮蔽，不是状态变更**

这台机器上有一个 user 作用域、`✘ disabled` 的 `agent-team@skills-dir`（指向开发工作树的软链）。
本轮的探针插件在**市场清单里也叫 `agent-team`**，于是装上之后：

    ❯ agent-team@skills-dir: ✘ Not loaded — the name "agent-team" is already taken by an
      installed plugin (agent-team@agent-team-marketplace), which takes precedence. …

**三条依据说明这不是我动了它**：① 全程没有 `enable` / `disable` / `uninstall` / `update`
过它；② `~/.claude/settings.json` 与基线**逐字节零 diff**，`"agent-team@skills-dir": false` 未变；
③ **`docs/17` 第 171 行早已逐字记过同一条 `already taken` 遮蔽**——M2d 那轮探针就观测到了，
是**已知行为**。收尾卸载之后那一行回到了 `Status: ✘ disabled`（§10.6）。

⚠️ **值得留一句的是这条遮蔽的方向**：被遮蔽的是那个 `✘ disabled` 的软链，
**遮蔽它的是一个新装上的同名插件**。也就是说，`disabled` 并不保护一个名字——
**一个 `disabled` 的插件仍然占着名字，而一个新装的同名插件会把它整个顶掉。**
这一条对本仓库有直接意义：开发者本机常常同时有「软链那一份」与「装上的那一份」。

**这一轮正是那张清单的第六个实物**，而且这一次的形状比前五次更直白：
§9.5.2 逐字写着「`0.1.1` 推上去之后……真的能拿到——**我没做**」，

要么还没推（没有新的可拿）。
**所以这条归属规则的毛病不是「没人认领」，是「认领的那个角色做不了这件事」。**
§3.9 那张清单前五条问的都是「保鲜期」，**这一条问的是另一件事：归属指给了谁。**

### 10.5 本节新出的「没能验证的项」——**逐条说清是哪一种**

分四类：**环境不允许** / **需要人来操作** / **结构上不可能** / **我没做**。
**本节四条里三条是「我没做」、一条是「需要人来操作」。**

#### 10.5.1 「上游真的动了之后，卸了重装能不能拿到新代码」——**我没做**

⚠️ **这一条是 §8.5.4 原样留下来的，本轮**有**机会做而没有做**，要说清楚。
本轮收尾确实跑了 `uninstall`，**但没有再 `install` 一次**——
收尾的目标是把机器还原成基线，再装一次就与那个目标冲突。
量它要在收尾之前多插一段：`uninstall` → `install` → 核新副本。**就是没做。**
**归属**：下一个开这类探针的人，在收尾之前顺手多跑一次 `install` 就拿到了。

#### 10.5.2 「`.orphaned_at` 标上之后，那个目录什么时候、由谁真的被删」——**我没做**

§10.3.1 量到了标记**被写上**的两个时刻（更新时写给旧目录、卸载时写给当前目录），
**没有**量到回收那一头：是下一次 `install` 顺手清、还是有定时清理、还是永远不清。
量它要么等（不知道等多久），要么去翻 CLI 自己的实现。
**本轮两个目录最后都是我手工 `rm -rf` 删的**，所以这一条没有观测到自然的终点。

#### 10.5.3 「CLI 比两个 `version` 串用的是 semver 还是文本序」——**我没做**

与 §9.5.1 同一条，**本轮仍然答不了**：`0.1.0` → `0.1.1` 两种读法同向。
控制方明确交代不要为了答它去造 `0.9.0` / `0.10.0` 的假版本推上去，
**所以本轮只顺带记一句：CLI 打出来的两种措辞
（`updated from 0.1.0 to 0.1.1` 与 §8.4.3 那句 `is already at the latest version (0.1.0)`）
里没有任何能区分这两种读法的字样**。这不是证据，是「找过、没找到」。

### 11.3 ⭐ 夹具：为什么不必跑一趟真流程

§5.1 把这件事的成本估成「一次完整流程」。**核下来不是。**
读一遍 `hooks/gate.mjs` 就能看出：H3 / H4 / H5a / H5b 都靠 `readRunContext` 从
**用户项目的磁盘上**读 `.agent-team/`，而那个函数**只校验形状，不校验来历**
——它不问这份 run 是谁建的、是不是 `/at-init` 跑出来的。
（`rework` 更省：它**根本不经过 `readRunContext`**，只认「这次写的是不是
`runs/*/state.json`」。）

所以夹具是**四个文件**，一个约 30 行的零依赖 node 脚本写出来的：

| 文件 | 内容 | 它让哪一道有话可说 |
|---|---|---|
| `.agent-team/current-run` | `20260921-1530-gatecheck` | 让 `ctx.ok` 为真，H3/H4/H5 才走得到判定 |
| `.agent-team/runs/<id>/state.json` | `stage: S2`、`roster: ["at-product"]`、`rework: {S2: 2}`、`history` 里 S2 三次 | H5 的阶段判据；H6 的「派生值是 2」 |
| `.agent-team/runs/<id>/00-contract.md` | 一行 `probe step1` | H2 的 `requires`；H4 要保护的那个文件 |
| `.agent-team/project.json` | 照抄 `templates/project.json` | H3 的 `project.paths` 一侧 |

**一趟真流程买到的是「真实性」，不是「可达性」。** 而 §5.1 那一轮要量的恰恰只是可达性
——**门禁会不会被调起来**，与那份 run 是怎么来的无关。这一条写进 §3.9 那张清单（第 7 条）。

⚠️ **动手之前先用装好那份副本里的 `gate.mjs` 跑了一遍预检**（喂合成输入、`cwd` 钉在探针目录，
写法仿 `tests/helpers/gate-runner.mjs`）。**这一步证明的是夹具对不对，不是平台会不会调 hook**
——后者只有真实会话能答，这条分界线在本节里不含糊。预检的价值是：
**它先把每一道该说的原话摆出来**，真实会话里再拿到同一段文字时，
「这是不是同一道门禁在说话」就不用猜。

### 11.5 本节新出的三条

#### 11.5.1 ⭐ 两道门禁同时拒同一次写入时，平台只把**其中一条**理由交给调用方——而且不是排在前面的那一条

`--agent general-purpose` 那一次写 `00-contract.md`，**H3 与 H4 都该拒**：
`writepath` 看到 `00-contract.md` 是 S1 的产物、归 `at-pm`，调用者不是它；
`contract` 看到调用者不是契约写者。**用装好那份副本逐个 check 跑过，确认两道都 deny**：

    agent_type=general-purpose  check=writepath -> deny
    agent_type=general-purpose  check=contract  -> deny

**而真实会话里只出现了 `contract` 那一条**——`writepath` 的那句
「`general-purpose` 不得写 …」在整份转录里**出现 0 次**。

⚠️ **关键在于它不是「第一条胜出」**：`hooks/hooks.json` 里这一组的顺序是
`writepath` → `contract` → `rework`，**胜出的是第二条**。
**这条对使用者是有后果的**：一次同时撞上两道门禁的写入，**只会被告知其中一道的理由**，
而被隐去的那一条可能恰恰是更该先修的那一条。
⚠️ **本轮只观测到一次，n = 1**——**按什么规则选的那一条，本轮没去找**（§11.6）。

#### 11.5.2 `SubagentStop` 的重试上限，实测是 10 次

`hooks/gate.mjs` 与 `hooks/lib/deliverable.mjs` 两处都写着「约 9 次」，
H5a 那条发给 PM 的告警正文里也逐字带着这个数。**本轮平台真的发了 10 次。**
**「约」这个字让它不算错**，但如果哪天要把这个数写进判据，
**它是 10，不是 9**，而且这是一次观测、不是一条规律（§11.6）。

#### 11.5.3 角色层会在门禁之前先拒绝，而这件事在「门禁强制」这个卖点上要说清楚

三次派子代理去撞 H4，**两次它在发出工具调用之前就自己拒绝了**，
理由逐字来自它自己的角色说明。**这不是缺陷**——两层都在做该做的事，
而且外层先拦下来更省。**但它改变了一句话的分寸**：
「门禁强制」在真实运行里**不是第一道防线，是第二道**；
第一道是角色说明，而角色说明**是模型在遵守，不是机器在强制**。
本轮之所以还是把 H4 量到了，靠的是**把第一道拿掉**（换一个不属于本插件的主会话角色）
——**那不是用户的正常路径，所以这一格的「真实性」比另外五格低一档，写在这里。**

### 11.6 本节新出的「没能验证的项」——**逐条说清是哪一种**

分四类：**环境不允许** / **需要人来操作** / **结构上不可能** / **我没做**。
**本节五条里四条是「我没做」、一条是「需要人来操作」**，
前两类一条都没有——理由与 §5 开头那段一字不改地同样适用。

1. **「H4 拒绝一个 `agent-team` 角色」——我没做。**
   本轮量到的 H4 拒的是 `general-purpose`（§11.4.4）。**判定逻辑走的是同一条路**
   （`isContractWriter` 只认 `MAIN` 与 `at-pm`，别的一律不是），
   **但「那边同形」不是「这边量过」**。两次派 `at-product` 都被角色层挡在前面；
   我**没有**再去找第三种办法——能想到的几种都要靠误导自己的子代理，**那个我不做**。
   （这既不是环境不允许，也不需要人来操作：换个角色、多试几轮措辞都在手上。**就是没做。**）
2. **「两道同时拒绝时平台按什么规则选那一条」——我没做。**
   §11.5.1 只有一次观测。是固定顺序、是先返回者胜、还是别的，**本轮没去找**。
3. **「`SubagentStop` 的重试上限是不是恒等于 10」——我没做。**
   §11.5.2 是一次观测。没有重复第二次，也没有换一种拒绝理由试。
4. **「`ledger` 的触达表分支」——我没做。**
   `.agent-team/project.json` 是夹具脚本写出来的，**不是会话写的**，
   所以那条只为 `/at-init` 留的缝（写 `project.json` → 回传 `reach`）本轮没被走到。
   让会话自己写一次 `project.json` 就能量，**没做**。
5. **「交互终端（真人手里那种）下的复核」——需要人来操作。**

⚠️ **一条操作上的坑，留痕**：`claude --add-dir <dir>` 的参数是**变长**的，
