## 总览

agent-team 的工程纪律整体扎实：有 910 条判据、做过变异验证、边界登记簿也很详细。门禁判定在以下前提下是对的：hook 的 cwd 就是项目根、路径按规范写法给出、PATH 上有合适版本的 node、控制文件能被解析、PM 按正路推进。本轮核实下来的问题，几乎都出在这些前提不成立的时候。唯一定为 high 的一条是门禁用 process.cwd() 当项目根：主会话 PM 执行一次常规的 `cd 子目录 && npm test`，或以 worktree 隔离派发，本会话余下的时间里 H1 以外的全部门禁都会静默放行。修法只需一行（改用 CLAUDE_PROJECT_DIR），而现在没有任何判据钉住这件事。其次是一组声明为 fail-closed、实际却 fail-open 的路径：lib 模块加载失败、PATH 上没有 node、或 CLI 早于 2.1.139 时，门禁整体消失。仓库又没有 CI，推 main 就是发布，一次坏提交就能直达所有用户。门禁本身有三处可绕过：H6 返工预算用两次 Write 就能清零，在 CRLF 文件上用一次多行 Edit 也能清零；路径比较只是字符串比较，Windows 短名、ADS、设备前缀和 macOS 大小写变体能让不持 Bash 的 at-acceptance 改写契约和 state.json；受信的账本回传会原样回显 state.json 字段，可以借此向 PM 注入伪造的指令。流程语义上：返工协议在提示层是空白，上一轮的旧产物会让 H2/H5 失明；阶段推进没有判据；H2 给跨段的 at-ui 选错阶段；H5b 与各角色的冒泡指令互相冲突。可观测性上：所有 fail-open 告警只写到模型和用户都看不到的 stderr；hooks.json 的接线也没有判据，被多刀变异改坏后仍然 910/910 全绿。多数危害受「本插件不是沙箱、Bash 不经门禁」这一已登记定位的限制，真正的增量集中在不持 Bash 的角色，以及正常操作下的无意触发。大部分修复是 S 级，建议按排序先做前 11 条。

## 逐条详情

### 1. 门禁以 process.cwd() 当项目根：主会话一次 cd 进子目录，或以 worktree 隔离派发，H1 以外的门禁全部静默放行

- **严重度**：高　**工作量**：S　**类别**：platform-assumption
- **位置**：hooks/gate.mjs:41（const ROOT_PROJECT = process.cwd()）及 :759（H6 拼 agentTeamDir）；hooks/lib/runctx.mjs:157-203（只看 <cwd>/.agent-team，不向上查找）；H1 派发分支（hooks/lib/decide.mjs）不检查 Agent 的 isolation 参数

**问题**　所有检查项都假定 hook 进程的 cwd 等于用户项目根。平台实际在 hookInput.cwd（会话当前 cwd）里起 hook 进程。主线程 Bash 执行 cd 后，这个 cwd 会一直保持，而 CLAUDE_PROJECT_DIR 不变。at-pm 是主线程、持有 Bash，正文还要求它跑构建与测试，所以一次常规的 `cd web && npm test`，或用户在主会话里执行 `! cd`，就足以触发。此后 PM 本身和它派出的所有子代理，hook 都在子目录里起进程，readRunContext 判为 no-run。于是 H2、H3、H4、H5a、H5b、ledger 全部 fail open，只往模型看不到的 stderr 写一句「当前没有进行中的 run」，还把排查方向引到 current-run 上。H6 因为 agentTeamDir 拼错，整段跳过，一个字节都不输出。以 isolation: worktree 派出的子代理同理，而 H1 不检查这个参数。对原报告的两处订正：子代理自己的 cd 不会跨调用保留，真正的触发者是主线程 PM 或用户；改用 hookInput.cwd 修不了，因为它本身就是漂移后的值。

**证据**　两位核验者读了本机 CLI 2.1.283 的内嵌源码，确认三点：hook 按 hookInput.cwd 起进程；主线程的 cd 会保持；子代理的 Bash 设了 preventCwdChanges。仓库外假项目实测：cwd 在项目根时，at-backend 写契约、写 src/ios、写 state.json，PM 把 rework 清零，S5 派 at-acceptance，全部 DENY。只把 cwd 换成 proj/src/server，这些全部变成 ALLOW，H5b 由 exit 2 变为 exit 0，H6 零输出。变异把第 41 行改成 CLAUDE_PROJECT_DIR 优先后，上面各项恢复 DENY。原版与变异版的套件都是 910/910 全绿，说明没有判据钉住这一假设。

**登记状况**　未登记。docs/04 只核过会话启动时 cwd 等于项目根。M1a 计划曾把它列为待核问题，预测的后果是 fail closed，这个预测已经过时。docs/11、docs/16 里没有 cwd 漂移或 CLAUDE_PROJECT_DIR 的记录。

**修法**　1）把 gate.mjs:41 改为 `process.env.CLAUDE_PROJECT_DIR || process.cwd()`，runctx 从这个根开始找 .agent-team（可以再向上查找）；no-run 提示里写出实际查找的目录。2）H1 对团队角色拒绝带 isolation 参数的派发。3）加子进程判据：cwd 为子目录、CLAUDE_PROJECT_DIR 为项目根时，H3/H4/H6 必须 deny；再加一条带 isolation 的派发被 H1 拒绝。

### 2. 模块加载期或解释器层失败时，声明 fail-closed 的门禁整体放行

- **严重度**：中　**工作量**：S　**类别**：fail-open
- **位置**：hooks/gate.mjs:10-33（静态 import）、:35-49（顶层语句与 installTrace）、:1280-1304（try/catch 只包住 main()）

**问题**　四道声明 failClosed 的门禁（delegation、writepath、contract、rework）只在 main() 内部崩溃时才会 deny。任何一个 lib 缺失、有语法错误或在模块顶层抛错，都发生在 ESM 链接阶段，此时 catch 还没建立：进程 exit 1、stdout 为空，平台按非阻断错误处理，工具照常执行。推 main 就是发布，所以一次坏提交就能让所有用户的门禁同时失效。

**证据**　核验者在仓库外的副本里删掉 hooks/lib/rework-guard.mjs，或往 trusted.mjs 末尾追加一行语法错误，再用本应被拒的输入跑 delegation、writepath、contract。结果全部是 exit 1、没有 deny JSON，stderr 是 ERR_MODULE_NOT_FOUND 或 SyntaxError 的栈。官方 hooks 文档写明：其他退出码且 stdout 为空时，the action proceeds as a non-blocking error。

**登记状况**　未登记。docs/11 §1.4 和 gate.mjs 末尾的注释只讨论了 main() 内部的崩溃。gate.mjs:1297-1302 的注释说兜底分支「外部不可触发」，实测可以触发。

**修法**　把 gate.mjs 拆成一个薄 bootstrap：只做 readStdin 与 argv 解析，用 try { await import('./gate-main.mjs') } catch 包住动态 import。加载失败时，按 checks.mjs 的 failClosed 表输出 deny JSON。加一条子进程判据：用 --import 注入一个会抛错的模块，或在副本里删掉某个 lib，断言四道 fail-closed 检查仍然 deny。

### 3. 没有 CI、main 没有保护、推 main 就是发布：坏提交直达用户，POSIX 上从没跑过测试

- **严重度**：中　**工作量**：S　**类别**：release-engineering
- **位置**：仓库根（没有 .github/workflows）；GitHub hangwenlei/agent-team 的 main 分支设置；tests/writepath.test.mjs:327、332（Windows 专属用例缺 skip）

**问题**　发布纪律完全靠人：没有 Actions，main 没有保护，没有 PR，测试只在这台 Windows 机器上跑过。结合第 2 条，任何没跑测试就推上去的语法错误，都会让所有用户的门禁 fail open。macOS 和 Linux 上的路径大小写、stderr 行为等差异，从来没有被执行验证过。

**证据**　gh api 查得 actions workflows 的 total_count 为 0，branches/main 的 protected 为 false；git ls-files 里没有 .github/。在 git archive 导出的副本里跑 node --test，910/910 通过，约 18 秒，CI 的成本很低。

**登记状况**　部分登记。docs/19 §9.2 裁定「版本纪律只立纪律、不配判据」，并付了三样；docs/21 §7 第 7 条登记了 POSIX 未测。但那条裁定的前提（没有可挂钩的发布事件）用 CI 就能消除，而且它没有评估坏提交会让门禁全体 fail open 的后果。

**修法**　1）加 .github/workflows/test.yml：ubuntu、macos、windows 三个系统，各配最低支持的 Node 与最新 LTS，跑裸 node --test。2）给 main 开分支保护，把这个检查设为 required status check。3）修掉 writepath.test.mjs:327、332 缺的平台 skip。4）可以在 CI 里顺带检查 plugin.json 的 version 相对上一个提交有没有变化。

### 4. 运行前提没有声明：需要 PATH 上有 Node、Claude Code 不低于 2.1.139，前提不满足时门禁全开

- **严重度**：中　**工作量**：S　**类别**：platform-assumption
- **位置**：hooks/hooks.json（8 条注册全是 exec 形式，command 为 node 加 args）；README.md（徽章与正文写「零运行时依赖」）；.claude-plugin/plugin.json

**问题**　门禁要靠 PATH 上的 node 起进程，而官方原生安装的 claude 本身并不需要 Node。hooks 的 args 字段是 2.1.139 才加的，更旧的 CLI 会把 hook 退化成裸 node 读 stdin，报 SyntaxError 后 exit 1。这两种情况下 gate.mjs 一行都不执行，角色与 PM 照常加载，六道门禁静默消失。Node 版本过低（缺 Object.hasOwn）时，H1 反而会拒掉 PM 的合法派发，造成死锁。README 却对外写着零运行时依赖。

**证据**　官方 setup 文档：The installed claude binary does not itself invoke Node。官方 hooks 文档：A hook that can't start lands in the same non-blocking bucket。CHANGELOG 2.1.139 条：Added hook args (exec form)。实测把 PreToolUse 输入管给裸 node，得到 SyntaxError、exit 1、stdout 0 字节。用 -r 预先删掉 Object.hasOwn 后，at-pm 的合法派发被拒。

**登记状况**　未登记。README 删掉 CLI 版本号，是 HANDOFF「README 对外只写结论」这条决策的结果；但用户侧的运行前提属于应当照写的用法与风险。

**修法**　1）README 中英两半的安装一节写明需要 PATH 上有 Node（按实际用到的 API 定最低版本，例如 18），以及 Claude Code 不低于 2.1.139；把「零运行时依赖」改为「零 npm 依赖」，同步改 tests/readme-sync.test.mjs。2）commands/at.md 第 0 节加一步自检：跑 node --version，不满足就停下告诉用户。3）可选：加一个 SessionStart hook 输出存活标记，at-pm 正文要求没看到标记就停手。

### 5. H6 返工预算用两次 Write 就能清零，全程没有任何回传

- **严重度**：中　**工作量**：S　**类别**：gate-bypass
- **位置**：hooks/lib/rework-guard.mjs:33（任一侧不是普通对象就 ok:true）；hooks/gate.mjs:800-812（parseOrNull）
