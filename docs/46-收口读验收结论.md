# 收口读验收结论：验收结论的固定首行，推进出验收段与收口时门禁读它，照现状交付由用户经规范标签批准

> 2026-10-06，M4k，分支 `m4k-close-reads-acceptance`。`docs/39` §5 第五轮的后一半「收口读验收结论」：`docs/35` §5 登记的「收口不读验收结论」，

> 已由前一半「契约的账」兜住，`docs/45`）。开工之前做了一轮设计评审，实现照评审之后的设计（§8）。

## 0. 一句话结论

- **验收结论的固定首行**：`07-acceptance.md` 的第一个非空行写三句之一——「结论：通过」「结论：不通过」「结论：判不了」。有一条没过就是不通过；
  没有没过、有判不了的就是判不了；全都过了才是通过。
- **门禁读它**：推进出验收那一段（S7）与收口时，H6 读这一行；不是「结论：通过」、又没有门禁记下的「照现状交付」批准，拒，出路按首行分。
  【阶段】在 S7 齐了时也读它，S8 的收口阻碍里也列它。
- **照现状交付是用户的决定**：用户在 AskUserQuestion 里选了「照现状交付」、或者在对话里单独发了这一句，门禁记进 `approvals.jsonl`，按 sha 绑在
  那一刻的验收结论上（结论再改一个字就不算了）。它之后的第一次改契约算记这条答复，不算改需求、验证段的结论不用重出；之后只往那几块修订块里补写
  也不算。一份验收结论只批一次、只盖一次修订。

## 1. 修法

### 1.1 验收结论的固定首行

- 新模块 `hooks/lib/verdict.mjs`（单一真源）。首行的规定与判法写进 `agents/at-acceptance.md` 的「你判什么」。
- `acceptanceVerdict`：取第一个非空行，NFKC 之后匹配。行首容许 Markdown 装饰（`#`、`>`、`*`、`_`、反引号、`-`）与「【；「结论」前面可以带「验收」；
  冒号两侧容许空白与强调。「不通过」「判不了」按前缀认——后面夹了话（「结论：不通过（第 2、3 条没过）」）照认，拦的效果一样；「通过」严格，之后
  只容许强调、空白、句末标点与」】。认不出（「结论：通过（第 3 条判不了）」、第一行是标题、逐条的写法）给 null，算读不出。BOM、CRLF 照读。
- `acceptanceOf`：产者里有 `at-acceptance` 的验证段与它的产物（插件自带的链上是 S7 与 `07-acceptance.md`），不写死文件名。

### 1.2 H6 读它（`decideAcceptance`，排在 H6 最后）

- 只管两种写入：推进（往阶段链后面挪，而且验收那一段在到达段之前——插件自带的链上就是推进出 S7）与收口（`closed_at` 新写上、写入前没收口；
  写入前的 `state.json` 读不出也算收口，与 `decideClosing` 同一个口径）。回退、原地重写、补记别的字段不判。
- 跳过：验收那一段整段裁掉、这一趟在那一段谁都没叫过（`advance.mjs` 的 `wholeStageTrimmed`）；验收结论不在、空的、还是上一轮的（前面的判据
  已经拒了）。放行：首行「结论：通过」；或者 `approvals.jsonl` 里有门禁记下的照现状交付批准，sha 等于验收结论现在的 sha。
- 拒绝理由按首行分：
  - 不通过：照 `/agent-team:at` 第 3 节「回退」回到要重做的那一段。
  - 判不了：要人补跑测试的回 S6；新行为缺自动化测试的回 S5；环境跑不起来的照第 4 节 `env-blocked` 问用户；契约或完成定义没写清楚的照第 4 节
    `contract-hole` 问用户。
  - 读不出：还在 S7 的，在 S7 同段重派 `at-acceptance` 照格式重写（同一段里重派不计返工）；在 S8 的（收口时），照「回退」回到 S7（写明 S7、S8
    各记一轮返工）。
  - 照现状交付的出路按首行写：在什么情形下才轮得到问用户（不通过：返工预算耗尽、用户说不修；判不了：环境跑不起来、返工预算耗尽、用户说不补），
    escalation 记哪一类 kind，交付那一项的标签逐字写「照现状交付」。首行读不出、还在 S7 的不附（同段重派不花钱）。
  - 末尾接批准记录的诊断（与返工预算那一支同一份）：门禁找不到进行中的 run 时，用户的回答会记不下。
- 阶段链上认不出验收那一段（插件的 `stages.json` 改坏了）：不读，留一行痕。
- 排在契约基线判据之后：对着上一版契约的结论先重出，读它的首行才有意义。

### 1.3 照现状交付的批准（扩展 `approval-ask`、`approval-prompt` 两个记录器）

- 规范标签 `DELIVER_LABEL = '照现状交付'`，与返工批准的标签同在 `hooks/lib/budget.mjs`（`verdict.mjs` 原样再导出）。认法同一套归一化（NFKC、删掉全部
  空白、剥一次末尾的推荐后缀），整条等于它才算；含有它却夹了别的话的，算「像批准却认不出」。排除也同一套：多选、数组形状、离开键盘、追问、
  另写了一段话、选项旁写了备注。
- 记不记（`approvals.mjs` 的 `planApprovals` 新一支）：已收口、没有验收结论（不在、空的）、还是上一轮的、对着上一版契约的（契约基线记着——测试报告
  与验收结论有一份对着上一版就算）、首行是通过的、这一份验收结论已经记过的（同一次里两道题都选了也只记一条）——不记，各给原因；别的记一行
  `{ at, source, kind: "deliver-as-is", product, sha }`。返工批准的 `readGrants` 只认带 `covers` 的行，返工上限
  不受影响。
- 回传（approval-ask 的【门禁】）：记下了——只对现在这份验收结论有效；照第 4 节补 escalation 的 `answer`、答复写进修订块、交付文档写明哪些没过
  没验证、再推进或收口。没记下——按原因说，重问说的是照现状交付的标签。approval-prompt 照旧一个字不往 stdout 写。
- 给用户的一行：记下、没记下各一句「agent-team 照现状交付：…」；记录器读不出输入、出错的那两句改叫「批准记录」（那一刻还不知道是哪一种批准）；
  加载失败、Node 太旧、崩溃时给项目经理与用户的那几句也说两种批准都要再批一次。返工预算那一问的门禁文字写明「这一轮的」验收结论，问不了用户时也给
  照现状交付的标签。
- 门禁专属文件的拒绝理由、`/agent-team:at-status` 的「返工批准」一行跟上。

### 1.4 与契约基线（M4j）的衔接：批准之后的第一次修订不算改需求

- 照现状交付的答复照第 4 节写进修订块。照 M4j 按修订块标题分，它多半算改需求（多在 `contract-conflict` 那一问里，或者用户主动说的）：重拍验证段
  快照，刚批准的那份验收结论成了「对着上一版契约」，重出之后 sha 变了、批准作废，绕不出来。
- 修法：契约基线多记两项：`deliver_used`（用过的照现状交付批准，按验收结论的 sha 记）与 `deliver_blocks`（用掉批准的那几块修订块的标题）。契约修订时，
  `approvals.jsonl` 里有验收结论现在这份的照现状交付批准、`deliver_used` 里还没有它：这次修订不算改需求，只换指纹与标题，sha 记进 `deliver_used`、这次新加的
  修订块记进 `deliver_blocks`，【契约】说一句。之后修订指纹不计那几块——往里面补写不算修订；改别处、加新块照常判。一份验收结论只盖一次修订。
- 不靠项目经理在标题里写标记：设计稿原来让照现状交付的答复在标题末尾加「· 照现状交付」，评审指出漏写会绕圈、冒充只要一行字（§8 F1、F2）。

### 1.5 【阶段】

- S7 齐了时也读首行（与 H6 同一份 `acceptanceBlock`；验收结论对着上一版契约的不说——H6 先按契约判据拒、出路是重出）：项目经理写 `state.json` 时收到「推进出 S7 会被 H6 拒」与出路；`at-acceptance` 写出读不出的首行，
  回传叫它自己把第一行改好再停（它有 Write，省一次重派）；`at-acceptance` 写出没过的首行，说推进会被拒、由项目经理定、回报时照实说。
- S8 的收口阻碍多一种（`closing.mjs` 的 `blockerLine`）：首行没过又没批准时列它与出路，不说「该收口了」；验收结论已经因为缺、空、上一轮的、对着上一版
  契约列在阻碍里的不重复列。
- 返工预算那一问（`budget.mjs` 的 `askUserText`：H6 的拒绝理由、【阶段】、【返工预算】共用）加一句：验收结论已经写成、第一行不是「结论：通过」的，
  可以加第三个选项「照现状交付」。

## 4. 仍然开着的边界

- **首行跟下面逐条一不一致不核**：写「结论：通过」、下面有没过的条目，门禁照通过算；验收角色判错了，门禁看不出。
- **测试报告的结论不读**：验收那一段整段裁掉时，收口不读任何结论。
- **H5b 不核首行格式**：`at-acceptance` 停下时不拦；它写 `07-acceptance.md` 那一刻【阶段】叫它改，推进出 S7 时 H6 拒。
- **Bash 写得进**：`approvals.jsonl` 与 `07-acceptance.md`（与别的门禁专属文件同一档）；项目经理用 Edit/Write 改验收结论，H3 已经拒。
- **批准按 sha 绑**：原样重写（逐字相同）还算。
- **用掉批准的那几块修订块**：之后往里面写的任何东西都不算修订（包括真改需求的话）——门禁不读内容；改了那一块的标题就不再认它。
- **M4d 之前派出 `at-acceptance`、没有派发记录的旧 run**：先单独一次写入删名字、再写 `trimmed` 并收口，门禁不读验收结论（与 `docs/35` §5「改 `stage_roles`
  绕开叫过」同一档）。
- **「批准之后的第一次改契约」不看内容**：批准之后先为别的事改了一次契约，那一次就用掉了批准，之后记答复的那一次照标题分，可能算改需求、要重出；
  真改需求的修订赶在批准之后的第一次，也被当成记答复的那一次。
