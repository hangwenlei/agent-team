# 返工轮认得出上一轮的产物

**日期** 2026-10-01 ｜ **口径** 分支 `m3y-rework-freshness`（`59c9250`、`0941feb`、`6bc2c85` 与其后的复核修订），版本 `1.7.0`；修的是全量审查（`docs/24-附录-全量审查报告.md`）
第 15 条。真实会话在本机 CLI 2.1.286 上

## 0. 一句话结论

交没交、齐没齐的判据——H5a/H5b 的交付物、【阶段】与 H5a「停在旧阶段」的判齐、H2 的「齐了就跳过前置」与前置在不在——原来只问文件在不在。
回退之后上一轮的产物都还在磁盘上，于是回退那一刻【阶段】就催推进，执行角色零改动停下 H5b 放行，`at-qa` 不重跑也放行，H2 被旧产物满足、
连前置都不查。现在 `state.json` 多一个 `rework_base`：回退那一次写入照磁盘记下各份产物的 sha（H6 对着磁盘核），之后到下一次回退为止原样带着；
磁盘内容与它记的 sha 相同的产物就是上一轮的，上面那几道都不把它算成这一轮交的。PM 声明「这一轮接受它原样」就把那一条改成 `"accepted"`；
推进离开一段时，那一段里还是上一轮的产物会让 H6 拒掉推进。没回退过、`rework_base` 缺失或为 `{}` 的 run，判定与 v1.6.0 相同。

## 1. 问题（审查原文与复现）

  夹具设为 S6、`history` 里有一次回退到 S5、`06-test.md` 是上一轮的，`at-qa` 带着「我没有重新跑测试」停下，仍是 status 0。

  提前开工也没人拦——S5 的实现记录还在，H2 判 S5「齐了」、前置不查；之后每一段重进都判齐（级联）。第 14 条留下的「返工轮一回退就判齐」
  （`docs/32` §4）是同一件事。
- 唯一的真实返工样本（`docs/15` 那一趟）里，各角色自发重写了产物；门禁并不要求这件事。那一趟的 `rework.S6` 是 1，`docs/15` 把它记成
  「第二次返工」，是误读：S6 只回退过一次，回到 S6 时 S6 在 `history` 里第二次出现，H6 按派生量要求 `rework.S6` 加 1——转录里 11:49:41

  11:49:51 是 PM 读回磁盘、照旧是 S5，11:50:08 补上 `S6: 1` 重写才通过，`at-qa` 11:50:40 才派出去。订正写在 `docs/15` 原话的三处标题底下与 `docs/11` 那一节里；`hooks/lib/coverage.mjs`

  算好的整份。

## 2. 修法

### 2.1 `rework_base`

- **形状**：`{ 产物名: sha 或 "accepted" }`。sha 的口径与 `artifacts` 同一个（`sha256OfContract`：先统一 BOM 与行尾），只改行尾不算重写。
- **回退写入**：`history` 新追加的条目里，有一条所在段在阶段链上不晚于它前一条（往回走，或原地再进一次，含 S5→S5；前一条可以是写入前就有的
  最后一条）。回到的段 T 取最后那条回退条目的段。
- **回退那一次写入记什么**：T 及之后各段（每一段按全部 `producers` 展开，`stages.mjs` 的 `productsOfStage`，不按这一趟叫到谁——上一轮叫过、这一轮
  没叫的人留下的那份同样是上一轮的）在磁盘上的每一份产物：现在的 sha；写入前 `rework_base` 里 T 之前各段的合法条目原样带过来（第二次回退到
  更晚的一段时，更早那次回退留下的条目不丢）。读不出来的产物不核（不写、写一个 sha 都行）。应当记的一份都没有时，缺失与 `{}` 都放行。
  所在段不晚于这次写入后 `stage` 的产物，sha 那一格这一次就可以写成 `"accepted"`（真实会话之后改的，见 §3）。
  所以 `rework_base` 记的不全是「最近一次回退那一刻」的 sha：T 之前各段沿用更早那次快照。
- **之后到下一次回退为止**：每一次写入原样带着——键集合不变，值只许不变、或从 sha 改成 `"accepted"`，而且那份产物所在的段不晚于这次写入后的
  `stage`。写入前没有快照（缺失或 `{}`）时，之后只许缺失或 `{}`：快照只在回退那一次生成。写入前就坏了的条目（值不合法、或不是任何阶段的产物，
  经 H6 的几条跳过路径、`Bash` 直写，或者阶段链的 `produces` 改了之后留下的）可以删掉或标 `"accepted"`——否则 `validateState` 每次记账叫 PM 改掉它、H6 又要求原样带着，两道门禁的指令互相矛盾（复核找到的）。
- **为什么是 `"accepted"` 而不是删掉那一条**（设计评审改的）：删得掉的话，「原样带着」只剩「不许加」能核，一次写入悄悄丢掉一条，那份上一轮的
  产物就算这一轮的了；标记是显式的，H6 能核它只落在当前段及更早段。
- **推进把关**（设计评审加的）：不是回退的写入里，`stage` 往后走时，离开的各段（写入前的 `stage` 到写入后的 `stage` 之前，含跳过的段）里，
  `rework_base` 值是 sha、磁盘内容与它相同的产物不许留着——先让产者重写，或者在推进的同一次 Write 里标 `"accepted"`。只靠【返工】回传是事后的：
  初稿逐帧走查里，PM 续跑时不重派、直接 S5→S6，S6 的 `requires` 不含实现记录，H2 放行、之后一路无声。阶段链最后一段没有「推进出去」这次写入，
  收口不经 H6（审查第 24 条：链尾没有收口标记）——【返工】、`/agent-team:at` 与 `/agent-team:at-resume` 对最后一段改说「收口之前重写或标 `"accepted"`」。
  > **收口（2026-10-02，M4a，`docs/35`）**：收口有了标记 `closed_at`，收口那一次由 H6 核最后一段的前置与产物（在、不是空文件、读得出、不是上一轮的），
  > 「收口不经 H6」不再成立；`08-delivery.md` 与 `06-test.md`、`07-acceptance.md` 一样是验证段的产物，返工轮里只能重写，不能标 `"accepted"`。
- **`stage_roles` 不清空**（`docs/32` §4 留的问题）：回退时那一段的名单原样留着。名单里的人这一轮没再叫到的，它的产物照旧是上一轮的、那一段
  判不齐——PM 要么派它重写，要么标 `"accepted"`。清空的话，只记在那一段的角色会被「`roster` 里的角色哪一段都没记」报出来。
- **为什么不用时间**：调研量过 mtime 与 `history.at`。任何一次 Write/Edit（含同内容）都刷新 mtime；`Bash` 能把它改成任意值，`git checkout`、`cp -p`、tar 会把它推前或推后；
  `history.at` 是 PM 手写的字符串，151 个 PM 会话里只有 57 个写得准（全是跑过 `date -u` 的）。sha 与时钟无关；代价是同内容重写判「还是上一轮的」，
  出口是在末尾追加一节说明这一轮核过、为什么不用改。

### 2.2 H6 怎么核

纯函数在 `hooks/lib/rework-guard.mjs` 末尾的 M3y 一节（`restartInfo`、`decideReworkBase`），排在返工计数那四条（`decideRework`）之后。I/O 在
`hooks/gate.mjs` 的 H6 分支：阶段链读插件自己那份 `stages.json`（剥 BOM，与 runctx 同一份归一化；读不出来或形状不对——与 runctx 判「插件坏了」
共用 `stages.mjs` 的 `isStageChain`——这几条整段跳过、往 stderr 留痕）；产物逐份读，run 目录就是 `state.json` 所在的目录，stat 不到（ENOENT、
ENOTDIR）或者是目录算不在，别的 stat 错误与读、算 sha 出错都算「在、但读不出来」，不核。判定本身不包 try：它抛异常时照旧 fail closed。写入前的
`state.json` 读不出来时这几条也跳过（与 `decideRework` 的修复路同一条）。

拒绝理由按值从哪来引（`docs/27` §2.1）：从阶段链展开出来的产物名原样输出；段 id（回到的段、写入前后的 `stage`，都取自 `state.json`，写入后的 `stage`
可以不在链上）、这次写入带来的键、写入前的键过 `quote`；写入前与期望的整份过 `safeJson`。
回退写入的拒绝先列差异（缺的、值不对的、多出来的；没写或不是对象时也列缺哪些），再给整份期望值；读不出来的那份说清不核；这次写入在回退那一条
之后还追加了前进的条目（补记）时，附一句：快照照磁盘现在的内容算，回退之后已经重写过的也会被记成上一轮的，把它们标 `"accepted"`；同一段再追加一条
（原地重来）时，附一句：同一段里重派一个角色不是回退，去掉新追加的 `history`——H6 分不出原地重来与误追加，判定不变。

### 2.3 新鲜度与四处调用点

`hooks/lib/freshness.mjs` 的 `makeFreshness({ artifactExists, artifactBytes, reworkBase })`：

- `isStale(name)`：`rework_base` 是普通对象、有这个自有键、值是合法的 sha、磁盘那份读得出且 sha 相同。值是 `"accepted"` 的不旧；读不出来的不旧
  （与 H2、H5 的 fail open 一致；不能拿 `sha256OfContract(null)` 去比——它算的是字符串 `"null"`，形状合法）。只在有这一条时才读字节：没回退过的
  run 一个字节都不多读。
- `artifactCurrent(name)` = 在、而且不旧。

`gate.mjs` 里 `isStageDone`（【阶段】、H5a「停在旧阶段」）、`decideDeliverable`（H5a、H5b）、`decideReadiness`（H2）的每一处调用都把
`artifactExists` 换成 `artifactCurrent`，后两个另传 `artifactStale`：「缺」与「还是上一轮的」分开说，没有上一轮的产物时 `decideDeliverable`、
`decideReadiness` 的理由与 H5a 的交付物模板与 v1.6.0 逐字相同。账本比对不变：它比的是 `artifacts` 记账，返工轮里重写过的照旧报「记账之后被改过」，
PM 照它记新值。

### 2.4 回传

- **H5b**（说给停下的那个角色）：「X 还是上一轮的——这是返工轮…」，两条出口：这一轮核过、确实不用改的，在末尾追加一节写明核过什么、为什么不用改
  （还旧的里有 `.html` 时，用 `<!-- -->` 注释写这一节）；这一段确实不需要产出、或者不该由它改，就不要写，把理由写进回报。
- **H5a**（说给发起派发的人）：「缺」与「上一轮的」分开；出路按收件人分——写得了 `state.json` 的（PM）给「在 `rework_base` 里标 `"accepted"`，否则
  等它写完（异步派发时）或者重派；推进时 H6 会拦」，别人给「`rework_base` 只有项目经理改得了：等它写完，或者重派它；判断不用改就冒泡，由项目经理
  标 `"accepted"`」。H5a「不是当前阶段的执行者、也派不到」那一支补一句返工的出路：PM 照 `/agent-team:at` 的「回退」记一次回退（这一次已经重写过的
  记完标 `"accepted"`，不必再派一遍），别人冒泡——原来那句「不要靠把 `state.stage` 改回旧阶段来消掉这条」把合法的回退也挡在外面。这一句首轮也发：
  第一次驳回之后的返工恰好发生在一趟从没回退过的 run 上。
- **H2**（说给派发者）：还是上一轮的前置单独说、带出处（「04-dispatch.md（S4 的产物）还是上一轮的」），出路按派发者分，谓词与 H3 同一个
  `isContractWriter`；判不出来时落「改不了」那一支。
- **【返工】**（写 `state.json` 时，只有 PM 写得了）：列出当前段与更早段还是上一轮的产物，分开说；更早段的多半是回退记晚了、或者文件被改回了旧内容。
  更晚的段还旧是返工轮的常态，不列。出路：这一轮重写（PM 自己那几段的产物自己写，别的派产者），或者标 `"accepted"`；最后一段说收口不经 H6。
- **【阶段】**：下一段在 `history` 里已经出现过时（返工轮里再进 S6），多一句「同一次 Write 把 `rework` 里那一段照派生量加 1」。

### 2.5 产者交代

当前段在阶段链上时，**链上晚于它的段不算走过**（`coverage.mjs` 的「走过的阶段」多了这一条）。一段没走完就回退（S5 里发现设计错，回 S3）时，S5 还没
派到的产者原来在 S3、S4 每写一次 `state.json` 就被点一次名，而三条出路（写 `trimmed`、派它、补记）一条都不对——这一轮会重走到 S5。重走过、推进
出去之后照常查。首轮 `history` 只往前走，没有晚于当前段的段，不受影响。复核的反驳者建议只改正文：怕改代码会把首轮的真漏派藏到重走之前；首轮
走不到这一格，藏起来的只是回退之后要重走的那几段，所以改了代码。

### 2.6 校验、模板与正文

`validateState`（`rework_base` 在时；缺失不报）：不是对象；键不是任何阶段的产物；值既不是 sha 也不是 `"accepted"`（值不回显，点名是哪一条）。
`templates/state.json` 加 `"rework_base": {}`；`/agent-team:at` 建 run 那一段与规格 §4.4 的例外名单改成三个键。

`commands/at.md` 第 3 节新增「回退」：先记回退再派；同一次 Write 改 `stage`、`history`、`rework`、`rework_base`，离开的那一段照常记账、`stage_roles`
更早各段不清空、没走完的那一段还没派到的人不写 `trimmed`；`rework_base` 的值取 `artifacts` 里记的，没有或对不上时照 H6 给的整份写，用户说过不用改的这一次就标；
之后到下一次回退为止原样带着、只许当前段及更早段标 `"accepted"`、坏条目可以清掉、推进时还旧会被拒、最后一段收口不经 H6；记晚了的代价；
同一段里重派一个角色不是回退。第 3 条记账补上 `rework`：返工轮里推进进走过的段，同一次 Write 把它加 1。第 6 节收尾补一句：最后一段的产物还是上一轮的，
先重写或标 `"accepted"` 再收口。`agents/at-pm.md` 的返工红线旁给出「回退」的可读路径；`commands/at-resume.md`：返工轮里「在磁盘上」不等于这一轮写过，
推进被 H6 拒时照理由走，标 `"accepted"` 之前先读驳回那一段的产物，最后一段收口的例外，记账字段里加上 `rework`，`stage_roles` 里的非产者不是不一致，
`artifacts` 落后于磁盘时等下一次派发的【账本比对】给值；`agents/at-pm.md` 另补一句：没走 `/agent-team:at-resume` 就让你接着跑时先读它；`commands/at-status.md`：列「返工基线」、
只列不判新旧；`agents/at-qa.md`：返工轮要在这一轮的实现上重跑；规格 §4.4（示例、说明、例外句）与 §6 的 H6 一行（限定「只拦减少」说的是返工计数、
失败策略补上新的跳过，顺手订正 M3r 之后就不对的「新旧任一读不出时放行」）；`stages.README.md` 的 H6 一节与 H5a 静默表 S5 行的收口。

  > **收口（M3z，`docs/34`）**：先派后记被门禁拦下之后，补记多半走不到；还走得到的是协调者自己改了早段产物、或者同一次写入又往前记了几段，
  > 处理照旧。
  > **订正（2026-10-02，M4a，`docs/35`）**：验证段（S6、S7、S8）的产物不再能标 `"accepted"`，补记里它们要再出一次；补记照推进核离开的段，
  > 跨过验证段（它的产物在快照里）的补记直接拒、要拆开写；一次 Write 只许记一次回退。
- **回退写入漏记离开的那一段叫到了谁**：`validateState` 照样自洽，产者交代对晚于当前段的段不查，要等重走、推进出那一段时才查出来；run 在重走之前
  被放弃时，这条记录就丢了。真实会话里 haiku 回退时漏记过 S6 的 `at-qa`。要配一道不误报的判据（那一段的产物这一轮真交过、产者却不在 `stage_roles` 里），
  单独立项。
- **一次追加几条、中间又往回**（例 `[S2, S4, S3]`）：T 取最后回到的那一段；人造的形状，真实会话里没见过。
  > **部分收口（2026-10-02，M4a，`docs/35`）**：一次 Write 里有不止一条回退的（例 `[S2, S4, S3]`），H6 现在直接拒，拒绝理由叫它先单独记最早
  > 那次回退，之后每段推进各一次 Write。只有一条回退、回退之前先往前记了几段的（例停在 S2 时追加 `[S3, S5, S4]`）照旧放行，T 取那条回退（S4）。
- **跳过的回退补不回快照**：回退那一次写入时阶段链读不出来（或写入前的 `state.json` 读不出来）就不核。那一次没写快照的，之后补不回来，那一轮
  退回只看在不在；写了的照样落盘、之后原样带着，只是没经过对磁盘的核对（例如照落后的 `artifacts` 写的值）。
- **防疏忽，不防伪造**：`Bash` 改 `state.json` 或产物不经任何 hook；主线程不带 `agent_type` 时一切按 PM 算。
- **超大产物**：算 sha 要整份读进来，大到转不成字符串的那种（`docs/27` §4）照旧。H6 只在回退写入与推进时读产物，平时的记账一份产物都不读（每次写 `state.json` 会多读一次插件自己的 `stages.json`）。
