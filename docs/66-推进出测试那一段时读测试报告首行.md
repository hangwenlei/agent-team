# 推进出测试那一段时读测试报告首行

> 2026-10-10，分支 `r24-test-verdict-line`。第二十四轮（从开放边界索引挑）：`docs/46` §4「测试报告的结论不读」。`/agent-team:at` 第 3 节一直写着「推进之前读结论：
> `06-test.md` 判不通过的照回退处理，不要推进」，门禁只核测试报告在不在、空不空、是不是这一轮的。

## 0. 一句话结论

- 测试报告（插件自带的链上是 `06-test.md`）的第一个非空行固定写「结论：通过」「结论：不通过」「结论：跑不起来」之一，不通过、跑不起来后面可以接冒号写原因
  （「结论：不通过：缺测试」）。推进出测试那一段的那一次 H6 读它：不通过的拒（回退到实现那一段），除非用户经「照现状交付」批准过这一份（门禁记下、按 sha
  绑在测试报告上——项目里本来就挂着的用例、不稳定的用例、返工预算耗尽，那是用户的决定）；读不出的拒（同段重派 `at-qa` 照格式写）；跑不起来的放行——
  那是正文里 `env-blocked` 那一问，用户定。`at-qa` 在测试那一段停下时首行读不出，H5b 拦它当场改；【阶段】在测试那一段齐了、首行不通过或读不出时补一句。

## 1. 问题

- 测试结论只在正文里：项目经理没照着读、带着一份「不通过」推进出 S6，门禁不拦——之后要等验收角色自己发现，或者整段验收被裁掉时一路收口。
- 验收结论在 `docs/46` 已经有了固定首行与门禁读它的一套；测试报告没有。

## 2. 修法

- 新模块 `hooks/lib/test-verdict.mjs`（单一真源，纯函数）：
  - `testVerdict(bytes)`：第一个非空行按 NFKC 之后匹配，「通过」严格（后面只容许强调、空白、句末标点），「不通过」「跑不起来」按前缀认；回 `'pass'` `'fail'` `'env'`，
    读不出回 null。与验收结论的认法（`verdict.mjs` 的 `acceptanceVerdict`）同一路写法。
  - `testStageOf(stages)`：阶段链上第一个产者里有 `at-qa` 的验证段、它的第一份产物、它之前最近的执行段（测试没过回到那里）。从 `stages.json` 派生。
  - `testBlock`：测试那一段整段裁掉、谁都没叫过的不拦（「叫过」并上写入前的状态与门禁的派发记录，推进那一次才裁掉 `at-qa` 的照样核）；报告不在交给别的判据；
    首行通过、跑不起来不拦；门禁记下的照现状交付批准的 sha 等于它现在的 sha，不拦。
  - `decideTestVerdict`：只管推进出测试那一段的那一次（写入前停在测试那一段、写入后到了后面的段）。不在之后的推进与收口读——之后由验收结论管，已经走过测试
    那一段的旧 run 不受牵连。
  - 文案：不通过——「照 /agent-team:at 第 3 节的『回退』记回到 S5（测试没过、缺测试都回那里），修好之后重新走到这里」；读不出——列出三种写法，「在 S6 里同段
    重派 at-qa，让它把第一行照格式写（同一段里重派不计返工）」。不通过那一句还说根因在更早一段的回到那一段，并给用户的出路：照第 4 节问用户、标签逐字写
    「照现状交付」，门禁记下之后放行。
- 照现状交付延伸到测试报告（`docs/46` 那一套）：两个记录器停在测试那一段时把批准绑在测试报告上（`acceptanceOnDisk` 按种类读首行、带上「测试报告」的说法），
  写「跑不起来」的回「不需要批准、照常推进」；`hooks/lib/approvals.mjs` 的回传按「验收结论／测试报告」换词。契约基线那一侧（`unusedDeliverApproval`）也认测试
  报告的批准——记那条答复的修订不算改需求，不然那一次修订把测试报告记成对着上一版契约、H6 叫它重出，绕回原地。
- `hooks/gate.mjs`：
  - H6：排在验收结论判据之前接上 `decideTestVerdict`。
  - 【阶段】：测试那一段齐了、首行不通过或读不出时补一句（与验收那一句同一个位置——两段不会同时是当前段）：写者是 `at-qa`、读不出的叫它把第一行改好再停；写者是
    `at-qa`、不通过的说推进会被拒、回报时照实说；别的写者照 H6 的拒绝理由给出路。
  - H5b：`at-qa` 在测试那一段停下、报告首行读不出——拦，理由是【阶段】给写者的那一句加冒泡的尾巴（S5 没交齐、红线里的敏感操作才冒泡）。与验收角色那一支
    （`docs/62`）同一个写法、同一个 `isBubbleStop`。
- 正文：`agents/at-qa.md` 写明第一行的三种写法与判法（实现自己编译不过、缺依赖、一起就崩的是不通过，只有环境的原因才是跑不起来；这一趟之前就挂着的用例照样判
  不通过、逐条注明）；`/agent-team:at` 第 3 节加「S6 测试报告的第一行」一条（含用户的出口）；README 两半「测试或验收没过时……」。
- 牵连的旧判据：`tests/gate-contract-base.test.mjs` 的测试报告夹具推进出 S6 时首行不是三种之一，改成「结论：通过」打头；`tests/gate-stop-verdict.test.mjs` 里「at-qa 的
  测试报告不核首行」那一格改成只断言不说验收结论那一句（它自己的测试报告现在另有一条）。

## 3. 判据与变异

- `tests/gate-test-verdict.test.mjs`：
  - `testVerdict` 的认法（通过严格、不通过与跑不起来按前缀、全角冒号与强调、标题打头读不出）。
  - 推进出 S6：通过、跑不起来放行；不通过拒（回退到 S5）；读不出拒（列出三种写法、同段重派 `at-qa`）。
  - 只在推进出 S6 的那一次读：S6 里原地重写不读，已经走过 S6、停在 S7 推进到 S8 的不按测试报告拦；S6 整段裁掉、磁盘上留着一份报告也不读。
  - H5b：`at-qa` 在 S6 停下、首行读不出——拦、带冒泡的出口；三种之一照常放行；不在测试那一段停下的不核。
  - 【阶段】：`at-qa` 写的读不出——叫它改；项目经理在 S6 齐了、不通过时写 `state.json`——说推进会被拒；通过的不说。
  - 照现状交付：停在 S6、不通过，用户选「照现状交付」——记下、绑在测试报告上，推进放行、【阶段】不再说会被拒，报告改一个字批准就不算了；拒绝理由里给这条出路；
    写「跑不起来」的不需要批准、还没有报告的说还没有；批准之后把答复写成修订——不算改需求（记进 `deliver_used`），推进放行。
  - 推进那一次才裁掉 `at-qa`（派发记录里有它、或写入前记着它）照样读；对着上一版契约又不通过——先说契约那一句，【阶段】不补测试那一句；`at-qa` 写不通过拿到的是
    它自己那一句；已经走过 S6、停在 S7 的【阶段】不说推进出 S6。
  - 正文两句在。
- 变异（备份在仓库外，每一刀改完逐字节还原）：H6 不读测试报告、跑不起来当不通过、跑不起来也拦、通过不严格、之后的推进也读、不通过不说回退、读不出不说同段重派、
  H5b 不核测试报告、H5b 不看是不是测试那一段、【阶段】不补测试那一句、`at-qa` 写的读不出也给项目经理那一句、整段裁掉也读——每一刀都有判据红。「还旧的也按首行拦」
  存活：还旧的报告在 H6 里由排在前面的推进判据先拒，【阶段】那一侧也不判齐——那一行走不到，删掉了。复核修订之后又加了：不认批准、不传批准（三处）、记录器在 S6
  不换成测试报告、跑不起来也记批准、契约基线不认测试报告的批准、H6 不传派发记录、不并写入前的状态、【阶段】不排除对着上一版的、【阶段】不看当前段、`at-qa` 写不通过

- 没起真实会话：H6、H5b、【阶段】的判定在子进程里全走到了。

## 4. 仍然开着的边界

- **跑不起来的放行**：环境阻塞要用户定（`env-blocked`），推进出测试那一段不要批准；之后验收结论没过时照现状交付的批准绑在验收结论上。验收那一段整段裁掉、测试又跑不起来时，
  收口不读任何结论（`docs/46` §4 那一条剩下的一半）。
- **升级时停在测试那一段的旧 run**：旧格式的报告推进被拒，要在 S6 里同段重派 `at-qa` 照新格式写。
- **没有派发记录的旧 run 分两次写**：先单独一次写入删掉 S6 的 `at-qa`、推进时再裁掉，不读测试报告首行（与 `docs/46` §4 里验收那一条同一档）。
- **只核首行**：首行写「通过」、下面写着有用例挂了，门禁照通过算——与验收结论那一条同一档。
- **已经走过测试那一段的旧 run**：不回头读。

## 5. 没量到的

- 真实会话里 `at-qa` 照新格式写第一行、被拦回来之后改不改，项目经理被拒之后照不照回退。

## 8. 复核与修订

第一版推上分支、CI 全绿之后，起了一个对抗复核的子代理：照 `/agent-team:at` 第 3 节的每条回退规则在子进程里按真实顺序走了一遍（S6 不通过回 S5、返工轮还旧、
跑不起来走 `env-blocked` 再到 S7 照现状交付、S7 判不了回 S6、读不出同段重派），都放行；拿 49 种写法对照首行认法，与验收结论那一套一致。一个高、几个中等与小问题，
都在这一轮改了：

- **高 1：「结论：不通过」没有用户的出口，两句门禁回传互相走不到**——停在 S6、用户选「照现状交付」，记录器说「等验收结论写成再问」，H6 又不让离开 S6。项目里本来就
  挂着的用例、不稳定的用例、返工预算耗尽，这一趟会卡死。→ 照现状交付延伸到测试报告（§2），记录器、H6、【阶段】、契约基线都认它。
- **中 2：几刀变异全量判据打不红**——H6 不传派发记录、不并写入前的状态（推进那一次才裁掉 `at-qa` 就绕过）；检查挪到契约基线之前、【阶段】不排除对着上一版的（两句打架）。
  → 补了那几格。
- **低 3：【阶段】不看当前段、`at-qa` 写不通过拿到项目经理那一句、走不到的空白判断**。→ 补判据、删掉那一行。
- **低 4–7：正文**——`at-qa` 两处「不通过：缺测试」少了「结论：」前缀；给 `at-qa` 的那句没说通过这一行不夹别的话；跑不起来与实现自己的问题没分清；不通过的出路写死
  回 S5。→ 都改了。
- **低 8：`settleWords` 的注释说「排在所有拒绝之后」**，测试首行与验收结论那两条排在它后面。→ 改准注释（建 run 那一次走不到它们；被它们拒掉的续跑写入照样作废原话记录）。
