# M2a 阶段链与返工闭环 设计

> 里程碑：M2 的第一轮。M2 原定义（规格 §11）是「加五个角色、补返工预算、驳回路由、
> `never_invoked`、升级条件、S6–S8、发布条件」——那是好几个独立子系统，按 M1 的先例
> （M1a 闸 / M1b 流程 / M1c 角色）拆成三轮：
>
> | | 内容 | 结束时能验证什么 |
> |---|---|---|
> | **M2a（本文）** | 五个占位 agent + S6–S8 + S5 多产者 + 返工写时强制 + 驳回路由 + H5a 重算 + `docs/11` §1.3/§1.4/§1.5 | 一趟 S1–S8 真能跑完，返工计数拦得住 |
> | M2b | 五个角色真正文 + 闭包测试 | 十角色齐，形状同 M1c |
> | M2c | README 双语、LICENSE、marketplace、两条警告 | 具备发布条件 |
>
> 占位 agent 放 M2a，是因为 `stages.json` 的 `S6.role` 不能指向一个不存在的 agent——
> M1b 当时也是靠 M0 留下的占位符才能先做流程层。

## 0. 这一份要做什么

把阶段链从 S5 接到 S8，并补上**只有接上之后才第一次成立**的两个机制：返工预算的写时
强制、驳回路由。

入口条件是 `docs/11` §1.1–§1.5 与 §5.6。这些不是「顺手一起做」的清单——**§1.1 与 §1.2
是扩链本身强制触发的**：不重算 H5a 的静默集合，那条告警会在 M2 第一天失灵；不做写时
强制，「第 3 轮终局」这条硬上限就只有事后告警守着。

## 1. 四个必须先答的问题与裁定

### 1.1 S5 的产物槽位 —— 规格本来就是模式，实现把它窄化成了字面量

**事实**：规格 §4 阶段表写的是

| S5 | 实现 | at-architect 分发 | `05-impl/<role>.md` + 代码 |

`<role>` 是一个**模式**。而 `stages.json` 写的是

```json
"S5": { "role": "at-backend", "produces": ["05-impl/at-backend.md"] }
```

一个**字面量**。

`docs/11` §5.6 记的那个「前端干完活写不进自己的实现记录」，成因就在这里——不是漏配了
一行，是模式被实现成了字面量。2026-09-19 那趟真实 run 里 PM 只好代写
`05-impl/at-frontend.md`，并如实报了欠账。

**M2a 会把这个缺口乘以四**：at-ui / at-ios / at-android 都是执行角色，都要在 S5 产出。

**为什么不能简单地把三个名字加进 `produces` 数组**：`isStageDone` 的判据是
`produces.every(artifactExists)`（`hooks/lib/state.mjs:84`）。一趟只派了后端和前端的 run，
`05-impl/at-ios.md` 永远不会存在——静态列全名字会让 S5 **永远不 done**，整条链卡死。
「S5 的产物集合取决于这一趟派了谁」是这个阶段的固有性质，不是可以绕开的实现细节。

**裁定：`stages.json` 引入 `producers` 字段，`produces` 支持 `<role>` 占位符；
新增单一真源 `stageRoles(stage)` 返回 `producers ?? [role]`，所有消费方一律走它。**

```json
"S5": {
  "role": "at-backend",
  "producers": ["at-backend", "at-frontend", "at-ui", "at-ios", "at-android"],
  "requires": ["03-arch.md", "04-dispatch.md"],
  "produces": ["05-impl/<role>.md"]
}
```

`role` 保留（单产者阶段继续只写 `role`，S1–S4、S6–S8 都不动），`producers` 只在 S5 出现。
展开规则按消费方**各有各的集合**，这一点必须写清楚，否则会出第二个 §5.6：

| 消费方 | `<role>` 展开成 | 理由 |
|---|---|---|
| H3 写路径（`writepath.mjs`） | **写入者自己** | 角色 R 可以写 `05-impl/R.md`，当且仅当 `R ∈ producers`。不需要知道别人派了谁 |
| `isStageDone`（推进判据） | **`roster ∩ producers`** | 「这一趟实际派到的执行角色都交了」才算 done。没派的角色不该拖住推进 |
| 账本比对（`artifact-drift.mjs`） | **`roster ∩ producers`** | 与推进判据同一个集合，否则「该有而没有」和「有而没记账」会互相打架 |
| `ledger` 的 `produce` 回传 | **写入者自己** | 与 H3 同源：刚写的那个文件属于哪个槽位 |

**代价（写下来，不要等它咬人）**：`isStageDone` 与账本比对从此依赖 `roster`——而 `roster`
是 PM 写的控制文件。**PM 少写一个角色进 `roster`，那个角色的产物就既不拖住推进、也不进
账本比对的视野。** 这不是新洞（`docs/13` §6.1 已经记过「PM 代笔与伪造机制上无法区分」），
但 M2a 让它多了一条新路径，必须在 `docs/11` 记明。

**若错**：`producers` 这一层抽象是多余的，退路是把 S5 拆成五个单产者阶段（S5a–S5e）——
代价是阶段链长度翻倍、`nextStage` 的线性推进要改成图，比现在这个方案贵得多。

### 1.2 返工预算的写时强制 —— `PostToolUse` 看不到，但 `PreToolUse` 看得到

**`docs/11` §1.2 的原话**：「拦住一次『把计数改小』的写入要看到改之前那一版，
`PostToolUse` 看不到。」

这句话对，但它只排除了 `PostToolUse`，没有排除 `PreToolUse`——而 `PreToolUse` 触发时
**磁盘上还是旧版、`tool_input` 里是新版，两边都在手上**。

**裁定：新增 `PreToolUse` 检查项 H6「返工预算」，挂在既有的 `^(Edit|Write|NotebookEdit)$`
matcher 上，fail-closed，只对 `runs/*/state.json` 生效。**

判据（只拦**减少**，不碰增加——PM 每推进一个阶段都要正常重写这个文件）：

1. `history` 数组长度变短 → deny
2. 任一阶段在 `history` 里的出现次数变少 → deny
3. 任一 `rework[S]` 小于 `reworkFromHistory(新 history)[S]` → deny
4. 任一 `rework[S] > REWORK_LIMIT` → deny（这条 `validateState` 已有，H6 把它从告警提到拦截）

**两种工具都要处理，不能只做 `Write`**：

- `Write`：`tool_input.content` 就是新全文，直接 parse
- `Edit`：读旧文件，按 `tool_input.old_string` / `new_string` / `replace_all` **自己套用一次
  替换**，再 parse。这是确定性的——Edit 的语义就是这一次替换

**fail-closed 的边界**：旧文件不存在（本趟第一次写）→ 放行；新内容 parse 不出 JSON →
**放行并回传告警**，不 deny。理由：一个写坏的 `state.json` 会被 `ledger` 的 `kind:'state'`
报出来，而在 H6 这里 deny 会让 PM 连「把写坏的文件修回去」都做不到——那正是
`gate.mjs:306` 那条 I2 豁免的同一个理由（不要把运维人逼进死角）。

**代价**：H6 是第六个闸，`hooks.json` 的 `PreToolUse` 写路径 matcher 上从两个检查项变三个，
每次写文件多跑一个 node 进程。实测每个检查项 30s 超时上限、实际耗时毫秒级，可接受。

**若错**：判据太严会拦住合法写入。缓解是四条判据全部只看「减少」，且有
「parse 不出就放行」的逃生口；真出问题时改判据不改架构。

### 1.3 H5a 静默集合重算（`docs/11` §1.1 强制）

**M1 的那张表为什么完整**：H5a 在「返回角色能传递派发到当前阶段执行角色」时静默。
M1 里只有停在 S5 会被静默，而 **S5 是 M1 的最后一段——「停在 S5」在 M1 里不存在**。

**M2a 接上 S6–S8 之后**：实际在 S6、`state.stage` 停在 S5 时，任何能传递派到 `at-backend`
的协调者返回都会被静默——那正是「停在旧阶段」的标准形状，也正是这条告警存在的理由。

**裁定：静默判据从「返回角色能传递派到当前阶段的 role」改成
「返回角色能传递派到当前阶段的 role **且当前阶段尚未 done**」。**

落到代码上是 `hooks/gate.mjs:621` 那个条件加一项（当前逐字是
`CHECK === 'deliverable' && r.skipped === 'role-not-in-stage' && !isCoordinatorFor(ctx, role)`，
注意它是**告警触发**条件，静默是它的反面）：

```js
// 改前：!isCoordinatorFor(ctx, role)
// 改后：!isCoordinatorFor(ctx, role) || isStageDone({ ...current, roster })
```

逐行验一遍下面那张表：协调者 + 未 done → `false || false` = 不报（对）；
协调者 + 已 done → `false || true` = **报**（这正是要抓的「停在旧阶段」）；
非协调者 → `true || …` = 报（不变）。

加的是后半句。理由：这条告警要防的是「阶段停在旧的没推进」，而「没推进」的**充分判据是
产物还没齐**，不是「谁能派到谁」。原判据把协调者合法返回和停滞混在一起，只好用可达性
近似区分；补上 `isStageDone` 之后，两者就分开了：

| 情形 | 当前阶段 done? | 返回角色可达 role? | 旧判据 | 新判据 |
|---|---|---|---|---|
| S5 进行中，at-architect 分发完返回 | 否 | 是 | **静默**（对） | 静默（对） |
| 实际在 S6，`stage` 还停在 S5 | **是**（S5 产物已齐） | 是 | **静默**（错，这正是要报的） | **报**（对） |
| 停在 S1/S4（`at-pm`） | 否 | 否（花名册不变量） | 报 | 报 |

**连带**：`docs/11` §5.3 第 1 条记着账本比对现在与 H5a 共用同一条 `CHECK === 'deliverable'`
分支、同一次 `emitLedger`，且**不受这张静默表约束**。重算时把它一起算进去——账本比对
是**独立信号**（产物内容对不对得上账），与阶段推进与否无关，**裁定为继续不受静默约束**。

**若错**：新判据会在「产物齐了但确实还在同一阶段做别的事」时误报。M1 的阶段语义里
产物齐即阶段完成，不存在这种状态；若 M2b 的角色正文引入了这种用法，回来改判据。

### 1.4 驳回路由与阶段回退

**规格 §4.3 的表**：

| 驳回类型 | 回到 | 重跑区间 |
|---|---|---|
| 需求理解错 | at-product | S2 → S8 |
| 设计错 | at-architect | S3 → S8 |
| 实现错 | 对应执行角色 | S5 → S8 |

唯一升级情形：驳回暴露 `00-contract.md` 自身存在内在矛盾——非执行错误，只有用户能裁。

**现状**：`nextStage(stages, current)` 只会前进一格（`hooks/lib/state.mjs:55`，按
`Object.keys` 的插入序取下一个）。**没有任何回退路径**，也没有任何地方消费 §4.3 这张表。

**裁定：新增 `rejectTo(kind)` 纯函数与 `REJECTION_KINDS` 常量，把 §4.3 那张表搬进代码，
成为单一真源；回退表现为 `history` 追加一条目标阶段的记录，`stage` 改成目标阶段。**

```js
export const REJECTION_KINDS = ['requirement', 'design', 'implementation', 'contract-conflict']
export function rejectTo(kind) { /* → 'S2' | 'S3' | 'S5' | null（contract-conflict 走升级） */ }
```

三条必须同时成立，否则返工计数会算错：

1. **回退 = `history` 追加**，不是修改或删除已有条目。`reworkFromHistory` 靠出现次数算返工，
   回退到 S2 就是 `history` 多一条 `S2` → `rework.S2` 变 1。与 M1b 那份自洽示例
   （规格 §4.4 下方）的语义完全一致
2. **`validateState` 必须允许 `stage` 指向一个更早的阶段**。现在它不校验前后关系，所以
   **不需要改**——但要补一条测试钉住「回退之后的 state 仍然合法」，否则将来有人顺手加一条
   「stage 只能前进」的校验，这条路径会静默断掉
3. **`contract-conflict` 不路由，走升级**：`ESCALATION_KINDS` 已有五类（`state.mjs:25`），
   驳回暴露契约内在矛盾归入其中，`rejectTo` 返回 `null` 表示「这一类不由代码决定回哪」

**代价**：`history` 会变长且同一阶段多次出现，`/at-status` 的展示要能读懂。这是规格
§4.4 示例本来就有的形状（那份示例里 S5 出现两次、`rework.S5` 为 1），不是新引入的。

**若错**：`rejectTo` 把表搬进代码之后，规格 §4.3 与代码成了两处知识。缓解：补一条测试
把两者钉在一起（形状同 M1c 那条「角色正文提到的阶段 id 必须在 stages.json 里」）。

## 5. 已知风险

1. **`isStageDone` 与账本比对从此依赖 `roster`**（§1.1 代价段）——PM 漏写一个角色，
   那个角色的产物就不在视野里。与 `docs/13` §6.1 记的「代笔与伪造机制上无法区分」同族，
   M2a 只是多开了一条路径。**必须记进 `docs/11`。**
2. **H5a 新判据依赖「产物齐 = 阶段完成」这条语义**。M1 的阶段语义如此；M2b 写角色正文
   时若引入「产物齐了还要再做点别的」的用法，这条判据会误报。
3. **返工上限 3 与 S6/S7 两条驳回边同时计数**——规格 §4.2 ③ 说「S7 驳回同样计数」，
   但没说两条边是共用一个预算还是各自一个。**本轮裁定：共用同一个 `rework[S]`**
   （计数挂在被重跑的阶段上，不挂在驳回来源上），理由是 `reworkFromHistory` 本来就按
   阶段出现次数算，分两个预算需要第二个计数器。若错，M2b 真实跑起来会看到「实现错驳回
   两轮 + 测试失败一轮」就触顶，届时再拆。
