## 1. 五个必须先答的问题与裁定

### 1.1 at-ui 在 S2 的产物槽位 —— S2 也要变多产者，但形状与 S5 不同

**事实**：规格 §4 阶段表与 `stages.json` 对不上，**两处**：

| | 规格 §4 | `stages.json` 现状 |
|---|---|---|
| S2 | `01-prd.md`、**`02-ui-spec.md`**、**`02-wireframe.html`** | 只有 `01-prd.md` |
| S3 | `03-arch.md`、**`03-alignment.md`** | 只有 `03-arch.md` |

**`02-ui-spec.md` 与 `02-wireframe.html` 是 at-ui 在 S2 的全部工作。** 槽位不存在时：
H3 拦住它写（不在任何 `produces` 里）、H5 从不检查它的交付、账本比对看不见它——
**这正是 `docs/11` §5.6 记的 `at-frontend` 那个形状**，M2a 花一整轮（外加终审两次追加）
才修干净。**不能在写 at-ui 正文时再制造一个。**

**S3 不需要新机制**：`03-alignment.md` 与 `03-arch.md` 都是 at-architect 一个人的产物
（规格写「at-architect + 并行拉通」，并行拉通是它去**收集输入**，产物仍归它）。
单产者多产物现有机制已支持，**只改 `stages.json` 一行**。

**S2 需要新机制，因为它与 S5 形状不同**：

| | 形状 | 现有机制 |
|---|---|---|
| S5 | **一个模式配 N 个角色**：`05-impl/<role>.md` × {backend, frontend, ui, ios, android} | `producers` + `<role>` ✅ |
| S2 | **每个角色产物各不相同**：at-product → `01-prd.md`；at-ui → `02-ui-spec.md` + `02-wireframe.html` | ❌ 建模不了 |

用现有机制硬套会错得很具体：`produces: ["01-prd.md","02-ui-spec.md","02-wireframe.html"]`
加 `producers: ["at-product","at-ui"]`，三项都不含 `<role>`，于是 `expandProduces` 对
**任何**角色都返回全部三项 —— `decideDeliverable(at-ui)` 会要求 at-ui 交出 `01-prd.md`，
`decideDeliverable(at-product)` 会要求它交出 wireframe。两边都判错。

**裁定：`produces` 支持第二种形式——按角色映射的对象；数组形式保留不变。**

```json
"S2": {
  "role": "at-product",
  "producers": ["at-product", "at-ui"],
  "requires": ["00-contract.md"],
  "produces": {
    "at-product": ["01-prd.md"],
    "at-ui": ["02-ui-spec.md", "02-wireframe.html"]
  }
}
```

S5 **不改**，继续用数组 + `<role>`：

```json
"S5": { "producers": [...5 个], "produces": ["05-impl/<role>.md"] }
```

**为什么保留两种形式而不统一**：把 S5 也写成对象形式意味着五个角色各写一行、加一个
执行角色要改五处；而把 S2 写成 `<role>` 模式根本表达不了「产物名不同」。**两种形式对应
两种真实存在的阶段形状**，不是随意的多态。数组形式是「所有产者交同一个模式的东西」的
简写，对象形式是「各交各的」。

**落点全部在 `expandProduces` 一处**（`hooks/lib/stages.mjs`）——它已经是那八九个消费方
共用的单一真源，改它一处，H2/H3/H5/账本比对/`validateState` 一起生效。**不要在任何
调用点另写分支**。

**代价**：`expandProduces(stage, roles)` 的语义从「按 roles 展开模式」变成「按 roles 取
它们各自的产物」，对数组形式是前者、对象形式是后者。两条路径都要有变异验证钉住。
`producedNames`（全部可能）与 `expectedArtifacts`（这一趟该有）的语义不变。

**若错**：对象形式是多余的复杂度，退路是把 S2 拆成 S2a（at-product）与 S2b（at-ui）两段
——代价是阶段链变长、`nextStage` 的线性推进要处理一个本质上并行的关系。

### 1.2 `at-pm` 的派发宇宙与花名册边（M2a Task 2 的硬前置）

**事实**：`agents/at-pm.md` 的 `tools:` 行里那个 `Agent(...)` **不是「PM 能派谁」，
是整个会话的 agent 宇宙**（主规格 §3.3 U2 实测，被所有子孙代理继承）。现在是

```
Agent(agent-team:at-product, agent-team:at-architect, agent-team:at-backend, agent-team:at-frontend)
```

五个新角色**一个都不在里面**。M2a Task 2 把它们做成孤立叶子（`can_delegate_to: []`）
正是因为这个：`tests/roster-sync.test.mjs` 要求**花名册全部 `can_delegate_to` 的并集
⊆ 这个宇宙**，先加边会直接红。

**裁定：宇宙先扩到九个角色，再加花名册边。顺序反了必红。**

```
Agent(agent-team:at-product, agent-team:at-architect, agent-team:at-backend,
      agent-team:at-frontend, agent-team:at-ui, agent-team:at-ios,
      agent-team:at-android, agent-team:at-qa, agent-team:at-acceptance)
```

**`at-outsider` 仍然不在里面**——它是「任何角色都不应能派发它」这条不变量的测试替身，
进了宇宙就失去意义。

花名册边按规格 §3.3 的层级与 §4 的阶段执行者：

```json
"at-pm":        { "can_delegate_to": ["at-product", "at-architect", "at-qa", "at-acceptance"] },
"at-product":   { "can_delegate_to": ["at-ui"] },
"at-architect": { "can_delegate_to": ["at-backend", "at-frontend", "at-ui", "at-ios", "at-android"] },
```

三条理由：
- **`at-pm → at-qa` / `at-acceptance`**：S6 与 S7 的执行者，规格 §4 表里它们直接对 PM 负责
  （S8 又回到 at-pm）。它们不写代码，不属于「第三层执行角色」那一类
- **`at-product → at-ui`**：规格 §4 S2 写的是「at-product → at-ui」，产品设计派 UI
- **`at-architect → at-ui`**：S5 里 at-ui 也可能出实现产物（它在 S5 的 `producers` 里），
  由架构师分发。**同一个角色出现在两条边上是有意的**，不是重复

**⚠️ 这会让 H5a 的静默集合第三次需要重算**（`docs/11` §1.1 第一次、M2a Task 6 第二次）。
加了 `at-pm → at-qa` 之后，`at-qa` 第一次变成「有人能传递派到」的角色，S6 的静默行为
随之改变。**M2b 必须重算那张表并更新 `stages.README.md`**，不能只加边。

### 1.3 五个角色的工具面

**`at-ui` / `at-ios` / `at-android` 是执行角色**，与 at-backend / at-frontend 同类：
`tools: Bash, Read, Glob, Write, Edit`。

**`at-qa` 要 `Bash`**——它的工作就是**跑**测试。`tools: Bash, Read, Glob, Write`。

**它不写代码，只写 `06-test.md`**（S6 的 `produces`，走 run 目录那条路）。
不给 `Edit`，也**不给它 `project.paths`**——这正是 `docs/11` §1.3 点名的那件事：
`at-qa` 与 `at-acceptance` 不认领任何路径，所以「可用班底」再也不能从 `paths` 的键集合
派生，`available_roles` 是唯一来源（M2a Task 2 已经按这条做了，并补了两条测试钉住）。

**自审时我先把这条写错了**：初稿写的是「它写 `06-test.md` 与测试文件」——写测试文件就
需要 `paths`，与上一段自相矛盾。**at-qa 跑既有测试、读实现、写结论，不新增代码文件。**
若 M2c 发现它确实需要产出测试代码，那是一次 `paths` 扩张，要连 `never_invoked` 的
派生口径一起重新想，不是顺手加一行。

**`at-acceptance` 不给 `Bash`**：业务验收看的是「做出来的东西符不符合契约」，
不跑构建、不改代码。`tools: Read, Glob, Write`。

**代价（要写下来）**：`tools:` 的上界模型（§3.3.1）意味着给这四个角色 `Bash`，
`at-pm` 必须也有——它已经有了（M1c 的论证降级，规格 §6.2.1），**这一轮不新增暴露面**。

**四个持有 `Bash` 的新角色各自必须带三句实质红线**（`tests/agents.test.mjs` 强制，
M1c 终审补的）：
1. 「不得用 `Bash` 绕过写路径隔离」
2. 账本比对**管不到**「写别人的代码目录」这一半
3. 「连 `artifacts` 一起改也无痕」这一半

**这三句不是装饰**：M1c 终审发现三份正文只写了第一半、把「写别人的地盘会留痕」说成了
事实（`compareArtifacts` 只遍历 `stages[*].produces`，代码目录根本不在范围内），
**在一个以「如实说出边界」为交付物的里程碑里，在最显眼的地方说反了**。

### 1.4 `model:` 重定（`docs/11` §5.10b）

五个占位符现在是 `model: haiku`（M2a Task 2 评审要求补的显式字段，理由是「占位符语义上
就是最小成本占位」）。**五个真角色都是 `model: sonnet`。**

**裁定：五个全部改成 `sonnet`。** 理由：`at-qa` 要读实现、设计测试、判断失败原因；
`at-acceptance` 要对着契约逐条核验收标准——都是实质判断，不是转写。at-ui/at-ios/at-android
是执行角色，与 at-backend/at-frontend 同类。

**这条此前只活在 git-ignored 的 SDD 账本里**，M2a 终审点名后才搬进 `docs/11` §5.10b。

### 1.5 S6 能在 S5 没交齐时开工（`docs/11` §5.10a）—— 本轮不修，但要写进正文

M2a 终审实测：`H2 对 at-qa（S6）的判定 = allow` 与 `isStageDone(S5) = false` **同时成立**。
成因是 `isStageDone` 的两个消费方（ledger 的 `PostToolUse` 通知、H5a 的静默判据）
**都没有 deny 出口**，所以 S5→S6 这条边上只有一条劝告性提示。

**裁定：M2b 不加 H2 判据，改为写进 `at-qa` 的正文。**

理由：
- 加判据要改 `decideReadiness` 的语义（「当前阶段的前一阶段未 done 则拒」），那是**阶段链
  机制**，属 M2a 那一类工作；M2b 的交付物是角色正文，混进机制改动正是 M2 拆三轮要避免的
- `at-qa` 是**唯一**会撞上它的角色，而它的正文本来就要写「你开工前先确认什么」
- 代价可控：这是一条 fail-open 的流程辅助缺失，不是安全洞

**`at-qa` 正文里要写的那句**（措辞按 §1.3 的体例，直陈、给判据）：

> 你开工前**自己确认 S5 的实现记录都在**——`stages.json` 的 S5 `producers` 里，
> 这一趟 `roster` 提到的每一个，都该在 `05-impl/` 下有一份。H2 不会替你拦这一条
> （它只查 `requires` 里静态列出的产物），**缺了就回报上级，不要在残缺的实现上跑测试**。

**若错**：把一条机制缺口写成了角色的自觉，模型可能不照做。缓解是 M2c 仍可补 H2 判据，
这句话不会因此作废。**已记进 `docs/11`，不是只活在这里。**

## 3. 测试策略

沿用 `docs/11` §3.3 两条硬规矩，**brief 给的测试代码不豁免**——M2a 九个任务里 brief 被
抓出**十五处**真错误。

| 要钉住的 | 判据 | 否定断言的正向锚 |
|---|---|---|
| `produces` 对象形式 | at-ui 在 S2 只被要求交自己那两份 | 前置断言 at-product 只被要求交 `01-prd.md` |
| 两种形式并存 | S5 数组形式行为**逐字不变** | 既有 S5 测试全绿 |
| 宇宙 ⊇ 花名册并集 | 既有 `roster-sync` 遍历，自动覆盖 | — |
| 五份红线 | 四份持 `Bash` 的各含三句 | 复用既有 `HAS_BASH` 遍历（要扩到七个） |
| H5a 静默表 | 重算后的每一行各一条 | 一条「各行夹具互不相同」 |
| `model:` | 十一份 agent 的 `model:` 是预期值 | `deepEqual` 身份锚，不用 `length > 0` |

**变异验证清单**（交付前逐条跑，`cp` 备份、**按行号定位**、不用 `git checkout`）：

1. `expandProduces` 的对象分支短路 → at-ui 的 S2 测试必须红，S5 测试**不红**
2. `expandProduces` 的数组分支短路 → S5 测试必须红，at-ui 的 S2 测试**不红**
3. 任一份红线删掉一句 → 对应那条必须红
4. `at-pm` 的宇宙删掉一个角色 → `roster-sync` 必须红

**第 1、2 条成对**：它们证明两种形式**各自**被测到，不是一条测试同时盖住两者
（M2a Task 5 栽过「三条锚全在同一半」）。

   但**所有消费方都会经过它**（清单见规格 §4 那张表。**那条注记此前报过的数字是错的**——它从写下当天起就把一个同一天早些时候刚被删掉的 producesOf 当成独立一项数了进去，是 M2b Task 1 的实现者用 git merge-base 查出来的。现在改成只列举、不报总数：清单可以 grep 核，数字不能）——改错一处，H2/H3/H5/账本比对一起错。
   变异验证第 1、2 条成对就是为这个。
2. **H5a 静默表第三次重算**。前两次分别由 `docs/11` §1.1 与 M2a Task 6 做，
   **每次都是被扩链/加边逼出来的**。这一次是加 `at-pm → at-qa` 逼出来的。
   `stages.README.md` 那张表是它的唯一落点，**改边不改表就是下一个漂移点**。
3. **`at-qa` 的「自己确认 S5 交齐」是一条写进正文的自觉，不是机械强制**（§1.5）。
   M2c 若补 H2 判据，这句话不作废但会变成冗余——届时一并处理。
