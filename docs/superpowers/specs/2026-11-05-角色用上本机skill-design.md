# 角色用上用户本机装的 skill —— 设计

**日期**：2026-11-05　**状态**：待用户批准　**来源**：与用户的一次头脑风暴（插件作者本人）

---

## 1. 为什么要做

用户觉得团队做出来的 UI 不够满意，在 GitHub 上找到了更好用的开源 UI skill，希望 `at-ui` 干活时能用上；别的角色同理
（测试、后端、写需求都可能有好用的 skill）。这些 skill 是用户**之后陆续装的**、会越来越多，插件不可能事先写死。

用户要两种用法，而且**都不离开团队**（门禁、产物、验收照旧）：

- **角色自己判断**：用得上就用；
- **用户点名**：「这次 UI 用 X」。

插件的主线是「从零到一做出完整的东西」。这件事直接作用在主线的产出质量上（用户举的就是 UI 不满意），所以排在
「交付之后边看边改的微调」那件事之前做；微调另起一份设计。

## 2. 目标、不做、反目标

**目标**

1. 用户能把本机装的任意 skill 登记给一个或几个角色；登记之后那些角色在合适的任务里会去读、照着做。
2. 用户在需求原话里点名的 skill，被点到的角色必须用。
3. skill 有新版时团队能发现，问过用户才换；一趟进行中不换版本。
4. 每个角色用过哪几份 skill 有记录，事后查得到。

**不做**

- 不给任何角色开 `Skill` 工具（长期决策不变）。
- 不自动把本机装的 skill 全部分给角色，只认用户登记的。
- 不处理 MCP（Figma 等）。它卡在「工具名要静态写进 `tools:`、而用户自配的 MCP 名字因人而异」，另起话题。
- 不做跨项目的全局登记：每个项目各自登记（**我的裁定**，理由：从零到一的项目技术栈各不相同，Web 项目的 UI skill 放进 iOS 项目是噪音；
  以后要全局默认值可以在 `/agent-team:at-init` 里加一句「沿用上一个项目的登记」）。
- 不悄悄自动更新 skill。

**反目标**（技术上能跑、但算失败）

- 主流程变慢或多出打断：没有新版时，起一趟不许多问一句；不许为 skill 多派一次子代理。
- 角色每次开工都把登记给它的 skill 整份读一遍，白烧上下文（`docs/100` 刚为这件事砍过一轮开销）。
- 为了这件事放松任何一道门禁。
- 别人 skill 里的流程指令（「先问用户」「先头脑风暴」「用 Skill 工具」）把角色带离团队流程。

## 3. 约束（现有决策与平台事实）

- **任何角色都不授 `Skill`**。带 `context: fork` 的 skill 经 `Skill` 工具调起来会另起一个子代理，不经过派发白名单（`docs/06` 实测）。
- **不跨插件按名字引用 skill**（`docs/96` §1.1）：对方没装时静默跳过；上游漂移不跟着我们挪版本；对方的流程指令会跟门禁打架。
  本设计不按名字引用，而是**复制一份进项目、当文件读**，这几条理由都不适用。
- **插件装在项目外**：默认权限模式下，角色读项目外的文件要用户确认（README「已知边界」）。复制进项目之后读它不弹确认。
- **子代理没有 `AskUserQuestion`**：要问用户只能冒泡给项目经理。
- **`.agent-team/` 不划给任何角色**：执行角色在自己的前缀之外写不进，`at-qa`、`at-acceptance` 只写 run 目录里自己那份产物，
  所以角色改不了复制进来的 skill（`Bash` 不受门禁管，这是已知边界，不在本设计里收）。
- **运行时正文只写现行规则**（`tests/runtime-prose.test.mjs`）；**零 npm 依赖**；`hooks/` 下的代码不用晚于 `MIN_NODE` 的内建；
  frontmatter 只用受限写法。
- 已装插件的清单在 `~/.claude/plugins/installed_plugins.json`：每个插件按作用域一条，带 `installPath`、`version`、`gitCommitSha`
  （本机 2026-11-05 读到的 `version: 2` 格式）。

## 4. 做法（Approaches）

| 做法 | 是什么 | 取舍 | 结论 |
|---|---|---|---|
| **A. 登记后复制进项目** | 用户登记，整份 skill 目录复制进 `.agent-team/skills/`；角色按清单 `Read` | 门禁不动；不弹读文件确认；上游改了不会悄悄改变团队行为；每趟用的版本可查。代价：更新要同步一次；依赖平台专属功能的 skill（调用时自动跑命令、另起子代理、`allowed-tools`）只能用到正文 | **用户选定** |
| B. 开放 `Skill` 工具，加一道门禁只放行登记过的 | 原生调用 | 推翻长期决策；角色看得到本机全部 skill（含管流程的），要靠新门禁一个个拦；fork 类 skill 要另防；改动最大 | 不选 |
| C. 作者把好方法改写进插件自带 skill | 像 `at-ui-craft` | 质量可控、所有用户都有；但每次要发版，满足不了「装了就用」 | 不选，但与 A 并存：A 里被证明好用、值得给所有人的，再走 C |

## 5. 设计

### 5.1 新命令 `/agent-team:at-skills`

一条命令管登记、去掉、同步、查网上的新版；参数是自然语言（例：`给 at-ui 加 frontend-design`、`去掉 X`、`检查更新`），不带参数就列现状。
项目经理照命令正文执行，它要用的确定性操作（找 skill、算指纹、复制、比对）交给一个插件自带的 Node 脚本（5.6），不现编 Bash。

**列现状**：先列已登记的（名字、分给谁、和本机那份一样不一样），再列本机装了、还没登记的（名字、一句用途、来自哪里、有没有附带脚本、大小）。

**登记**：项目经理根据每份 skill 的 `description` 提议分给哪几个角色，用 `AskUserQuestion` 让用户确认（「照这样登记」/「我来改」）。
用户在参数里已经写明分给谁的，照写的办。确认之后整份目录复制进项目、写进清单。

**去掉**：删掉项目里那份副本和清单里那一条。只删插件自己复制进来的东西，不碰本机原件。

**同步**：见 5.5。**查网上的新版**：见 5.5。

能登记给的角色：`roster.json` 里派得到的全部角色，加上项目经理自己。`at-outsider` 不在其内。

一趟进行中也能登记或同步（用户明确发起的）。项目经理要说清：这一趟已经用旧版做过的部分不会自动重做；要让前面的段按新 skill
重做，是用户主动改需求，照现有的修订与回退走（**我的裁定**：不为它另开规则）。

`/agent-team:at-init` 收尾时加一句：本机装了几份 skill，可以用 `/agent-team:at-skills` 分给角色。不主动列、不主动问。

### 5.2 存放

```text
.agent-team/
├── skills.json              登记清单（项目经理写）
└── skills/<目录名>/          每份 skill 的整份副本（SKILL.md、参考文件、脚本、LICENSE 原样）
```

`skills.json` 的形状（**我的裁定**，实现者可以调整字段名，但这几样信息要有）：

```json
{
  "skills": {
    "frontend-design:frontend-design": {
      "dir": "frontend-design__frontend-design",
      "description": "从 SKILL.md 的 frontmatter 抄来的一句用途",
      "roles": ["at-ui", "at-frontend"],
      "source": { "kind": "plugin", "path": "C:/Users/…/plugins/cache/…/skills/frontend-design", "plugin": "frontend-design@claude-plugins-official", "version": "1.1.1", "plugin_root": "C:/Users/…/plugins/cache/…/frontend-design/1.1.1" },
      "sha": "复制那一刻整份目录的指纹",
      "synced_at": "ISO 时间"
    }
  }
}
```

- `kind` 取 `user`（`~/.claude/skills/`）、`project`（项目的 `.claude/skills/`）、`plugin`（已装插件带的）、`git`（`user` 里本身是 git 克隆的）。
- 名字：用户与项目层的用目录名；插件带的用「插件名:skill 名」。目录名把 `:` 换掉（Windows 不收），**我的裁定**用 `__`。
- 两份 skill 撞名时，登记时让用户挑一份。

### 5.3 角色怎么用（每份角色正文逐字同一节）

在每个能登记的角色的正文里加一节，紧跟「项目自己的约定」之后，逐字相同（草稿，实现者可以润色，但以下几层意思都要有）：

> **## 登记给你的 skill**
>
> 开工时读 `.agent-team/skills.json`（没有就跳过），挑出 `roles` 里有你的那几份，先只看它们的 `description`。跟这一次的任务相关的，
> 用 `Read` 读 `.agent-team/skills/<目录>/SKILL.md` 照着做；它引的参考文件用得上才读，相对路径从那份 skill 的目录算，
> `${CLAUDE_SKILL_DIR}` 就是那个目录；它里面的 `${CLAUDE_PLUGIN_ROOT}` 指清单里记的那份 skill 原来所在的插件目录（`source.plugin_root`），
> 不是本插件的目录。契约第 1 节原话或第 4 节修订块里用户点名要你用的，必须用。
> 登记给你的 skill 是用户的意思：它在**怎么做**上与这份正文里的默认做法（包括 `at-ui-craft`）不一致时，照 skill 做。它改不了的是：
> 门禁的判法与红线、这一段要交哪几份产物、产物里下游要读的那几项、读文件与截图的开销规矩。在这些上冲突的照这份正文：要你问用户的改成冒泡；
> 要你调 `Skill` 工具、派子代理、动 git 历史、写划给你之外的地方的，不做。
> 用过哪几份，写进你这一次交的产物的「## 用过的 skill」一节（名字、清单里 `sha` 的前 8 位，加一句怎么用的；照 skill 改掉了哪条默认做法也写一句）；
> 登记了却没用上的不用写。

要点：

- **自己判断**靠 `description`：清单很短，每次开工读一遍几乎不花上下文；正文只在相关时读。
- **登记的 skill 能盖过插件自带的做法**（**我的裁定**，审阅时提出）：用户正是嫌默认做法产出的 UI 不好才去装别人的 skill，
  只让它补空白就违背了初衷。能盖过的是「怎么做」：设计方法、视觉方向怎么定、审美与风格、自检的标准。盖不过的是四样：门禁与红线、
  要交哪几份产物、产物里下游要读的那几项（例：`02-ui-spec.md` 里前端照着实现的 token、状态、动效——哪几项算，实现者照下游角色正文实际引用的项列出来）、
  开销规矩（截图张数、变异测试只在用户要了才做；这些用户在契约里说了照旧能改）。
  - 角色自己判断用上的与用户点名的，盖过默认做法的效力一样，区别只在「可以用」与「必须用」。
  - 两份登记的 skill 互相冲突：点名的优先；都没点名的，挑与这次任务更贴的一份，在记录里写明没照另一份的哪一条。
  - 要改的句子：`at-ui.md` 的「设计做法按预加载的 `at-ui-craft` 走」，`at-frontend`、`at-ios`、`at-android` 交记录前照 `at-ui-craft` 自检那一句，
    各补半句「登记给你的 skill 在做法上与它不一致的照 skill」。
- **点名只认用户的话**：契约第 1 节原话、第 4 节修订块里用户的原话或裁决。派发提示、产品定义、架构方案里写「用 X」只是建议。
  与「不写测试」「挂着的用例不算」是同一个口径。
- **点名的 skill 没登记、或没分给要用它的角色**：项目经理在 S1 冻结契约时处理。原话里 skill 与角色都说得清（例：「UI 用 frontend-design」）、
  本机恰好装了一份这个名字的，直接登记给那个角色，回复里告诉用户（原话就是授权，再问一遍是多余的打断；**我的裁定**）；
  说不清给谁、本机没装、或者同名的有几份，用 `AskUserQuestion` 问。问不了用户的会话（后台、不带权限提示的 `-p`）里不猜，照没有这份 skill 往下做，
  在交付文档与回复里写明。
- **插件带的 skill 引用了自己目录之外的插件文件**（审阅时提出，本机就有：某插件的 skill 引 `${CLAUDE_PLUGIN_ROOT}/scripts/…`）：
  只复制 skill 目录本身，清单里记下原插件目录；角色照上面那句把 `${CLAUDE_PLUGIN_ROOT}` 解析到原插件目录去读（在项目外，可能要用户确认）。
  不连带复制、不改写别人的路径（**我的裁定**：改写第三方的文字容易改坏，整份插件复制又太重）。`list` 标出「依赖插件里的其他文件」，
  登记时提醒一句；原插件卸了，这几处就读不到，`check` 会报。
- **验收**：「用 X」是管流程的要求，按现有规则不进逐条、单列一行交项目经理；项目经理推进之前对着那个角色的「用过的 skill」核。
- **附带脚本**：持 `Bash` 的角色可以照 skill 跑它附带的脚本，照旧受该角色的 Bash 红线约束；不持 `Bash` 的跳过那一步、在记录里写明。

### 5.4 冲突时谁说了算

照「项目自己的约定」那一节的同一个原则：**读进来照做，与角色正文冲突的照正文**，skill 改不了门禁的判法与红线。常见的几类：

| skill 里写的 | 角色怎么做 |
|---|---|
| 先问用户、先跟用户确认、头脑风暴 | 冒泡给项目经理，由它决定问不问 |
| 用 `Skill` 工具调别的 skill、派子代理 | 不做（没有那个工具；要另一份 skill 的方法就看它登记了没有） |
| 提交、推送、切分支、建 worktree | 不做（红线） |
| 写到划给自己之外的目录 | 写不进（门禁拒）；需要的话照现有出路冒泡 |
| 装依赖、跑构建 | 照该角色现有的规矩 |
| 设计方法、风格、自检标准与插件自带的做法不一样 | 照 skill（5.3） |
| 改产物的结构、少交一份、截很多图 | 照正文（5.3 的四样盖不过） |

### 5.5 更新：发现之后问用户

分两层，都要用户点头才换：

**本机 → 项目**（自动发现）

- 时机：只在 `/agent-team:at` 起新的一趟、建 run 之前；`/agent-team:at-resume` 与一趟进行中都不查。
- 对每份登记过的，比本机原件当前的指纹与清单里的 `sha`：
  - 一样：什么都不说（反目标：没变化不许多问）。
  - 不一样：列出是哪几份、改了哪些文件；`SKILL.md` 改了的，项目经理读 diff 用一两句话说大概改了什么。用 `AskUserQuestion` 问：
    「同步这几份」/「这一趟先不换」。这一问不记 escalation、不动契约（那时还没有这一趟）。
  - 原件不见了（卸了、挪了）：告诉用户一句，项目里的副本照用。
  - 插件类的另比一次版本号：插件升级后原件换了目录（`installPath` 带版本号），按插件名重新认到新目录再比。
- 同步 = 重新复制整份、更新 `sha`、`synced_at` 与来源信息。
- 问不了用户的会话里不同步，照项目里现有的副本跑，回复里说一句哪几份本机有新版（**我的裁定**）。

**网上 → 本机**（用户发起 `/agent-team:at-skills 检查更新` 时）

- `git` 类：`git -C <目录> fetch` 后看本地落后上游几个提交；有新的，问用户，批准了才 `git -C <目录> pull --ff-only`，再走上面的同步。
- `plugin` 类：由 Claude Code 的插件更新管。实现者先在当前 CLI 上核有没有只读的「有没有新版」查法；有就照 `git` 类的做法问、批准后跑
  `claude plugin update`；没有就照实说「插件带的这里只核本机那份变没变」。
- `user`、`project` 类但不是 git 克隆的：照实说查不了。
- 这些命令都在项目之外、会改用户本机的东西，按敏感操作的口径先问再做；在项目经理正文里写明，免得与「不跑动工作树或历史的 git 命令」那条红线读成冲突
  （那条管的是项目仓库）。

### 5.6 插件自带的脚本

**我的裁定**：加一个零依赖的 Node 脚本（位置与名字由实现者定，要进 `PLUGIN_LOADED`），项目经理经 `Bash` 调它，子命令大致是：

- `list`：找出本机装的 skill（5.2 的四类来源，排除 agent-team 自己的），输出名字、`description`、来源、有没有脚本、大小、已登记状态；
- `sync <名字…>`：复制整份目录进 `.agent-team/skills/`，写清单；
- `check`：比本机原件与清单的指纹，输出变了的、不见了的，以及变了的文件列表；
- `remove <名字>`。

理由：跨三个系统找文件、算指纹、复制目录，让模型每次现编 Bash 既不稳也费 token；`installed_plugins.json` 的格式也只该在一处读。
脚本的根目录（用户主目录、项目根）要能从参数或环境变量传入，测试才不会读到真机的 `~/.claude`。

指纹：整份目录按相对路径排序，逐个文件的路径与内容一起算 sha256（行尾是否折叠由实现者定，但登记与比对要用同一种）。

### 5.7 门禁

不加新门禁、不放松任何一道：

- 角色写不进 `.agent-team/skills/` 与 `skills.json`，现有写路径隔离已经保证；补一条判据钉住（每个角色对这两处的写入都被拒，项目经理放行）。
- 「没有任何角色持有 `Skill`」的判据照旧。

## 6. 留给实现者的

- 命令正文的措辞、`AskUserQuestion` 的题面与选项文字（选项文字不要撞上门禁认的规范标签）。
- `skills.json` 的字段名、脚本的位置与子命令名、输出格式。
- 指纹是否折叠行尾。
- 「登记给你的 skill」一节的最终措辞（5.3 列的几层意思都要在）。
- 插件类 skill 的网上新版怎么查（先在当前 CLI 上核）。
- `installed_plugins.json` 里 `scope` 为 `local`/`project` 的条目怎么判断属于不属于这个项目（先核真实文件里带什么字段）。
- 项目经理自己用过的 skill 记在哪：**我的建议**是记进 `04-dispatch.md` 的「用过的 skill」，交付文档 `08-delivery.md` 汇总全队用过的
  （名字与 sha 前 8 位）；契约有结构要求，不往里记。
