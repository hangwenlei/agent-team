# 边看边改的微调，与「一趟只归一个会话」—— 设计

**日期**：2026-11-05　**状态**：已批准（2026-11-05；审阅子代理提的四个问题按「我的裁定」补进正文）。第一步（§8 第 1 条）的实现与裁定见 `docs/103`；完整一趟的「放弃」收尾挪到第二步　**来源**：与用户的头脑风暴（插件作者本人）；接在「角色用上本机 skill」（v7.7.0）之后

---

## 1. 为什么要做

插件的主线是**从零到一做出完整的东西**：用户把一整个需求交出去，团队沿 S1→S8 走完，门禁把关，回来拿一份核验过的交付物。
这一套是为「委托、人走开」设计的，所以重。

交付之后（或者一个跑过 at-init、还没走过完整一趟的老项目上），用户常有一类**微调**：换全站字体、把某页的小标题换掉、把弹窗换成从右边滑出的抽屉，后端也有同类小改动。共同点是
改哪里、改成什么用户已经说清了，改完一眼能看出对不对，往往要来回几轮（「抽屉再宽一点」「标题去掉」）。为它们写产品定义、
架构方案、派发裁决、业务验收，纯属空转；可在团队外面开个普通会话自己改，团队的记录（契约、各角色认领的目录、测试）就和
代码对不上，下一次需求是照着过期的记录干活。用户的话：微调「不脱离 Agent Team」，但小改动不需要团队「开会」。

用户还要两件事：

- **并行**：多开几个会话，各跑一个微调，同时改几处。
- **一趟完整的需求只归一个会话**：一个会话正在跑 `/agent-team:at`，另一个会话里再起 `/agent-team:at` 不放行，问用户是不是要
  补充需求；是，就回到最开始起那一趟的会话去补充；不是，就结束这次。今天的做法是新会话里问「续跑那一趟还是放弃它另起」，
  两个会话会同时驱动同一趟、或者一个会话悄悄把另一个会话正在跑的一趟切走。

这两件事和微调共用同一套底子：**门禁按会话认这一趟**。所以写在一份设计里。

## 2. 目标、不做、反目标

**目标**

1. 新命令 `/agent-team:at-tweak <要改什么>` 起一趟**微调**：不走产品定义、架构方案、派发裁决、业务验收；改了就给用户看，
   用户说「可以了」才收尾。
2. 每一轮派**负责的执行角色**改（前端的改动派 `at-frontend`，后端的派 `at-backend`……）。写路径隔离、敏感操作红线、
   登记给角色的 skill 照旧。
3. 收尾时跑一遍项目的全部测试，列出改了哪些文件，停掉开给用户看的服务，留一页交付记录。
4. 多个会话可以同时各跑一个微调；两个微调不会改到同一个文件。
5. 一趟（完整的或微调）只归一个会话。别的会话碰不到它：起 `/agent-team:at` 时问是不是补充、引回原会话；原会话没了，
   用 `/agent-team:at-resume` 在新会话里明确接手。

**不做**

- 不自动判定「小」。用户用 `/agent-team:at-tweak` 发起就是按小改动走；项目经理复核一下，发现其实不小就停下来建议改走
  `/agent-team:at`，走不走用户定。
- 微调不改产品定义、架构方案（它们留在上一趟完整需求的记录里）。要改它们的，就不是微调。
- 不在会话之间自动转话。插件拿不到跨会话的工具；补充由用户回原会话自己说，新会话把要说的话整理好给他。
- 不用 git worktree 做并行（理由见 §4.1）。
- 完整的一趟不并行：同一个项目同一时刻最多一趟没收口、归某个会话的完整需求。

**反目标**（技术上能跑，但这样就算失败）

- **主流程变慢、变复杂。** 正常一趟的阶段链、花名册、门禁判定与角色正文的主干不因微调多出步骤；判据要钉住「正常一趟的
  行为不变」。
- **微调成了绕过团队的后门**：大需求假装小改动、一路微调下去。
- **两个会话同时驱动同一趟**，或者两个微调互相覆盖对方改的文件。
- **一趟卡死**：原会话关了、一趟永远收不了口，挡住之后所有完整需求。

## 3. 约束（现有决策与平台事实）

- **任何角色都不授予 `Skill` / `SendMessage` / `ListAgents`**：项目经理不能「接着跟同一个子代理说」，每一轮都是新派一次，
  新起的子代理要重新读要改的文件（每个角色开局约 1.7 万 token）。
- **花名册是派发白名单**（H1）：今天项目经理只能派产品、架构、测试、验收；执行角色只有架构师能派。`at-pm` 的 `tools:` 里
  `Agent(...)` 已经列着五个执行角色，不用动工具面。
- **阶段链里产品、架构两段裁不掉**：S5 的前置是 `03-arch.md`、`04-dispatch.md`；「整段裁掉」要求把要它当前置的段一起裁掉。
- **同一段里再派同一个角色，门禁不当重做**（`hooks/lib/redo.mjs`：只拦候选段全都早于当前段的派发），所以 S5 里来回派几轮
  本身不碰返工预算。
- **门禁今天只认一个「当前这一趟」**：`.agent-team/current-run` 一个指针，`hooks/lib/runctx.mjs` 与 `gate.mjs` 的好几处按它找
  run、读 `stages.json`（`runctx.mjs`，以及 `gate.mjs` 里直接读阶段链、花名册的几处）。
- **门禁已经有一半「按子代理认回那一趟」的底子**：`completion.mjs` 的 `elsewhereRunOf` 按 `agent_id` 在所有 run 的派发记录里
  认出派它的那一趟（停下、完成、再往下派时用）；写路径隔离今天仍按当前这一趟判。
- **原话记录是项目一级的单份**：`.agent-team/user-words.json` 只放一份挂起的记录（`hooks/lib/user-words.mjs` 的 `pendingRecord`），
  记录器的 matcher 锚定 `^agent-team:at$`。两个会话同时起命令会互相覆盖。
- **主会话的 `session_id`**：命令展开那一刻（UserPromptExpansion）的会话 id 与主会话之后各次工具调用的 hook 输入里那一个相同
  （`docs/50`）。子代理触发的 hook 里带的是不是同一个，**没核过**（§7 实测项）。
- **门禁专属文件的算法或格式变了，不许让同一份磁盘状态被改判**：升级时进行中的 run 照旧口径（没有归属记录的旧 run 不按会话管）。
- **运行时正文只写现行规则**；零 npm 依赖；`hooks/` 不用晚于 `MIN_NODE` 的内建；每次推 main 挪版本号；插件自带的 frontmatter
  只用受限写法。
- **项目经理不跑动工作树或历史的 git 命令**；退回改动照 `sensitive` 问用户、按文件退。
- **起过的服务**记进各自产物的 `## 起过的服务`，收口时核、还在跑的问用户（`docs/101`）。

## 4. 做法（Approaches）

### 4.1 并行：同一个目录里多开，还是每个会话一份代码副本

| | A. 同一个目录里多开（选定） | B. 每个会话一份 git worktree |
|---|---|---|
| 互不干扰 | 靠门禁：按会话认这一趟、认领文件 | 天然隔离：文件、测试、页面服务各管各的 |
| 用户看效果 | 一个页面服务，所有改动都在里面 | 每个副本一个页面服务，端口各不相同 |
| 收尾 | 改动已经在同一份代码里 | 要把几份副本合并回主线、解冲突；项目经理按红线不跑合并，得用户自己来或另开普通会话 |
| 准备 | 不用 | 每份副本各自初始化团队（`.agent-team/` 建议不进 git，副本里没有）、装依赖；local 装的插件在副本里认不认要实测 |
| 门禁改动 | 大一些 | 几乎不用 |

用户把选择交给了我。**选 A**：微调都小、几个微调通常改的是不同文件；A 让用户待在一个目录、一个页面里看全部改动，不用合并。
B 是大块并行开发的常规做法，但合并和多个页面服务正是小改动不该有的负担。而且「一趟只归一个会话」本来就要「按会话认这一趟」，
A 复用它。

### 4.2 每一轮谁动手改

- **A. 每轮派负责的执行角色（用户选定）**：写路径隔离、角色的做法、登记的 skill 都在；代价是每轮等一个子代理从头起来。一次说
  几处改动可以少来回几轮。
- **B. 项目经理自己改**：一轮几十秒；但不带角色的做法与 skill，写路径隔离管不到它，而且「项目经理只派不干」这条线一松，
  主流程里它也会开始自己动手——撞反目标第一条。

### 4.3 门禁怎么认微调

- **第二条短链，按这一趟的种类选（选定）**：`state.json` 记这一趟是哪种，门禁按它选阶段链与派发白名单。正常的一趟一个字不变。
- 同一条链靠裁剪：裁不掉（S5 要读架构方案），硬裁要改「整段裁掉」的口径，波及正常的一趟。
- 门禁不管微调、在 run 之外改：记录与代码对不上，正是用户要「不脱离团队」的反面。

## 5. 设计

### 5.1 用户看到的样子

```
你：/agent-team:at-tweak 把设置页的弹窗换成从右边滑出的抽屉
项目经理：算小改动，归前端改，会碰到设置弹窗和它的两条测试。派前端去改……
项目经理：改好了，刷新 http://localhost:5173/settings 看。  [可以了，收尾] / 直接写下一轮要改的
你：抽屉再宽一点，标题去掉
项目经理：（再派一次前端）改好了，刷新看。  [可以了，收尾] / …
你：可以了，收尾
项目经理：全部测试跑过，通过；页面服务已停掉。改了 3 个文件，记录在交付文档里。
```

另一个会话里，那一趟完整的需求还没收口时：

```
你：/agent-team:at 列表页加一个导出按钮
项目经理：另一个会话正在跑一趟（11 月 5 日 14:30 起，需求是「做一个记账应用……」），这里不能另起。
          你这次说的是要补充给那一趟吗？  [是，回那个会话补充] / [不是，结束这次]
你：是，回那个会话补充
项目经理：回到侧边栏里标题以「做一个记账应用」开头的那个会话，把这句发给它：「补充需求：列表页加一个导出按钮」。
          这个会话可以关掉了。
```

### 5.2 一趟只归一个会话

- **归属**：每一趟（完整的、微调）记下归哪个会话。建 run 的那个会话就是它的主人。记法照原话绑定：PreToolUse 只记意图，
  同一次写入落盘之后（PostToolUse）才算数——建 run 的写入可能被并行的门禁拒、被用户在权限确认里拒（`docs/58` 的教训）。
  归属记录是门禁专属文件（H3 对任何人的 Edit/Write 都拒）。
- **门禁拦什么**：项目经理（主线程）以外的会话对一趟有归属、没收口的 run——写它的 `state.json`、契约、产物，写 `current-run`
  把它切走，以它的名义派人——一律拒。拒绝理由说这一趟归另一个会话、出路两条：回那个会话；那个会话没了，用
  `/agent-team:at-resume` 在这里接手。
- **新会话里起 `/agent-team:at`**（`commands/at.md` 第 1 节，「先看 current-run 指着的那一趟」那一步之前）：门禁在命令展开那一刻
  告诉项目经理「这个项目里有一趟没收口的 run（id、起的时间、原话开头），归另一个会话」。项目经理不读别的、不写任何文件，
  用 `AskUserQuestion` 问「你这次说的是要补充给那一趟吗？」，两个规范标签：
  - 「是，回那个会话补充」：给出找那个会话的线索（起的时间、原话开头——桌面应用侧边栏的标题一般就是命令那一行）和一句整理好、
    可以原样发过去的话「补充需求：<这次的原话>」，结束。
  - 「不是，结束这次」：说这一次不起新的一趟、会话可以关掉；顺带一句：那个会话已经关了、想在这里接着跑，用
    `/agent-team:at-resume` 接手。结束。
  - 回到原会话说「补充需求：…」，那边照现有的「用户主动改需求」走（修订块标「用户主动提出」）。
- **别的会话的那一趟已经交付、只差收口**（停在最后一段、交付文档写了，常见于收口第三步问停不停服务时用户关了窗口）：今天第 1 节
  是新会话直接替它收口。现在门禁在命令展开那一刻把「还在跑」和「已交付、只差收口」分开说；后一种项目经理问的是「那一趟已经
  交付、只差收口，要在这个会话接手、替它收口，再开始你这次的需求吗？」，规范标签「接手并收口，再开始这次」与「回那个会话」。
  选前者，接手（同下面「接手」那一条，门禁记）、收口、建新的一趟连着做，用户只点一次。不给归属门禁开「收口那一次写入」的例外——
  原会话可能正停在 S8 问服务，例外会让两个会话同时驱动同一趟；接手之后原会话再写，门禁拒。（我的裁定）
- **还没建 run 时不算占用**：另一个会话起了 `/agent-team:at`、还在问需求时，这边照常往下走；两边都问完、都去建 run，后建的那一次
  门禁拒，拒绝理由把项目经理引到上面「是不是补充」那一问。不按「别的会话挂着的原话记录」提前挡——那要定挂着多久算过期，
  一次中途放弃的问需求会一直挡人。原话记录按会话分开记，挪进第一步发版（§8），不然这边的命令展开会覆盖那边挂着的原话，
  那边建 run 时绑不上、契约第 1 节悄悄不核。（我的裁定）
- **同一个会话里**再起 `/agent-team:at`：照今天的做法（续跑还是放弃另起），不变。
- **接手**：在不是主人的会话里跑 `/agent-team:at-resume`，项目经理先问「原来那个会话还在吗？」——还在就回那边；不在了，用户在
  `AskUserQuestion` 里选规范标签「在这个会话接手」，批准记录器把归属改成这个会话（只认这个标签，对话里打字不认，同 `BRIEF_LABEL`）。
  之后原会话再写，门禁拒，理由说已被另一个会话接手。
- **没有归属记录的旧 run**（升级之前就在跑的）：不按会话管，行为与今天相同。

### 5.3 微调的短链

`state.json` 加一个键记这一趟的种类（建 run 那一次定下、之后不许改；没有这个键的是完整的一趟）。微调沿用正常链的段号与产物名，
只取其中几段、改谁产出与前置：

| 段 | 谁 | 前置 | 产物 |
|---|---|---|---|
| S1 | 项目经理 | — | `00-contract.md`：第 1 节是用户发起时的原话；之后每一轮的反馈作为修订块追加（标「用户主动提出」） |
| S4 | 项目经理 | `00-contract.md` | `04-dispatch.md`：小不小的复核、谁改、预计改哪些文件、波及哪里、用户怎么看效果、起过的服务 |
| S5 | 叫到的执行角色 | `04-dispatch.md` | `05-impl/<role>.md`：每一轮改了什么、改了哪些测试、起过的服务 |
| S6 | 项目经理 | `04-dispatch.md` | `06-test.md`：第一行结论（通过 / 不通过 / 跑不起来），跑的命令与结果 |
| S8 | 项目经理 | `06-test.md` | `08-delivery.md`：原话与每轮反馈、改了哪些文件、测试结果、停掉的服务 |

- 沿用段号与产物名的理由：`at-status`、`at-resume`、门禁回传与各角色正文里「S5」「实现记录」这些说法在微调里意思不变，
  测试结论、收口、交付快照、新鲜度这些现成的判据能直接认。
- **派发白名单**：只在微调这一趟里，项目经理能直接派五个执行角色；产品、架构、测试、验收不派。正常的一趟照旧。
- **S6 由项目经理产出**：它不是被验的一方，跑的是项目自己的测试命令（`project.json` 里 at-init 记下的那条）。没有测试命令的，
  结论写「跑不起来」，收口时照现有规矩要用户批准「照现状交付」。
- **用户满意才出 S5**：每一轮改完，项目经理用 `AskUserQuestion` 告诉用户改了什么、去哪里看，规范标签「可以了，收尾」；用户也能
  直接写下一轮要改的（选「其他」打字，或在对话里说）。门禁记下「可以了，收尾」（经两个批准记录器，与「照现状交付」同一套；
  对话里单独发这一句也认），推进出 S5 的那一次 H6 核它：最后一次修订之后有这条记录才放行。它替代的是业务验收。
- 测试红了：回退到 S5 派回去修（照「回退」记，占返工预算——测试修不好的循环要有上限）；用户在 S6 之后又提一轮改动，是修订，
  `06-test.md` 跟着过期、要重跑（契约基线现有的口径）。

### 5.4 复核小不小（S4）

项目经理读契约原话与相关代码，写 `04-dispatch.md`。下面任一条成立就**不算小**，停下来问用户：改走 `/agent-team:at`，还是
照微调继续（用户说了算，用户坚持的照微调走、在派发里写明）：

- 要在前后端或几端之间**新约定接口**、改已有接口的形状；
- 要改数据结构（库表、持久化格式）；
- 要**新增页面或流程**，或改产品定义、架构方案里定下的东西。

一次微调可以叫到几个执行角色（例：全站字体 Web 与 iOS 一起换），只要它们之间不用新约定接口。要设计帮忙的（「这个抽屉帮我
设计得好看点」），叫 `at-ui`；只是照用户说的改样式、文案的，直接派实现那一端。

### 5.5 来回改（S5）

- **看效果**：前端改动，项目经理在第一轮之前把本地页面服务起来、一直开着，告诉用户地址，用户在自己的浏览器里刷新看；后端改动，
  项目经理把接口调用结果贴给用户。服务记进 `04-dispatch.md` 的 `## 起过的服务`。执行角色不另起页面服务给用户看，也不截图——
  用户自己看（它们照旧可以跑构建、测试来核自己的改动）。
- **派发提示**带上一轮改了哪些文件、这一轮用户的原话，执行角色不用重新探索整个项目。
- **测试**：改了行为的（弹窗换抽屉），改的角色把相关测试改成新样子或补上；纯样式与文案（字体、标题文字）不要求新测试，但已有
  测试断言了旧文案的，要跟着改。
- **登记的 skill**：照「登记给你的 skill」那一节，不变；用户这一轮点名「用 X」的，写进修订块，同契约点名的口径。

### 5.6 并行：按会话认这一趟、认领文件

- **门禁认这一次属于哪一趟**：子代理触发的（带 `agent_id`）先按派发记录认（扩展 `elsewhereRunOf` 那一套到写路径隔离与每一道
  门禁）；主线程触发的按会话：这个会话是某一趟没收口的微调的主人，就是那一趟；不然是 `current-run`。微调不写 `current-run`。
- **互斥**：
  - 互斥里认的「完整的一趟」，只认 `current-run` 指着的、没收口也没放弃的那一趟，不论有没有归属记录（升级之前就在跑的旧 run
    也挡：它的执行角色认领的是整个目录，不进认领记录）。今天同一个会话「放弃它、另起这一趟」切走指针的那些旧 run，指针不在它们
    身上，不算。所以门禁不用扫 `runs/` 下所有完整的 run，`at-status` 也不会一直列着放弃过的。（我的裁定）
  - 有那样一趟完整需求时（不论归哪个会话），不能起微调——门禁在建微调的那一次写入拒；项目经理在命令展开那一刻
    就知道，照 §5.2 问「是不是要补充给那一趟」（同一个会话的，直接作为补充在这里做）。
  - 有没收口的微调时，不能起完整的一趟（完整一趟的执行角色认领的是整个目录，必然撞上）；告诉用户有几个微调还开着、各归哪个
    会话，等它们收尾。
  - 一个会话同一时刻只做一趟：已经有一趟没收口的微调时再起 `/agent-team:at-tweak`，问用户是先收尾那一趟，还是把这次的话当成
    那一趟的下一轮。
  - 微调和微调之间可以并行。
- **认领文件**：每一趟微调的执行角色**第一次写**一个项目文件时，门禁把它记成这一趟认领的（先写先得）；`04-dispatch.md` 里预计
  要改的文件也在派发那一刻记上。别的、还没收尾的微调认领了的文件，写路径隔离拒，理由说「另一个微调正在改它（归哪个会话），
  等那边收尾」——执行角色以「冒泡：」停下，项目经理告诉用户。收尾（或放弃）时释放。认领记录放在**每一趟自己的 run 目录**里
  （每个会话的门禁只写自己那一趟的，避开跨会话同写一份文件的丢更新）；判的时候读所有没收尾的微调的那一份。两边在同一毫秒
  第一次写同一个文件的竞态不挡，登记为边界。
- **收尾跑测试**会跑到别的微调改了一半的代码。红了，项目经理看失败的测试碰到的是不是自己这一趟认领的文件；不是的，告诉用户
  问题可能在另一个微调那边（归哪个会话），等它收尾再跑一次，或者照现状交付（用户批准）。
- **页面服务共用**：前一个微调起的服务，后一个微调直接用、不另起；收尾停服务时，别的微调还开着，问用户的时候说明那边可能还在用。

### 5.7 放弃与卡住

- **放弃一趟微调**：用户说不改了，项目经理列出这一趟改过的文件，退不退回照 `sensitive` 问用户（现有规矩：按文件退，不用整棵树
  的命令），再做一次由门禁认的「放弃」收尾——冻结这一趟、释放认领、不再挡完整的一趟。放弃不核产物。
- **完整的一趟也能这样放弃**：用户不想续跑 `current-run` 指着的那一趟、也不另起新需求（比如想先做几个微调）时，同一个「放弃」
  收尾冻结它，它就不再挡微调。同一个会话里「放弃它、另起这一趟」照今天切走指针的做法，不强制先做放弃收尾。（我的裁定）
- **原会话没了**：那一趟（完整的或微调）一直没收口，会挡住后来的完整需求。出路是 §5.2 的接手：新会话里 `/agent-team:at-resume`
  接手之后，接着做完或放弃。`/agent-team:at-status` 列出所有没收口的一趟：种类、归哪个会话、最后一次动静的时间。

### 5.8 没走过完整一趟的项目

跑过 `/agent-team:at-init` 就能用 `/agent-team:at-tweak`，不要求先有一趟收了口的完整需求——「刚装上插件、想先改个字体」的老项目
是常见用法，不碰主流程。（我的裁定）

- 没跑过 at-init 的，照今天别的命令的做法引去先跑它（微调要用 `project.json` 里的认领目录与测试命令）。
- `runctx.mjs` 今天的判别是「`current-run` 不在、`runs/` 下却有子目录，就判读不出」：第一趟就是微调的项目，每个会话的门禁都会把
  整个运行上下文判坏。要改成只拿完整的那几趟判（微调的 run 不算），或者把微调放到 `runs/` 之外——实现者定，判据钉住两种项目
  （先有完整一趟、只有微调）都不判坏。
- S4 复核时没有产品定义与架构方案可比：§5.4 的头两条（新约定接口、改数据结构）与「新增页面或流程」照代码判，第三条里「改产品
  定义、架构方案里定下的东西」那半句不适用。

## 7. 怎么验证

**判据**（`node --test`）

- 正常一趟的行为不变：现有判据全绿；加「上一版状态的夹具」——没有种类键、没有归属记录的 run，门禁的每一个判定与今天相同。
- 归属：别的会话写 `state.json`、契约、产物、`current-run`、以它的名义派人，拒；同一个会话放行；接手之后原会话拒；旧 run 不管。
- 短链：微调里项目经理派执行角色放行、派产品与架构拒；正常一趟里项目经理派执行角色照旧拒；S5 没有「可以了，收尾」推不出去；
  S6 由项目经理产出、结论照测试结论的口径读；收口核 S8。
- 互斥与认领：完整一趟开着时建微调拒；微调开着时建完整一趟拒；两个微调写同一个文件，后写的拒、理由点名另一个会话；收尾、
  放弃之后释放。
- 原话记录：两个会话先后起命令，各自的原话各绑各的一趟。
- 正文：`runtime-prose`、命令清单（六条命令）、`readme-sync`、红线与工具面那几份照旧过；新加的逐字段落整句钉。
- 变异：改坏每一道新判定，看判据红不红。

**实测**（真实会话，CLI 当前版本）

1. 子代理触发的 hook 输入里 `session_id` 是不是主会话那一个（门禁优先按 `agent_id` 认，这一条决定退路要不要用）。
2. 命令展开那一刻的回传能不能让项目经理看到（模型读得到，不只是进转录）。
3. 同一个目录里两个会话各跑一个微调：认领、各自的测试、共用页面服务、各自收尾。
4. 一个会话跑着完整的一趟，另一个会话起 `/agent-team:at`：问补充、两个选项各走一遍；原会话关掉之后 `/agent-team:at-resume` 接手。
5. 一趟真实的微调走完（弹窗换抽屉这一类），来回至少两轮，量每一轮的时间与 token。

## 8. 发版与顺序

建议分三步、各自发版（每步都能单独用，后一步建在前一步上）：

1. **一趟只归一个会话**：归属记录、门禁拦别的会话、`/agent-team:at` 的「是不是补充」与「接手并收口」、`/agent-team:at-resume`
   接手、`at-status` 列归属、原话记录按会话分开、完整一趟的放弃收尾。这一步就交付了用户提的 `/agent-team:at` 新规矩。
2. **单个微调**：`/agent-team:at-tweak`、种类键与短链、派发白名单、「可以了，收尾」、微调的放弃、没走过完整一趟的项目、
   各角色「在微调里」一节。
3. **并行微调**：按 `agent_id` 认这一趟扩到每一道门禁、认领文件、互斥、共用页面服务。

每一步照发版纪律挪版本号、写 CHANGELOG、先推功能分支等 CI 全绿再合 main；实现记录写进 `docs/` 新的一份，开放边界跟着加行。
