# 103 一趟只归一个会话

**日期**：2026-11-05　**版本**：7.8.0　**设计**：`docs/superpowers/specs/2026-11-05-边看边改微调与会话归属-design.md`（§5.2、§8 第 1 条）　**计划**：`docs/superpowers/plans/2026-11-05-一趟只归一个会话.md`

---

## 0. 一句话结论

每一趟 run 记下归哪个会话。别的会话写它、切走它、另建一趟、以它的名义派人，门禁拒。别的会话起 `/agent-team:at` 时，项目经理先问这次是不是要补充给那一趟；
原来那个会话没了，用 `/agent-team:at-resume` 明确接手（题面带 run id，门禁记）。原话记录按会话分开记，两个会话起命令不再互相覆盖。这是边看边改微调那份设计的第一步，
第二、三步（单个微调、并行微调）建在它上面。

## 1. 起因

用户的原话：一个会话在跑 `/agent-team:at`，另起一个会话也跑 `/agent-team:at`，要「禁止另起 at，询问是否补充，是就回到最开始起 at 的那个会话去进行补充，
否就直接结束当前新 at 会话」。今天第 1 节的做法是新会话里问「续跑那一趟还是放弃它另起」：两个会话会同时驱动同一趟，或者一个会话悄悄把另一个会话正在跑的
一趟切走。并行微调（设计 §5.6）要的「门禁按会话认这一趟」也是同一套底子，所以先做这一步。

## 2. 裁定

### 2.1 归属在账本记，「建 run」用 H6 的口径

建 run 的那一次 Write 落盘之后，账本写 `runs/<id>/owner.json`（门禁专属）。认「这一次建出了这一趟」用 H6 认 `stage_roles` 的同一个口径：run 目录里还没有任何一份门禁
专属文件。没有另设一份项目一级的「打算建哪一趟」的意图文件——PreToolUse 那一刻 run 目录还不在、写入还可能被拒，等落盘之后（PostToolUse）一次做完更直接。
代价：升级之前建的、还停在第一段、一份门禁专属文件都没有的 run，下一次被写时归给写它的会话。

### 2.2 只管主线程

项目经理与不带 `agent_type` 的主会话、而且不带 `agent_id` 的调用才判归属。子代理照旧按派发记录认回派它的那一趟（`completion.mjs` 的 `elsewhereRunOf`）。

### 2.3 没有归属记录的 run 一切照旧

升级之前建的、跑过一阵的（目录里已经有门禁专属文件）、hook 输入里没有会话 id 时建的，都没有 `owner.json`，门禁不按会话管它们（升级兼容：同一份磁盘状态
不被改判）。用 Bash 建的 run 若在第一份门禁专属文件出现之前被主线程用 Write 写了一次 `state.json`，会归给写它的会话（§2.1 的代价）。`owner.json` 坏了也当没有，留痕；
hook 输入里读不到会话 id 时判不出来、放行，碰到有主人、没收口的一趟时 H3、H2 各留一行痕。

### 2.4 拦在哪

H3（写路径）拦写这一趟的文件、另建一趟（写一份新的 `state.json` 而 `current-run` 指着别的会话的一趟）、把 `current-run` 从它切走；H2（就绪）拦以它的名义派人。两处都
排在读运行上下文之前：建 run 那一刻、运行上下文读不出来时照样判。

**改指针只判切走，不判指向哪一趟**（终审的应当修第 1 条）：指针空着（丢了、指着已收口或这个会话自己的一趟）时，指到别的会话的一趟放行。单是指过去什么都拿不到——
写与派照旧被拒，两个批准记录器也不记（§2.6），直到用户在这个会话接手；而丢了指针、放弃了的一趟要在别的会话里接回，正得先把指针指过去，接手才认得到它。原来
「指到它」也拒，`at-resume` 第 1 节「丢了指针就写回」那一步在原会话之外走不通，接手又读不到指针、回「不用接手」，会绕成死循环。

### 2.5 指针与 run 目录怎么认（安全审查）

- 指针两路都认：规范化之后的路径就是 `current-run`（经链接、8.3 短名写的），或者叶名是它、所在目录就是 `.agent-team`（流后缀、结尾的点与空格）。
- 只判切走之后，改成什么不用算：Edit 写指针不再重放内容（安全审查曾要求重放、算不出时扫 `runs/`，那是「指到它」也拒时的配套，随之撤掉）。
- run 目录按规范化之后的真名查归属：照字面取的话，经一个名字不合 run id 格式的链接写进去就查不到。结尾带空格的目录本来就被原有的怪路径规则拒。

### 2.6 接手

只认 `AskUserQuestion` 里的「在这个会话接手」「接手并收口，再开始这次」，对话里打字不认（门禁看不到用户是对着哪一道题说的）。题面里要原样写着 `current-run` 现在指着的那一趟的
run id（`mentionsRunId`，按词边界认，`r1` 不算写了 `r10`）——安全审查：问和答之间指针换了、问的是别的一趟，接手都不能落到现在这一趟。没有归属记录的旧 run 选了
接手也记，给它补上归属。指针不在时选了接手，回传叫项目经理先把指针指到要接回的那一趟、再问一次（原来说「不用接手」）。

`current-run` 那一趟归别的会话时，两个批准记录器（返工批准、照现状交付）不记，回传说归另一个会话（安全审查：指针空着时别的会话指得过来，不核的话这个会话里的回答会记进别人那一趟）。

**`/clear` 会换一个新的会话 id**（实测，§8）：同一个窗口清空之后就成了「别的会话」，项目经理写自己那一趟会被拒。清空前后的两个 id 门禁不自动连起来——SessionEnd 的旧 id
与 SessionStart（source 为 clear）的新 id 之间没有可靠的配对，两个窗口同时清空会配错——改由问法与拒绝理由写明「同一个窗口里用过 /clear 的，原来那个会话就算关了」，
用户在这个会话接手一次。压缩与 `--resume` 前后会话 id 不变。

### 2.7 【会话】

命令展开时（UserPromptExpansion，`/agent-team:at`、`at-resume`、`at-status`）一个新的、标了 `speaks` 的检查项 `session-notice` 用 additionalContext 告诉项目经理：run id、起的时间
（`history` 第一条）、原话开头（run 目录那份原话记录的第一行，截到 40 个字）、那一趟是不是只差收口（停在最后一段、交付文档在且不空）。建它的会话、没有归属记录、已收口、
没有 `current-run` 的不出声——正常的一趟不多一个字。

### 2.8 原话记录按会话分开

项目一级的 `user-words.json` 改成 `{ version: 2, sessions: { 会话 id: 记录 } }`，旧的单份记录读成只有它那个会话的一张表（升级之前挂着的照旧认）。读、改这个会话那一条、写回
都在一把锁里（`withFileLock`，批准记录那把抽出来的）；写回时顺手清掉别的会话里已经绑上或作废的条目（之后没有读者，不清的话这张表只增不减、每个起过命令的会话都留着
整段原话），还挂着的不动；表空了删掉文件。run 目录那份（绑上之后的）仍是单份记录。

### 2.9 其余

- 完整一趟的「放弃」收尾挪到第二步：没有微调时它不改变任何行为（设计 §8 第 1 条原来把它排在这一步）。
- 回原会话说「补充需求：…」的，那边照 `/agent-team:at` 第 4 节「用户主动改需求」办（计划里写成第 5 节，那一段实际在第 4 节）。
- 插进第 1 节的新段之后，紧跟着那段里的「照上面那一段」改成「照本节开头那一段」，免得被读成指新段。
- 顺手修了 `mayBeGateFile`：它写死了门禁专属文件的叶名，加 `owner.json` 时漏认；改成从清单派生，配一条「清单里每个叶名都认」的判据。
- `tests/gate-ledger.test.mjs` 的 `writeState` 夹具补上 `session_id`：真实 hook 输入总带它，不带时账本为「这一趟不记归属」留的那行痕撞了三条「stderr 为空」的断言。

## 4. 门禁不核（三样）

项目经理拿到【会话】之后照不照正文问用户、题面写得对不对（接手那两个标签与 run id 除外）、用户选了「是，回那个会话补充」之后真的回去说了没有，门禁都不核。

- **拒绝的判据长什么样**：有【会话】的那一轮里项目经理调 Write 或派人就拒——这一半已经由 H3、H2 的归属判定做了；剩下的「问没问、怎么问」要读模型的回复。
- **它打不红的那一刀**：项目经理不问、只回一句「去那个会话」；或者问了，却把「补充需求」那一句里的原话改了。
- **什么会让答案改变**：真实会话里看到项目经理拿到【会话】之后还去读写别的、把用户引错会话，或者用户照着发过去的那句话对不上原话。

## 5. 仍然开着的边界

- 归属只管主线程的 Edit/Write 与派发；Bash 写 `.agent-team` 下的文件不挡（既有边界：门禁不加 Bash 的 matcher）。
- 门禁分不出原来那个会话还在不在：接手靠用户判断。原会话还开着时用户在新会话里接了手，原会话之后的写入与派发被拒（这是要的结果），但原会话已经派出去的子代理照旧
  按派发记录认回那一趟、交它们的产物。
- 两个会话都还没建 run 时不算占用：都问完需求、都去建 run，后建的那一次被拒，那几轮问需求白问（有意，设计 §5.2）。
- 两个会话几乎同时建 run（前一个已落盘、还没写指针，后一个的 `state.json` 也落了盘）：后一个写指针时被拒，留下一个没人管的空壳。
- 【会话】只在三条命令展开时说：用户在对话里直接叫项目经理「接着做」、不走命令，项目经理要等写入或派发被拒才知道（拒绝理由给了同样的两条出路）。
- `-p`、后台会话里问不了用户：项目经理只能说明两条出路、什么都不做（§8）；接手必须在能弹出问题的会话里做。
- 同一个窗口里用过 `/clear`、或者分叉出新会话 id 的续会话（`--fork-session`），都成了「别的会话」，要接手一次（门禁不自动连两个 id，§2.6）；`--resume` 与压缩不变（§8）。
- 指针空着时别的会话能把 `current-run` 指到这一趟（为了接回）：指过去之后原会话那边读 `current-run` 的命令看到的仍是这一趟，只是别的会话写与派都被拒，直到接手。
- 升级之前的插件版本不认 `owner.json`：被旧版本驱动的会话不按会话拦。
- 完整一趟的「放弃」收尾在第二步做。
- 终审列的小问题没修：`approval-ask` 崩溃时给项目经理与用户的文案没提两个接手标签；H2 的归属判定对不带 `agent_type` 的主会话派任何 agent（含非团队角色）都拦，比「以它的名义
  派人」宽；两处拒绝理由末尾的 `selfCheckIdentity` 恒为空串；折叠大小写的文件系统上拒绝理由里的 run id 是小写。

## 6. 没量到的

- 交互会话里几个选项各走一遍：三场实测都在 `-p` 下，只看到「问不了用户」那一支；接手之后接着推进一段也没跑。
- 桌面端重开会话走不走 `--resume`（会话 id 变不变）；自动压缩（只核了手动的 `/compact`）。
- 子代理触发的 hook 输入里的 `session_id` 是不是主会话那一个（第三步要用；这一步只管主线程）。
- 经文件链接写指针那条判据在本机 Windows 上跳过（建文件链接报 EPERM），红绿只在 CI 的 Linux、macOS 上跑。

## 8. 变异与实测

**变异**（`tests/owner.test.mjs`、`gate-owner`、`user-words`、`gate-user-words`、`gate-brief`、`owner-prose`、`control-files` 一起跑）：22 刀，本机 20 刀红——`blocksMe` 的三个条件、
不判另建、不判切走、算不出新指针时不扫、run id 不按词边界、接手不看备注、建 run 不看门禁专属文件、建 run 时子代理也记、H3 子代理也走归属、H3 不拒、H2 不拒、接手不核 run id、
接手不判已归我、接手不判已收口、【会话】不判归属、`withWords` 丢掉别的会话、旧单份记录不认、预筛写死叶名。两刀本机绿：「指针只按叶名认」要靠经文件链接写指针那条判据杀
（本机建不了文件链接，跳过）；「指针只按规范化路径认」要靠流后缀那条判据杀（Windows 的规范化本身认流后缀）。两刀都预期在 CI 的 Linux、macOS 上被杀，没在本机核。

**实测**（CLI 2.1.310，`claude -p --plugin-dir <本工作树>`，探针目录在仓库外）：现场是一个跑过 at-init 的项目，磁盘上直接造一趟归「另一个会话」（假的会话 id）的 run。

1. 停在 S2，起 `/agent-team:at 列表页加一个导出按钮`：【会话】作为 hook 的附加上下文进了模型的请求；项目经理没建 run、没写任何文件、没调任何工具，说明工具面里没有
   `AskUserQuestion`、问不了，列出两条出路，给出一句原样可发的「补充需求：列表页加一个导出按钮」与找那个会话的线索；磁盘上 `current-run` 与 `runs/` 不变。
2. 同一个现场起 `/agent-team:at-resume`：没接着跑、没写、没派，说清两条出路，接手那条说要在能弹出问题的会话里做、题面会带 run id。
3. 改成停在 S8、交付文档已写，起 `/agent-team:at 列表页加一个导出按钮`：【会话】说只差收口，项目经理列出「接手并收口，再开始这次」与「回那个会话」两条出路，磁盘不变。
4. 一个最小的会话（另挂一个只追加、不写 stdout 的记录钩子，记 SessionStart、UserPromptSubmit、PreCompact、SessionEnd 的 `session_id` 与 `source`）：`--resume` 之后、
   `/compact` 之后（SessionStart 的 source 是 compact）hook 输入里的 `session_id` 都不变；`/clear` 之后换了一个新的（SessionStart 的 source 是 clear）。Git Bash 里要
   `MSYS_NO_PATHCONV=1`，不然 `/compact` 被当成路径转成 `C:/Program Files/Git/compact`。

**第二轮变异**（终审修补那几处）：9 刀 8 红——切走判定去掉、拒绝理由不提 /clear、缺会话 id 不留痕、批准记录器不核归属、原话记录不清理、清理时连自己的也清、【会话】不给起的
时间加引号（被 trusted-echo 杀）、原话记录不加锁（被并发判据杀，三遍都红）。「no-run 回传又说不用接手」是等价变异（前面已有专门的 no-run 分支）。

## 9. 终审

一个新的审阅者看了整条分支，结论「修好再合」，没有必须修的。处置：

- 应当修第 1 条（丢了指针、放弃了的一趟在别的会话接不回，死循环）：改成只判切走（§2.4），接手时指针不在的回传改说先指过去（§2.6）；配「丢了指针之后接回」「放弃了的
  那一趟被接回」「指针指着自己的一趟时改指到别的会话的一趟放行」三条判据。它放开的口子由安全审查再补一道：批准记录器核归属（§2.6）。
- 应当修第 2 条（`/clear` 与压缩前后的会话 id）：实测（§8 第 4 条），`/clear` 换 id——问法与拒绝理由补一句（§2.6）。
- 小问题里按影响升级、这一轮修了的：缺会话 id 不留痕（计划写了要留）、原话记录只增不减、trusted-echo 入口没补（仓库常设规矩）、锁没有并发判据（计划承诺过）；
  文档两处（§2.3 与 §2.1 说法不一、`docs/00-现行参考.md` 里报总数的「这几行」）随文档改掉。其余的登在 §5 末尾。
