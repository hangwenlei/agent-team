## 账一：PM 在稳态下写不了 `state.json` / `project.json`

### 事实

原始记录在 `hooks/lib/writepath.mjs` 的 run 目录判定块里（I3 已知缺口）。要点：

被 `settings.json` 钉成主线程的 `at-pm` **不是** `callerOf` 判定的 `MAIN`——M0 实测过，钉住
时主会话的 hook 输入带裸的 `agent_type: 'at-pm'`。所以一旦进入稳态（`project.json` 存在、
run 正在跑），PM 就是一个受完整 per-role 隔离约束的普通角色。实测：

    at-pm 写 runs/<id>/state.json              -> deny（不是任何阶段的 produces）
    at-pm 写 runs/<id>/00-contract.md（S1）    -> allow
    at-pm 写 runs/<id>/04-dispatch.md（S4）    -> allow
    at-pm 重写 .agent-team/project.json        -> 取决于 paths 里有没有 at-pm 这个键

而规格要求 PM 做得到这些：§7 的 `templates/` 明确列了 `project.json` 与 `state.json`；
§4.5 要求「计数写在 `state.json`，不交给模型自己数」；`/at-resume` 从 `state.json` 续跑；
`/at-init` 重跑勘察要重写 `project.json`。

现有三条豁免都盖不住：它们只覆盖 `ctx.kind === 'no-run'`、真 MAIN（无 `agent_type`）、
以及 ctx 读不出来时的 PM——**三者都是异常态或空白态，稳态不在其中。**

### 两个原候选方向都有问题

M1a 留了两个方向。逐一看：

**(a) 给 `.agent-team/` 一条独立于 `project.paths` 的「PM 专属可写」规则。**
方向对，但**写成「整个 `.agent-team/` PM 都能写」就太宽**：PM 因此能在 run 目录下凭空
造出 `01-prd.md`。那正是 M1a 评审 Important 2 花三轮堵掉的洞——`artifactExists` 在
`runDir` 下解析，H2 拿它当前置产物的判据，能随便写就能伪造。只不过这次伪造者从
「任意执行角色」变成了「PM」。**PM 是用户的代理，它伪造出的「已完成」信号是拿去骗用户的，
不比别的角色伪造更可接受。**

**(b) 在 `project.json` 模板里把 `.agent-team/` 划给 at-pm，并给 `state.json` 单开例外。**
走不通，而且是被代码结构挡住的：run 目录那块判定**排在 `project.paths` 之前**，
`.agent-team/runs/<id>/state.json` 在 runDir 里，无论 `project.paths` 怎么写都会先被
「不是你这个阶段的 produces」拒掉。所以 (b) 必须带那条例外——**一个概念用两套机制表达，
而且例外那条没有判据来源。**

### 决策

**引入「控制文件」与「阶段产物」的区分，两者都在 `.agent-team/` 下，但判据不同。**

| | 是什么 | 谁能写 |
|---|---|---|
| **控制文件** | `.agent-team/current-run`、`.agent-team/project.json`、`.agent-team/runs/<id>/state.json` | **只有 PM** |
| **阶段产物** | `stages[*].produces` 里列出的文件 | 只有**该阶段自己的角色**（现有规则不变） |
| 其余 | run 目录下其它任何文件 | 一律 deny（不变） |

「PM」复用已经导出的 `isContractWriter(agentType)`（`hooks/lib/contract-guard.mjs`），
它判的是 `MAIN || at-pm`。**不要另写一遍 `role === 'at-pm'`**——M1a 评审在 H4 那里已经
因为同一个谓词写两份而开过一轮循环，那次的结论是抽成单一导出。

### 为什么这条比 (a)(b) 都准

1. **它解开了死锁**：PM 能写 `state.json` 与 `project.json`，§4.5 的计数、`/at-resume`
   的续跑、`/at-init` 的重跑都走得通。
2. **它没有放开伪造**：`01-prd.md` 是阶段产物不是控制文件，PM 写它仍然走「自己阶段的
   produces」那条——而 `at-pm` 的 produces 只有 `00-contract.md`(S1) 与
   `04-dispatch.md`(S4)。**H2 的判据对所有角色（含 PM）继续不可伪造。**
3. **它是一个概念而不是一条例外**：控制文件是编排层自己的账本，本来就不该参与「角色
   认领产物」这套判据。`writepath.mjs` 的注释已经指出来了——「真正的问题不是认领表漏了
   一行，是『PM 的运维动作该不该走角色认领这套判据』从来没有被决定过」。**本条就是决定
   它：不该走。**
4. **判据有来源**：控制文件是一个**闭集合且可枚举**，不像 (b) 的例外那样凭空冒出来。

### 实现约束（给 M1b 的计划）

- 控制文件清单**必须是单一真源**，不要在 `writepath.mjs` 与模板里各写一遍。放哪里由计划
  决定，但它和 `stages.json` 一样属于「插件侧的结构定义」，不是用户项目的配置。
- `decideWritePath` 会因此再加一个入参或改判定顺序——**改之前先过一遍 `docs/08` §3 那五问**，
  尤其第 4 问（为修 A 而改的东西有没有动到 B 的前提）。M1a 有两次连续栽在这上面。
- **不要动**「同一角色的多个阶段 produces 都能写」这条（at-pm 的 S1/S4 那两条 allow）。
  它是这块唯一已经正确的行为，`tests/writepath.test.mjs` 与 `tests/gate-writepath.test.mjs`
  各钉了一条。
- 新增判定必须同时有**纯函数单测**与**子进程级传导链测试**。M1a 的 Task 3 栽在只有前者
  （`docs/08` ②）。

## 账二：H3 的「实际写入触达」没有显式不变量

### 事实

`docs/04` §9「对设计的影响 ①」记的实测：`at-product` 被 H3 拒绝写 `src/web/x.ts` 之后，
**没有任何人要求它这么做**，它当场把同一个写入转手派发给那条路径的合法拥有者
`at-frontend`。挡住它的是 H1（`at-product.can_delegate_to` 里没有 `at-frontend`），
**不是 H3**。

原始记录在 `Desktop\at-m1a-证据备份.md`（`tool_use` + 配对的 `tool_result`，
`toolDenialKind: "permission-rule"`）。

推论：**一个角色的实际写入触达 = 自己认领的路径 ∪ 它能（传递地）派发到的所有角色认领的
路径。** 规格 §6 把五道闸写成互相独立的一张表，没有记录这个耦合——**改一条
`can_delegate_to` 就可能悄悄放大某个角色的写入范围，而没有任何测试会红。**

还有一条加重它的事实：**H3 的拒绝措辞本身在提示这条绕法**——「跨角色的改动要经上级
协调」被代理读成了「那我派给拥有者」，而不是「冒泡给上级」。

### 决策

**不新增门禁，改为让「触达」可见且变更时必须被确认。** 三件事：

**① 把「实际写入触达」做成可计算的函数**（插件侧，纯函数）：
给定 `roster` 与 `project.paths`，算出每个角色的传递触达集。这是纯数据推导，能脱离
Claude Code 单测，和 `decideDelegation` / `decideWritePath` 同一层。

**② 仓库里钉机制，不钉具体项目的数据。**
`project.json` 属于**用户项目**，插件的测试不可能知道真实项目的 paths。所以仓库里的测试
用夹具验**算法本身**（含传递闭包、环、自引用这些退化输入），不去断言某个具体的触达表。

**③ 具体项目的触达表由 `/at-init` 生成、由 `/at-status` 可见。**
`/at-init` 生成 `project.json` 时一并算出触达表并落盘进 run；`/at-status` 显示它。
**这样「谁实际上能写谁的地盘」从一个没人算过的隐含属性，变成一个摆在台面上的产物。**

### 为什么不是「加一道闸」

本来最直觉的做法是让 H1 在派发时也查「这次派发会不会绕开 H3」。不做，理由三条：

1. **它会拦掉正当的协调。** `at-pm → at-architect → at-frontend` 去写 `src/web/` 正是
   规格设计的层级协作，H3 的拒绝措辞说的「经上级协调」就是指它。分不清「绕行」与
   「协调」的闸只会制造噪音。
2. **判据在派发那一刻不存在。** 派发时不知道子代理接下来要写哪个文件——真要拦，得把
   意图当判据，而意图是提示词里的自然语言。
3. **M1a 的教训是「闸越多越容易互相拆台」**（H3 曾把 H2 的判据变成可伪造的）。这里
   缺的不是拦截，是**可见性**：没人算过这个数，所以没人发现它变了。

### 实现约束（给 M1b 的计划）

- 触达表**不是**安全边界，是**审计产物**。文档与命令输出里都不要把它说成「限制」——
  说成「当前配置下，各角色实际能写到哪些地方」。
- 算法要处理环（`A → B → A`）。花名册当前无环，但 `tests/roster-closure.test.mjs`
  没有禁止环。
- `/at-status` 的输出里，凡是「某角色的触达 ⊋ 它自己认领的路径」，要标出来并指明是经
  哪条派发边扩大的——**这才是这件事的全部价值所在。**
