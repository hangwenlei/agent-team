# 本机实测结论

> 环境：Windows 11 · Claude 桌面客户端 Code tab · 2026-09-15
> 本文只记录**在本机实际跑出来的观测**。文档推论一律不写进这里。
> 与 01/02/03 冲突时，以本文为准。

## 0. 环境事实（进程链实证）

| | 路径 | 版本 |
|---|---|---|
| 本会话真正的引擎 | `%APPDATA%\Claude\claude-code\2.1.270\claude.exe` | **2.1.270** |
| 桌面应用外壳 | `Program Files\WindowsApps\Claude_1.52386.6.0_x64__pzs8sxrjxfjjc` | 1.52386.6.0 |
| 终端版（独立安装，与桌面端无关） | `~/.local/bin/claude.exe` | 2.1.237，`autoUpdates:false` |

桌面客户端自带并自动更新它自己的 claude-code 引擎（同目录下有 2.1.266 / 2.1.270，两天一更）。
**因此 03 报告里「用户落后 35 个发行版」的判断作废**——那读的是终端版安装。

桌面应用启动引擎时的关键参数（进程命令行实测）：

    --setting-sources=user,project,local   ← 项目级与本地级 settings 会被读
    --permission-mode auto
    （没有 --agent 标志）

剩余的唯一版本闸门：workflow 撞用量上限时自动暂停等重置需 **2.1.271+**，当前 2.1.270
差一个版本，撞上限的 agent 会直接 fail 而非等待。

## 1. 嵌套派发深度 —— 通过，三层

方法：主会话 spawn L1（general-purpose），L1 spawn L2，L2 spawn L3，每层自报是否持有 `Agent` 工具。

    L1_HAS_AGENT_TOOL=Agent   L1_SPAWN_OUTCOME=SUCCESS
    L2_HAS_AGENT_TOOL=Agent   L2_SPAWN_OUTCOME=SUCCESS
    L3_VERBATIM=DEPTH3-REACHED

**结论**：主会话之下三层全通，`Agent` 工具每层都在。
`PM(主会话) → 产品经理 → 技术架构师 → 执行角色` 这个组织图在桌面端可搭，且还有余量。

---

## 2. `agent` 设置键在桌面端 —— 生效

方法：`_probe/.claude/settings.json` = `{"agent":"pm-probe"}`，
`_probe/.claude/agents/pm-probe.md` 定义身份令牌 `PMPROBE-ACTIVE`，
在桌面客户端新开会话、工作目录选 `_probe`，发一句 `ping`。

观测：回复开头即 `PMPROBE-ACTIVE`，且复述了 pm-probe 系统提示里的约束，
自报 `NAME = PM-PROBE`。

**结论**：`.claude/settings.json` 的 `agent` 键在 Claude 桌面客户端 Code tab **确实把主会话钉成具名 agent**。
插件根 `settings.json` 同样只支持 `agent` 与 `subagentStatusLine` 两个键（官方 plugins-reference），
所以**一个插件可以自带「主会话就是项目经理」这个身份**，用户无需手工配置。

旁证（2.1.270 引擎自身）：`claude --help` 原文 `--agent <agent>  Agent for the current session.
Overrides the 'agent' setting.`；二进制内 `mainThreadAgent` 出现 33 次、`subagentStatusLine` 9 次。

## 3. `tools: Agent(x)` 白名单在设置键激活的主线程下 —— 硬强制

这是官方文档明确留白的一条（文档只写了 `claude --agent` 那种情况）。

方法：pm-probe 的 frontmatter 写 `tools: Agent(probe-allowed), Read, Glob`，
同目录另有 `probe-allowed` 与 `probe-forbidden` 两个 agent 定义，让它两个都派。

    ALLOWED_SPAWN   = ALLOWED-OK
    FORBIDDEN_SPAWN = Agent type 'probe-forbidden' not found. Available agents: probe-allowed

**结论**：白名单被强制执行，非白名单类型在调度层直接被拒，未进入执行。

> ⚠️ **本节的结论正确但不完整，读到这里请一并看 §8。** 本节测的是**项目级** agent
> （`.claude/agents/` 下的 pm-probe），没有命名空间、也没有子代理。§8 用**插件级** agent
> 测出两件本节看不到的事：插件 agent 的注册名带 `agent-team:` 前缀（白名单写裸名会被
> 过滤成空集），以及白名单过滤的是**整个会话**可见的 agent 宇宙并**被子孙代理继承**
> ——它表达的不是「谁能派给谁」这条边。

三点细节，都对设计有用：

1. **实现方式是过滤注册表，不是拒绝调用**。错误措辞是 `not found` 而非 `not permitted`/`denied`——
   与官方 sub-agents 文档「the agent sees only the allowed types in its prompt」一致。
   **角色根本看不见它不该派的角色**，比事后否决干净。
2. **错误信息会枚举可用类型**（`Available agents: probe-allowed`）。白名单本身不是秘密，
   误派时错误消息自带「你能派谁」的提示，对调试有利。
3. **拒绝是逐调用独立判定的**。两个 spawn 在同一个 tool-use block 里并发发出，
   `probe-allowed` 正常返回，没有因同 block 内存在非法调用而连带失败。

⚠️ **边界**：这一条只对**主线程**成立。官方 sub-agents 文档明文：
「In a subagent definition, listing `Agent` in `tools` lets that subagent spawn subagents of its own
while the depth limit allows it, but **any type list inside the parentheses is ignored**.」
所以 `PM → 产品经理` 这条边能靠一行 frontmatter 硬管，
**`产品经理 → 其余角色` 这条边不能**，只能靠 PreToolUse hook 或角色提示词。

## 4. `initialPrompt` 对设置键激活的主线程 —— 不加载

观测：pm-probe 的 frontmatter 带了 `initialPrompt`，新会话发 `ping` 后它没有自动执行探针；
追问时它明确报告**上下文里根本没有那段文字**，且指出系统提示里「the probe described above」
的 “above” 指向的内容是空的。

**结论**：frontmatter 正文（系统提示）加载了，`initialPrompt` 没有。
阶段启动不能依赖它，必须由 slash command 触发——这与官方 `code-modernization` 插件的形态一致，
不构成损失。

## 5. 对设计的直接推论

| 机制 | 状态 | 用在哪 |
|---|---|---|
| 插件根 `settings.json` 的 `agent` 键 | ✅ 实测生效 | 把主会话钉成**项目经理**，装上插件即生效 |
| 主线程 `tools: Agent(...)` 白名单 | ✅ 实测硬强制 | 过滤整个会话可见的 agent 宇宙，被子孙代理继承；**不能**用来表达单条边的约束 |
| 三层嵌套 | ✅ 实测通过 | PM → 产品经理 → 架构师 → 执行角色 |
| subagent 层的 `Agent(...)` 白名单 | ❌ 官方明文忽略 | 第二层以下的派发约束要另想办法 |
| hook 派发门禁（含前缀归一化） | ✅ 实测通过 | 第二层以下的派发约束 |
| `initialPrompt` | ❌ 实测不加载 | 阶段启动改用 slash command |
| workflow 中途问人 | ❌ 官方明文不支持 | 人工审批只能是命令之间的缝 |
| subagent 里的 `AskUserQuestion`/`Workflow` | ❌ 官方明文剥离 | 问人和扇出只能在主会话 |

## 7. M0 · U3 派发门禁实测

**怎么测的**：插件经 junction 挂载为 `agent-team@skills-dir`；`claude plugin details agent-team`
确认 6 个 agent 与 1 个 PreToolUse hook 已注册（排除「插件没加载」这个假阴性来源）；
然后在 Claude 桌面客户端新开会话，工作目录选本仓库，逐轮派发观测。

**第一轮 · 裸名**

派发 `subagent_type = "at-architect"`（裸名，主线程）：

    Agent type 'at-architect' not found. Available agents: agent-team:at-architect, agent-team:at-outsider, agent-team:at-pm, agent-team:at-product, agent-team:at-worker-a, agent-team:at-worker-b, claude, claude-code-guide, code-simplifier:code-simplifier, Explore, general-purpose, Plan, statusline-setup

派发 `subagent_type = "at-outsider"`（裸名，主线程）：

    角色 __main__ 不得派发给 at-outsider。它可以派发的角色是：at-product、at-architect。如果这项工作确实需要 at-outsider，把它冒泡给上级，不要绕过花名册。

**第二轮 · 全限定名**

派发 `subagent_type = "agent-team:at-architect"`（主线程）：

    角色 __main__ 不得派发给 agent-team:at-architect。它可以派发的角色是：at-product、at-architect。如果这项工作确实需要 agent-team:at-architect，把它冒泡给上级，不要绕过花名册。

**第三轮 · 前缀归一化修复之后**

    架构师是否启动 = 是
    架构师派 worker-a = A-OK
    架构师派 outsider = 角色 at-architect 不得派发给 at-outsider。它可以派发的角色是：at-worker-a、at-worker-b。如果这项工作确实需要 at-outsider，把它冒泡给上级，不要绕过花名册。

**结论**：

- **U3 = 是**。拒绝理由是 `gate.mjs` 自写的中文原文，证明 Windows 下 hook 被调起、拿到输入、
  deny 输出被平台接受。规格 §6 五个 hook 的地基成立。
- 主线程 hook 输入**不带** `agent_type`（caller 为 `__main__`）。
- **hook 先于平台的名称解析生效**——第一轮裸名那次 hook 放行了，之后才撞上 not found。
- 插件 agent 的注册名带插件前缀（`agent-team:at-xxx`），裸名不解析。
- allow 与 deny 两条路径在**主线程**与 **subagent** 两层均已实证；拒绝消息里列出的可派发集合
  随调用者变化（主线程列 at-product/at-architect，架构师列 at-worker-a/at-worker-b），
  说明花名册按调用者查而非硬编码一份。

**遗留**：`agent_type` 的原始形态**未观测到**——因为拼拒绝理由之前 caller 已被归一化，
消息里永远显示裸名。归一化对裸名与全限定名两种形态等价，所以不影响正确性；但 `roster.json`
里 `__main__` 与 `at-pm` 双键能否合并，要等 Task 4 钉主会话身份时才能判定。

## 8. M0 · U1/U2/U4 主线程身份与白名单实测

**怎么测的**：插件经 `claude plugin enable agent-team@skills-dir` 启用（注意：不带
`@skills-dir` 会报 `Plugin "agent-team" not found in any editable settings scope`）；
每轮在桌面客户端新开会话；角色定义在会话启动时加载，所以改了 frontmatter 必须新开会话。

**第一轮 · U1，`settings.json` 为 `{"agent":"at-pm"}`（裸名）**

新开会话发 `ping`，回复：

    AT-PM pong ✅
    M0 占位版已就绪，待命中。

**第二轮 · U2，`at-pm.md` 白名单当时是裸名 `Agent(at-product, at-architect)`**

    派 agent-team:at-product  → Agent type 'agent-team:at-product' not found. Available agents: none
    派 agent-team:at-outsider → 角色 at-pm 不得派发给 at-outsider。它可以派发的角色是：at-product、at-architect。如果这项工作确实需要 at-outsider，把它冒泡给上级，不要绕过花名册。

**第三轮 · U2-B，白名单改成全限定名之后**

    派 agent-team:at-product  → AT-PRODUCT
                                PRODUCT-OK
    派 agent-team:at-outsider → 角色 at-pm 不得派发给 at-outsider。它可以派发的角色是：at-product、at-architect。如果这项工作确实需要 at-outsider，把它冒泡给上级，不要绕过花名册。

**第四轮 · U4 并发派发，白名单当时仍是两个角色**

派 `agent-team:at-architect`，要求它在一条消息里并发派两个 worker：

    是否一条消息内并发 = 是（at-architect 明确报告：同一个 function_calls 块里两个 invoke，不是先后两次消息）
    worker-a 返回 = Agent type 'agent-team:at-worker-a' not found. Available agents: agent-team:at-architect, agent-team:at-product
    worker-b 返回 = Agent type 'agent-team:at-worker-b' not found. Available agents: agent-team:at-architect, agent-team:at-product

**结论**：

- **U1 = 是。** `settings.json` 的 `agent` 键接受**裸名** `at-pm`。注意这与 `subagent_type`
  相反（后者必须全限定名）。
- **U2 = 是，白名单硬有效，但语义不是「PM 能派谁」。** 第二轮的 `Available agents: none`
  是因为白名单写裸名、注册名带前缀，交集为空。改全限定名后第三轮通过。
- **主线程白名单过滤的是整个会话的 agent 宇宙，且被所有子孙代理继承。** 第四轮是决定性
  证据：架构师看到的 `Available agents` 恰好等于 `at-pm` 的白名单，而架构师自己的
  frontmatter 是没有括号列表的光秃秃 `tools: Agent, Read, Glob`。**推论**：`at-pm` 的
  白名单必须列出团队全部角色，否则架构师够不到执行角色；层级约束只能由 hook 花名册承担。
- **U4 = 是。** subagent 能在同一个 `function_calls` 块里并发发出多个 Agent 调用。

⚠️ **诊断陷阱**：角色不在宇宙里时，**hook 先放行**（花名册认为该派发合法），之后平台才报
`not found`。错误信息指向被派的一方，真正的原因却在 `at-pm.md` 的 `tools:` 行里。
