# H6 返工预算

**日期** 2026-09-29 ｜ **口径** 分支 `m3r-rework-guard`（`8b38c62`…），版本 `1.0.0`；修的是全量审查（`docs/24-附录-全量审查报告.md`）
第 5、6 条，顺带第 32 条

## 0. 一句话结论

H6 要拦「把返工计数改小、把 history 删短」。它此前在两处算不准的时候直接放行：新旧任一侧的 JSON
解析不出来，以及 Edit 重放匹配不上。于是返工史不用 Bash 也能清零，两次 Write、或者在 CRLF 文件上一次
多行 Edit 就够。现在新内容必须是合法的 JSON 对象；Edit 只在门禁算得出与真实落盘逐字一致的新内容时才
放行，算不出就拒，让 PM 改用 Write。第一版修法在「算得出」这一侧与平台有落差，被复核抓到，第二版改成
只镜像平台一个字不改的那一层。

## 1. 问题

- **第 5 条：两次 Write 清零。** 「parse 不出来就放行」对新旧两侧同样生效。第一步把合法的 `state.json`
  写成垃圾，新的一侧读不出来，放行；第二步写一份清零的合法版本，旧的一侧读不出来，放行。落盘之后
  `validateState` 挑不出任何问题，ledger 也不报。
- **第 6 条：CRLF 上一次多行 Edit 清零。** 平台的 Edit 读文件时先把 CRLF 折成 LF；H6 按字节重放，多行
  `old_string` 在 CRLF 文件上匹配不上，算不出新内容，按「parse 不出来」放行，而平台照常落盘。Windows 上
  `core.autocrlf`、编辑器、PowerShell 都会写出 CRLF 的 `state.json`。
- **第 32 条（顺带）：带 UTF-8 BOM 的文件。** Windows PowerShell 5.1 的 `Out-File -Encoding utf8` 会写 BOM。
  `JSON.parse` 遇到 BOM 直接失败：H6 把这样的旧文件当成「坏文件」，任何清零都放行；runctx 则把整趟
  run 判成读不出来，拒掉所有非 PM 的写入。
- **ledger 那张网不存在。** `docs/11` §5.31 说写坏的 `state.json` 会被 ledger 报出来。实际上 run 读不出来时，
  ledger 只往 stderr 写一句，模型和用户都看不见。

## 2. 修法

### 2.1 新内容必须是合法的 JSON 对象

`decideRework` 只在**旧的**一侧读不出来时放行，也就是第一次写、或者文件本来就坏了。这是 PM 把坏文件修
回去的路。**新的**一侧必须是合法的 JSON 对象，否则拒，理由里点名要写一份合法的 JSON 对象。PM 锁不死：
它总写得出一份合法的 JSON。

### 2.2 Edit 只镜像平台「精确命中」那一层

平台 Edit 的实现（见 §5）有四层匹配。只有精确命中时，它把 `new_string` 原样写进去；其余几层会改写
`new_string`。`replayEdit` 只镜像精确命中这一层：

- 文件只折 CRLF，UTF-8 BOM 原样留着；
- `old_string` 逐字命中；`new_string` 原样放入；
- 多处命中又没带 `replace_all` 时返回 null（平台报错、不落盘）；
- 空 `old_string` 只在文件不在、或只有空白时写（与平台一致）；
- 其余情形都返回 null。门禁据此拒，理由点名 `old_string` 在文件里找不到，让它改用 Write。

放行的每一次 Edit，门禁算出的新内容与真实落盘的逐字相同（行尾除外，行尾不影响 JSON）。

### 2.3 归一化只有一份

`hooks/lib/text-norm.mjs` 的 `normalizeText` 负责剥开头的 BOM、把 CRLF 折成 LF，三处共用：

- 契约哈希（`normalizeContract` 委托给它，行为逐字不变）；
- runctx 读 `state.json` 与 `project.json`；
- H6 解析 `state.json`（`parseStateText`）。

### 2.4 ledger 回传写坏的 state.json

刚写的正是某个 run 的 `state.json`、而它读不出来时，ledger 回传一条 `【state.json】`，让 PM 用 Write 写回
一份合法的完整文件。它不回显文件内容：审查第 7 条提醒过，受信通道原样回显 `state.json` 的字段，会被
拿来做注入。H6 现在拒掉「合法 → 坏」的写入，所以走到这一步的，只可能是第一次就写坏、或者坏了之后
又写坏的情形。

### 2.5 提示

`agents/at-pm.md` 补了一句：改 `state.json` 用 Write 整份重写；H6 只在算得准新内容时才放行 Edit。

## 3. 复核

**第一轮**：四路并行，分别是找绕过、变异扫描、从二进制核对平台 Edit、设计与提示评审。找绕过的那一路
试了单步、多步、JSON 等价写法（重复键、`\u` 转义键、`-0`、`1e999`……）、Edit 的各种形状、别名路径，
**没有找到**能把返工计数改小的写法，也没有误拦 PM 的合法运维。但变异那一路的一位核验者把一条「等价
变异」推翻了，并把严重度从低提到高：

- 第一版 `replayEdit` 剥掉了 `new_string` 的 BOM。`new_string` 以 U+FEFF 开头、插在文件中间时，门禁算出
  合法 JSON，平台却原样写进去，文件就坏了。下一次 Write 走「旧的读不出来」那条修复路放行，两步清零
  照样做成。
- 同一结构的第二条：第一版做了弯引号互认，却没做平台随之而来的改写。`old_string` 用直引号去碰原文里的
  弯引号时，平台会把 `new_string` 的直引号也换成弯引号，JSON 同样被写坏。

两条都实测复现了。第二版改成只镜像平台一个字不改的那一层（§2.2），两条洗账路径的第一步各配一条
判据。变异验证：剥 BOM、加回弯引号那一层、去掉多处命中检查、不折文件的 CRLF、空 `old_string` 一律
新建，五刀各自打红。

**第二轮**：聚焦在「门禁算的与平台落盘的有没有落差」。

- **差分搜索**：按平台的真实实现写了一个落盘模拟器，由真实门禁子进程判定，跑了 6000 轮随机与构造
  输入，外加多步序列。**没有找到**「门禁放行、而平台落盘解析失败或计数变小」的输入。
- **变异**：五条发现都是实现正确、但判据没钉住，都补了判据。其中两条会重新打开两步清零：
  - 把 `split/join` 换成字符串版的 `replaceAll`：门禁会展开 new_string 里的 `$'`、`$&`、`$$`，平台用函数
    替换、按字面写入；
  - 把孤立的 `\r` 也折成 `\n`：平台只折成对的 CRLF。

  另外三条：`replace_all` 的正向接线，以及 ledger 新分支的两个条件。拒绝理由也补上了「出现不止一处」
  「用了弯引号或转义写法」两种原因，此前一律说成「找不到」。

  补记：写这份文档时，编辑脚本用 `String.prototype.replace(a, b)` 做锚串替换，而 `b` 里恰好有 `$'`、`$&`，
  被展开成替换模式，这一段一度被搅乱，已提交到功能分支之后才发现。这正是上面那条判据防的那类错误，
  换了个地方又犯了一次。之后的锚串替换一律用切片拼接。

## 4. 仍然开着的边界

- **修复路本身**：旧的一侧读不出来时放行任何合法对象。H6 挡住了「合法 → 坏」，所以用 Edit/Write 进
  不了这条路；用 Bash 写坏再用 Write 清零仍然可以。Bash 本来就不经门禁。
- **UTF-16 编码的 state.json**：平台按 UTF-16 读写它，门禁按 UTF-8 读，读出来是乱码，于是按「旧的读不
  出来」放行。要造出这样的文件得用 Bash，所以同上。
- **另起一个 run**：写新的 `current-run` 指向 r2、配一份新的 `state.json`，返工计数就从零开始。这是审查
  第 24 条那一族（全局只有一个 `current-run` 指针），不在 H6 的管辖之内。
  > **更新（2026-10-02，M4a，`docs/35`）**：正文那一半做了——`/agent-team:at` 第 1 节建 run 之前先看旧的那一趟收没收口，收不了口的先问用户
  > 续跑还是放弃；门禁那一半仍开着（`current-run` 的切换不拦），另起的那一趟返工计数照旧从零开始。
- **多拒的 Edit**：`old_string` 用了弯引号或 `\uXXXX` 转义写法、或者在文件里出现不止一处的 Edit，一律被拒，
  需要 PM 改用 Write。这是有意的取舍。

## 5. 平台事实（源码级，本机 CLI 2.1.283 的内嵌实现）

- **读文件**：先探测编码（开头是 FF FE 就按 UTF-16LE，否则 UTF-8），UTF-8 的 BOM 不剥，然后把 CRLF 折成 LF。
- **匹配**依次是四层：精确；弯引号（U+2018、U+2019、U+201C、U+201D）折成直引号后再找；`old_string` 里的
  `\uXXXX` 字面量解码后再找；非 ASCII 字符对着文件里的 `\uXXXX` 转义再找。
- **多处命中**且没带 `replace_all`：报错，不落盘。
- **空 `old_string`**：文件不在时新建；文件在且不是全空白时报错；全空白时整份覆盖。
- **`new_string`**：精确命中时原样写入；其余几层会经过弯引号风格保持与转义写法保持，被改写。
- **写回**：按原文件的编码与行尾写回，CRLF 文件整份转成 CRLF，BOM 保留。

## 6. 没量到的

- Write 落盘时会不会按旧文件的编码、行尾、BOM 改写 `content`，没有从二进制里逐字核到。门禁对 Write 按
  `content` 原样判，而行尾与开头的 BOM 都不影响解析结果，所以对判据没有影响。
- 没有起真实会话，平台行为都是源码级。
