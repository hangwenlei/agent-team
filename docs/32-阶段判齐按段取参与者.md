# 阶段判齐按段取参与者

**日期** 2026-09-30 ｜ **口径** 分支 `m3x-stage-done-roster`（`26fbfa1` 与其后的复核修订），版本 `1.6.0`；修的是全量审查（`docs/24-附录-全量审查报告.md`）
第 14 条。子进程与真实会话都在本机 CLI 2.1.283 上

## 0. 一句话结论

`roster` 记的是整趟叫到过谁，不分段。`at-ui` 是 S2 与 S5 的产者：它在 S2 进过 `roster`，S5 就把它当成 S5 的产者——S5 不派它时永远判不齐
（写 `trimmed` 也救不回），它的实现记录先落盘又让【阶段】提前宣布 S5 齐了，S5 正常收尾、PM 还没记账时架构师一返回就被 H5a 报成「停在
旧阶段」，产者交代也看不见「S5 没叫它、也没裁它」。现在 `state.json` 多一个 `stage_roles`（`{ 段: [角色] }`，`roster` 按段拆开），PM 在推进出
那一段的同一次 Write 里记；问「这一段」的消费方经 `participantsOf` 按段取，没有这个字段的旧 run 退回 `roster`。

## 1. 问题（审查原文与复现）

- `at-ui` 在 `roster` 里、S5 只有 `at-backend` 与 `at-frontend` 的实现记录：`expandProduces(S5, …)` 含 `05-impl/at-ui.md`，`isStageDone(S5)` 为假，
  【阶段】不发；加上 `trimmed {at-ui:'S5'}` 照样不发（`isStageDone` 不读 `trimmed`）。连带：`at-qa` 照正文拒测，`/agent-team:at-resume` 去补派，
  `/agent-team:at-status` 永远标 ✗。
- 修法设计前的调研（照审查原文复现、按消费方逐个量）多量出审查原文没有的三格。两格是反方向的，判早了：S5 还没记账、`at-ui` 的实现记录先落盘
  → 【阶段】立刻宣布 S5 齐了（P1）；S5 正常收尾、三份实现都在、PM 还没记账 → 架构师返回时 H5a 报「这正是停在旧阶段」（D4）。一格是审查原话
  那个错在 S2 返工上的镜像（`at-ui` 只在 S5 干过、S2 却去等它的两份，永远判不齐）。
- 产者交代那一半早有登记：`docs/11` §5.22 的 B 格（早段叫过、后段被裁，判据看不见），当时判为要单独设计。
- 审查说的「【阶段】在正路上仍然不发」是另一半——时序：`commands/at.md` 规定先派、核实，再记账，产者落盘那一刻 `roster` 里还没有它。
  M3k 那两条夹具（产者写入时 `roster` 已经含它）在正路上到不了。

## 2. 修法

### 2.1 `stage_roles`

- **形状**：`{ 段 id: [角色...] }`。口径与 `roster` **同一个「叫到」**、按段拆开：那一段真被叫起来干了活的每一个——含下级派出去的、含 PM 在 S5
  叫去分发的架构师、含被叫去做非产出活的角色（S3 被叫来澄清需求的 `at-product`），不论交没交。不含 PM 自己（`roster` 本来就不含）。
  不变量：各段的值合起来就是 `roster`。
- **怎么记**：`commands/at.md` 第 3 节第 3 条——产物齐了，**同一次 Write** 改 `stage`、`history`、`roster`、`stage_roles`（刚走完的那一段）、`trimmed`。
  理由：分两次写，推进的那一次落盘时刚走完那一段还没记它叫到了谁，产者交代会把那一段的产者当漏派报出来（这一条今天就成立：M3x 之前第 3 步推进、
  第 4 步再累加 `roster`，照字面分两次写在基线上同样假报）。返工轮只并入、不删。PM 自己做的那几段不写键。
- **旧 run**：没有 `stage_roles` 键的不加，照旧只累加 `roster`——门禁对它们按 `roster` 判，判定与 v1.5.0 相同；回传文案有两处新旧 run 一起改了：
  产者交代的护栏（§2.4）与【阶段】的推进说明（§2.5 末段）。
- **模板**：`templates/state.json` 加 `"stage_roles": {}`；`/agent-team:at` 建 run 那一段与规格 §4.4 的例外名单改成「除 `trimmed` 与 `stage_roles` 以外」。

### 2.2 谁按段、谁整趟

`hooks/lib/stages.mjs` 新增 `participantsOf(state, stageId)`，按段的消费方都按它取「那一段叫到了谁」。`isStageDone`（`gate.mjs` 两处调用）与
`/agent-team:at-status`、`/agent-team:at-resume` 第 2 节的展开，再交给 `stageRolesInRun` 与那一段的产者求交；产者交代 `decideCoverage` 不经
`stageRolesInRun`，报的是那一段的产者里既不在它给的人里、也不是 `trimmed` 任何一个键的那些（它给 `undefined` 时按空集算，与 `stageRolesInRun`
退回全部产者方向相反）；`at-qa` 的自查在正文里照同一口径拿 S5 的产者与 `stage_roles` 的 S5 求交。`participantsOf` 的取法：

- `state` 不是对象 → `undefined`；`stage_roles` 不是普通对象（缺失、`null`、数组、标量）→ 当它不在，退回 `roster`（数组时）；
- `stage_roles` 是对象：`stageId` 不是字符串、没有这个自有键、值不是数组 → `[]`；否则只留字符串。
- 「有字段、没这一段的键」是**空集，不退回 `roster`**：那就是「这一段还没记账」。退回 `roster` 等于把这一条要修的错原样请回来。
- `stageId` 先判类型再查键（`docs/27` §2.5）：`{"toString":1}` 拿去当属性键会抛。

| 消费方 | 口径 |
|---|---|
| `isStageDone`：ledger 的【阶段】、H5a 的「当前阶段齐了没」（`gate.mjs` 两处调用） | 当前段（`participantsOf(ctx.state, ctx.state?.stage)`） |
| 产者交代 `decideCoverage` | 走过的每一段各取各的；`trimmed` 照旧按键判 |
| `/agent-team:at-status`、`/agent-team:at-resume` 第 2 节、`at-qa` 的自查 | 那一段 |
| 账本比对 `compareArtifacts` 的 `drifted` / `missing` | **整趟**（有意） |
| H2 `decideReadiness` 的 `done` | **整趟**（有意） |
| `never_invoked` | 整趟（收口时按 `available_roles` 减 `roster`） |

**为什么那两处不按段**：当前段记账之前，按段取是空集。账本比对按段的话，S2/S5 的产物整体掉出 `drifted`/`missing` 的范围——S5 进行中时
`01-prd.md` 记账之后被改，不报。H2 按段的话，S5 记账之前只剩目标自己那一份：重派时它已在磁盘上，就判「齐了」、前置不查就放行。整趟口径
不会比这更松，但它多等的，只有别段叫到过的 S5 产者的实现记录（有界面的项目里是 S2 的 `at-ui`）；这些人不在 `roster` 里（比如 S2 裁掉了
`at-ui`），或者都已交了，两种口径都放行——「目标自己那份在就跳过前置」是 H2「齐了就跳过」的既有设计，不是按段引入的；首次派发时它那份
不在，两种口径都查前置。两处各有一条子进程判据（`tests/gate-deliverable.test.mjs` 的「M3x 整趟口径」与 `tests/gate-readiness.test.mjs`
的「readiness（M3x）」），H2 那条取的是 `at-ui` 在 S2 叫过的开局。

### 2.3 校验

`validateState`（`stage_roles` 在时；缺失不报）：不是对象；键不在阶段链里；值不是字符串数组；值里的角色不在 `roster` 里；`roster` 里的角色哪一段
都没记——后两条是双向不变量的两半。**不做**的两条：「必须是那一段的产者」（分发的架构师、被叫去做非产出活的角色都是如实的叫到，评审实跑过：
加上这一条，调研那一格没有任何合法写法）；「与 `trimmed` 同段冲突」（叫到之后又裁掉两样都是真事；拿 `trimmed` 的值当匹配键会撞上 §5.22 那条
「值是出处」，返工轮叫回首轮裁掉的角色也误报）。报文里的外部值一律 `quote`，`tests/trusted-echo.test.mjs` 补了四个入口。

### 2.4 产者交代的文案

带 `stage_roles` 的 run 上，被点名的角色可能就在 `roster` 里（`at-ui` 在 S2 叫过、S5 没记），旧文案的头一句「这一趟既没叫到它们」是假话；它也
可能在 S5 真干过活、只是 `stage_roles` 漏记，那时「把它派出去」会让它重做一遍。所以 `decideCoverage` 回一个 `perStage`，文案据此：头一句改说
`state.json` 没记着它在那一段被叫到；多第三条出路「补记 `stage_roles`」（收件人改不了 `state.json` 时说清补记是 PM 的动作）；「不要为了让提示
消失就写进 `roster`」扩到 `stage_roles`。旧 run 的产者交代文案除下面这一处订正外不变。

护栏原来许诺「只写名字不派人，下一次账本比对会把它报成 missing」——那是假的，而且从 M3a 写下那天起就不成立：
`compareArtifacts` 只比对记过账的产物，没记账的名字直接跳过。复核时实跑过：只把名字写进 `roster` 或并进 `stage_roles`，之后几次
派发返回都没有任何 missing。现在照实说：门禁不会再报它，还看得见它的只剩 `at-qa` 开工前对 S5 实现记录的自查与
`/agent-team:at-status` 的 ✗。补记 `stage_roles` 与只写名字在 `state.json` 里一模一样，分界只在「它在那一段真被叫到过没有」。

### 2.5 正文

`commands/at.md`（建 run 的例外名单、第 3 节记账并成同一次、「叫到」的口径管 `stage_roles`、返工轮并入、旧 run 不加、产者交代那句按段说）；
`agents/at-qa.md`（自查读 `stage_roles` 的 S5）；`commands/at-status.md`、`commands/at-resume.md` 第 2 节（展开口径经 `participantsOf`；at-status 标「本段
未记账」；at-resume 的空集「只说明这一段还没记账」、「齐了」那一支指回同一次 Write）；`agents/at-architect.md`（「不要指望后面有判据兜底」的理由换成
「它只在推进出 S5 之后才报，报出来时你那句理由不在里面」）；规格 §4 母表与 §4.4；`stages.README.md` 的消费方表（补上漏了的 H2、产者交代、`at-qa`
三行）。关键句由 `tests/stage-roles-prose.test.mjs` 按条目或段落定位钉着。

复核补的几处：`/agent-team:at-resume` 的「产物齐了」先 `Read` `${CLAUDE_PLUGIN_ROOT}/commands/at.md` 的「逐段推进」再记账，并写出两个字段的
方向（`stage_roles` 是 `{ 段: [角色] }`，`trimmed` 是 `{ 角色: 段 }`）——续跑时主会话手上没有 `/agent-team:at` 的正文，引用某一节处都带上路径；
空集那一支补了两句：`stage` 还等于这一段就是还没推进出去（`history` 里有它只说明进过）、run 目录下的产物用 `.agent-team/runs/<run_id>/` 开头的
路径去 Glob；S2 的空集那一支不把 `at-ui` 的两份写成判齐的必要条件（只在这一趟要用 `at-ui` 时才算缺，不用就在记账那次 Write 里写进 `trimmed`）；
`/agent-team:at-status` 只对展开出空集、还没记账的段标「本段未记账」（PM 自己做的段从来不写键，产物固定的段与参与者无关）；
【阶段】的推进说明写明用同一次 Write 记账（`stage_roles` 只对有它的 run 说，旧 run 的 PM 不该因此加它）。

## 3. 复核

**设计评审**（判定语义、判据与正文两个镜头，20 条反对意见各配一位反驳者）推翻了初稿的三处：

- 初稿把 `stage_roles` 定成「叫到、交了产物」。评审实跑出它与 `roster` 的「叫到」口径、与双向校验互相矛盾：S5 派了没交的 `at-frontend`、在 S3
  被叫去调研而 S5 又裁掉了的 `at-ios`，任何如实的写法都会被报（评审走的是首轮形状；真跑时首轮 S3 会被 H2 按 S5 的前置拒，返工轮回到 S3 时才走得到）。
  改成与 `roster` 同一个「叫到」口径；「交没交」是 `isStageDone` 的事。
- 初稿的两条校验——「必须是那一段的产者」「与 `trimmed` 同段冲突」——拿掉（理由在 §2.3）。
- 初稿 §4 把「S2 返工镜像」列在纯函数判据里，没写期望值；§0 又把它算作本条修好的一格。评审指出这一格只在返工轮到得了，断言它「齐」，等于把
  第 15 条的「一回退就判齐」钉成正确行为。反驳者核实后收窄：真正会钉住第 15 条的，是在 hook 层断言「回退就发【阶段】」；纯函数层只钉期望集合
  （S2 不再等 `at-ui` 的两份）则不会。于是这条判据留在纯函数层，注释写明它只钉期望集合，返工轮登记归第 15 条（§4），不加 hook 层的断言。

另外补了评审点名的整趟口径判据（把四处 `roster` 实参全换成按段的，原有判据一条不红）、`participantsOf` 先判类型再查键、调用点判据的判别式，
以及正文清单（产者交代文案、`at-architect`、规格、模板例外名单）。
