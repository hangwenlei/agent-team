# state.json 里重复的键

> 2026-10-11，分支 `r32-state-dup-keys`。第三十二轮（从开放边界索引挑）：`docs/55` §4「JSON 里重复的键：后一个盖掉前一个，不报（解析之后就分不出了）」。

## 0. 一句话结论

- 项目经理写 `state.json` 时，同一个对象里一个键写了不止一次（任何一层：顶层的 `stage`、`trimmed` 里的角色名……），账本在【state.json】那几条里各报一行：「键 X 写了
  不止一次（在 Y 里）：JSON 只认最后一个，前面写的等于没写——留下要的那一个、删掉别的」。只报不拦，跟认不出的键同一档（`docs/55`）。
- 安全审查与复核之后（§8）：三道上限（原文超过一百万字符不扫、嵌套超过 32 层只数括号不认键、最多报 20 条，末尾一行说还有几个）；转义照 `JSON.parse` 解全；数组里的对象
  路径带上第几条；措辞改成「门禁读到的是最后写的那个值……删掉前面几个不改变门禁读到的值，要改值就改最后那一个」；账本里挪到交付快照、契约基线两次写盘之后。

## 1. 问题

- `JSON.parse` 碰上重复的键只留最后一个，前一个悄悄丢掉；门禁读的是解析之后的对象，分不出原文里写过两次。模型手写一大段 JSON 时，把 `trimmed` 或 `stage_roles` 写两遍、
  后一遍漏了几项，门禁按后一遍判，前一遍里的决定就没了，一声不吭。

## 2. 修法

- `hooks/lib/state.mjs` 的 `duplicateKeys(text)`：扫原文，不解析值——跟踪字符串（含转义）、对象与数组的嵌套，对象里冒号之前的那个字符串是键；同一个对象里第二次见到的
  键报一次（`{ path, key }`，`path` 是外层各级键名；数组里的对象各算各的，数组里重复的值不算）。`duplicateKeyLines` 拼成账本那一行（键名与路径是磁盘上的值，`quote` 引）。
- `hooks/gate.mjs` 的账本：写 `state.json` 时读原文，把那几行并进 `validateState` 的问题清单（进【state.json】那一块）。复核之后排在交付快照、契约基线两次写盘
  之后。
- 安全审查与复核之后：`DUP_LIMITS`（`chars`、`depth`、`report`）；转义表（`b f n r t " / \` 与 `\uXXXX`）；数组帧数下标、子对象的路径带上它；账本那一行的措辞。

## 3. 判据与变异

- `tests/state-dup-keys.test.mjs`：顶层、嵌套对象里重复的键都认、路径带上；数组里的对象、字符串值里写着键名、转义的引号与反斜杠、数组里重复的值、两个键值相同，都不误认；
  写了三次只报一次；读不出的给空。账本：项目经理写的 `state.json` 里 `stage` 写了两次，【state.json】里报它；没有重复的不说。复核之后又加了：三道上限（对象深嵌套
  不慢、超过深度不认键、条数封顶与末尾那一行、原文太长不扫）；`\u` 写法与原字是同一个键、`\n \r \b \f` 不是字母；数组里的对象带下标、三个元素的数组；账本里嵌套的带路径、
  中文键、与认不出的键同一块；`tests/trusted-echo.test.mjs` 补了「重复的键与外层路径是载荷」那一格。
- 变异（备份在仓库外，每一刀改完逐字节还原）：账本不接、每次重复都报、不带路径、不认转义、数组当对象（补了「数组里重复的值」那一格才红）、逗号之后不认键、值里的字符串当键
  （补了「两个键值相同」那一格才红）——每一刀都有判据红。复核之后又加了：三道上限各去掉、跳过的层里照认键（深层那段换成三个键才红）、路径不经 `quote`（trusted-echo
  也红）、行里不带路径、数组父层塞键名、数组不数下标、只把数组的 `obj` 置真、不认 `\u`、`\u` 只跳两格、转义表只认 n t、按 latin1 读、只在没有别的问题时并进、账本
  不接、措辞回旧——每一刀都有判据红。

## 4. 仍然开着的边界

- **只报不拦**：项目经理不改，后一个照样盖掉前一个（与 `docs/55` §4 同一档）。
- **被 H6 拒掉的那一次看不到这条提示**：这次写入没落盘、账本不跑（与 `docs/55` §4 同一档）。
- **只看 `state.json`**：`project.json`、`reach.json` 里的重复键不报。
- **扫的是原文**：不是合法 JSON 的原文给已经扫出的部分（那种写入门禁别处先报读不出）。
- **三道上限**：原文超过一百万字符整份不扫；嵌套超过 32 层的那几层不认键；最多列 20 条（末尾一行说还有几个）。正常的 `state.json` 碰不到。
- **新一趟的第一份 `state.json`**：写的那一刻 `current-run` 还没指过去，账本不把它当这一趟的 `state.json`，不报（与 `validateState` 同一档）。

## 5. 没量到的

- 真实会话里模型写出重复的键、收到这一行之后改不改。

## 6. 归属

## 8. 复核与修订

第一版推上分支之后，后台的安全审查报了资源耗尽：每进一层对象复制一份路径，深层嵌套是平方级的时间与内存；报出的条数、原文长度都没有上限。对抗复核随后实测：
嵌套四万层、约 240KB 的 `state.json` 让账本子进程内存耗尽崩掉（try/catch 接不住），连带排在它后面的交付快照与契约基线这一次都不写。两边的问题都在这一轮改了：

- **资源耗尽**（安全审查、复核中 1）→ 三道上限；扫描挪到两次写盘之后；计时判据改用对象嵌套（数组本来就不慢，原来那一条打不红平方级的毛病）。
- **复核中 2：新拼进回传的键名与路径，trusted-echo 的入口清单没补**（把路径改成不经 `quote`，全绿）→ 补了那一格。
- **低**：转义只认 `\n \t \u`，`\r \b \f` 解成字母会误报、把键名报错（对拍二十万份随机 JSON 有一千六百多份不一致）→ 补全转义表、配三格判据；数组里的对象有重复
  只报「在 history 里」→ 带上第几条；「留下要的那一个」可能把项目经理引去改写入前就有的 history 条目（H6 会拒）→ 改成「门禁读到的是最后写的那个值，删掉前面几个
  不改变读到的值」；几刀打不红的（行里不带路径、数组父层塞键名、只在没有别的问题时并进、按 latin1 读、只把数组的 `obj` 置真）→ 各补一格；§4 补登上限与新一趟
  第一份 `state.json` 不报。
