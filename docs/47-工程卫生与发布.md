### 1.3 第 45 条：更新记录与 tag

> **订正（M4m，2026-10-06，`docs/48`）**：「历史各版也交给它补，不手工推」做不到，见 §0 的订正。现在的口径（`scripts/tag-release.mjs` 的头注释、HANDOFF 的
> 发布纪律）：平常要打的只有当前这一版，它的提交就是 `main` 的最新提交，GITHUB_TOKEN 推得了；要补的旧版所在提交里带着与 `main` 现在不同的工作流文件时，
> 作业红，由有 `workflow` 权限的人在本地跑 `node scripts/tag-release.mjs --push`（不带 `--push` 只列出要打什么，本地不建 tag、远端不动）。
> 本地那一次推了 22 个 tag，GitHub 没有为它们生成推送事件（一次推超过三个 tag 就不生成），旧提交上没有起任何 CI——§7 第一条担心的事这一次没发生，
> 靠的是数量过了三个，不是设计。M4l 起工作流的 push 只认分支，以后补推这之后的提交上的 tag 不再触发 CI。

- `CHANGELOG.md`：开头一段说明（一版一行、最新的在最上面、版本号的挪法、每一版都有 tag），下面每一版一行「- x.y.z：这一版改了什么」。2.9.0 及更早的 48 版照它
  第一次合进 `main`（`main` 的 first-parent 历史上 `plugin.json` 第一次是那个版本的提交）的那一次提交的标题整理，去掉提交类别前缀与末尾的版本号注记。
- 版本检查（`scripts/lib/version-bump.mjs` 的 `latestChangelogVersion` 与 `judgeVersionBump` 的 `changelog`）：版本号往前挪时，事件之后那个提交的 `CHANGELOG.md`
  最上面那一行（第一个以「- 」开头的行）要是「- 这一版：…」（冒号后面有话）——没有这个文件、没写这一版、写在下面、最上面那一行写坏了，都不通过。CLI 总是
  传它；纯函数不传就不核（只测版本号那几条的判据）。
- tag：`scripts/tag-release.mjs`（认法在 `scripts/lib/release.mjs`）沿 HEAD 的 first-parent 历史，每一版打在 `plugin.json` 第一次是它的提交上（合进来的一版打在合并
  提交上），远端缺的都补上、一次推完；远端已有、指向别处的不挪，报出来、退出码 1。`ci.yml` 的 `tag` 作业在推 `main`、本工作流的判据（三个系统）与版本检查都过了
  之后跑它（min-node 是另一份工作流，等不了它）；只有这个作业有写权限，工作流默认只读。
- 历史各版也交给它补，不手工推：GITHUB_TOKEN 推的 tag 不触发任何工作流；手工推旧提交的 tag，GitHub 按那个提交里还没有分支过滤的 `on: push` 起 CI。
  `ci.yml`、`min-node.yml` 的 `push` 改成只认分支（`branches: ['**']`），之后手工推的 tag 也不触发它们。
- README 两半：更新那一段写明每一版改了什么在 `CHANGELOG.md`、每一版都有 tag；开发者那一节的版本纪律补一句每挪一次在最上面加一行、推 `main` 之后 CI 打 tag。

> **收口（M4m，2026-10-06，`docs/48`）**：合进 `main` 之后 ci 三个系统与 min-node 全绿；`tag` 作业第一次跑红——27 版打上、22 版被拒（§0 的订正）。

## 4. 不做的与仍然开着的

> **订正（M4m，2026-10-06，`docs/48`）**：漏了一条仍然开着的——**某一版的 tag 没打上、之后又改过工作流文件**：CI 补不上它（GITHUB_TOKEN 推不了），
> `tag` 作业每次推 `main` 都红，直到有人在本地补推。

- **at-outsider 挪出载荷：不做。** 它是花名册不变量（「任何角色都不该能派它」）的对照物：`roster.json` 里有它的键，`hooks/lib/project.mjs`、`writepath.mjs` 按它判，
  十来份判据拿它当被拒的那一方。挪出 `agents/`，要么花名册里留一个指向不存在的角色的键，要么判据改用测试期另搭的花名册——两样都让判据测的不再是发出去的那一份。
  用户这边的代价是 agent 列表里多一个只有 `Read`、描述写着「测试替身，不是真角色」、谁都派不到的条目。**什么会让答案改变**：有用户因为它困惑；或者做「载荷挪进
  子目录」时一起挪（那时测试本来就要指向另一份花名册）。
- **载荷挪进子目录（L）**：照旧暂缓（`docs/39` §2.4）。
- **推 `main` 时 CI 红了**：`main` 已经推上去、用户已经能更新，那一版的 tag 等下一次全绿时补上；在那之前 README 说的「每一版都有 tag」对它不成立。
- **主版本号是进位计数**（第 45 条第四点）：照旧。版本号的挪法是机械的（`claude plugin update` 只比字符串），中间一位满了进到第一位，不表示不兼容；
  `CHANGELOG.md` 开头写明了挪法。
- **第 33 条修法里「underAny 并进 underDir」**：没做。两处的目录边界各自被判据钉着（WP1 与路径归一化的判据），合并是重构、不改行为。
- **历史各版的更新记录照提交标题整理**：早期几版的标题写的是过程（「九次还是十次」这类），不是给用户看的结论；不回头改写。
- **之前签出的 CRLF 副本**：在 git 重新签出之前还是 CRLF；锚串替换照旧断言命中数、写完扫控制字节。

## 7. 复核与修订

> **订正（M4m，2026-10-06，`docs/48`）**：第一条的改法（「`tag` 作业自己补齐缺的，不手工推」）合并之后被证伪了一半：GITHUB_TOKEN 补不了提交里带着与
> `main` 不同的工作流文件的那 22 版，最后是在本地补推的（§0、§1.3 的订正）。复核说的风险（手工推旧提交的 tag 会按旧工作流起 CI）本身是对的；这一次没起，是因为
> 一次推了 22 个、超过了 GitHub 生成事件的上限。

提交 `5465f48` 之后做了一轮对抗复核（只读，在仓库外的副本里跑判据、变异，并在临时仓库里实测）：没有高；一条中、五条低，都修了：

- **中：手工补推历史 tag 会按旧工作流起 CI**——GitHub 用事件对应的那个提交里的工作流，旧提交的 `on: push` 没有分支过滤，一次推不超过三个 tag 就会产生事件。
  改成 `tag` 作业自己补齐缺的（GITHUB_TOKEN 推，不产生任何事件），不手工推（§1.3）。
- **低：tag 作业只打当前版本、等不了 min-node、判据只核字样**——某一次红了那一版就永远没有 tag；注释说「全部判据都过了」不确切；把「已经有了就不动」改反、
  改成打在上一个提交上，判据照绿。打 tag 挪进 `scripts/tag-release.mjs`，补齐缺的，在临时仓库加裸远端里测；注释改准。
- **低：版本检查的两处**——只改了版本号时改动清单被拿空，在核 `CHANGELOG.md` 之前就放行了；写坏的那一行，理由不说读到的是什么。改成版本号往前挪就先核、理由引出
  那一行。
- **低：`.gitattributes` 的口径**——已有的副本 `pull` 之后没改动的文件仍是 CRLF，「装下来的副本是 LF」只对新安装成立；还有几处旧说法没跟上。措辞改准，补列进 §6。
- **低：`scratchpad/` 进了忽略清单之后看不见了**——`node --test` 照样收它下面的判据。加了「仓库根下没有 `scratchpad/`」的判据。
- **低：该列没列的**——第 45 条第四点、第 33 条修法里合并两个前缀函数，登记进 §4；`CHANGELOG.md` 里给用户看的两行带 `docs/` 编号，去掉了。

复核「查过、没问题」的几条：`tag` 作业的 `needs` 等全部矩阵、作业级写权限盖得住仓库默认的只读、并发推 `main` 不会打错版本；`branches: ['**']` 匹配带斜杠的分支、
PR 不受影响；48 版与 `main` 的 first-parent 历史逐版一致（含八个直接提交）；PR 事件读 head 那一侧的 `CHANGELOG.md` 是对的；CRLF 的副本跑全套照绿；语法检查覆盖的
脚本、白名单那一处的写法；第 33 条那几条判据的变异全部打红（macOS 上 `normalize` 先在路径归一化里抛，同样落在最外层 catch）；at-outsider 不挪的理由站得住。
