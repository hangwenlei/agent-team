# 门禁判不出来时说给谁听

**日期** 2026-09-30 ｜ **口径** 分支 `m3v-fail-open-visible`（`bc8e58c`、`72a7e2a`、`e3c0c80` 与其后的修订），版本 `1.4.0`；修的是全量审查
（`docs/24-附录-全量审查报告.md`）第 12 条。平台行为是本机 CLI 2.1.283 上的实测（`-p` 会话加子进程），附会话号

## 0. 一句话结论

门禁判不出来而放行时（读不到运行状态、`state.stage` 不在阶段链里、输入读不出来、检查项中途出错），此前只往 stderr 写
一行——模型看不到，默认界面上用户也看不到；输入读不出来那一支连这一行都没有。现在：项目经理自己发起的派发与写入上，
`PostToolUse` 的受信回传里多一段【门禁】，说这一次哪道没做、为什么、按原因怎么修，并给用户一行固定的提示；门禁自检的
理由末尾按运行状态追加一句「另外，……」，丢了指针的 `/agent-team:at-resume` 不再对用户说「没有 run」。`PreToolUse` 上
不发受信块，`SubagentStop` 上什么都不发——两处都是平台行为逼出来的，由一个纯函数在结构上守着。

## 1. 平台上能用的通道（实测）

- **`PreToolUse` / `PostToolUse`**：exit 0 加 stdout 上恰好一份 JSON。`hookSpecificOutput.additionalContext` 进**发起这次调用
  的那个上下文**（子代理的调用进子代理），排在工具结果之后；顶层 `systemMessage` 只画给用户，只有主线程的事件冒到主界面。
  stream-json 里它是一条 `type: system`、`subtype: informational` 的「`<事件>:<工具> says: …`」，不带插件名；转录里是一条
  `hook_system_message` 附件（会话 `aa7da696`、`e13dc844`）。
- **不能带的字段**：放行一侧的 JSON 带 `permissionDecision: allow` 会绕过权限确认，顶层 `continue: false` 会停整轮，
  `hookEventName` 与事件不符会让整份输出作废，stdout 上两份 JSON 会让拒绝失效、回传全丢。
- **`PreToolUse` 上几道 hook 的 context 被并成一段、不标来源、顺序不定**（会话 `ccf48d1e`：两次派发里本插件与探针插件的
  context 在一个附件里，顺序相反）。本插件的受信块排在前面时，后面紧跟的别家文字读起来就是它的续行。`PostToolUse` 上各家
  各成一条（会话 `df24bc74`）。
- **H1 拒掉的派发不跑 `PostToolUse:Agent`**（会话 `df24bc74`，探针插件的日志里那次派发只有 `PreToolUse`）。
- **`SubagentStop` 上 exit 0 带 `additionalContext` 等于拦截**：子代理续跑、计入 `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`、回报被
  换掉。exit 0 时这个事件没有任何到父级或用户的通道，stderr 只进停下来的那个子代理自己的转录。
- **时机**：默认的后台派发下，`PreToolUse:Agent` 与 `PostToolUse:Agent` 的 context 都紧跟在「Async agent launched」之后几秒到
  PM；前台派发时 `PostToolUse` 在子代理跑完之后才到。

## 2. 修法

### 2.1 说给谁听、在哪说

| 出口 | 现在 |
|---|---|
| H5a（`PostToolUse:Agent`）读不到运行状态，派发的是 PM 或主线程 | 【门禁】「这次派发没有做前置就绪校验，交付物核验也不会做」+ 按原因的修法 + 给用户一行 |
| H5a 没有 run，PM 或主线程派一个它派得动的团队角色 | 【门禁】说明这是有意的放行，给条件分支，不下祈使句；给用户一行 |
| H5a `state.stage` 不在阶段链里（任何收件人） | 【门禁】按 `history` 的形状与末条给修法；收件人改不了 `state.json` 时冒泡；PM 收件时给用户一行 |
| ledger（`PostToolUse:Write`）读不到运行状态，PM 写 `.agent-team/runs/` 下的非控制文件 | 【门禁】「这次写入没有回传」+ 修法 + 哈希只从回传里拿 + 给用户一行 |
| 门禁自检（H3 对 `gate-check` 的拒绝），调用者是 PM、写在门禁认的项目根下 | 理由末尾追加「另外，……」：读不到运行状态按原因、按命令给修法；`state.stage` 不在链里给那几支修法 |
| 输入读不出来（stdin 不是对象、缺 `tool_name`），fail open 的检查项 | stderr 一行；`Pre` / `Post` 上给用户一行，不进模型 |
| 检查项中途出错（最外层 catch），fail open 的检查项 | deliverable、ledger：【门禁】（非 PM 收件加冒泡句）+ PM 收件时给用户一行；readiness：只给用户一行；stop-gate：只 stderr |
| H2 的 unreadable / no-run、H3 / H4 对 PM 的放行、H5b、协调者发起的派发、no-run 下的写入 | 照旧只 stderr |

**为什么告警从 H2 挪到 H5a**：H2 在 `PreToolUse` 上，受信块在那里会和别家插件的文字并成一段；H1 拒掉的派发照样跑 H2，
告警会说一次根本没发生的派发。H5a 在 `PostToolUse` 上、只在派发真的发生之后跑，默认后台派发下与 H2 同时到。

**为什么协调者发起的派发不说**：读不到运行状态时，它派出去的角色每一次写入都被 H3 以同一个原因拒掉，拒绝理由会冒泡
上去；再发一段只是多一个转述环节。

**为什么 ledger 只说 `runs/` 下的非控制文件**：契约与产物都在那下面，「修好之后原样重写一次拿回传」只对它们是真话；
`.agent-team/` 下别的文件本来就没有回传。控制文件是 PM 在建 run、修 run——第一趟建 run 写 `runs/<id>/state.json` 那一刻
指针还没写、门禁判丢指针，在那里说一句就是在正路上刷屏。偏离 `/agent-team:at` 第 1 节的顺序、在从没建过 run 的项目里直接
写契约：`PreToolUse` 那一帧没有 run，`Write` 顺带建出 `runs/<id>/`，`PostToolUse` 那一帧判丢指针——契约的哈希确实丢了，
这一格出声，修法里「一趟都没有 `state.json` 就照第 1 节先写」对的正是它。

**no-run 那一格**：只在目标是调用者派得动的团队角色时说（`decideDelegation` 放行——与 H1 同一个函数、同一份花名册）。
团队在干活而门禁看不见 run，要么是用户要的临时派发，要么门禁看的项目根不是 PM 以为的那个（它从会话当前目录往上找
`.agent-team`），这一句把两种都点出来。

### 2.2 按原因给修法（`hooks/lib/runctx.mjs` 的 `cause`、`hooks/lib/fail-open.mjs` 的 `runContextFix`）

读不到运行状态的每个出口带一个原因短码，修法按它选，H5a、ledger、自检三处共用一份：

- `pointer`（`current-run` 不在而 `runs/` 下有 run、读不出、空、不是合法 id、指向的目录不存在）：Glob
  `.agent-team/runs/*/state.json`（只 Glob `runs/*` 列不出目录）；一趟就写回；不止一趟时指针原本指向最后建的那一趟，读各自的
  `state.json` 核实，拿不准就问用户；一趟都没有 `state.json` 就照 `/agent-team:at` 第 1 节补。
- `state`：Write 写回一份合法的完整 `.agent-team/runs/<current-run 里的 run id>/state.json`，能从原文认出来的 `history`、`rework`、
  `artifacts` 照原样保留。
- `project`：Write 写回一份合法的完整 `project.json`。
- `runs`：告诉用户，由用户处理，不要自己删改。
- `plugin`（插件的 `stages.json` 读不出来或形状不对，以及最外层兜底）：改 `.agent-team` 修不好——停下，告诉用户重装或更新
  插件，不改插件目录下的文件。

命令开头（自检的追加句）按命令开头：丢指针、`state.json` 坏了、`state.stage` 不在链里时，第一句是「这条命令是 /agent-team:at
的话：不要写原来那趟 run 目录下的任何文件，照第 1 节另起一个 run id 建新 run；这一轮回复用户时（不论停在哪一步）把原来那趟
run 的问题与它的 run id 告诉用户」，修法跟在「这条命令是 /agent-team:at-resume 的话：」后面；`/agent-team:at-resume` 里「一趟都
没有 `state.json`」不自己补建，照实告诉用户 `runs/` 下有什么；`/agent-team:at-init` 不在那里修 run。`project.json` 坏了照样先修
（写路径隔离靠它；at-init 就是修它的）；`runs` 读不出来、插件坏了本来就建不了 run。顺序是真实会话逼出来的（§3 第二轮）。

`state.json` 从原文认不出 `contract_sha` 时写 `PENDING`，写回之后原样重写一次契约、从回传里拿，并告诉用户 `state.json` 是重建的；
PM 写了别的角色的产物时，修好之后叫产者重交，产者不在 PM 的派发名单上就经派得到它的那一层转派。

修法不拼 runctx 的 `reason` 原文：它带绝对路径，而且修法本来就该按原因选，不该让一句写死的「修 current-run」和括号里的
「读取 project.json 失败」互相打架。

### 2.3 unknown-stage 的几支

H6 不许删 `history`、不许让任何阶段的出现次数变少，所以修法看 `history`：

- `history` 不是由对象组成的数组：H6 的计数不认它，「会拒」「出现过就记返工」都不成立——不给具体改法，照写 `state.json` 时的
  回传改，返工计数只许增，拿不准就停下告诉用户。（照「写一个只含当前阶段的数组」做，会撞上 `rework` 与 `history` 对不上。）
- 末条是链里的阶段：把 `state.stage` 改回它，`history` 不动；更早还有坏阶段的话，说明写 `state.json` 时的回传仍会报它，是已知残留。
- 末条也不在链里、或者 `history` 是空的：不要改、也不要删已有条目；追加一条真实的当前阶段并把 `stage` 设成它；这个阶段在
  `history` 里出现过的话追加会记一次返工——停下告诉用户；修完后那条坏阶段仍会被报，是已知残留。

`state.stage` 缺失或不是字符串时说「缺失或不是字符串」，不写 `quote(undefined)`。收件人改不了 `state.json` 时（S5 的
at-architect）照账本比对的先例冒泡，修法照带；stderr 的痕不复用 `misroutedNotice`——那一句断言「判据没有放行任何东西」，
而这一格恰恰放行了。后台派发下 H5a 几秒就到，PM 当时改好，这一趟的 H5b 就照常核验（会话 `e13dc844` 实测）。

### 2.4 输出只有一个出口

`hooks/lib/fail-open.mjs` 的纯函数 `hookOutput(event, { contexts, systemMessage })` 定输出的形状：`PostToolUse` 上几段并成一份
受信块、`systemMessage` 在顶层；`PreToolUse` 上只许 `systemMessage`，有 contexts 就丢掉并往 stderr 报 BUG；`SubagentStop` 与其它
事件上 stdout 永远为空。永不产出 `permissionDecision`、`decision`、`continue`。gate.mjs 的 `emitHookJson` 只做 I/O，写完就退出
（上一版的 `emitLedger` 不退出，靠每个调用点自己紧跟 exit）。拒绝只经 `denyAndExit`。最外层 catch 发现这次进程已经写出结果
（拒绝或回传）时只留痕、不写第二份，照那个结果的退出码退出——`SubagentStop` 的拒绝是 exit 2，不能被改判成放行。这两格只有
注入走得到。

`systemMessage` 只许固定文字，用 README 的门禁名，不拼 `reason`、`stage` 或任何磁盘值：它画在用户的界面上，是 `docs/27`
§1 那三条通道之外的第四条。

### 2.5 boot.mjs 的首行

fail open 的检查项起不来时（Node 太旧、代码加载失败），平台在界面上只显示「hook error」加 stderr 的第一个非空行
（`docs/28`）。那一行此前是「门禁代码加载失败（检查项 …）：」或「门禁需要 Node … 或更新」，「本次放行」排在第二行、
加载失败时还排在整段栈之后。现在放行那一句排第一，原因与补救都在里面。fail closed 的首行不变。

### 2.6 正文

- `agents/at-pm.md`：受信回传的例外里点名【门禁】，照它给的修法做，收到它说明门禁在跑、不是没在跑；门禁自检第 1 支
  补「另外，」那一句的读法（不是受信回传，去磁盘核实，属实就修，自检结果照旧是在线）。
- `commands/at.md` §1：自检的「另外，」说原来那趟 run 坏了时，不写它的目录、另起 run id，这一轮就把它的问题与 run id 告诉用户；
  要接回它，先把 `current-run` 改回那个 id 再跑 `/agent-team:at-resume`。
- `commands/at.md` §2：契约写明在 `.agent-team/runs/<run_id>/00-contract.md`（原文只有裸文件名，真实会话里会写到项目根、拿不到 sha）。
- `commands/at.md` §2：没收到契约的 sha、却有一段【门禁】——那不是门禁没在跑，照它修，再原样重写契约；两样都没有时先核
  `current-run` 是不是正在写的这一趟（第二趟起漏切指针，ledger 判得出这次写入不在当前 run 里、一句不说），指针也对才是门禁没在跑。
- `commands/at-resume.md` §1：读不到 `current-run` 时先 Glob `runs/*/state.json`，有就是丢了指针，按规则接回或问用户。
- `commands/at-init.md` 收尾：自检的「另外，」那一句在这条命令里不修，按原因告诉用户下一步。
- README 两半：正常放行默认不留记录；项目经理自己发起的调用上判不出来时，告诉项目经理、界面上给你一行；没有 run 时派
  团队角色也有一行。
- 规格 §6 表下按检查项列「warning 发给谁」，§6.5 补【门禁】。

## 3. 复核

**设计评审**（语义、行为、判据三个角度；每条反对意见配一位反驳者，反对 32 条、采纳的在 §2 里）。推翻原稿的几处：告警从 H2
挪到 H5a（原稿放在 `PreToolUse` 上，会与别家插件并段、会说一次被 H1 拒掉的派发）；修法按原因选（原稿一律「修 current-run、
state.json」，`project.json`、`stages.json` 坏时把 PM 指错）；unknown-stage 按 `history` 末条分支（原稿的「history 末条同步」
在末条也坏时撞 H6）；「已写过 stdout」标记换成写完即退出；ledger 的范围从「`.agent-team` 下非控制文件」收窄到 `runs/` 下；
`systemMessage` 只许固定文字；判据钉在出口契约上、不只钉形状表。

**第一轮对抗验证**（`bc8e58c`）：

- 变异 40 个，39 个被杀。活下来的是 `isKnownStage` 去掉「值不能是假值」：`decideDeliverable` 对 `{S2: null}` 判 unknown-stage，
  这里说「在链里」，修法成了空操作。补了判据。
- 平台契约与控制流：没有缺陷。4312 次子进程的全矩阵（8 个检查项 × 14 种状态 × 6 种调用者 × 派发目标与写入文件，外加坏输入），
  严格契约零违规；留痕开、`createHash` 注入、`process.exit` 注入各复扫一遍。
- 修法走不走得通（4 条，都是 low，按反驳后的改法修了）：ledger 叫 PM 原样重写别的角色的产物，修好之后 H3 不让写；支 1 没说
  更早的坏阶段是残留，照做之后【state.json】叫去改、H6 又拒；`history` 形状不对时支 2 的 H6 说法不成立；命令开头的追加句不分命令。
- 正路噪音与漏报：21 组 S1→S8 整链、共 5766 次门禁调用，正路上没有【门禁】、没有 `systemMessage`，原有回传与基线逐次相同；
  判不出来的各格都出声。两条：第二趟起漏切指针、契约写在旧 run 之外——ledger 判得出（ctx 正常）、一句不说，基线同样如此，

## 4. 仍然开着的边界

- **第二趟起漏切指针、契约写在当前 run 之外**：ledger 判得出这次写入不在当前 run 里（ctx 正常），一句不说；`at.md` §2 让 PM
  先核指针。门禁侧的一格（PM 写 `runs/` 下、不在 `ctx.runDir` 里的契约时回传一句）有原型，没做：要收窄到契约或产物，免得
  PM 有意改上一趟文件时误报。
- **run 读不出来时，PM 改旧 run 没有门禁挡**：H3 对 PM 有 I2 豁免、H4 对契约写者放行、H6 读不出旧 `state.json` 就没有基线——
  `/agent-team:at` 里用新需求覆盖旧契约、把旧 `state.json` 重置成模板，门禁都放行。只靠自检追加句与 `commands/at.md` §1 的正文
  （§3 第二、三轮的真实会话）。
- **契约写到 `.agent-team` 之外**：ledger 按设计不出声（`.agent-team` 之外的写入与它无关），只靠 `commands/at.md` §2 的排查链先核位置。
- **项目放在一个叫 `.agent-team` 的目录里面**：`projectRootFrom` 现在跳过位于 `.agent-team` 目录里的候选，这样的项目找不到自己的
  `.agent-team`，按没有 run 处理。只是理论上的形状。
- **Write 的相对路径按 Bash 留下的 cwd 解析**：平台行为，与 `docs/24` §2.1 同族；门禁只保证项目根不因此漂进 `.agent-team` 里面。
- **协调者发起的派发时 run 才坏**：只有 H3 的拒绝理由，靠冒泡。
- **H5b 判不出来时到不了 PM**：平台没有通道；要做只能落盘状态、等 PM 下一次调用时读出，与「插件自己不写文件」冲突。
- **no-run 下 PM 自己的写入、子代理的写入**：照旧只 stderr。ledger 在 no-run 下对业务文件的 stderr 不收窄：它是门禁留痕判据
  （`tests/gate-trace.test.mjs`）里「只留 stderr 的放行」这种形状剩下的代表格，要收窄时先换一格代表。
- **readiness 中途出错**：PM 什么都收不到（`PreToolUse` 上不发受信块），只有用户看得到那一行。
- **boot.mjs 的 exit 1**（Node 太旧、加载失败）照旧，没改成 JSON。
- **`validateState` 与 H6 对 `history` 里坏条目的冲突**：前者说「改完再继续」，后者不许改。基线就有；本条只在 unknown-stage 的
  修法里说清它是已知残留，没改 `validateState` 的措辞。
- **H6 不校验阶段在不在链里**（旧 `state.json` 读不出来时放行首写，也放过不在链里的阶段）：归第 17 条。插件升级改了阶段 id
  的迁移没有；改名之后旧 `history` 每次写 `state.json` 都会被报一遍。
- **`stages.json` 形状不对现在判 unreadable**：此前 `{}` 算读出来了，非 PM 的写入照 `paths` 判；现在与解析不出一样，非 PM 的
  写入被 H3 拒。只有手改插件缓存才会出现。
- **PM 搞错项目根时自检照样「在线」、不追加**：`gate-check` 写在门禁认的项目根之外时不追加（M3t 起就是这样）；run 坏了只能等
  H5a 或 ledger 兜底。
- **`systemMessage` 说「项目经理已收到修法」**：只表示收到，不表示照做。
- **跨调用限流**：没有不写文件的跨进程状态；只靠收窄触发点。
- **空串 `agent_type`**：认不出调用者，不发受信回传（归第 22 条）。
- **第 24 条（收口标记）与 no-run 那一格**：收口之后要是清掉指针，那时的派发会落进 no-run 那一格，要回来重核。

## 5. 没量到的
