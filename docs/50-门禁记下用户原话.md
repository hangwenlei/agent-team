# 门禁记下用户原话

> 2026-10-07，M4o，分支 `m4o-user-words`。第八轮，从 `docs/00-开放边界.md` §1 挑的一条：全量审查第 20 条（中）剩下的修法 A——门禁记下用户在
> `/agent-team:at` 后面写的那段话，契约第 1 节对着它核。`docs/45` 做了修法 B（推进出第一段之后锁住第 1 节），修法 A 一直卡在「先在最低支持版本上
> 核 UserPromptExpansion 这个事件」（`docs/39` §6、`docs/45` §4）。正文是复核修订之后的样子，两路对抗复核与改了什么在 §9。

## 0. 一句话结论

- **平台**：斜杠命令展开时平台发 UserPromptExpansion，输入里的 `command_args` 就是换进 `$ARGUMENTS` 的那一份。本机能跑的最旧版本 2.1.278 上
  事件就在，`-p` 与 `--bg` 都触发（§1）。下限 2.1.276 的二进制本机已经没有，没跑过；推断那一版上要是还没有这个事件，结果只是不记、不核（§1.2）。
- **修法**：
  - **记**：`/agent-team:at` 带着参数展开时，门禁把原话、会话 id、那一刻已有的 run 记进项目一级的 `.agent-team/user-words.json`；不带参数的那一次，
    清掉这个会话还挂着的那份。
  - **绑**：这个会话之后用 Write 建出一趟新 run 的 `state.json`（H6 里写之前文件还不在）的那一次，把记录绑进那一趟的 run 目录。项目经理续跑了
    命令之前就有、没收口的那一趟，记录作废。
  - **核**：第一段里写契约时第 1 节对不上原话，【契约】当场说是哪一行、从第几个字起不一样；第一段的产物齐了，【阶段】那一句补上；推进出第一段那一次，
    H6 拒。行尾空白、空白的写法（不换行空格、全角空格、连续几个）、看不见的格式字符不计，整段写成引用块也认。
  - 两份记录都是门禁专属文件。
- **真实会话**：第一版（绑在写契约那一次）跑过一趟——项目经理第 1 节逐字照抄，推进到 S2 放行，全程没有误报（§4）。
- 实测时核准了一件平台事实：这两个事件上 hook 的 stderr 进不进转录看 stdout——门禁在这两个事件上的留痕行转录里一行都没有，只在调试日志里。
  现行参考的留痕判读表订正了（§1.3）。

## 1. 平台实测

### 1.1 事件与字段

探针插件挂三条：UserPromptExpansion 带 matcher、不带 matcher 各一条，UserPromptSubmit 一条，把 stdin 原样记下。在 2.1.286 与 2.1.278 的二进制上各用
`-p` 跑；2.1.286 另用 `--bg` 跑。参数带多行、首尾空白、中文、引号与反引号：

- UserPromptExpansion 先于 UserPromptSubmit 触发，字段如下：
  - `expansion_type`：`slash_command`；
  - `command_name`：带插件名的全名 `probe:at`；
  - `command_source`：`plugin`；
  - `command_args`：去掉了首尾空白，中间的换行与行尾空格保留；
  - `prompt`：命令名加一个空格加 `command_args`；
  - `session_id`：与主会话之后各次工具调用的 hook 输入里那一个相同。
- 从转录核过：换进命令正文的 `$ARGUMENTS` 就是 `command_args`，一字不差。
- UserPromptSubmit 拿到的是用户敲的原样，首尾空白没去。
- 2.1.278 与 2.1.286 上，上面每一条都一样。

matcher：

- 写成锚定的 `^probe:at$` 只放 `probe:at`。
- 写成 `probe:at`（含冒号，平台按正则不锚定匹配）连 `probe:at-x` 一起放进来。
- 写成 `at`（只有字母，平台按名字整串比）连 `probe:at` 都不放。

门禁注册写 `^agent-team:at$`，门禁自己再核一遍 `command_name`。

裸名 `/at` 不会解析成插件命令：

- `-p` 下当成普通文字发给模型，不触发展开；
- `--bg` 下报「Unknown command: /at」，命令不执行。

插件命令要用全名调用，`command_name` 就是 `agent-team:at`。

### 1.2 下限

- 2.1.276 的二进制本机已经不在（`docs/28` 当时读过它）。2.1.278 的二进制里这个事件有完整的输入定义（`expansion_type`、`command_name`、
  `command_args`、`command_source`、`prompt`），并且在能拦截的事件之列。Claude Code 的公开更新记录里一次都没提过这个事件。
- 往探针 hooks.json 里加一个不存在的事件名：2.1.278 与 2.1.286 上，其余钩子照常触发。更新记录 2.1.101 有一条：settings.json 里认不出的 hook
  事件名不再让整份文件作废（说的是 settings.json，不是插件的 hooks.json）。
- 推断：下限上要是还没有这个事件，那一条注册被跳过，记录器不触发，门禁不记、不核（退回修法 B），别的门禁不受影响。这是推断，没在 2.1.276 上跑过。
  最坏的情形是整份插件 hooks.json 被丢掉——那样门禁自检拿不到「在线」，项目经理照自检那一节停下，是响的失败，不是静默放行。

### 1.3 hook 的输出进不进转录

`docs/38` §5 写过「UserPromptSubmit 上的 stderr 在转录里看不见」，判读表一直没跟上。这一轮在 2.1.286 上分三种 stdout 量了这两个事件（每种都往 stderr
写一行留痕样式的字）：

- stdout 为空：转录里这一次 hook 没有任何记录，stderr 跟着丢；
- stdout 是带 additionalContext 的 JSON：转录里只有那段上下文（`hook_additional_context`），stderr 不记；
- stdout 是纯文本：转录里有一条 `hook_success`，stdout 与 stderr 都记下。
- `--debug-file` 的调试日志里，三种都有 `Hook <事件> (<事件>) success:`，stdout 与 stderr 都打。

门禁在这两个事件上的检查项从不写纯文本 stdout（`approval-prompt`、`user-words` 不写，`completion` 只写 additionalContext），所以它们的留痕行转录里一行
都没有，只能在调试日志里数。现行参考的判读表原来说 `approval-prompt`、`completion` 两行在转录里每次「一行」，改成「转录里没有，调试日志里一行」，新的
一行同样这么写；表下补一条说明，并订正「转录数出来的是下限」那一条里「stdout 非空时调试日志只打 stdout」的说法（`docs/00-现行参考.md` §1）。

### 1.4 第 1 节在真实会话里的写法

翻之前各场实测的转录：

- 大多数项目经理把原话直接写在「## 1. 用户原话」底下；
- 也有一批整段写成引用块（每行前面一个「> 」）。

门禁两种写法都认。

## 2. 修法

### 2.1 记录器

新检查项 `user-words`：

- 挂 UserPromptExpansion，matcher 是 `^agent-team:at$`。它是生命周期事件里唯一带 matcher 的一项，`checks.mjs` 里声明，接线判据照声明核。
- 带参数、带会话 id 的那一次（`hooks/lib/user-words.mjs` 的 `wordsOf`）：往项目一级的 `.agent-team/user-words.json` 整份重写一份——原话、会话 id、
  那一刻 `runs/` 下已有的名字（`runs_before`），`bound` 与 `dropped` 都是 null。最近的一次命令为准。
- 不带参数的那一次（`blankAtSession`）：这个会话还挂着（没绑也没作废）的那份清掉——这一次的需求在之后的对话里给，留着它会绑给这一次建的那一趟。
  别的会话的那份不动。
- `.agent-team` 不在不建它。没跑过 at-init 的项目，项目经理本来就会停下叫用户先跑 at-init；之后用户没重发命令、在对话里叫它接着做的，这一趟不核（§5）。
- 不拦任何东西：这个事件上 exit 2 会把用户的命令拦掉。stdout 一个字都不写，只往 stderr 留一行。
- 记录器标 `recorder: true`、`records: 'user-words'`。读不出输入、崩溃、加载失败、Node 太旧时，说的是「这次的原话没有记下」「这一趟契约第 1 节不跟它核」，
  不说「回答」「再批准一次」。

### 2.2 绑定与作废

`bindDecision` 判，`gate.mjs` 的 `settleWords` 写，`runWords` 读：

- 只看同一个会话、还没绑也没作废的记录。
- **绑**：这个会话用 Write 建出一趟**新** run（不在 `runs_before` 里）的 `state.json`、停在第一段的那一次——H6 里写之前文件还不在（`creating`）。先把项目一级
  那份标上 `bound`，再写 run 目录那份（多一个 `bound_at`）；后一步写不进时，记录不会挂着、被下一趟绑上，这一趟只是不核。之后这一趟只认 run 目录那份。
  照 `/agent-team:at` 第 1 节的顺序（`state.json`、`current-run`、契约），绑在第一步。
- **不晚绑**：别的会话建的、不经门禁建的（例如 Bash 写的）、已经走过第一段的，之后怎么写都不绑——晚绑会跨会话绑错，别的会话推进出第一段之后回退到第一段时，
  晚绑的原话与契约基线记下的第 1 节互相卡死。
- **作废**：项目经理写了一趟**命令之前就有**、没收口的 run（账本：当前这一趟的 `state.json` 或契约；H6：任何一趟的 `state.json`），不论它自己带没带记录，
  项目一级那份标上 `dropped`。那是续跑了它（`/agent-team:at` 第 1 节「用户选续跑」那一支），这条命令的需求被搁下了；之后另起的一趟抄的是用户的消息，
  不是这条命令的参数。
- 替它收口的那一次（写完之后它已经收口）不作废：收口之后照常建新的一趟，这条命令的需求接着用。
- 已经绑过的不再绑：收口之后照第 6 节自己另起的第二趟不绑、不核。
- H6 在所有拒绝之后才处理：被拒的写入不绑、不作废。

### 2.3 核

`section1Mismatch` 的认法：

- 从「## 1.」那一行往下跳过空行，逐行就是原话；之后到下一个编号节标题之间只能有空行。
- 比之前两边都把空白变体（不换行空格、全角空格、窄空格、制表符）折成一个普通空格、连续几个算一个，去掉看不见的格式字符（零宽空格与连接符、
  双向控制、软连字符），去掉行尾空白；BOM、CRLF 不计。
- 整段写成引用块也认：每行一个「>」或「> 」，空行写「>」或空着。
- 按原话的行数往下认：原话里自带的「## 安装」「## 2. 第二部分」不会把它切断。
- 对不上时报第几行、两边各是什么（都过 `quote`）、从第几个字起不一样与两边那个字的码位（一边是另一边的开头时不报），以及原话记在哪（这一趟
  run 目录的 `user-words.json`，args 那一项）。

三处说同一句（`wordsMismatchText` 与 `WORDS_FIX`）：

- **账本**：还在第一段、项目经理写契约时，【契约】当场说，末尾是「改好之前推进不出 S1」。写 `state.json` 时第一段的产物齐了，【阶段】「齐了」那一句
  补上「推进出 S1 会被拒」。写契约那一次只说一次，【阶段】不再补同一句。
- **H6**：推进出第一段那一次拒，末尾是「再推进」。排在契约判据之后、验收判据之前。第一段推进时契约基线还没有，两样不会一起说。第一段里不推进的写入
  （例如记 `contract_sha`）不拒。
- 走过第一段之后，三处都不按原话核。第 1 节之后再变，归契约基线管（`docs/45`）。

### 2.4 门禁专属文件

- `control-files.mjs` 的 `GATE_FILES` 加 `runs/*/user-words.json`。
- 新增 `PROJECT_GATE_FILES = ['user-words.json']`：项目一级那份是唯一一份不在 `runs/<id>/` 下的门禁专属文件，命令展开那一刻这一趟的 run 还没建。
- `isGateFile`、`mayBeGateFile` 两样都认。H3 对任何人的 Edit/Write 都拒，理由说清这是门禁在用户发出命令时记下的原话、对不上就照它改第 1 节。
  Bash 照样写得进（与别的门禁专属文件同一档）。

### 2.5 正文

- `/agent-team:at` 第 2 节：命令带了参数的，门禁记下了 `$ARGUMENTS`、在哪两刻核、哪几种情形不核；两份都是门禁专属，不要用别的办法改。

## 5. 仍然开着的边界

- **命令没带参数**：需求在之后的对话里给出时，不记、不核。
- **命令在 at-init 之前发的**：`.agent-team` 不在，不记；跑完 at-init 之后用户没重发命令、在对话里叫项目经理接着做的，不核。
- **收口之后照第 6 节自己另起的一趟**：抄的是用户的消息，不是这条命令的参数，不核。
