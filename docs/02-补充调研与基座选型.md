## 2. 基座定论

### 2.1 桌面应用 + 2.1.237 下的层级手段全表

| 手段 | 能做 | 不能做 | 官方依据 |
|---|---|---|---|
| **嵌套 subagent**<br>`agents/*.md` + Agent 工具 | 唯一能承载 10 个角色**身份**的地方（系统提示 / tools / model / effort / skills / memory）。默认可嵌套 **3 层**（主会话之下），刚好覆盖 PM→产品→角色→子任务。插件内 agent 自动带命名空间 `plugin:agent`，子目录变 id 一段（`my-plugin:review:security`）。返回值只有一段摘要，中间过程不污染上级上下文 | ① **不能向人提问**（AskUserQuestion/EnterPlanMode/ExitPlanMode 被剥离）；② **不能启动 workflow**（`Workflow` 被剥离）；③ `tools: Agent(a,b)` 的**括号内类型白名单被忽略**——无法约束「产品经理只能派给架构师」；④ 自 v2.1.198 **subagent 默认后台运行**，后台态只保留 20 个内置工具（Read/Grep/Glob/Bash/PowerShell/Edit/Write/NotebookEdit/WebFetch/WebSearch/TodoWrite/Skill/ToolSearch/EnterWorktree/ExitWorktree/Monitor/TaskStop/SendMessage/Artifact），其余静默消失；⑤ 并发上限 20；⑥ 无共享任务表、无中途可见性、无法中断后续跑 | [sub-agents](https://code.claude.com/docs/en/sub-agents)、[settings](https://code.claude.com/docs/en/settings) |

### 2.2 推荐组合（一句话）

> **把主会话用 `agent` 设置键钉成项目经理，10 个角色写成插件内的 subagent，每个阶段做成一条 slash command（人打下一条命令就是审批），命令内部的扇出交给 dynamic workflow，越界与缺交付物由插件级 hook 用 `exit 2` 兜底。**

理由：这是**唯一一条每一环都在 Desktop 存在**的路径，且它把三个互斥的约束各自安置在了能容纳它们的层：**顺序**只有 workflow 给得了，**人工审批**只有主会话给得了，**否决**只有 hook 给得了——所以审批必须是两条命令之间的缝，而不是 workflow 里的一步。

排序理由（从最不可替代到最可替代）：

1. **dynamic workflow** — 确定性顺序的唯一来源。
2. **嵌套 subagent** — 角色身份的唯一容器。
3. **`agent` 设置键** — 层级为真而非扮演的唯一开关（Desktop 无 `--agent`）。
4. **plan mode / AskUserQuestion** — 可强制人工闸门的唯一位置，且只在主会话。
5. **hooks** — 兜底否决；能做角色感知（`agent_type`），但不能排序。
6. **跨会话消息** — 最后。不能建会话、不能唤醒、不能批准，只适合业务体验官这类需要独立上下文的旁路。

## 3. 打包定论

### 3.1 容器：plugin，不是 skill

只有 plugin 能同时装下 `agents/` + `commands/` + `skills/` + `workflows/` + `hooks/` + 根 `settings.json`——本项目四样都需要。

- **开发与运行路径**：`C:\Users\82370\.claude\skills\agent-team\`（含 `.claude-plugin/plugin.json` 即被识别为 `agent-team@skills-dir`，下次会话自动加载，无 marketplace、无安装步骤、无信任弹窗；personal scope 在**所有项目**生效）。
- **不要用 project scope**（`<cwd>/.claude/skills/`）：它**不会向上找仓库根**，从子目录启动会漏掉插件；逃生口 `/cd` 需 **v2.1.246+**，本机 2.1.237 没有。
- **目录纪律**：只有 `plugin.json` 在 `.claude-plugin/` 里，其余全部在插件根。官方原文："All other directories (commands/, agents/, skills/, workflows/, output-styles/, themes/, monitors/, hooks/) must be at the plugin root, not inside `.claude-plugin/`."
- **活样板**：Anthropic 自家 `claude-plugins-official/plugins/code-modernization/` 就是这个形状——`commands/` 10 个扁平文件（modernize-assess / -brief / -map / -preflight / -uplift / -transform / -reimagine / -harden / -status / -extract-rules）+ `workflows/` 6 个脚本。**每阶段一条命令 + 扇出丢给 workflow**，不是我们发明的。

依据：[plugins-reference](https://code.claude.com/docs/en/plugins-reference)、[plugins](https://code.claude.com/docs/en/plugins)、[code-modernization](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/code-modernization)

### 3.2 角色：10 个全部是 subagent，0 个是 skill

判定规则（三分法，问「这东西**是什么**」而不是「它**代表谁**」）：

| 类型 | 形态 | 官方依据 |
|---|---|---|
| **干活的**：接一个有边界的任务、烧大量 token 读写、返回一份交付物 | `agents/*.md` | "Each subagent starts with a fresh, isolated context window"；适用场景含 "The task produces verbose output you don't need in your main context" |
| **主线程执行的流程**：需要跟人来回 | `commands/*.md` | "Consider Skills instead when you want reusable prompts or workflows that run in the main conversation context" |
| **标准 / 模板 / 清单**：里面没有任务 | `skills/*/SKILL.md`，**不 fork** | "`context: fork` only makes sense for skills with explicit instructions…the subagent receives the guidelines but no actionable prompt, and returns without meaningful output" |

**10 个角色全是第一类，所以全是 subagent。** 角色做成 skill 会在主上下文里跑，第 3 个角色就把编排者的窗口撑爆。

两处不对称：

- **项目经理是同一个文件的两种用法**：既是 `agents/pm-lead.md`，又被插件根 `settings.json` 的 `{"agent":"pm-lead"}` 拿去当主会话身份。**PM 永远不被派发，PM 就是会话本身**——这才是「层级」而不是扮演。
- **技术架构师是唯一需要自己往下派的角色**，`tools` 里要给 `Agent`。但记住 `Agent(frontend-dev,backend-dev)` 的括号内容**被忽略**，允许派给谁只能写进它的正文当指导，不是强制。

**共享契约做成 skill**，用角色 frontmatter 的 `skills:` 字段预加载（"Skills to preload into the subagent's context at startup"）：`team-protocol`、`prd-template`、`arch-decision-record`、`api-contract`（前端/后端/iOS/Android 四个角色同时预加载**同一份**接口契约）、`acceptance-criteria`。**这是产品里最便宜的跨角色对齐机制，01 调研的整个生态里没有一个人用了它。**

### 3.3 阶段触发与 PM 审批闸门

**每阶段一条 slash command，不做链式自动推进。** 每条命令干且只干五件事：

1. 从**磁盘**读上一阶段产物（不从上下文读）；
2. 上一阶段产物缺失或未签字 → **拒绝并停止**；
3. 干活。需要扇出就丢给 workflow：`Workflow({scriptPath:"${CLAUDE_PLUGIN_ROOT}/workflows/align-roles.js", args:{...}})`；
4. 写自己的产物到 `docs/agent-team/NN-*.md`；
5. 打印摘要 + **下一条要敲的命令**，然后停。

**闸门是两层的：**

| 层 | 机制 | 为什么合法 |
|---|---|---|
| **一层：命令之间的缝** | 人敲下一条命令这个动作**本身就是审批**。不自动推进 = 结构性闸门，实现成本为零 | 这正是官方 "run each stage as its own workflow" 的直译 |
| **二层：`/agent-team:at-decide`** | 这条命令**内部一个 workflow 调用都没有**，纯主线程。它读 `03-alignment.md`，把各角色冲突的立场和各方案代价摊开，**然后问人并阻塞**。人答完才写 `04-decision.md`（含决策、被否方案、签字人）。第 5 阶段没有这个文件就拒跑 | 「运行中不能接受人输入」约束的是 **workflow run**，不是对话轮次。主线程命令问人并等待是默认行为 |

**由此得出本架构的划分法则：**

> **扇出放 `workflows/*.js`，判断放 `commands/*.md`。** 决策点绝不能进 workflow 脚本——脚本问不了人。八路角色并行投票也绝不能留在命令里——主上下文装不下六份完整角色记录。

映射到用户的流程：

```
业务需求
  → /at-intake     PM 主线程访谈人            → 01-intake.md
  → /at-product    派 product-manager          → 02-prd.md
  → /at-align      workflow: 架构/UI/前/后/iOS/Android/测试/业务体验官 并行投票（schema 强制结构化）→ 03-alignment.md
  → /at-decide     ★PM 闸门，无 workflow，问人并阻塞★ → 04-decision.md（签字）
  → /at-dispatch   产品经理切工单              → 05-workorders/*.md
  → /at-build      workflow: 四端并行，架构师监督 → 代码 + 06-build-report.md

```

`/at-align` **必须用 `schema`**：强制每个角色返回 `{role, verdict:"ok"|"concern"|"blocker", cost_days, objections[]}`。八份散文无法合并，八份 JSON 能排成一张 PM 真能据以决策的表。**坑**：`agent()` 被中断或遇到不可恢复的 API 错误时返回 `null`，`pipeline()` 会把 `null` 原样留在结果数组里——**数票前必须 `.filter(Boolean)`，否则一个挂掉的角色会被读成「无异议」**。

### 5.5 一条容易被误抄的坑（来自各框架的负面经验）

| 别抄什么 | 为什么 |
|---|---|
| **supervisor-as-classifier 循环**（LangGraph 每个 worker 完了都重新调一次顶层 LLM） | LangGraph 能这么干是因为它的路由调用极便宜（一个 `{next: Literal[...]}` 结构化输出、无工具）。Claude Code 的等价物是**一整个主会话轮次，带着整段对话**。顺序已知的流水线（需求→产品→架构→UI/开发→测试→业务验收）应把顺序硬编码进 `pipeline()`，只在**两个真正的分叉点**（角色对齐后的 PM 决策、测试+验收后的发/返工）调模型 |
| **handoff / handoff-back 消息对** | LangGraph 里它们是**日志装饰**（控制权早已由静态边转移，所以它们可开关）。在 Claude Code 里复刻成对话轮次买不到任何控制权，只烧上下文。写进 `docs/agent-team/log/handoffs.md` 或直接省掉 |
| **ADK 的单父 ValueError** | 它解决的是 Python 对象上一个可变反向指针的别名 bug——Claude Code 的 subagent 是无状态提示文件，**没有这个 bug**。照抄会禁止技术架构师同时被产品经理和后端咨询，而那正是用户的需求。**要抄派发 ACL（H3），不要抄所有权规则** |
| **ADK 的 `transfer_to_agent`（模型自选下一步）** | 注入提示原文是「If another agent is better…call transfer_to_agent」——这正是 01 已经发现的、所有扁平角色库做得最差的那件事。用它的**白名单计算**，不用它的**路由决策** |
| **ChatDev 的 C-suite 层级** | 是装饰：没有任何 agent 能派发、批准或升级，`chat_chain.py` 就是按序走数组，`Chief Human Resource Officer` 在花名册里但**零个 phase 用到它** |
| **SPARC 把约束在 15 个角色提示里各复述一遍** | "Files < 500 lines" 与 "no hard-coded env vars" 在 ~12/15 个提示里逐字重复：每次 agent 启动都付这笔提示税、改一处就漂移、且完全无法强制。一个 PostToolUse hook 检查一次，免费而且真的会挡 |
| **Roo 的 `switch_mode`（原地换角色、保留会话历史）** | **无对应物。** `agent` 设置键只在会话开始生效。不要围绕「中途换角色」设计 |

## 6. 成本模型

### 6.1 那两个倍率数字的出处判定

| 说法 | 判定 |
|---|---|
| **「plan mode 约 7 倍」** | **官方，但语境不同。** [costs](https://code.claude.com/docs/en/costs) 原文："Agent teams use approximately 7x more tokens than standard sessions **when teammates run in plan mode**, because each teammate maintains its own context window and runs as a separate Claude instance." 三个限定：① **没有说几人**（不是「N 人 N 倍」）；② 限定在 plan mode（最贵的 teammate 模式）；③ **它定价的是 Agent Teams**——桌面应用里不存在的东西。**拿它去报本用户的顺序流水线是范畴错误** |
| **「5 人约 5 倍」** | **查无此源。** 三个最常被误当成它的：① **Max 5x 订阅档**（$100/月，是套餐名不是 token 测量，这是最常见的混淆源）；② [agent-teams](https://code.claude.com/docs/en/agent-teams) 的定性句 "Token costs scale linearly: each teammate has its own context window and consumes tokens independently"——线性、无系数；③ Systima 的实测，而那是**两个 agent 5.9 倍**，不是五个 |
| **唯一的第三方实测** | [Systima「The Subagent Tax」](https://systima.ai/blog/subagent-tax)（2026-07-22）：同一个小编码任务跑三种形态，自家代理 Meridian 在线计量，区分 metered input / cache write / cache read。Opus 2 subagent = 2.6x、Opus 5 subagent = 3.2x、Fable 2 subagent = 5.9x、Fable 5 subagent = 4.7x；按 API 价加权，双 subagent 扇出约为顺序的五倍成本。测量台已开源（[github.com/systima-ai/agentic-coding-tools-comparison](https://github.com/systima-ai/agentic-coding-tools-comparison)，已核实存在，7 star，1 commit，**提交日期未核实**）。**可信度：方向可用，数字不可用。** 加分：数据与台子公开、线上计量而非自报、缓存读写拆开。减分：厂商内容（它卖的就是那个代理）、n=1、无重复次数、**且数字对 agent 数非单调**（Fable 5 个比 2 个便宜）——这说明单次方差大于被测效应 |
| **本项目该用的锚** | Anthropic 工程博客原文："agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats"，且 "token usage by itself explains 80% of the variance"。**15 倍是相对聊天，不是相对单个 Claude Code 会话——而 Claude Code 本身就是那个 4 倍项。** 同口径的「多 agent 相对单 agent」= 15/4 ≈ **3.75 倍（估算）**。它正好夹在官方 7 倍（plan mode，贵端）与实测 2.6–3.2 倍（Opus 扇出，便宜端）之间 |

**给本用户的判断：2–4 倍，不是 7 倍（估算）。** 顺序 10 角色交接在结构上比上述四个来源测的扇出都便宜——扇出是 N 个 agent 各自独立探索同一份代码库，那才是 7 倍和 15 倍的来源；顺序交接同一时刻只有一个角色在跑，且每个角色应当**接收**前一个的发现而不是重新发现。但它付另一笔账：固定重入 ×10 + 交接重读 + 交接没能阻止的重复探索。**做得好 2.0–2.5 倍；做得糙（每个角色重读全仓、交接 = 整段 transcript）4–6 倍——退化成扇出的成本曲线，却拿不到扇出的并行。**

⚠️ **同一篇官方博客直接点名了本设计**："some domains that require all agents to share the same context or involve many dependencies between agents are not a good fit for multi-agent systems today"，且编码 "involve fewer truly parallelizable tasks than research"。agent-teams 文档说同一件事："For sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective."
**含义：这套 10 角色方案的价值主张必须是「治理与可复核」，永远不能论证成「更快」或「更省」。**

### 6.2 钱花在哪（降序）

| # | 项 | 量级（估算） | 说明 |
|---|---|---|---|
| 1 | **重复探索** | **一趟约 120k token** | 6 个重角色各自回答「这里的鉴权怎么做的」，各拉 20k 同样的源码，而一个会话只付一次 20k。**这一项比固定重入 + 交接重读之和还大**，且在所有已发表倍率里都看不见（那些基准都在互相独立的切片上扇出）。交接文档存在的意义就是压掉这一项——所以**薄交接是成本 bug，不是节省** |
| 2 | **交接重读（可平方可线性）** | 15k ↔ 67.5k | 每个下游都收到累积全量：1.5k × (0+1+…+9) = 67.5k；只读稳定规格 + 直接前驱：10 × 1.5k = 15k。**同样的信息架构，4.5 倍差距，纯设计选择** |
| 3 | **固定重入** | ~3,790 × 10 ≈ 38k | 官方 [context-window](https://code.claude.com/docs/en/context-window) 拆项：subagent 自己的系统提示 900 + **项目 CLAUDE.md 自己的一份 1,800**（"Same file, same content, but it counts against the subagent's context, not yours"）+ MCP/skills 970 + 派发提示 120。**按 cache-write 或未缓存价计，不是 cache-read 价** |
| 4 | **CLAUDE.md 重注入（上一项里最大的一条）** | 10 角色 ×1,800 = 18k | [sub-agents](https://code.claude.com/docs/en/sub-agents)：非 fork 的 subagent 加载 "every level of the CLAUDE.md hierarchy the main conversation loads"（内置 Explore 与 Plan 跳过）。costs 文档的「CLAUDE.md 保持 200 行以内」在这里的载荷是平时的 **~11 倍** |
| 5 | **缓存连续性丢失（上述所有项的乘数）** | — | [prompt-caching](https://code.claude.com/docs/en/prompt-caching)："A subagent starts its own conversation with its own system prompt and tool set, separate from the parent's. Its first request doesn't read the parent's cache…Subagents fall outside the main-conversation TTL bucket, so they get **five minutes** even on a subscription." 顺序拓扑**恰好是用不上扇出前缀共享的那种拓扑**（前缀共享要求同型兄弟近乎同时启动） |
| 6 | **轮次放大（为什么轮数比上下文大小更要命）** | — | costs 文档："Claude Code sends your full conversation with every request, and each time Claude uses tools it sends another request carrying that batch of tool results." 计费输入 ≈ 平均上下文 × 助手轮数。40k×40 轮 = 1.6M；40k×12 轮 = 480k。**削轮数的手段（精确派发提示、预过滤交接、hook 预 grep 输出）优于削上下文的手段** |

**最容易被误读的一条**：subagent 保护的是**父级上下文窗口**，不是账单——"the only content that returns to the parent conversation is the subagent's final summary"。PM 会话可以整天停在 30k 上下文，同时烧掉单会话 4 倍的钱。**任何拿 `/context` 当成本代理指标的人都会得出「这个设计是免费的」这个结论。** 更糟的是唯一报告缓存健康的 `Prompt cache (main)` 行**明确不覆盖 subagent**。

### 6.4 一趟的量级（全部为估算，价格为实价）

场景：一个中等功能「在 Web / iOS / Android 上加保存的搜索」，走完十个角色，一趟不含返工。

计费恒等式：**计费输入 ≈ 平均上下文 × 助手轮数**；有效单价 = h×0.1 + (1−h)×1.25（h = 缓存命中率）。

| 场景 | 说明 | token 读取量 | 成本 |
|---|---|---|---|
| **A 未调优** | 10 角色全 Opus 5，全量交接。角色内命中 ~80%（有效系数 0.33） | ~14.5M → 折 4.8M | **≈ \$30 / 趟** |
| **B 单会话对照** | 同样的活，一条长对话 + 定期 `/compact`。缓存连续性好（h≈0.90）、无 10 次冷启动、无重复探索、无交接复述 | ~8M → 折 1.7M | **≈ \$14 / 趟** |
| **C 调优后** | 四个轻角色降 Sonnet/Haiku、磁盘交接只回路径+摘要、QA 输出过滤 hook、续跑角色 1h TTL、四端共用定义 | ~10M → 折 3.3M | **≈ \$22 / 趟** |

**校准证据**：场景 B 的 \$14 恰好落在官方口径上——costs 文档："the average cost is around \$13 per developer per active day and \$150-250 per developer per month, with costs remaining below \$30 per active day for 90% of users"。这是本模型不是凭空编的最强旁证。

**隐含倍率**：\$30 / \$14 ≈ **2.1 倍**（做得好），糙做 4–6 倍。与推导锚 3.75 倍相容，**低于官方 7 倍**（那是并发 teammate 在 plan mode）。调优后仍有 **0.6 倍溢价，那就是治理的价钱**——十份可复核的角色产物加一道人工闸门。**目标是把溢价压在 2 倍以内，不是消灭它。**

⚠️ **这个设计会永久性触发官方告警**：workflows 文档 "When a workflow schedules more than 25 agents, **or its projected token total passes 1.5 million**, its progress line…shows a `Large workflow` warning"。10 角色永远到不了 25 个 agent，但 ~14.5M token 读取每一趟都会越过 150 万那一半。而把 `workflowSizeGuideline` 调成 `large` 只把 **agent 阈值**抬到 50，**token 阈值原地不动**。**提前告诉用户，否则他会当 bug 报。**

**月度**：一趟 \$22–30、含返工一个功能现实 2–4 趟 = **\$45–120 / 功能**，即官方日均 \$13 的 3–8 个活跃日被一个功能吃掉。订阅制下真正会先撞的**不是钱而是滚动 5 小时/周窗口**——十个角色一天内顺序跑完，中途耗尽窗口是可能的，**而流水线死在第 7 个角色 = 1–6 的钱付了、东西没交**。⚠️ 本机 2.1.237 下 workflow 撞上限是**直接失败**而不是等待（见 §3.5）——这是升级的第一理由。

**替换本节全部估算的最便宜办法**：拿一个刻意小的切片（一个页面、仅 Web、只跑角色 1–5）跑一趟，然后读 `/usage` 的 subagent 归因。这也正是官方教的："To gauge the spend before committing to a large task, run the workflow on a small slice first."

### 6.5 每角色模型建议（分配为估算，价格为实价）

| 角色 | 模型 | CLAUDE.md | 其他 | 理由 |
|---|---|---|---|---|
| **项目经理** | Opus 5 | 开（`omitClaudeMd` 对主会话 agent 无效） | 主会话钉死 | token 上很便宜（只路由与决策），但决策管住一切，降档省不到钱只承担风险 |
| **技术架构师** | **Opus 5** | **开** | `cacheTtl: 1h` | **下游消费者最多的角色，错误被付十遍。** 它的交接质量直接决定六个实现角色重复探索多少。**绝不 `omitClaudeMd`**——与仓库自身惯例冲突的架构决策是最贵的失败 |
| 前端 / 后端 / iOS / Android | Sonnet 5（个别难任务按次升 Opus） | 开 | **共用一份定义**（吃前缀共享） | 要往仓库里写代码，需要惯例 |
| **测试工程师** | Sonnet 5 | 开 | `cacheTtl: 1h` + **PreToolUse Bash 输出过滤 hook** | **轮数最多、工具输出最长**，按轮次放大它常是第 1–2 大开销。大多数方案在这里省模型、又不过滤输出——正好反了 |
| 产品经理 | Sonnet 5 | **关**（2.1.271+） | — | 从业务简报与 PM 收单产物工作，不从代码库。喂它编码惯例是纯浪费且轻微有害（开始往产品文档里写实现细节） |
| UI 设计 | Sonnet 5（设计系统已成文则 Haiku 4.5） | **关** | 设计令牌由派发提示显式传入 | 不要让它读仓库 |
| **业务体验官** | Haiku 4.5 / Sonnet 5 | **关——这是刻意的，不是省钱** | `disallowedTools: Write, Edit`；上下文三态取**净室**（X8） | 它要拿建成的东西对照**最初的业务诉求**。给它 CLAUDE.md 与仓库惯例，就是让验收被实现俘获——它会开始解释「偏离为什么是合理的」而不是标记偏离。**能背出借口的验收者不是验收者。** 它的上下文只该有：原始业务请求、验收标准、运行中的产物 |

**分档到底省多少（估算，诚实版）**：把四个轻角色从 Opus 降到 Sonnet/Haiku，在我估的 \$30 全 Opus 一趟上省 \$1.50–2.00，即 **5–7%**。
**钱不在分档上。** 按降序：① 阻止六个重角色重复探索同一批代码（占一趟 40–60%）；② 磁盘交接只回路径+摘要（既是第 2 项也是第 ① 项的主要解法）；③ 用精确派发提示与输出过滤 hook 削轮数；④ 给闸门后续跑的角色开 1h TTL；⑤ 模型分档。**任何把模型分档放在最前面的建议，都在优化第五大的杠杆。**

**顺带的排期规则**：effort **没有 per-role 设置**（sub-agents 文档："There is no per-subagent thinking setting"；agent-teams："Teammates inherit the lead's effort level"），而**会话中途改 effort 本身就是成本事件**（prompt-caching："changing the effort level mid-session means the next request reads the entire conversation history with no cache hits"）。所幸闸门本来就把每阶段切成独立 run——**让阶段边界与 effort 边界重合**，就永远不付这笔失效成本。
