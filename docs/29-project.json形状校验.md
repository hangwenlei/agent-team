# project.json 的形状校验

**日期** 2026-09-29 至 09-30 ｜ **口径** 分支 `m3u-project-shape`（`f3d29b7`、`f0faf67`、`70be4be`、`f9a788f`、`a43b74f`…），版本 `1.3.0`；修的是
全量审查（`docs/24-附录-全量审查报告.md`）第 10 条。真实会话都在本机 CLI 2.1.283 上，项目经理跑在 `at-pm.md` 钉的 sonnet 上

## 0. 一句话结论

写路径隔离（H3）此前只要 `project.json` 是个合法对象就照单全收：`paths` 缺失、键名拼错、带插件前缀、键被删掉、run
进行中整份文件被删——调用者在 `paths` 里「没有键」——一律静默放行；前缀 `../` 认领到项目根之外，`''` 与 `.` 认领整个
项目根。现在形状问题分三档（阻断、要改、请确认），外加单列的插件问题：H3 对花名册里的角色按「没有键就拒、自己的条目坏了
就整条作废」判，只有按设计不认领路径的 `at-qa`、`at-acceptance` 没有键时照旧放行；ledger 在 PM 写控制文件的几个时机把
问题说出来，`project.json` 写坏、或者在 run 进行中被别处弄坏，也会说出来。`/agent-team:at` 正文把后果方向写反的那句改对了。

## 1. 问题

读代码并逐格实测（`main` 上 `0afce9d`）：

- `decideWritePath` 在控制文件与 run 目录保护两段之后，`!project || !project.paths` 放行，`!Object.hasOwn(paths, role)`
  放行。于是 `paths` 为 `{}`、`project.json` 被删或清成 `{}`、`paths` 写成数组、键名写成 `path`、角色键拼成
  `at-fronted`、键带 `agent-team:` 前缀，全都从「按角色隔离」变成「谁都能写 run 目录外的任何地方」，不留痕迹。
- `underAny` 把前缀拼在项目根后面再解析：`../` 认领项目根的父目录，`''`、`.`、`./`、`src/..` 认领整个项目根——
  `.claude/`、`CLAUDE.md`、`.git` 都对这个角色敞开。
- 值里的元素不是字符串时比较会抛，被 gate 的兜底接住按门禁异常拒掉，理由不指向 `project.json`。
- `commands/at.md` §0 写着「没有 `project.json`，写路径隔离没有判据，每个执行角色都会被拒」——实际是全放行，方向写反了。
- `project.json` 写坏（注释、尾逗号、顶层不是对象）时，runctx 把整趟 run 判成读不出来，ledger 只往 stderr 留痕：
  `/agent-team:at-init` 收不到触达表，按「没收到就停下：门禁没在跑」把用户引去排查一个不存在的问题；run 进行中被手改坏时，
  PM 写 `state.json`、`current-run`、契约都收不到任何东西，停在 S1。

## 2. 修法

### 2.1 分档（`hooks/lib/project.mjs`）

`validateProject(project, { roster })` 是纯函数，返回 `{ block, fix, confirm, plugin }`，每条是一句话，外部值一律过
`quote`（`docs/27`）。

- **阻断**：H3 据此拒持有这个条目的角色——只算 H3 会拿这个键去判的（建了键的 `at-qa`、`at-acceptance`、`at-outsider`
  也算）。条目级：值不是数组、元素不是字符串、前缀出了项目根、认领整个项目根、带冒号。整份级：`paths` 缺失或不是对象
  （拒 `at-qa`、`at-acceptance` 以外的执行角色）。
- **要改**：`/agent-team:at-init` 明令不许、或者按字面比较一定落空的写法——键不是花名册角色名；给 `at-pm`、`at-qa`、
  `at-acceptance`、`at-outsider` 建了键；前缀落在 `.agent-team` 下、含反斜杠、含 `*` 或 `?`、首尾有空白、有以点或
  空格结尾的段、含零宽空格之类的格式字符（写出码点）；`available_roles` 缺失、不是数组、有非花名册名字或不是执行
  角色的名字。H3 不拿来判人的键（`at-pm`、`__main__`、认不出的键）上的条目级阻断降到这一档。
- **请确认**：可能是有意的——`available_roles` 里的角色在 `paths` 里没有键（写成 `[]` 表示有意只写 run 目录，就不再
  提）；一个角色的前缀严格包含另一个角色的（外层也能写进内层；只在 H3 会判、整条没作废的条目之间比）；前缀以 `/` 开头；
  前缀落在 Claude Code 会自动加载或执行的地方（`.claude/`、`.git/`、项目根下的 `CLAUDE.md`、`CLAUDE.local.md`、
  `.mcp.json`）；给 `__main__` 建了键。
- **插件**：`roster.json` 读不出来。不是 `project.json` 的问题，改它修不好，单列。

前缀的落点、嵌套、「落在哪个目录下」都按 H3 的拼法在一个虚拟根上解析之后判（`..` 先折叠）：按字面比会让
`src/server/..` 这类字面上窄、实际认领整个 `src/` 的写法漏报，嵌套的方向还会说反。

每条阻断有两种说法：给 PM 的带改法（出根的删掉、别换成项目里的同名目录、收尾告诉用户；认领根的逐个列文件；冒号的
换个名字），给执行角色的（H3 第 8 步拼进拒绝理由）只说问题本身——执行角色改不了 `project.json`、也见不到用户，它的
出路是冒泡。

「按设计不认领路径的角色」只有一份常量 `NO_PATHS_ROLES`，判据核它等于模板的 `available_roles` 减去 `paths` 的键。

### 2.2 H3 的新尾段（`hooks/lib/writepath.mjs`）

控制文件与 run 目录保护两段照旧在前。之后逐步：

1. PM 放行（给 `at-pm` 错建的键不起作用）。
2. `at-qa`、`at-acceptance` 在 `paths` 里没有键时放行，不看 `project.json` 的其余部分——它们的正文照此写着。
3. 花名册读坏时拒（不能落成下一步的「不在花名册里就放行」：读坏时退回 `{}`，那样对所有人全开）。判「读坏」与
   H1 共用 `isValidRoster`：`null`、非对象、数组、空对象都算。
4. 不在花名册里的调用者放行（不归本插件管）。
5. run 进行中而 `project.json` 不在：拒。
6. `paths` 缺失或不是对象：拒。
7. 调用者没有键：拒，理由附上 `paths` 里认不出的键（多半是拼错的那一个）。
8. 调用者自己的条目有阻断问题：只拒它，整条条目作废——连它其余合法的前缀也写不了，理由里说出来。
9. 其余照旧：认领了放行，别人的拒，没人认领拒。认领者查找只看 H3 会判的键上合法的前缀（不说「这条路径归 at-pm」
   「归拼错的键」）。

第 5–8 步的理由写明「这是配置问题，冒泡给派你的上级，由 PM 改 `project.json`（规则见 `/agent-team:at-init` 第 2 节）」；
「没人认领」那一步也改成冒泡，但不说「这是配置问题」——没人认领也可能是这次调用越界了。

**为什么不照审查原文把形状错误判成读不出运行上下文**：那会让 H2、H5、ledger 一起降级——一个键名拼错，交付物校验就
停摆。形状问题只影响 H3 的判据，所以只让 H3 看它。

### 2.3 ledger 的【project.json】与【插件】

- PM 写 `project.json` 时（有 run、没有 run 两条路）：三档全报，排在【触达表】之前；【插件】又排在它之前。
- 每趟 run 开头写 `current-run` 时：三档全报——已装用户的旧配置在 S1 就露面，不等到 S5 撞上拒绝。
- 写 `state.json` 时：只报阻断与插件问题，覆盖升级前开始、升级后续跑的 run，不报另外两档免得每次记账都刷一遍。
- 写 `project.json` 时花名册读坏、或者有阻断：不发触达表的 JSON，改成一句「这次不发」，说清为什么、什么时候会收到。花名册
  读坏时触达表拿 `{}` 算，恒得出「没有角色的触达超出」（实测 PM 用这份 `{}` 覆盖了一份正确的 `reach.json`），那句话叫 PM 让
  用户重装后新开一个会话再跑（插件更新只对新会话生效）。有阻断时一律等改完再发：元素级、前缀级阻断下触达表照整条作废的条目
  算，把门禁不放行的前缀也算成「还能写到」，与【project.json】自相矛盾；整份级阻断下它算得与 H3 一致，但改完就会变——
  所以话里只说「改完阻断之后才会收到」，不说算得不对。只有要改、没有阻断时照发。写 `state.json`、`current-run` 时不出这一段。
- `project.json` 写坏（解析不出、不是对象）：写它的那一次回传一句固定的话，不回显文件内容、不发触达表。门禁自己最多再读
  三次、两次之间停 25ms：撞上短暂的占用、读到别人写了一半的内容时，不对一份合法的文件说「写坏了」，也不退成只留痕
  （stdout 空着，at-init 会按「门禁没在跑」叫停）。文件根本不在（ENOENT）时不重读、不停。
- `project.json` 在别处被弄坏（用户在两趟 run 之间手改，加了注释或尾逗号）：PM 写 `.agent-team` 下任何别的文件都回传那句
  话的变体。run 进行中时说明契约与产物的哈希这时回传不了、改好之后原样重写一次刚才那个文件；没有 run 时说改好
  `project.json` 就会收到报告与触达表。`.agent-team` 之外的写入照旧一声不吭。
- UTF-16 编码的文件（Windows PowerShell 5.1 的 `Out-File` 与 `>` 的出厂默认）直说编码：只说「注释和尾逗号」会把 PM 引开。
  判定看 NUL 在奇偶位上的分布（跳过 BOM 解出来的 U+FFFD，奇数位或偶数位绝大多数是 NUL、另一半几乎没有），尾部补 NUL、
  整份清零、UTF-32 都落回泛说的口径（「常见原因：注释、尾逗号、文件不是 UTF-8 编码」）。措辞说可观测的现象与兜底：CLI
  2.1.283 上 Read 看到的是一字一隔的乱码；Write 第一次去掉 BOM、仍写成 UTF-16LE，第二次才是 UTF-8——所以说「第一次写完
  多半仍是 UTF-16、只少了开头的 FF FE，照原样再写一次；连写两次 project.json 仍收到才删掉它再新建，写别的文件时收到的不算次数；
  不用写别的文件试探」。修 UTF-16 要连写两次
  `project.json`，run 进行中时，早先那条「在别处被弄坏」回传末尾的「修好后原样重写刚才那个文件」隔着两段回传，多半被丢掉；
  所以写的正是它、UTF-16、run 进行中这一格，修好之前的最后一条回传提醒「收到触达表之后，把这之前写过、没拿到回传的
  `state.json`、契约或产物各原样重写一次」。

阻断那一档的标题写明按角色生效；首句说「只有 PM 该改它」，不对收件人说「你是唯一改得了它的人」——没有 run 时 H3 对
所有角色放行，收件人可能不是 PM。

### 2.4 正文

- `commands/at.md` §0 那句改对；§1 写完 `current-run` 收到【project.json】先改完阻断与要改再进 S2，「会被拒」只挂在
  阻断上；说 `project.json` 读不出来时先改好再写契约。§2「没收到就停下」之前先排除 `project.json` 读不出来这一种，
  原样重写契约拿回传，第 1 节逐字不动。
- `commands/at-init.md` §1：第一步单独一条消息读用户项目里的旧 `project.json`；读到了就是重跑，重跑不读模板（旧文件不是
  合法 JSON 也一样），以旧文件为底改，描述旧文件只能照这次读到的说。§2：首跑才照模板骨架写；早退放行在执行角色里只对
  `at-qa`、`at-acceptance`（`at-pm` 另行放行）；其余会被派到的角色都要有键，`[]` 是「只写 run 目录」的正式写法；前缀留在
  项目里、按字面比较、可以是单个文件；出根的删掉，不要换成项目里的同名目录；重跑时缺键的角色逐个判。§3：先处理
  【project.json】，三档怎么处理，阻断按角色生效；【插件】改 `project.json` 修不好，停下让用户重装。§4：请确认的留下了
  哪几条；重跑时说和旧文件比改了哪些键。§3 的结构：【插件】单成一段排在最前（先停下、不写 `reach.json`、让用户重装后重跑），
  它不挂在「里面要是有【project.json】」底下——只有花名册坏时回传里没有【project.json】；【触达表】说这次不发时照做，连这一段
  都没收到才判门禁没在跑。
- `commands/at.md` §1 写 `current-run` 时也处理【插件】（at 流程第一次收到它就在这里）。
- `commands/at-resume.md` §3：【project.json】里的阻断算「报了问题」；【插件】是例外。
- README 两半的已知边界：写路径隔离管项目经理以外的各个角色，没有条目在 run 目录之外哪都写不了，`at-qa` 与
  `at-acceptance` 是例外。

**设计评审**（三个角度：语义、绕过、判据与正文；每条反对意见配一位反驳者）。采纳的修订：写坏的 JSON 原稿一声不吭——
加了写坏回传；原稿把所有阻断判成全队阻断——改成只拒持有问题条目的角色，整份级才拒全员；原稿按字面形状分档——改成按
解析后的落点；原稿的两条警告互斥、又要求「改到没有为止」，只写 run 目录的角色怎么配都有警告——拆出「请确认」一档，`[]`
定为正式写法；原稿只在写 `project.json` 时报——加了写 `current-run`、写 `state.json` 两个时机；`at-qa`、`at-acceptance` 的
无键放行提到最前，它们的正文不变假；正文、README、`docs/11` 里会随之变假的句子列全。

## 4. 兼容性：升级之后会变的

- 花名册里的角色在 `paths` 里没有键（早期模板没有它、被删、拼错、带插件前缀）：此前 run 目录外全放行，现在全拒，
  直到 PM 给它建键或写 `[]`。ledger 在写 `project.json`、每趟 run 写 `current-run` 时报出来。
- 前缀是 `.`、`./`、`''`（认领整个项目根）、`../x/`（出根）、或者带冒号：此前照认领，现在这个角色整条条目作废——
  连它其余合法的前缀也写不了，直到 PM 改掉。run 跨升级、中途续跑时，由写 `state.json` 的回传报阻断。
- run 进行中 `project.json` 被删、`paths` 缺失或不是对象：此前全放行，现在拒 `at-qa`、`at-acceptance` 以外的执行角色。
- 给 `at-pm` 建的键：此前与现在都不起作用，现在会报「要改」。
- 「没人认领」的拒绝理由：不再叫执行角色自己改 `project.json`，改成冒泡。
- 仓库没有 CHANGELOG；这一节就是发布说明，合并说明里照抄要点。

## 5. 仍然开着的边界

- **没有键的 `at-qa`、`at-acceptance` 在 run 目录之外哪都能写**，包括 `CLAUDE.md`、`.claude/`、项目根之外（审查第 34 条）。
  本条把范围缩到了这两个角色：其余花名册角色没有键时被拒。
- **显式认领 `.claude/`、`.git/`、项目根下的 `CLAUDE.md` 只提醒、不拒**；子目录里的 `CLAUDE.md` 是任何目录前缀都带着的
  风险。门禁层面对所有角色拒写这些路径归第 34 条。
- **被认领的前缀若是项目里一个指向项目外的链接**（junction、软链），持有者经它写、或直接写链接目标都放行：H3 按物理位置
  比较（`docs/25`），`validateProject` 不碰文件系统，报不出来。建链接要 Bash。
- **根级共享文件与 `tests/` 默认没人认领**（审查第 21 条）：修法 2（拒绝文案的出路）这一轮顺手做了，修法 1、3 仍开着。
- **`project.json` 解析不出仍判成读不出运行上下文**：H2、H5 这时按读不出放行，H3、H4 拒。ledger 现在会说出来，但门禁
  的降级本身没改；把解析失败改交 H3 单独阻断，是一条可以做的后续。
- **`at-resume` 可能在写任何 `.agent-team` 文件之前就派发**：`project.json` 坏着时，这一步没有回传，执行角色被 H3 拒，
  理由里带着 runctx 读 `project.json` 失败的原因。
- **`quote` 不转义格式字符与双向控制符**：键名里的零宽字符、同形字照原样回显。前缀里的已由「要改」写出码点；键名的
  由「不是花名册里的角色名」报出，实测模型读得出差别。改 `quote` 牵动所有回显点，没有在这里做。
- **at-init 重跑不读模板靠正文**：累计 26 次里 6 次读了模板（没有错描；读了的会话里有的收尾自称没读，所以 §4 不要求 PM 汇报
  读没读模板）；判据钉得住正文，钉不住行为。
- **UTF-16 的出路依赖 CLI 的 Write 行为**：「第一次写完多半仍是 UTF-16」是 2.1.283 上的实测，Write 的编码处理一变，这句就要改。
- **开头有较多非 ASCII 字符的 UTF-16 文件判不出来**：按 UTF-8 解码时字节会并成一个字符、奇偶错开，落回泛说的口径（里面也提到
  「文件不是 UTF-8 编码」），方向安全。模板与 at-init 写出来的文件开头是 ASCII，触发面小。要修得按字节信 BOM。
- **`reach.json` 是最近一次落盘时的快照**：`/agent-team:at-status` 不核它与当前 `project.json` 是否一致——手改 `project.json`、
  at-init 在阻断或【插件】处停下，都会让它落后；PM 还会把旧的 `reach.json` 当成「上一版配置」的证据引用。归全量审查第 28 条。

> **收口（M4f，2026-10-05，`docs/41`）**：「没有键的 `at-qa`、`at-acceptance` 在 run 目录之外哪都能写」收口——现在一律拒（审查第 34 条）。
> 收的是 Edit/Write 那一路：`at-qa` 用 `Bash` 写照旧拦不到，挡它的是红线。
