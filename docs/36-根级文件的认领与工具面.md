# 根级文件的认领与工具面

**日期** 2026-10-04 ｜ **口径** 分支 `m4b-shared-paths-and-tools`（`391afca` 与其后的复核修订），版本 `2.0.0`；修的是全量审查
（`docs/24-附录-全量审查报告.md`）第 21 条修法 1 的改形、第 29 条，顺带第 22 条的一点（插件 `settings.json` 的 `agent` 写全名）。
排在这里的依据是 `docs/24` §5 那条 2026-10-01 的核验更新。探针与真实会话在本机 CLI 2.1.286 上，另有一臂在 2.1.278。

## 0. 一句话结论

根级清单、构建配置、顶层测试目录原来在模板配置下没人认领，执行角色写 `tsconfig.json`、`tests/` 被写路径隔离拒，正文又没有一步回头补认领。
现在不加 `shared` 键，改成四步：S0 由模板与 at-init 先列上，S3 的架构方案带「落盘清单」，S4 照清单逐行补进 `paths`（已经归别人的也共列），
S5 被拒的在实现记录里留一节「被写路径隔离拒绝」、补完标「已解决」才算交齐。工具面：十个团队角色加 `Grep`，`at-product`、`at-architect`
加 `Edit`。实测推翻了仓库里一条老结论：主线程（`at-pm`）的 `tools:` 只封顶派发宇宙与主会话自己，不封顶子代理的工具。另一条实测：插件
`settings.json` 写裸名 `at-pm` 时，项目里一份同名的 `at-pm.md` 会抢走主会话，改成全名 `agent-team:at-pm`。

## 1. 问题

**第 21 条（修法 1）。** 照模板写的 `project.json`，执行角色写 `package.json`、`package-lock.json`、`tsconfig.json`、`vite.config.ts`、
`.env.example`、`tests/…` 一律被 H3 拒（理由「没有被任何角色认领」）；只划给一个角色时，另一个角色拿到「这条路径归 "at-backend"」，
还要再冒泡一轮。真实 run 里撞上过：`docs/14` 那一趟 PM 为躲开它把后端从 TS 改成 JS、整段回退到 S3；`docs/15` §10.4 那一趟 PM 在 S4 前后
自己只给 `at-backend` 补了 `package.json`。根子在时机：`paths` 在 S0 定、目录布局在 S3 定，`/agent-team:at` 在两者之间没有一步回头对齐。
修法 2（拒绝文案改成冒泡给 PM）M3u 已经做了。修法 3（执行角色为新行为补自动化测试）没做，见 §2.10。

**第 29 条。** 没有任何角色有 `Grep`：`at-architect`、`at-product`、`at-acceptance` 不持 `Bash`，只能按文件名找内容。写文档的角色没有
`Edit`，只能整份重写。`at-pm` 的 `tools:` 让装了插件的项目里主会话拿不到 MCP 与网页工具，README 却写「普通会话能做的它都能做」。

**实测带出来的两件（§4）。** 一是 P4：子代理的工具不受主线程 `tools:` 封顶，仓库里「`at-pm` 那一行是整个会话（含子代理）的能力天花板」
在工具这一维不成立，只在派发宇宙这一维成立。二是 P8：插件 `settings.json` 的 `agent` 写裸名时，项目里放一份 `.claude/agents/at-pm.md`
就能当上主会话；门禁按剥掉前缀的名字认 PM，冒名者还会拿到控制文件的写权。

## 2. 修法

### 2.1 不加 `shared` 键

审查原文的修法 1 是在 `project.json` 加一个 `shared` 配置，H3 对它放行执行角色。按 `docs/16` §3 付三样：

- **拒绝的判据长什么样**：模板加 `"shared": ["package.json", "tests/"]`，H3 对 S5 的产者放行 shared 前缀。
- **它打不红的那一刀**：前缀按字面比较、单文件精确匹配；从空目录起的项目在 S0 时 `vite.config.ts`、`Podfile` 之类还不存在，布局在 S3
  才定——加了 `shared`，S4 漏补一份配置照样撞「没人认领」。不管加不加新键，S3 与 S5 之间那一步「照布局补认领」都省不掉。`shared` 只省掉
  「同一份清单在几个角色下各写一遍」，而今天同一前缀列给几个角色门禁就全放行、`validateProject` 零报告（模板的 `src/shared/` 就是这样写的）。
  审查原文的「放行 `04-dispatch.md` 里被分配到的执行角色」在 S5 当段做不到：`04-dispatch.md` 是自由文本，`stage_roles` 推进出那一段才记。
- **什么会让答案改变**：前缀支持了通配；真实 run 里共列的几份清单反复漂移（一边加了、另一边忘了），撞「归 X」的往返比补认领更多；
  H3 的 matcher 扩到 `Bash`。
- 代价：`shared` 要动 `project.mjs`（新形状档、`[]` 的语义、设计类角色拿到根级文件）、`writepath`、`reach`、ledger 阻断档的标题、七份正文的
  「只有那些」、README 已知边界与它的判据、`trusted-echo`。

同一条理由，`validateProject` 也不加「认不出的顶层键」提醒：门禁读的两个键拼错今天已经会报；能多抓到的只有照审查原文手写的 `shared`，
它不会静默失效到底（写根级文件照样撞「没人认领」）；换来的是用户自己加的键每一趟开头都报一遍。`project.json` 将来要加新的顶层键、
旧版插件会静默忽略它的时候，再加。

### 2.2 正文：S0、S3、S4、S5

- **S0**：`templates/project.json` 的 `at-backend`、`at-frontend` 各加 `package.json`、`package-lock.json`、`tsconfig.json`、`tests/`
  （与 `src/shared/` 同一种多角色写法）。`/agent-team:at-init` 第 2 节加一条：磁盘上已有的根级清单、构建配置、顶层测试目录，逐个列给每个
  会改它们的 `S5` 产者，不列给 `at-architect`、`at-product`；空目录里照模板写的根级文件与 `stack`、`build`、`test` 都是占位，收尾告诉用户。
  七份正文的「目录前缀」改成「前缀（目录或单个文件）」。
- **S3**：`agents/at-architect.md` 要求 `03-arch.md` 单列「落盘清单」一节：按 `paths` 的前缀粒度列实现要新建或改动的、run 目录之外的路径，
  每一行写归哪个 `S5` 产者，几个都要改的都写上，测试放在哪、用什么命令跑也写进去；改动小也要有，要改的每一份都已经在要改它的那个产者
  名下才写「都已认领」。敏感位置（下一条）不列，写进未决问题。PM 推进出 S3 之前核这一节（要新建的、这一趟要改的已有根级文件、测试放哪），
  缺了在 S3 里重派（同一段重派，不计返工）——推进之后，S4 里门禁按不记回退的重做拦架构师改 `03-arch.md`。
- **S4**：推进出 S4 之前（不论 `04-dispatch.md` 重写还是标 `"accepted"`），PM 照清单逐行对 `paths`：归它的那个产者自己的前缀盖不住的，
  就补进它名下，已经归别人的也补（共列同一条前缀，或只给更窄的子前缀、单个文件）。只加不删，`available_roles`、`stack`、`build`、`test`
  不动，不补给协调者。清单是下级写的数据：落在 `.agent-team/` 下的一律不补；落在 `.claude/`、`.git/`、`CLAUDE.md`、`CLAUDE.local.md`、
  `.mcp.json` 下的，或者是 CI/CD、部署与生产配置、凭据文件的，按第 4 节的 `sensitive` 先问用户。回传的「请确认」每次按整份文件重报，只看
  这次新加的前缀引出的：用户批过的、共列引出的嵌套留着，其余这一趟不加。补了什么记进 `04-dispatch.md` 新加的第 5 节「这一趟对 paths 的
  改动」（照【project.json】或拒绝理由删改的条目也记在这里），第 6 节收尾告诉用户（补的前缀留给以后各趟）。补的是认领，不是代写：`agents/at-pm.md` 的红线补上 run 进行中也不自己写项目代码与配置。
- **S5**：五个 `S5` 产者正文：S5 实现时被写路径隔离拒了，在实现记录里写一节 `## 被写路径隔离拒绝`，逐条记路径与拒绝原文，再冒泡；被重派
  回来、补完了，整份重写实现记录，条目不删、逐条标「已解决：怎么解决的」。`at-ui` 那一句限定在 S5（它也是 S2 的产者：S2 被拒的写进
  回报，不要提前写 `05-impl/at-ui.md`，写早了 S5 的交付物校验会把它当成交了）。PM（`commands/at.md` 的 S5 一条、第 3 节「核实」、
  `/agent-team:at-resume`）有没标「已解决」的条目就不推进，逐条看拒绝理由：没照方案布局写的让它照方案改；「没人认领」或者清单上也归它的
  补 `paths`（共列）；清单上不归它的交给架构师——该由认领者做的改派认领者（认领者不在班底里的，叫它进来或者共列），被拒的角色也该改的，
  架构师先在 S5 里把它补进落盘清单再冒泡，PM 照清单补（两边同一个判据）；没有键、条目作废这类配置问题先修 `project.json`；改的是别人的
  阶段产物的，按产者在 S5 有没有活分（`03-*` 交给架构师，`at-ui` 的 `02-*` 由架构师派它改；`01-prd.md` 是改设计，照回退走）；用户不批或决定不补的改写到别处或不做（契约要求的不能 PM 定，问用户；不要求的记进 `04-dispatch.md` 第 3 节，交付文档与
  汇报都写）；然后在 S5 里重派架构师（不计返工）。
  推进之后才发现的，先记回到 S5 的回退，再补、再重派。架构师改派认领者之后，要让被拒的角色把那一条标「已解决：改由 X 做」。
  `at-qa` 开工前自查把有没解决条目的实现记录算成没交齐，没开跑也写进 `06-test.md`（固定首行「结论：没开跑——S5 没交齐」）；PM、续跑与
  续跑见到它先核实现记录，确实没交齐才回 S5、不回 S6；都交齐了的，在 S6 是 S5 补齐之前的旧结论（返工轮里续跑会读到），在 S6 里重派
  `at-qa`，在 S7 是 `at-qa` 这一轮判错了，回 S6。验收把 `at-qa` 报的根因写进回报与 `07-acceptance.md`，回哪一段由 PM 核过再定。架构师派要改同一份文件的执行角色时串行派、不放到后台，`subagent_type` 写全名。
- **写文件用 `Write`、`Edit`，不用 `Bash`**：五个 `S5` 产者与 `at-qa`（它没有 `Edit`，只说 `Write`）的「你有 `Bash`」一节补上。真实会话里
  执行角色用 heredoc 写了全部代码与实现记录（§4 L1、L3），写路径隔离与账本都看不见那些写入，被拒那条路也就不会出现。加依赖先 `Edit` 清单、
  再不带包名照清单装（`npm i <包>` 会绕开清单的认领）；脚手架只在自己的前缀里跑；`at-qa` 只照现有清单装。

### 2.3 H3 的拒绝理由

`hooks/lib/writepath.mjs`：「这条路径归 X」列全认领者（只认 H3 会判人的键），每个各带引号；出路按调用者分——叶子执行角色要几个角色一起改的，
冒泡、由 PM 在 `paths` 里共列；协调者拿「这是认领者的活：到你分发它的那一段再派给 X（还在出方案的写进落盘清单）」，点名的认领者排除了
按设计不该有键、条目作废的（调用者自己派不到的那一个，靠紧跟着的「派不到的，冒泡」兜住，不按 `can_delegate_to` 再筛）；认领者按设计不该有键（`at-qa`、`at-acceptance`、`at-outsider`）或者它的条目整条作废，点明并叫 PM 改配置，不叫协调者去派它；
花名册里调用者那一条坏了，不给「列到你名下」。「没人认领」那一支把调用者自己的认领清单逐条引（整份只过一次 `quote` 会被截在 80 个
字符，截掉的正是之后补进来的）；两支都一并说出调用者自己条目里「要改」档的前缀（不可见格式字符写出码点）。调用者是建了键的 `at-qa`、
`at-acceptance` 时不走这两支：第 7b 步让它写自己合法的前缀照旧放行，别的一律说「这次写入不是你的活，键不该有、由 PM 删掉」——不说
删了就能写（删了它确实在 run 目录之外整段放行，对正想写别人代码的它说这句等于教它绕过去）。

### 2.4 执行段「齐了」时门禁提醒先读被拒那一节

`hooks/lib/stages.mjs` 新加 `isRolePatternStage`（`produces` 是 `<role>` 模式的段，插件自带的链里是 S5；按形状认，不写死段号）。
ledger 的【阶段】「齐了」与 H5a 对协调者说的「当前阶段的产物已经全部齐备」，在执行段末尾固定加一句（`hooks/lib/ledger.mjs` 的
`IMPL_RECORD_NOTE`）：先逐份读实现记录，有没标「已解决」的条目那一份不算交齐。门禁不读那一节写了什么；旧 run 与返工轮里这两句会催 PM
推进，三处正文各有漏口，这一句一处盖住。【阶段】也会发给 PM 以外的写者，按写者分三档：PM 拿上面那句；这一段的产者（`stages.json`
这一段的 `role` 与 `producers`，写的是自己的实现记录）拿它自己的一句（自己那一份里还有没解决的条目，照实回报，不要只报「齐了」）；其余
非 PM 写者（S5 里改 `03-arch.md` 的架构师、提前被派来写 `06-test.md` 的 `at-qa`）拿一句不预设「你自己的实现记录」的。非 PM 回报给上级的
都是「都在磁盘上了」而不是「齐了」。PM 与否的谓词与 H3 同一个 `isContractWriter`。H5a 对
非协调者那一支（例：旧 run 的 S5 已经齐了，PM 先派了 `at-qa`）在 PM 收件、执行段已经齐了时也带这一句。

### 2.5 工具面

- `Grep` 给除 `at-outsider`（派不起来的测试替身）之外的十个团队角色。只读，不经任何门禁。
- `Edit` 给 `at-product`、`at-architect`（写文档、不在验证段）。`at-qa`、`at-acceptance` 不给：它们是验证段（`verifies`）的产者，返工时产物
  要整份重出，不给 `Edit` 让「在上一轮那份末尾补一句」从一次小编辑变回整份重写。这是**摩擦，不是屏障**：`Write` 读一遍再整份写回照样做得到，
  持 `Bash` 的 `at-qa` 一行 `>>` 也做得到；门禁只按 sha 判新旧，「只补一句」最终靠正文。主会话角色（S8 的产者）要用 `Edit` 追加契约修订块、
  改 `state.json`，豁免。判据（`tests/tool-surface.test.mjs`）：验证段的产者（主会话角色从 `settings.json` 剥前缀取）不持 `Edit`，正文写明
  「没有 `Edit`」与「整份」。`docs/11` §5.14 原来的理由「没有 `Edit` 就改不了已存在的实现文件，挡得住」不成立，收口写在它原话的标题底下。
- ledger 与 H4 在 `Edit` 路径上补判据（`tests/gate-edit-path.test.mjs`）：今天让它们只认 `Write` 整套照绿，而 ledger 的 `Edit` 路径今天就在用
  （PM 用 `Edit` 追加契约修订块；执行角色 `Edit` 自己的实现记录）。ledger 的 `NotebookEdit` 分支一并钉住。

### 2.6 订正「天花板」

P4 之后：主线程的 `tools:` 封顶两样——整个会话的派发宇宙（`Agent(...)` 类型表，U4，照旧成立）与主会话自己的工具面；每个子代理拿自己
`tools:` 里的工具。引作证据的「`… is disabled for this session, in subagents as well as here`」是一句固定文案（2.1.286 源码读法：调用方
清单里没有、内建工具目录里有的工具一律报它），`docs/15` §3.7 在 2.1.278 上的阴性对照早是反证。禁授三样（`Skill`、`SendMessage`、`ListAgents`）
因此靠每一份自己的 `tools:` 行：`tests/tool-surface.test.mjs` 的逐份禁授判据、「每份都解得出至少一个工具名」那条前置（没写 `tools:` 的角色按
官方文档继承全部工具，P5 没跑）、逐份期望值 `EXPECTED_TOOLS`。插件会加载的注释（`gate.mjs`、`ledger.mjs`、`artifact-drift.mjs`）与判据的
注释、失败文案就地改；规格与设计追加订正段；带日期的记录在原话标题底下写订正（§8）。

### 2.7 README

两半的 at-pm 那一段：工具面补 `Grep`；「普通会话能做的它都能做」拆成两面——能改动的范围与普通会话相当；它拿不到普通会话里的 MCP 工具与
网页搜索、抓取（WebSearch、WebFetch），其余角色也只拿自己清单里的工具。名字不加反引号（加了会被算进 at-pm 的工具面）。判据
（`tests/readme-sync.test.mjs`）按 MCP、网页两组**双向**判：「它拿不到」那句在不在，要等于 at-pm 的 `tools:` 里有没有这些工具；否定词要在
名字前面、同一小句里（按括号外的逗号切）。「团队里其余角色也拿不到」那半句在不在，要等于其余团队角色（测试替身除外）有没有谁持 MCP 或
网页工具，失败文案点名是谁——给某个叶子角色加网页工具（§2.10 推荐的方向）时，只改这半句，at-pm 那句真话不用删。「这不是沙箱」那段补一句：项目经理在实现之前（实现中有角色被拒时也会）照架构方案往 `paths` 里补前缀。
「也不要用 `--agent`、或在你自己的设置里设 `agent` 键，把主会话换成别的角色」两半同改。开发一节补「任何一位不长到 10」。

### 2.8 身份：`settings.json` 的 `agent` 写全名

插件 `settings.json` 改成 `{"agent": "agent-team:at-pm"}`。平台按名字找 agent 时先找完全同名、再找「:名字」后缀（2.1.286 源码；`--agent`
与 `agent` 键走同一个函数）；markdown agent 的名字不许含冒号（「names must not contain ":" (reserved for plugin namespacing)」），写全名就
没有谁撞得上。判据（`tests/plugin-name-sync.test.mjs`）从 `PLUGIN_PREFIX` 派生，不写字面量：全名找不到时平台只告警、退回默认主会话，

## 5. 仍然开着的边界

- **`Bash` 写文件**：执行角色用 `Bash` 写的东西写路径隔离与账本都看不见（L1、L3 两场都这样）。正文补了「写文件用 `Write`、`Edit`」，门禁不看
  `Bash`；越界的 `Bash` 写入照旧只靠正文。装依赖同理：`npm i <包>` 这类命令直接改清单，正文要求先 `Edit` 清单、再不带包名装。
- **PM 自己写根级文件**：H3 第 1 步对 PM 放行，账本只管 run 目录；红线写明 run 进行中不代写，门禁不拦。
- **`reach.json` 每补一次 `paths` 都要手抄一次**（审查第 28 条：写完没有任何校验）。S4、S5 补认领让这件事从 S0 一次变成每趟可能几次。
- **执行段「齐了」的提醒只是一句话**：门禁不读实现记录写了什么；实现记录里那一节写成「无」、或者写了却没标的，门禁都放行。
- **共列的根级文件互相覆盖**：两个执行角色都改 `package.json`，后写的整份覆盖前写的，门禁放行、不留痕。架构师正文写了要改同一份文件的串行派、不放到后台。
- **「没开跑」只靠首行的约定**：门禁把写着没开跑的 `06-test.md` 当成交了；PM、续跑与验收认的是 `at-qa` 写的固定首行，回不回 S5 靠 PM 逐份
  核实现记录（门禁不读内容，回退方向上 H6 不拦）。
- **S2 里 `at-ui` 被拒拿到的是给 S5 的出路**：H3 不知道当前段（`decideWritePath` 不收 `state`），叶子执行角色一律拿「由 PM 列到你名下」；
  `at-ui`、`at-product` 的正文写明 S2 不补 `paths`。
- **`/agent-team:at-status` 对没解决的实现记录照打 ✓**：它只报磁盘上在不在（§3.1 驳回的那一条）。
- **`at-qa` 写测试拦不住**：没有 `paths` 键的 `at-qa`、`at-acceptance` 在 run 目录之外整段放行（审查第 34 条）。
