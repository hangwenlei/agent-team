# M0 结论

> 依据：`docs/04-本机实测结论.md` §7（M0 · U3 派发门禁实测）与 §8（M0 · U1/U2/U4 主线程身份与白名单实测）。规格 §10 列了六条未知，本文件只回答 U1–U4——这四条是 M0 的范围。U5（`SubagentStop` exit 2 是否卡死角色）与 U6（十角色真实成本）刻意推迟到 M1，本文件不作答，状态维持 `未测`。下面每条未知的「原文观测」逐字摘自 `docs/04`，不做节选或改写；与该文件冲突时以 `docs/04` 为准。

## U1 · `agent` 键是否接受插件命名空间 id

**怎么测的**（docs/04 §8）

插件经 `claude plugin enable agent-team@skills-dir` 启用（注意：不带
`@skills-dir` 会报 `Plugin "agent-team" not found in any editable settings scope`）；
每轮在桌面客户端新开会话；角色定义在会话启动时加载，所以改了 frontmatter 必须新开会话。

**原文观测**（docs/04 §8 第一轮）

**第一轮 · U1，`settings.json` 为 `{"agent":"at-pm"}`（裸名）**

新开会话发 `ping`，回复：

    AT-PM pong ✅
    M0 占位版已就绪，待命中。

**结论：是**

- **U1 = 是。** `settings.json` 的 `agent` 键接受**裸名** `at-pm`。注意这与 `subagent_type`
  相反（后者必须全限定名）。

——docs/04 §8 结论（原文是同一份列表里的第一条 bullet）

忠实性说明：规格 §10 里 U1 原本问的是「`agent` 键是否接受插件命名空间 id」（即 `agent-team:at-pm` 这种全限定写法）。M0 实际验证、也是唯一有实际意义要验的形态是裸名 `at-pm`——插件自己的 `settings.json` 只会引用自己的 agent，没有理由写全限定名。命名空间形式本身没有单独测过；但裸名已确认可行，原问题关心的风险（「如果不接受，需换写法」）不成立，不需要再补测命名空间形式。

**对设计的影响**

插件根 `settings.json` 按规格 §7 目录树原定写法 `{"agent": "at-pm"}` 维持不变，不需要为命名空间形式做任何调整；`agent` 键这一环不构成 M1 的阻塞项。

## U2 · 插件提供的 agent 能否被主线程白名单按裸名引用

**怎么测的**（docs/04 §8，与 U1 同一批实测）

插件经 `claude plugin enable agent-team@skills-dir` 启用（注意：不带
`@skills-dir` 会报 `Plugin "agent-team" not found in any editable settings scope`）；
每轮在桌面客户端新开会话；角色定义在会话启动时加载，所以改了 frontmatter 必须新开会话。

**原文观测**（docs/04 §8 第二、三轮）

**第二轮 · U2，`at-pm.md` 白名单当时是裸名 `Agent(at-product, at-architect)`**

    派 agent-team:at-product  → Agent type 'agent-team:at-product' not found. Available agents: none
    派 agent-team:at-outsider → 角色 at-pm 不得派发给 at-outsider。它可以派发的角色是：at-product、at-architect。如果这项工作确实需要 at-outsider，把它冒泡给上级，不要绕过花名册。

**第三轮 · U2-B，白名单改成全限定名之后**

    派 agent-team:at-product  → AT-PRODUCT
                                PRODUCT-OK
    派 agent-team:at-outsider → 角色 at-pm 不得派发给 at-outsider。它可以派发的角色是：at-product、at-architect。如果这项工作确实需要 at-outsider，把它冒泡给上级，不要绕过花名册。

**结论：是**

- **U2 = 是，白名单硬有效，但语义不是「PM 能派谁」。** 第二轮的 `Available agents: none`
  是因为白名单写裸名、注册名带前缀，交集为空。改全限定名后第三轮通过。
- **主线程白名单过滤的是整个会话的 agent 宇宙，且被所有子孙代理继承。** 第四轮是决定性
  证据：架构师看到的 `Available agents` 恰好等于 `at-pm` 的白名单，而架构师自己的
  frontmatter 是没有括号列表的光秃秃 `tools: Agent, Read, Glob`。**推论**：`at-pm` 的
  白名单必须列出团队全部角色，否则架构师够不到执行角色；层级约束只能由 hook 花名册承担。

——docs/04 §8 结论（同一份列表里的第二、三条 bullet；第四轮的决定性证据见下面 U4 节）

**对设计的影响**

`at-pm.md` 的 `tools: Agent(...)` 白名单必须写全限定名（`agent-team:at-xxx`），且必须覆盖团队全部角色，不能只列 PM 的两个直属下级——否则技术架构师、产品经理这些二层角色够不到它们该带的执行角色。这条发现直接推翻了规格初稿「PM 白名单硬、下面的边软」的模型，规格 §3.3 已整节重写为「主线程白名单是『宇宙』，不是『边』」，结论是层级约束全部移交 hook 花名册（H1）承担。

## U3 · hook 在 Windows 下能否稳定拿到 `agent_type` 并 deny

**怎么测的**（docs/04 §7）

插件经 junction 挂载为 `agent-team@skills-dir`；`claude plugin details agent-team`
确认 6 个 agent 与 1 个 PreToolUse hook 已注册（排除「插件没加载」这个假阴性来源）；
然后在 Claude 桌面客户端新开会话，工作目录选本仓库，逐轮派发观测。

**原文观测**（docs/04 §7 三轮）

**第一轮 · 裸名**

派发 `subagent_type = "at-architect"`（裸名，主线程）：

    Agent type 'at-architect' not found. Available agents: agent-team:at-architect, agent-team:at-outsider, agent-team:at-pm, agent-team:at-product, agent-team:at-worker-a, agent-team:at-worker-b, claude, claude-code-guide, code-simplifier:code-simplifier, Explore, general-purpose, Plan, statusline-setup

派发 `subagent_type = "at-outsider"`（裸名，主线程）：

    角色 __main__ 不得派发给 at-outsider。它可以派发的角色是：at-product、at-architect。如果这项工作确实需要 at-outsider，把它冒泡给上级，不要绕过花名册。

**第二轮 · 全限定名**

派发 `subagent_type = "agent-team:at-architect"`（主线程）：

    角色 __main__ 不得派发给 agent-team:at-architect。它可以派发的角色是：at-product、at-architect。如果这项工作确实需要 agent-team:at-architect，把它冒泡给上级，不要绕过花名册。

**第三轮 · 前缀归一化修复之后**

    架构师是否启动 = 是
    架构师派 worker-a = A-OK
    架构师派 outsider = 角色 at-architect 不得派发给 at-outsider。它可以派发的角色是：at-worker-a、at-worker-b。如果这项工作确实需要 at-outsider，把它冒泡给上级，不要绕过花名册。

**结论：是**

- **U3 = 是**。拒绝理由是 `gate.mjs` 自写的中文原文，证明 Windows 下 hook 被调起、拿到输入、
  deny 输出被平台接受。规格 §6 五个 hook 的地基成立。
- 主线程 hook 输入**不带** `agent_type`（caller 为 `__main__`）。
- **hook 先于平台的名称解析生效**——第一轮裸名那次 hook 放行了，之后才撞上 not found。
- 插件 agent 的注册名带插件前缀（`agent-team:at-xxx`），裸名不解析。
- allow 与 deny 两条路径在**主线程**与 **subagent** 两层均已实证；拒绝消息里列出的可派发集合
  随调用者变化（主线程列 at-product/at-architect，架构师列 at-worker-a/at-worker-b），
  说明花名册按调用者查而非硬编码一份。

——docs/04 §7 结论

**遗留**（docs/04 §7 原文，已在 U2/U4 实测中解决）

`agent_type` 的原始形态**未观测到**——因为拼拒绝理由之前 caller 已被归一化，
消息里永远显示裸名。归一化对裸名与全限定名两种形态等价，所以不影响正确性；但 `roster.json`
里 `__main__` 与 `at-pm` 双键能否合并，要等 Task 4 钉主会话身份时才能判定。

后续判定见本文「五个平台事实」次要事实一条：`__main__` 与 `at-pm` 两个键都要保留，不能合并。

**对设计的影响**

规格 §6 五个 hook 的共同地基成立。但 U3 同时撞出一个死结：插件角色裸名派发过得了 hook 却被平台名称解析拒绝，全限定名过得了名称解析却被花名册（裸名书写）拒绝——两种写法都进不去，门禁对插件角色实际是「一律拒绝」。修复是在 `hooks/lib/decide.mjs` 里新增 `stripPluginPrefix`，只剥本插件自己的 `agent-team:` 前缀，不改花名册的裸名书写方式。此修复已写入规格 §6.0 第 4 条「命名空间归一化」。

## U4 · subagent 能否在一条消息内并发 spawn 多个 subagent

**怎么测的**（docs/04 §8，与 U1/U2 同一批实测）

插件经 `claude plugin enable agent-team@skills-dir` 启用（注意：不带
`@skills-dir` 会报 `Plugin "agent-team" not found in any editable settings scope`）；
每轮在桌面客户端新开会话；角色定义在会话启动时加载，所以改了 frontmatter 必须新开会话。

**原文观测**（docs/04 §8 第四轮）

**第四轮 · U4 并发派发，白名单当时仍是两个角色**

派 `agent-team:at-architect`，要求它在一条消息里并发派两个 worker：

    是否一条消息内并发 = 是（at-architect 明确报告：同一个 function_calls 块里两个 invoke，不是先后两次消息）
    worker-a 返回 = Agent type 'agent-team:at-worker-a' not found. Available agents: agent-team:at-architect, agent-team:at-product
    worker-b 返回 = Agent type 'agent-team:at-worker-b' not found. Available agents: agent-team:at-architect, agent-team:at-product

**结论：是**

- **U4 = 是。** subagent 能在同一个 `function_calls` 块里并发发出多个 Agent 调用。

——docs/04 §8 结论（同一份列表里的第四条 bullet）

同一轮实验同时是 U2「白名单是宇宙不是边」结论的决定性证据（详见上面 U2 节）：架构师两次 spawn 都被拒，且拒绝信息里的 `Available agents` 恰好等于 `at-pm` 自己的白名单，而不是架构师本该带的 `at-worker-a`/`at-worker-b`。这是白名单以「会话宇宙」而非「派发边」方式生效的直接证据。

**对设计的影响**

S3（技术对齐并行拉通）与 S5（实现并行扇出）设计里「架构师在一条消息内并发派发多个执行角色」的前提成立，不需要退化为串行。规格 §3.2.1 的修正（阶段内并行由架构师并发调用 `Agent` 实现，而非 dynamic workflow）在机制上是可行的。

## 五个平台事实（官方文档均无记载）

1. **hook 先于平台的名称解析生效**。裸名派发时 hook 先放行，之后平台才报 `not found`。

   撞出于：U3 第一轮·裸名（docs/04 §7）。主线程裸名派 `at-architect` 先被 hook 放行（花名册认为 `__main__ → at-architect` 合法），随后才被平台报 `Agent type 'at-architect' not found. Available agents: agent-team:at-architect, ...`。同一现象在 U2 收窄白名单那一轮（docs/04 §8 结尾）被独立撞出第二次，原文：
   「⚠️ **诊断陷阱**：角色不在宇宙里时，**hook 先放行**（花名册认为该派发合法），之后平台才报
   `not found`。错误信息指向被派的一方，真正的原因却在 `at-pm.md` 的 `tools:` 行里。」
   ——两次独立实验互证。

2. **插件 agent 的注册名带 `agent-team:` 前缀，裸名不解析**。

   撞出于：U3 第一轮·裸名（docs/04 §7）。上面那条 `not found` 错误信息本身枚举了带前缀的注册名列表（`agent-team:at-architect, agent-team:at-outsider, agent-team:at-pm, ...`），证明平台内部注册表用的是带插件命名空间的全限定名，裸名不在其中。

3. **`plugin disable/enable` 需要全限定名 `agent-team@skills-dir`，否则报 `not found in any editable settings scope`**。

   撞出于：U1/U2/U4 实测的准备阶段（docs/04 §8「怎么测的」），原文：「插件经
   `claude plugin enable agent-team@skills-dir` 启用（注意：不带 `@skills-dir` 会报
   `Plugin "agent-team" not found in any editable settings scope`）」。

4. **四个入口四套命名规则**：`settings.json` 的 `agent` 键吃裸名；`tools: Agent(...)` 白名单要全限定名；派发的 `subagent_type` 要全限定名；hook 输入的 `agent_type` 归一化后是裸名。

   撞出于：跨 U1–U3 三轮实测的综合——`agent` 键裸名见 U1（docs/04 §8 第一轮）；白名单须全限定名见 U2（§8 第二、三轮，`Available agents: none` → 改全限定名后放行）；`subagent_type` 须全限定名见 U3（§7 第一、二轮，裸名与全限定名各撞一次 not found）；`agent_type` 归一化后是裸名见 U3 结论（§7：「主线程 hook 输入不带 `agent_type`」）与 U2 的拒绝理由文本（§8 第二、三轮里「角色 at-pm 不得派发给…」，caller 已是裸名 `at-pm`）。已写入计划 `docs/superpowers/plans/2026-09-15-M0-地基验证.md` 的 Global Constraints 表格。

5. **主线程白名单过滤的是整个会话的 agent 宇宙，且被所有子孙代理继承——它表达不了「谁能派给谁」这条边**。

   撞出于：U4 并发派发实验（docs/04 §8 第四轮）。架构师的 frontmatter 是光秃秃的 `tools: Agent, Read, Glob`（没有括号列表），但它派 `at-worker-a`/`at-worker-b` 双双得到 `Available agents: agent-team:at-architect, agent-team:at-product`——与 `at-pm` 自己的白名单一模一样，而不是架构师本该带的两个 worker。这是本节所有发现里唯一直接推翻规格初稿架构模型（§3.3）的一条。

**次要事实**：被 `agent` 键钉住的主会话**带** `agent_type`（值为 `at-pm`），未钉住的主会话**不带**（按 `__main__` 处理）。

撞出于：对比两次独立实验的拒绝理由文本——未钉住的主会话（U3，docs/04 §7 第一轮）拒绝理由开头是「角色 `__main__` 不得派发给…」；钉住的主会话（U2，docs/04 §8 第二、三轮）拒绝理由开头是「角色 `at-pm` 不得派发给…」。因此 `roster.json` 里 `__main__` 与 `at-pm` 两个键都要保留：钉住走 `at-pm`，未钉住走 `__main__`。

## M1 开工判定

按 task brief Step 3 的判定表逐条对照：

| 若 | 则 |
|---|---|
| U1–U4 全为是 | M1 按规格原样开工 |
| U1 = 否 | 主会话无法钉成 PM。层级最上面一层失效，回 §3 重新选型，**不要开工 M1** |
| U2 = 否 | 上层白名单不硬。M1 的派发约束全部落到 hook，§3.3 要改写，H1 升为唯一防线 |
| U3 = 否 | **五个 hook 的共同地基塌了**。§6 整节作废，必须先找到替代强制手段，不要开工 M1 |
| U4 = 否 | S3/S5 改串行，M1 可开工，但耗时与成本估算要重算 |

实测结果：U1 = 是，U2 = 是，U3 = 是，U4 = 是——命中第一行。**M1 可以开工。**

但「M1 按规格原样开工」这句话本身需要一次澄清：M0 过程中「规格原样」已经不是 M0 启动时的那一版。下面三条前提，是这份「是」判定的具体化，不是额外附加的限制。

### 前提一：M1 基于「改动后」的规格与计划开工，不是原版

M0 期间设计被改动了三处，全部是 U1–U4 实测撞出来的，不是主观重构：

1. **前缀归一化**：`hooks/lib/decide.mjs` 新增 `stripPluginPrefix`，只剥本插件自己的 `agent-team:` 前缀。没有它，U3 撞出的死结（裸名过 hook 但平台 `not found`；全限定名过平台但被花名册拒）会让门禁对插件角色「一律拒绝」。已写入规格 §6.0 第 4 条「命名空间归一化」。
2. **四套命名规则**写入了计划 `docs/superpowers/plans/2026-09-15-M0-地基验证.md` 的 Global Constraints（`agent` 键裸名 / `Agent(...)` 白名单全限定 / `subagent_type` 全限定 / `agent_type` 归一化后裸名）。M1 的计划要延续这张表，不要凭直觉重猜命名形式。
3. **规格 §3.3 整节重写**：原模型「PM 那条白名单是硬的，下面的边是软的」被 U4 推翻。现版本 §3.3 标题已是「主线程白名单是『宇宙』，不是『边』（M0 · U4 实测改写）」，结论是层级约束全部由 hook 花名册承担（见前提二）。

M1 如果只看规格 §1/§2/§4 及以后、不带这三处修订的旧理解开工，会重新踩中 M0 已经踩过的坑。

### 前提二：H1 派发门禁现在是层级的唯一强制手段，不是补充手段

规格 §3.3 原文：「因此 §6 的 H1 派发门禁不是补充手段，而是层级的唯一强制手段。」

原设计假设 `tools: Agent(...)` 能管住「谁能派给谁」，H1 只需要补第二层以下。U4 证明白名单管的是「这个会话里存在哪些 agent」这个宇宙范围问题，管不了边。从 M1 开始，唯一在运行时拦住越权派发的机制是 hook 的花名册（`roster.json` + `decide.mjs`）。

推论：**M1 的第一优先级是把花名册与 H1 做扎实**——五个角色（`at-pm`/`at-product`/`at-architect`/`at-backend`/`at-frontend`）的 `can_delegate_to` 边要完整覆盖组织图（规格 §3.2）、花名册闭包不变量（§6.0 第 3 条）要在这个规模下重新验证、前缀归一化要有回归测试——而不是先铺开写五份角色正文。角色正文写得再好，花名册漏一条边，门禁就形同虚设。

### 前提三：`at-pm` 的白名单必须覆盖全部角色，不能只列直属下级

U2/U4 联合实证：主线程白名单是会话级宇宙，被所有子孙代理继承；子代理能看到的 `Available agents` 恰好等于 `at-pm` 自己的白名单，与子代理自己 frontmatter 里写没写括号列表无关。M0 的占位版已经按这个模式把 `at-pm.md` 的白名单扩到 M0 全部四个可派发角色（`agent-team:at-product, agent-team:at-architect, agent-team:at-worker-a, agent-team:at-worker-b`，由 `tests/roster-sync.test.mjs` 的「宇宙覆盖」测试强制）。

M1 把五个角色搭起来后，`at-pm.md` 的 `tools: Agent(...)` 白名单至少要包含这五个角色里除 `at-pm` 自己之外的全部四个（`at-product`/`at-architect`/`at-backend`/`at-frontend`），不能像规格初稿目录树那样只写 `Agent(at-product, at-architect, at-acceptance)` 这两三个直属下级——否则技术架构师够不到它该带的执行角色 `at-backend`/`at-frontend`。这条「宇宙必须覆盖全体已存在角色」的原则会一路延续到 M2：补满十角色后，`at-pm` 的白名单也要同步扩到全部十个，否则技术架构师够不到它该带的五个执行角色（前端/后端/iOS/Android/测试）。

### 结论

**U1–U4 全为「是」，M1 可以开工**，但开工的前提是上述三条：基于改动后的规格与计划、把 H1 与花名册作为第一优先级做扎实、`at-pm` 白名单覆盖 M1 阶段全部已存在角色并为十角色终态预留同一模式。这不是新增的限制条件，而是 M0 实测结果对「规格原样开工」这句话的具体化。

M0 到此结束。
