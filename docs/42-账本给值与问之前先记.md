## 0. 一句话结论

- **账本比对的两种行都带门禁按磁盘算出来的值**：「没记」与「记账之后被改过」。「没记」那一行还注明门禁知道的写者——派发记录里谁在那一段被派
  出去过，或者是项目经理自己的产物；给 PM 的收尾按注明的分开说，照值记、不自己算、不照着磁盘改账。协调者把下级报上来的 sha 原样转报给 PM。
- **PM 写完 `.agent-team/reach.json`，门禁按当前 `project.json` 与花名册重算核一遍**：对不上、写坏了给出正确的那一份；没有 run
  （`/agent-team:at-init`）与 run 进行中两条路都核。
- **产者交代并上门禁的派发记录**：派发记录里有、只是 `stage_roles`（旧 run 是 `roster`）没记的，单列成「漏记」，出路是看一眼磁盘之后补记，
  不再与真漏派报成同一句。`/agent-team:at` 第 4 条「叫到含下级派出去的那些」与 `at-ui` 那个例子有判据钉着了。
- **问用户之前先记一条 `answer` 为空串的 escalation**，答复之后补上——`/agent-team:at` 第 4 节、门禁的返工预算文字一个口径；
  `/agent-team:at-status` 的「待办升级」与 `/agent-team:at-resume` 认得出问了没答的。
- **用户主动改需求不是升级**：修订块标「用户主动提出」、记新的 `contract_sha`、不记 escalation，要重做的照「回退」；写契约时【契约】的漂移
  那一句、契约的格式与模板跟着分清两种合法修订。
- **`/agent-team:at-status` 的几处报法**：sha 取 `sha256:` 之后的 12 位；当前阶段照分工报（S5 不再报成 `at-backend`）；没走到的段写「未到」；
  S5 的实现记录读内容；引插件里的文件带上 `${CLAUDE_PLUGIN_ROOT}`。

## 1. 修法

### 1.1 第 28 条：sha 怎么记、触达表

- `hooks/lib/artifact-drift.mjs`：`unrecorded` 每一条从名字改成 `{ name, actual }`——`actual` 与 `drifted` 的、【产物】回传、`rework_base` 同一个算法
  （`sha256OfContract`：先剥 BOM、把 CRLF 折成 LF）。
- `hooks/gate.mjs` 的 `buildDriftNotice`：「没记」那一行带「门禁按磁盘算出来是 sha256:…」，并注明门禁知道的写者——派发记录里写它的那个角色在那一段
  被派出去过（「门禁的派发记录里 at-ui 在 S2 被派出去过」），或者它是项目经理自己的产物（写者由 `hooks/lib/stages.mjs` 的 `producerOfName` 认；派发
  记录只拿来判在不在里面，不往文字里拼）；「记账之后被改过」那一行同样说「门禁按磁盘算出来是」。给 PM 的收尾原来是「去 run 目录核实磁盘内容，
  需要的话把 artifacts 改成与磁盘一致」——行里不带值，PM 只好自己算（M5f 里 haiku 版 PM 真的去调了 `Get-FileHash`），带 BOM、CRLF 的产物上造出假
  漂移；照着磁盘改账还会把一次真漂移洗成合法（与契约那一条同一个理由，`docs/37`）。现在按行分：「没记」的，注明了派发记录或项目经理自己的产物的
  照值记，什么都没注明的先弄清是谁写的；「记账之后被改过」的，自己改的、返工与同一段里重派重写的照值改记，说不清的告诉用户，不照着磁盘改账；
  值一律用给的，不自己算。收件人改不了 `state.json` 的那一支（原样冒泡）不变。
- `/agent-team:at` 第 3 节记 `artifacts` 那一句原来说「写完一段产物之后，你会收到一条【产物】回传」——对下级写的不成立，【产物】发给写它的人。改成：
  自己写的收【产物】，下级写的由它在回报里报上来、经协调者的由协调者转报；原样写进去、不自己算；回报里没带的，之后还有派发的由【账本比对】带着值
  报它「没记」，最后一次派发交的（例如验收结论）只能靠回报——派的时候在完成定义里写上回报带 sha。`at-architect`、`at-product` 正文各补一句：下级
  回报里带的 sha 原样转报给 PM。
- `reach.json`：`hooks/lib/ledger.mjs` 新增 `reachCheckNotice`（语义比较：键序、BOM、CRLF 不算不同；给出的那一份经 `safeJson`）；`hooks/gate.mjs` 在 ledger
  的两条路径上接它——run 在时写 `.agent-team/reach.json` 归一类（`kind` 为 `reach`），没有 run 时（`/agent-team:at-init` 的正路）在那条只为
  `project.json` 留的缝旁边另开一条同样理由的缝：触达表的判据只有花名册与 `project.json`，与 run 无关；run 读不出时核了照样往 stderr 留痕。
  `project.json` 不在、有阻断或插件问题（花名册读不出）、`reach.json` 读不出时不核（那时【触达表】本来就叫 PM 先别写，「正确的那一份」也算不准）。
  写的人不是 PM 的（没有 run 时 H3 对谁都放行），那一段叫它原样冒泡、不要自己重写。`/agent-team:at-init` 第 3 节补一句：写完门禁会核，对不上在
  写 `reach.json` 的这一次回传里再给一段【触达表】；这一次没再收到就是对上了（与「写 `project.json` 那一次没收到就停下」分开说）。
- `tests/gate-fail-open.test.mjs` 那条「正路不出声」原来往 `reach.json` 写占位的 `{}`——现在会被核出来，改成写 PM 照抄的那一份。

### 1.2 产者交代并上派发记录

- `hooks/lib/coverage.mjs` 的 `decideCoverage` 多收一个 `dispatched`（`{ 段: [角色] }`，与 H6 判「叫过」同一份；`hooks/lib/advance.mjs` 导出 `dispatchedIn`
  给它与账本比对用）：派发记录里有它在那一段被派出去过的，gap 标 `dispatched: true`；别的段派过不算；读坏的记录按空集算。不选「并进叫到、一声
  不吭」：那样 `stage_roles` 永远记窄，`/agent-team:at-status` 与 `at-qa` 按它展开产物时会漏掉这个人。
- `hooks/gate.mjs` 的产者交代回传：标了的单列一段「漏记」——这不是漏派，门禁记着它在那一段被派出去过，只是没记账；出路是先去磁盘看一眼它那一段的
  产物：在，就补记（PM 并进 `stage_roles` 那一段、`roster` 里没有就一起累加；旧 run 只累加 `roster`），不重派、不写进 `trimmed`；不在（派了没交），
  照真漏派处理。已经收口的，补进 `roster` 时连 `never_invoked` 一起重算。收件人不是 PM 的，说补记是 PM 的动作、带上产物在不在、原样冒泡。
  真漏派那一段照旧，两种同时有时两段都出；「最后一段派不出去」那一支只算真漏派的。
- `/agent-team:at` 第 3 节：第 4 条删掉「今天没有任何判据钉着这一句（`docs/11` §5.24）」，换成门禁记着经过它的派发，记录里有的单列成漏记、没有的

  （`docs/39` §3）。第 3 条「为什么必须是同一次」那一句改成分两次写时漏记与漏派各怎么报，`S2`、`S5` 推进那一次要有这一段的键、推进之后补人照常

## 4. 仍然开着的边界

- **escalations 记没记，门禁不核**：问之前先记、答复之后补，都靠 PM。
- **`reach.json` 只在 PM 写它的那一刻核**：之后被人用 `Bash` 改了、或者 `project.json` 改了却没重写，`/agent-team:at-status` 照旧照它报。
- **不核的几种时候一声不吭**：`project.json` 有阻断或插件问题、`reach.json` 读不出、`project.json` 那一刻读不出（这条缝只读一次）——`/agent-team:at-init`
  那句「这一次没再收到就是对上了」在这几格里说宽了；前两种之前【触达表】已经叫 PM 先别写。
- **当前段的产物在前台派发跑完那一刻不进「没记」**（M4d 剔掉的，免得每次都报刚交的）：它们的值要等下一次派发返回才出现在【账本比对】里，
  这之前靠写它的人在回报里报；最后一次派发交的只能靠回报。
- **「漏记」只认门禁的派发记录，两个方向都会错**：记录读不出、被 `Bash` 删过行或写坏、派发没经过门禁（平台事件丢了）时，被叫过的人照旧与真漏派
  说同一句；记录被 `Bash` 加了一行、或者推进那一刻记录读不出而放过了缺产物的派发，真漏派会落进「漏记」——那一段叫 PM 补记之前先看磁盘，
  就是为这一格。
- **`/agent-team:at-status` 是正文**：没有判据去跑它，报法对不对只能看真实会话（`.handoff` 第 5 项；M8 看了一次，见 §3）。

## 8. 复核与修订

合进 `main` 之前做了一轮对抗复核（2026-10-06）：把新旧两版解到仓库外对照跑门禁子进程（十一组实验：用户主动改需求时的【契约】、reach 核对在各种
`project.json` 与 run 状态下、产者交代的分界、问之前先记那几次写入过不过门禁、各种怪形状不崩）、做了五十四刀变异，十一刀全套不红。门禁那一半
（reach 核对、账本比对带值、产者交代并上派发记录）在各种形状下没有误报、漏报、崩；没有派发记录时输出与 main 逐字相同。问题在新规矩没跟到门禁的
其余文字与几份正文、判据有缺口，逐条：

- **用户主动改需求时【契约】回传叫 PM「补上 escalations 记录」**：写契约那一刻的漂移那一句、契约的格式与模板都还说每次修订都留一条 escalation，与
  第 4 节新写的「不记」正面冲突——照回传记只能错记一类，写成 `answer` 空串则「待办升级」一直挂着、续跑去重问一个从没问过的问题。三处都改（§1.4）。
- **「没记」那一行的收尾盖不住正路上最常见的情形**：下级的下级写的产物（S2 的 `at-ui`、S5 的执行角色）值报给的是协调者，收尾却只认「写它的人回报里
  报过同一个值」——PM 照字面要么为例行记账去问用户、要么一直不记；最后一次派发交的产物之后也不会再有【账本比对】。改成门禁在「没记」的行上注明
  派发记录与项目经理自己的产物、收尾按注明的分开说、协调者转报 sha、`at.md` 不再许诺最后一次派发交的会被报（§1.1）。
- **`at-resume` 还叫 PM 照账本比对的值改账**：「下一次派发时的【账本比对】会给出磁盘上算出来的 sha，照它改」——正是这一轮要堵的照着磁盘改账，
  而换会话之后 PM 最说不清「是谁、什么时候写的」。改成照那一条的收尾做（§1.3）。
- **门禁的返工预算文字没跟上「问之前先记」**：H6 的拒绝理由、【阶段】、【返工预算】共用的那几句还是「先问」「停在这里时记一条」——先问后记在
  `-p`、`--bg` 下停住之后看不见这一问；问之前记了一条、停在这里又记一条，旧那条的 `answer` 永远是空串。照改（§1.3）。
- **`at-resume`「问了没答的」说不全**：照第 4 节重问会再追加一条；门禁已记下批准的那一条与上一段「不用再问」打架。补两句（§1.3）。
- **「漏记」的分界只说对了一半**：派发记录被加了一行、或者推进那一刻读不出而放过了缺产物的派发，真漏派会落进「漏记」并被说成「不用重派」。补「补记
  之前先看磁盘」，§4 两个方向都写上（§1.2）。
- **判据缺口**：花名册读坏时不核、给出的 JSON 经 `safeJson`、run 读不出时留痕、`reach.json` 读不出时不核、「最后一段派不出去」只算真漏派、旧 run 只补
  `roster`、两段同时出、「这不是漏派」那句、返工预算那几条——这十一刀全套不红。钉法见 §2。
- **`at-status`「当前阶段」说宽了**：照「列 `stage_roles` 里这一段记着的人」，S2、S5 进行中几乎总是「本段未记账」，返工轮里是上一轮的人。改成照分工报
  （§1.3）。
- **`at.md` 第 3 节几句旧话**：「那条误报和真漏派长得一模一样」紧挨着新句、「先推进后补记已经写不进去」容易读成漏记的出路会被拒、【阶段】「分两次写
  会被当成漏派」半过时、漏记的理由句放在 PM 亲手派的段上不对题、收口之后补记缺一步。都改了（§1.2）。
- **`at-init`「没有【触达表】就是对上了」与下一条「没收到就停下」挨在一起意思相反**，而且不核的几种时候也一样没有。改成分开说，§4 记下说宽的那几格。
- **小处**：`reachCheckNotice` 插在 `brokenProjectNotice` 的 JSDoc 与函数之间，那段 JSDoc 挂到了它头上——挪开；没有 run 时非 PM 写坏 `reach.json` 收到
  「原样重写」——改成原样冒泡（§1.1）。
