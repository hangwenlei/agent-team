# 推进出第一段时记上契约的账

> 2026-10-10，分支 `r21-s1-exit-contract-sha`。第二十一轮（从开放边界索引挑）：`docs/37` §5「PENDING 而契约不在，一律当还没写——过了第一段契约
> 丢了、`contract_sha` 还是 PENDING，派发返回与写 `state.json` 时都不报」（`docs/60` §4 也登着它）。

## 0. 一句话结论

- 推进出第一段的那一次写入，`contract_sha` 要与磁盘上的契约对得上，H6 才放行；对不上（还是 PENDING、记的是别的值、不是合法的 sha）就拒，出路照用【契约】
  那一句（第一段里漂了的那一支单写：契约还由项目经理写、可以改，记最近一次写契约的回传）。一次写入里先回到第一段、再推进出来的同样核。正常的推进
  走不到「过了第一段还是 PENDING」了；不经这一次的写法（§4）照旧到得了。

## 1. 问题

- `compareContractSha` 把「PENDING、契约不在」当成「还没写」（ok）：第一段里这是对的——契约还没写出来。过了第一段，契约丢了、`contract_sha` 又一直没记
  （项目经理在第一段里没照回传记），派发返回、写 `state.json`、派验证段时都不说话。
- `docs/37` 那一轮试过按阶段分（过了第一段算 `missing`），一批停在后段、PENDING 又不写契约的夹具跟着变红，退回了。
- 第一段的产物就是契约：推进出第一段时契约一定在（H6 的推进判据要它交齐），那一刻正好能要求把账记上。

## 2. 修法

- `hooks/gate.mjs` 的 H6（`rework`）：推进出第一段的那一次（写入前停在第一段、或者这次追加的 history 里有第一段，写入后到了后面的段），排在第 1 节对
  原话之后，拿这次写入的 `contract_sha` 对磁盘上的契约（`compareContractSha`）：不过就拒，`agent-team H6 返工预算：推进出 <第一段> 之前，这次写入的
  contract_sha 要与磁盘上的契约对得上。` + 出路：PENDING、不合法的照用【契约】那一句（`contractCheckNotice`：记写契约那一次回传给的值、手上没有就原样重写
  一次契约拿回传；不合法的先写成 PENDING）；漂了的单写一句——还在第一段，契约由你写、可以改，把最近一次写契约收到的【契约】回传给的 sha 记进
  `contract_sha`，手上没有就原样重写一次契约拿回传（通用那一句的「契约被人改过、不是第 4 节的修订——恢复原样」在第一段里会导向绕圈）。值只从回传来，不报
  磁盘上算出来的值。契约在、这一次读不出（被占着）不拦，留一行痕。
- 第 1 节对不上原话的拒绝理由补上「改好之后把那一次写契约收到的【契约】回传给的 sha 记进 contract_sha，再推进」——改好第 1 节契约的哈希就变了，省一轮被拒。
- 第一段里别的写入（原地重写、记 PENDING）不核——写契约之前、记账之前照常写 `state.json`。
- 正文：`commands/at.md` 第 2 节「S1 录入」那一句「之后每一次派发返回、每一次写 state.json，门禁都拿它对一遍」补上「推进出 S1 那一次」。
- `tests/gate-user-words.test.mjs` 的 `advance` 推进出第一段时原来带着 PENDING：改成照项目经理的做法记上门禁按契约算的值（真实的推进那一刻早该记上了）。

## 3. 判据与变异

- `tests/gate-s1-exit-contract.test.mjs`：记的就是磁盘上的——放行；还是 PENDING——拒，理由带【契约】那一句；记的是别的合法值——拒，说这次写入的值、不报
  磁盘上算出来的值、给第一段那一句（不说「恢复原样」）；不是合法的 sha——拒；第一段里原地重写、记 PENDING——不核；契约在却读不出（`inject-throw.cjs` 的
  `read:` 预加载，三个系统上都跑）——不拦、留这一条自己那一行痕；一次写入里先回到 S1 再推进出来——照样核；第 1 节对不上原话、契约的账也没记——先说原话
  那一句、出路里一并说记账；正文那一句在。
- `tests/trusted-echo.test.mjs`：补「推进出第一段那一次写入的 `contract_sha`（H6）」这个入口。
- 变异（备份在仓库外，每一刀改完逐字节还原）：推进出 S1 不核契约的账、核写入前的值、理由不带【契约】那一句、只在绑着原话时核；复核修订之后又加了读不出
  也拒、读不出不留痕、漂了那一支照用通用那一句、漂了那一支说写入前的值、一次写入里回到第一段不算、原话那一句不说记账、契约的账排在原话之前、把写入的值
  原样拼进拒绝理由——每一刀都有判据红（最后一刀由 trusted-echo 新加的那一格打红；落在「漂了」那一支里的同一刀是等价的：走得到那一支的值整串是合法的 sha）。
  第一版时「读不出也拒」只有 POSIX 那一格打得红，在本机用 PowerShell 以 `FileShare.None` 独占打开契约手工核过；改用预加载之后三个系统上都打得红。
- 没起真实会话：H6 的判定在子进程里全走到了。

## 4. 仍然开着的边界

- **不经「推进出第一段那一次」的写法**，照旧到得了「过了第一段、PENDING、契约不在」、照旧不说：这一版之前就推进出第一段的旧 run；过了第一段之后用 Write
  把 `contract_sha` 改回 PENDING（H6 不拦，账本只报一句），再用 Bash 删掉契约；建 run 那一次直接写成后面的段（H6 首写的跳过路径，`docs/38` 记过）。

## 5. 没量到的

- 真实会话里项目经理推进出 S1 时被这一条拒了之后，照不照【契约】那一句记上再推进。
  > **更新（2026-10-10，`docs/64`）**：正路在一趟真实会话里量过了——项目经理推进出 S1 之前就记上了写契约那一次回传的 sha，没有误拦；拒绝那一路仍没量到。

## 6. 归属

## 8. 复核与修订

第一版推上分支、CI 全绿之后，起了一个对抗复核的子代理：照 `/agent-team:at` 的顺序在子进程里走 S1（建 state.json、写契约拿回传、记账、推进），【契约】每一支
出路照做都推得出 S1；核了「先推进再原地重来」「跳段」「Edit 推进」「返工轮回到 S1 再推进」几种写入形状与 H6 别的判据的先后，拒绝理由里没有漏出外部值。
两个中等、几个小问题，都在这一轮改了：

- **中 1：S1 里改契约的那条路上门禁文字打架**——照原话改好第 1 节之后带着旧 sha 推进，被这一条拒，通用的漂移那一句第三条出路是「契约被人改过、不是第 4 节
  的修订——恢复原样」，照做会绕回原话那一条。→ 第一段里漂了的那一支单写；原话那一句的出路一并说记账。
- **中 2：「读不出」那一格锚得太松**——推进判据自己也留一行含「读不出」的痕，拿掉新加的那一行判据照绿。→ 断言认这一条自己那一行；改用预加载，三个系统上都跑。
- **低 3：「回到 S1 + 推进出来」写在一次里不核**。→ 追加的 history 里有第一段的也算推进出第一段（原话那一条同一个口径）。
- **低 4：「之后只剩旧 run 与 Bash」说大了**——Write 改回 PENDING、建 run 那一次直接写成后面的段都到得了。→ §0、§4、代码注释、HANDOFF 改准。
- **低 5：几刀变异打不红**——把写入的值原样拼进理由、漂了那一支说写入前的值、契约的账排在原话之前。→ trusted-echo 补入口、补断言与「先说原话」那一格。
- **低 6：文档**——`commands/at.md` 那一句在第 2 节，不是第 1 节；日期写成了 UTC 的次日。→ 改了。
